# Public API and agent surface

Hercule has one public API. The web app, the `hercule` CLI, agents inside sessions, built-in workflow actions and plugins all operate the system through the same set of operations, defined once in a framework-free service layer and described once in a shared contract package of Effect Schema declarations. HTTP routes are derived from that contract and call the service layer; the `hercule` CLI is a thin client over HTTP. Agents reach the API with a per-session token that carries their agent's permission profile; the user reaches it with an API key. Every mutation is stamped with its actor in the event log. No endpoint blocks: long waits are expressed as subscriptions whose matches arrive as queued input. This document pins the contract structure, the operation vocabulary, the transports and route style, the error envelope, the operation catalogue, the credential and attribution rules, the `hercule` CLI (including `hercule memory`), session subscriptions and the no-blocking rule. Rationale lives in [ADR 0013](../adr/0013-agents-operate-hercule-through-the-public-api.md), [ADR 0020](../adr/0020-assistant-memory-is-reached-only-through-the-api.md), [ADR 0021](../adr/0021-one-operation-vocabulary-coarse-grants-explicit-routes.md) and [ADR 0031](../adr/0031-the-backend-is-written-on-effect.md).

## 1. Contract structure

### 1.1 Service layer

A framework-free TypeScript service layer defines every operation: each operation is a method on an Effect service (`Tasks.create(input)`), the backend being written on Effect ([ADR 0031](../adr/0031-the-backend-is-written-on-effect.md)). *(Amended 2026-09-17, [#208](https://github.com/theagenticage/hercule/issues/208): the example was `session.spawn`. For an operation that ~~spans domains or~~ sends a frame to a runner, or that is the last resort for breaking a cycle in the domain graph, the service is the controller daemon rather than the domain that owns the rows (amended 2026-09-25, [#253](https://github.com/theagenticage/hercule/issues/253): touching a second domain no longer moves an operation up); the controller daemon is the layer above the controller's domains, [ADR 0033](../adr/0033-source-is-organized-by-domain-and-tests-are-colocated.md).)* "Framework-free" means: **no operation logic in any transport handler.** An HttpApi handler is a one-line call into the service method, and an RPC handler would be the same one line, so an operation can later be exposed over the WebSocket by adding one handler line, never by moving logic. Every consumer goes through it:

| Consumer | How it calls |
|---|---|
| HTTP routes | derived from the contract's HttpApi declaration (input validated and output encoded by the derived route); one-line call into the service method |
| `hercule` CLI (agent and ops) | over HTTP |
| Web app | over HTTP (plus one WebSocket for live topics, see [./14-web-app.md](./14-web-app.md)) |
| Built-in workflow actions (~~`workflow.run`~~ `run.start`, `notification.create`, `task.create`, `task.update`, `task.query`; `wait` calls no operation *(amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79))*; `signal.screen` *(amended 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395), [#399](https://github.com/theagenticage/hercule/issues/399))*) | in-process, same service layer |
| Plugins holding the public-API client capability | in-process, same service layer ([./05-plugins.md](./05-plugins.md)) |

Permission enforcement (section 5) and actor stamping (section 3) sit inside the service layer, so they bind every consumer identically.

**Request lifetime.** Each HTTP request or RPC call runs as one fiber. The transport handler resolves the credential and provides the current actor and a tracing span as request-scoped context, which service methods read (`CurrentActor`), never a context parameter threaded through signatures. A client disconnect interrupts the fiber, and an open transaction rolls back with it ([./04-state-store.md](./04-state-store.md)). Every service operation and repository call carries a span from day one; v1 exports spans nowhere beyond the log line, and an OpenTelemetry exporter is a later layer swap ([ADR 0031](../adr/0031-the-backend-is-written-on-effect.md)).

**Parity guarantee (hard rule):** nothing is reachable in-process that is not reachable over HTTP. A service operation without an HTTP route is a defect. The WebSocket carries live-topic subscriptions only; every query and mutation stays on HTTP ([ADR 0017](../adr/0017-the-web-app-is-a-static-pure-client-of-the-public-api.md)).

### 1.2 Contract package

`packages/contract` holds, per operation: its id, an Effect Schema input schema, an Effect Schema output schema, its error schemas, the grant it requires (section 5), and its HTTP route (section 1.4), all as one Effect HttpApi declaration. It is the pinned, expensive-to-retrofit asset. Consumers of the package: server-side validation, the `hercule` CLI, the web app (`client-core`, [./14-web-app.md](./14-web-app.md)), the plugin public-API client, and the workflow editor's schema-driven autocomplete.

From that declaration the server routes, request validation, the OpenAPI document and the typed client are derived ([ADR 0031](../adr/0031-the-backend-is-written-on-effect.md)); the route table of section 1.4 is what the declaration follows. The `hercule` CLI and `client-core` use the derived client. The same package holds the Effect RPC group for the WebSocket's live topics ([./14-web-app.md](./14-web-app.md)); every query and mutation stays on HttpApi (section 1.1). The deferral of RPC-framework adoption in [ADR 0013](../adr/0013-agents-operate-hercule-through-the-public-api.md) is withdrawn by its 2026-09-02 amendment.

### 1.3 Operation vocabulary

One identifier names an operation on every surface ([ADR 0021](../adr/0021-one-operation-vocabulary-coarse-grants-explicit-routes.md)):

- **Operation id** = `<entity>.<verb>`, entity singular: `task.create`, `session.spawn`, ~~`workflow.submit`~~ `run.start` *(amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79))*, `runner.drain`. Every entity is its own operation family.
- **Built-in workflow action id** = the operation id, unchanged. The built-in actions *are* the operations ([./07-workflows.md](./07-workflows.md) section 8). *(Amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79).)* `wait` is the one exception: it pauses a run, changes nothing, and has no operation.
- **CLI** = a command spelled for a terminal, written per operation in the contract's CLI table and one-to-one with the operations (section 6.3): `hercule task list`, `hercule session spawn`, `hercule runner join-token create`. One spelling per command, no aliases; `--help` names the operation id. *(Amended 2026-09-15, [#126](https://github.com/theagenticage/hercule/issues/126): was "the id split on the dot".)*
- **Grant** = `<family>.<verb>` in the coarse grant vocabulary of [./13-security.md](./13-security.md) section 6.1. Grant families are *not* one-to-one with operation families: `infra.write` covers `runner.*`, `plugin.*`, `provider.*` and `controller.*`, and also `providerAccount.*` and `modelProfile.*`, which replace the Provider Instance operations; `harness.*` and `provider.*` have reads only, under `infra.read` *(amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406))*. The operation-to-grant mapping is an explicit table in the contract package; a 403 and the CLI's `--help` both name the grant, so an agent never has to guess it.

Standard verbs, used with the same meaning on every entity that has them:

| Verb | Meaning |
|---|---|
| `query` | the one list operation of an entity: filters (including `text` where full-text search exists) plus pagination; no filters lists everything; returns `items: <Entity>[]`. There is no `list` and no `search` anywhere in the catalogue. |
| `read` | one entity by id |
| `create` / `update` / `delete` | the obvious; `update` is a partial patch |
| custom verbs | `spawn`, `steer`, `run`, `submit`, `emit`, `cancel`, `rerun`, `drain`, ...: named per entity in section 2 |

**Rule:** `<entity>.query` returns `<Entity>[]`. Something that returns another type is another entity's operation (transcript passages are `transcript.query`, not `session.query { text }`).

**Named exception:** `memory` keeps the verbs `list`, `read`, `search`, `write`, `append`, `delete` pinned by [ADR 0020](../adr/0020-assistant-memory-is-reached-only-through-the-api.md) and tested with real agents in [Prototype: assistant memory interface](https://github.com/theagenticage/hercule/issues/31). `list` returns the index and `search` returns matches, so they could not be one `query` under the rule above anyway.

### 1.4 Transports and route style

Two transports, one contract:

1. **HTTP** on the controller's origin. Bearer authentication (`Authorization` header) with either credential kind (section 4). Plain HTTP on LAN/tailnet by default ([./13-security.md](./13-security.md)).
2. **The `hercule` CLI** (section 6): the same binary in every role, speaking HTTP to `HERCULE_API_URL`.

*(Added 2026-10-19, [#791](https://github.com/theagenticage/hercule/issues/791).)* **JSON answers are compressed on request.** When a request's `Accept-Encoding` allows it, the controller compresses an answer whose body is JSON and at least 1 KiB, with brotli (quality 4) if the client accepts brotli, otherwise with gzip (level 6), and sets `Content-Encoding` to `br` or `gzip`. The controller picks by its own order, brotli first, and does not weigh the client's q-values against each other; it only skips a coding the client refuses with `q=0`. Every JSON answer, small ones too, carries `Vary: Accept-Encoding` beside the `Vary: origin` of CORS, because whether it is compressed depends on the request. A request that accepts neither coding (no `Accept-Encoding`, `identity`, or only other codings) gets the same bytes as before. Nothing in the contract changes, and every client decodes the answer without a library of its own: ~~Chromium (the web and desktop apps) and Bun's `fetch` (the CLI) accept both codings, and OkHttp (the Android app) asks for gzip alone, so it gets gzip.~~ *(Amended 2026-10-29, [#920](https://github.com/theagenticage/hercule/issues/920).)* Bun's `fetch` (the CLI) asks for both codings. Chromium decodes both, but asks for brotli only from an HTTPS or localhost address: over plain http, as on the LAN or a tailnet, it asks for gzip and deflate alone. The desktop app therefore asks for brotli itself, on every request to its saved controller ([./17-desktop-app.md](./17-desktop-app.md) §Reaching the controller). The web app cannot, because `Accept-Encoding` is a header a page's `fetch` may not set, so over plain http it gets gzip ([./14-web-app.md](./14-web-app.md) §Performance guardrails). OkHttp (the Android app) asks for gzip alone, so it gets gzip. No other coding is offered, so that no client is sent a coding it cannot read. Other bodies are sent as they are: an attachment's image (`attachment.readContent`), a runner's fetch of an attachment or a Skill Revision, the promotion transfer, the web bundle's HTML, JavaScript, CSS and other files that are not JSON, and anything under 1 KiB. The compression runs on the finished response, so a bare `413` or `411` and the CORS headers are unaffected. Section 1.5's order of checks does not change: compression happens after them all.

The web app additionally holds one WebSocket for live topics (subscriptions only), connected with a short-lived single-purpose ticket fetched over HTTP; bearer auth, no cookies. Details in [./14-web-app.md](./14-web-app.md).

A Hercule MCP server is not a v1 transport (section 10).

**Ids on the wire** are canonical lowercase UUIDv7 strings, except event ids, which are integers ([./04-state-store.md](./04-state-store.md)). The CLI accepts a full id or an unambiguous tail of eight or more characters for any id argument whose CLI row names the listing that resolves it (`conflict` if ambiguous; section 6.3, [#126](https://github.com/theagenticage/hercule/issues/126)) and prints tails in human output; `--json` always prints full ids. *(Amended 2026-09-04, [#57](https://github.com/theagenticage/hercule/issues/57).)* **Tail resolution is a CLI-side behaviour**: the CLI resolves a tail through the entity's `query` operation and reports `conflict` itself when more than one id matches. The wire carries canonical ids only - no `{id}` path parameter and no input schema accepts a tail - so a tail costs an extra round trip and needs the entity's read grant.

**Routes are resource paths with HTTP methods**, under `/api/v1/`. Every operation's `{ method, path }` is written explicitly in the contract's route table; the conventions below are what the table follows, and any exception (an irregular plural, a nested resource) is simply written in the table. One CI test asserts that operations and routes are one-to-one.

| Operation shape | Route | Example |
|---|---|---|
| `X.query` | `GET /api/v1/<xs>` + query string | `GET /api/v1/tasks?label=bug&label=ui&status=open&text=crash` |
| `X.read` | `GET /api/v1/<xs>/{id}` | `GET /api/v1/sessions/s_12` |
| `X.create` | `POST /api/v1/<xs>` | `POST /api/v1/tasks` |
| `X.update` | `PATCH /api/v1/<xs>/{id}` | `PATCH /api/v1/tasks/t_9` |
| `X.delete` | `DELETE /api/v1/<xs>/{id}` | `DELETE /api/v1/tasks/t_9` |
| custom verb on one entity | `POST /api/v1/<xs>/{id}/<verb>` | `POST /api/v1/sessions/s_12/interrupt`, `POST /api/v1/runs/r_3/rerun` |
| custom verb without an entity | `POST /api/v1/<xs>/<verb>` | `POST /api/v1/workflows/submit`, `POST /api/v1/events/emit` |
| owned sub-resource | `.../{id}/<sub>...` | `GET /api/v1/sessions/s_12/transcript`, `PUT /api/v1/assistants/a_1/memory/core` |

Path nouns are plural (`/tasks`) although operation ids are singular; that is the one place the two spellings differ. Query strings repeat the key for list-valued filters (`label=a&label=b`); the derived client serializes from the operation's input schema, so neither the CLI nor the web app hand-builds URLs. `me` is accepted wherever an id names the caller's own ~~session or assistant~~ session, assistant or Agent (`/api/v1/assistants/me/memory`, `agentId: "me"` on `transcript.query`): a session token resolves it, a user credential gets 400 `validation`, and so does a session that runs as no Agent, such as a Thread, where the id names an Agent or an assistant *(amended 2026-09-25, [#92](https://github.com/theagenticage/hercule/issues/92))*. *(Amended 2026-09-28, [#85](https://github.com/theagenticage/hercule/issues/85).)* `me` is also accepted as `sessionId` inside the input of a bound answer that a session creates with `notification.create`: the core replaces it with the creating session's id before it checks and stores the answer, and a run's step that uses it gets `validation` ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md) section 7.4). No other operation resolves `me` yet ([./16-open-items.md](./16-open-items.md) B).

### 1.5 Success and error shapes

**Success** bodies are the operation's output schema, bare: no `{ data: ... }` wrapper.

**Errors** use one envelope; the HTTP status is derived from the code:

```json
{ "error": { "code": "forbidden", "message": "missing grant session.spawn", "details": { "grant": "session.spawn" } } }
```

- `code` is a closed enum in the contract, extended additively: `unauthenticated` (401), `forbidden` (403), `validation` (400), `not_found` (404), `conflict` (409), `invalid_state` (409), `cap_exceeded` (422), `internal` (500). *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* Promotion adds two codes ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 8):
  - `promotion_in_progress` (409): a promotion is copying this controller's data, so it accepts no change. Every operation that changes something returns it until the switch, a cancel, or the promotion token's expiry. Reads still answer: every `GET` and `HEAD`, and the operations that change nothing but take a body, which the operation table marks `readOnly` (`workflow.validate`).
  - `controller_sealed` (503): this controller has moved to another machine and no longer serves. Every operation except `setup.read` returns it. The message names the new address and the `hercule login` command for it.
- `details` is typed per code: `forbidden` carries `{ grant }`; `cap_exceeded` carries `{ size, cap }` or `{ count, cap }` *(amended 2026-10-29, [#897](https://github.com/theagenticage/hercule/issues/897): for a live subscription that fell behind, `count` and `cap` are messages, or bytes when the 8 MiB limit ended it, [./14-web-app.md](./14-web-app.md) Live model)*; `validation` carries `{ issues: { path: string[]; message: string }[] }`, mapped from the schema library's parse issues; the wire contract names no schema library. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* `controller_sealed` carries `{ newAddress }`, the URL of the controller the data moved to. It is not signed: only a runner holds a key to check a signature with, and a runner learns the move from the signed `ForwardingPointer` frame instead ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 8.3).
- `message` is for people and is never parsed.
- **One response is not in the envelope.** A request body larger than the controller's cap is answered `413` by the transport, bare, before any of the body is read. Reading it to answer in the envelope is the cost the cap exists to avoid.

  *(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* **The cap is per route.** One check wraps the whole app, before routing, so it covers the derived routes, the runner join route and unmatched paths alike. It reads nothing first:

  - `POST /api/v1/attachments` (`attachment.create`) may carry up to 10 MiB (`MAX_ATTACHMENT_BYTES`). The listener's own cap is exactly 10 MiB, so the transport answers an upload of 10 MiB + 1 byte with a bare `413`.
  - Every other request whose `Content-Length` is over 2 MiB is answered with a bare `413`.
  - Every other request with `Transfer-Encoding` and no `Content-Length` is answered with a bare `411`, so a chunked body cannot get around the 2 MiB cap. The upload route needs no such rule, because the listener's 10 MiB cap bounds it.
  - *(Added 2026-10-18, [#312](https://github.com/theagenticage/hercule/issues/312).)* `POST /api/v1/skills/import` (`skill.import`) and `POST /api/v1/skills/propose` (`skill.propose`) may carry up to 10 MiB too (`MAX_SKILL_BYTES`), for the same reason: the body is one skill's tar archive (section 2, `skill`). Like the upload route, they need no rule for chunked bodies. A larger archive gets the bare `413` before any of it is read, so the message that a skill is too big comes from the CLI and the desktop app, which measure the archive they build before they send it.
  - The check sits inside the CORS layer, so a cross-origin client such as the desktop app sees the `413` or `411` with CORS headers.
  - Frames on the runner WebSocket stay capped at 2 MiB, a separate limit ([./13-security.md](./13-security.md) section 1).
- **One error per response.** The service layer runs its checks in a fixed order and the first failing check is the response: `unauthenticated`, then the static grant check (`forbidden`, before any entity is touched), then `validation`, then `not_found`, then entity-dependent `forbidden` (the `memory` scope rule, section 6.4), then business rules (`conflict`, `invalid_state`, `cap_exceeded`), then `internal`. A caller lacking a grant learns that before learning whether the entity exists. `validation` is the one code that reports everything wrong at once, so a caller fixes every field in one retry.

  *(Amended 2026-09-04, [#57](https://github.com/theagenticage/hercule/issues/57).)* On HTTP the derived route decodes and validates the payload before it ever reaches a handler, so the fixed order only holds if the grant check runs earlier: **the static grant check is performed by transport middleware, before payload decoding**. The contract's operation-to-grant table (section 1.3) is therefore load-bearing at request time, not documentation. Service methods keep the same check inside the method, for in-process callers (built-in workflow actions, plugins) that reach no transport; a caller over HTTP is simply checked twice, identically.

  *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* Two gates run before the credential is read, so the full order of checks on HTTP is:

  1. the body cap: a bare `413` or `411` (above);
  2. the promotion gate: `controller_sealed`, or `promotion_in_progress` for an operation that changes something;
  3. the pre-setup gate: `unauthenticated` for every operation but `setup.read` and `setup.complete` until setup is complete;
  4. the credential: `unauthenticated`;
  5. the static grant check: `forbidden`;
  6. payload decoding: `validation`;
  7. the service method's own checks, in the order above.

  The promotion gate comes first because a sealed or frozen controller refuses the request whoever sends it. So a caller with no credential, or a wrong one, still learns that the controller has moved, and where to.

The `hercule` CLI prints `message` (and, for `forbidden`, the grant on its own line); `--json` prints the envelope verbatim.

### 1.6 Pagination and sorting

Every `query` operation takes `{ limit?, cursor?, sort? }` and returns `{ items, nextCursor? }`. Cursors are opaque strings; the default `limit` is 50 and the hard maximum 500. ~~`sort` is `{ field, direction }` over an enum of allowed fields declared per operation.~~ *(Amended 2026-10-03, [#300](https://github.com/theagenticage/hercule/issues/300).)* `sort` is an ordered list of keys `{ field, direction? }` over an enum of allowed fields declared per operation, sent as one repeated query parameter per key (`sort=priority:desc&sort=createdAt:desc`). The first key sorts; each later key orders only the rows equal on the keys before it; after the caller's keys, rows are ordered by the listing's unique tie-break key, in the direction of the last key. A field may appear once; a repeated field is `validation`. A key with no direction is `asc`; with no `sort`, each operation keeps its default order. Inside the cursor the controller uses keyset pagination for stable sorts and an offset for relevance-sorted full-text results; callers never see the difference. There are no page numbers and no total counts in v1: the web app pages forward ("load more"), and jumping to a range is done with filters (`run.query { since, until }`), not pagination.

*(Amended 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395), [#393](https://github.com/theagenticage/hercule/issues/393).)* **One named exception to relevance order.** `event.query` with `text` keeps the log's own order, newest first, and pages by keyset. A search narrows the log and does not reorder it. Every other `text` filter, such as `task.query`'s, still sorts by relevance and pages by offset (section 2, `event`). **One named exception to paging.** `signal.query`'s `to-do` view returns the whole list and takes no `limit` or `cursor`; the client counts what it holds, so there is still no total count on the wire (section 2, `signal`).

## 2. Operation catalogue

```ts
interface TaskFilter {
  refs?: string[]        // provenance External Refs, canonical form, exact match
  labels?: string[]
  status?: TaskStatus[]
  projectId?: string
  handedOff?: boolean    // true: only Tasks with a provenance entry that has a signalId (added 2026-10-20, #801)
  text?: string          // SQLite FTS over title + description
}
```

Within one field the values are **any-of**; across fields the filter is **and**. No `or` across fields and no negation in v1. `TaskFilter` is defined once in the contract and used by the `task.query` operation and the identically named built-in action; the guard-before-agent pattern in [./07-workflows.md](./07-workflows.md) is `task.query` with `refs` set and `text` absent.

*(Added 2026-10-20, [#801](https://github.com/theagenticage/hercule/issues/801).)* **`handedOff`** keeps the Tasks that have a handoff entry: a provenance entry with a `signalId` ([./09-tasks.md](./09-tasks.md#provenance-and-external-refs)). `handedOff: false` keeps the Tasks that have none. Tracking asks for `handedOff: true` with `status: ["in-progress"]`. Its CLI row gains `--handed-off true|false`, with the line "Only tasks that were handed off from a signal (true), or only tasks that were not (false)."

*(Added 2026-10-20, [#801](https://github.com/theagenticage/hercule/issues/801).)* **`task.queryTracking`** returns the Tasks Intake's Tracking follows, with the facts a client works each Task's state out from, so a client needs no read per Task or per run. It is owned by the tasks domain. Its rows are every in-progress Task that has a handoff entry, never a deleted one, the most recently updated first:

```ts
interface TrackingTask {
  taskId: string
  title: string
  handoffs: { signalId: string; runId: string; at: string }[]   // the Task's newest handoffs, at most 10, newest first
  latestRun: TrackingRun                                         // newest by createdAt, then id
  latestLiveRun?: TrackingRun                                    // newest pending or running run, when one exists
  liveRunIds: string[]                                           // every pending or running run's id, newest first; empty when none (added 2026-10-21, #802)
}
interface TrackingRun {
  id: string; workflowId: string | null; workflowName: string
  status: "pending" | "running" | "completed" | "failed" | "cancelled"
  createdAt: string; startedAt?: string; finishedAt?: string
  awaitedSignalIds: string[]        // as RunSummary: the signal triggers a running run waits on, else empty
  failureCause?: string             // failed runs only; see below
}
```

- **`failureCause`** is the text `describeFailureCause` gives for the run: its failure message, else the message of the edge it failed at, else the error of the step that failed, else the failure reason in plain words ("workspace failed"). The words for a reason are one function in the contract, which the controller and `client-core` both import.
  - *(Amended 2026-10-21, [#803](https://github.com/theagenticage/hercule/issues/803).)* A cause is cut to `MAX_TRACKING_FAILURE_CAUSE` (300 characters, "…" included), as the output text is cut below, because an error message is as long as whatever produced it. The contract bounds the field at 300, in `task.queryTracking` and `task.readTracking` alike.
- *(Amended 2026-10-21, [#802](https://github.com/theagenticage/hercule/issues/802).)* **`liveRunIds`** lists the id of every pending or running run of the Task, newest first, so its first id is `latestLiveRun`'s. A Task can have two live runs at once: a second handoff on the same Task starts a new run while the first still goes on. `latestLiveRun` alone would hide the older one, and a client that decides whether a row Needs you (a session of one of its live runs has an open Request) must see every live run. The ids come from the same statement that finds `latestLiveRun`, so the read costs nothing more. The field is additive; a row's state still reads `latestLiveRun`.
- **Not paged.** Tracking counts and orders every row, as the to-do view of `signal.query` does (section 1.6). A row holds one Task's title, its newest handoffs (at most 10, `MAX_TRACKING_HANDOFFS` in the contract) and two runs with the ids of the live ones, never a Task's history, so the reply grows with the number of Tasks in progress and not with the work handed off before. A client that waits for its own handoff looks for its receipt among these; an older handoff has no bearing on where the work stands.
- **A Task with no run** is left out. A handoff starts its run in the transaction that tracks the Task, so none occurs.
- **Grants.** The operation's row names `task.read`, and the service also checks `run.read`, because a row holds what `task.query` and what `run.query` give. Any caller that holds both may read it, a session included: it could read the same facts from those two operations. A caller that lacks one is refused with `forbidden` naming it.
- **How it reads.** The tasks domain declares a read port for the runs, `TaskTrackingRuns`, and the controller daemon answers it from the runs repository, because the runs domain depends on the tasks domain (ADR 0033). It opens no transaction, so it reads on the read-only connection and never waits for a writer. The newest run of each Task is one lookup per Task on `runs_task_id`, and the live runs come from `runs_unfinished`, so no Task's history is read. The Tasks are the in-progress Tasks on the status index, each probed once for its newest handoffs on `task_provenance_handoff`, so the read does not touch the handoffs of Tasks that are done.
- Its CLI row is `hercule task tracking`. Purpose: "Lists the work handed off from Intake that is still followed." It takes no field. *(Amended 2026-10-21, [#802](https://github.com/theagenticage/hercule/issues/802).)* Its help text also names the ids of all the Task's live runs.
- `task.query`'s `handedOff` filter stays: it is a general read of Tasks that other callers may use. `run.query` has no Task filter: Tracking is the only reader that asks for runs by Task, and `task.queryTracking` answers it.

*(Added 2026-10-22, [#805](https://github.com/theagenticage/hercule/issues/805).)* **`task.queryLegs`** returns, for each given run that is the run of a handoff, where the work that handoff started stands, so a client draws "handed to X, tried again twice, finished" for a page of Done signals without reading any Task's history. It is owned by the tasks domain, like `task.queryTracking`:

```ts
interface HandoffLeg {
  runId: string; signalId: string; taskId: string
  taskStatus: TaskStatus                                    // the Task's status now
  workflowId: string | null; workflowName: string          // of the handoff's run, as when it started
  rerunCount: number                                        // the runs of the leg other than the handoff's run
  latestRun: { id: string; status: RunStatus }              // the newest run of the leg, by createdAt, then id
  liveRunIds: string[]                                      // the leg's pending and running runs, newest first, at most 20
  next?: { signalId: string; runId: string; at: string; workflowName: string }
}
```

- **Which legs.** One per distinct given run id that is the run of a handoff entry (a provenance entry with a `signalId`) of a Task that is not deleted. Any other id is left out of the reply, which may then hold fewer legs than ids: an unknown run, a run of no Task, a run of a deleted Task, a run that only re-runs a handoff's run, and a run whose own Task is not the Task of the entry that names it. The legs come in the order of the ids, and a repeated id gives one leg. At most `MAX_LEG_QUERY_RUNS` (50, the size of a page) ids, and at least one, else `validation`.
- **What a leg holds.** The handoff's run, and every run that can be reached from it through `originalRunId` (a re-run, a re-run of a re-run, and so on) and has the same `taskId`. Time never decides it: a re-run of an earlier handoff's run that started after a later handoff stays in the earlier leg. `rerunCount` and `latestRun` come from the whole leg. `latestRun` is only the run's id and status, which is all a client reads: the status says how the leg stands, and the id opens the run. It carries no failure cause, so the read opens no failure message and no step record.
- **`next`.** The Task's handoff entry that follows this one by time, then by the order it was appended, among all the Task's handoff entries and not only the requested ones, with the workflow name of its run. Absent for the Task's newest handoff. The order is `at`, then the order of appending, because two entries may share a time; it is the order `task.readTracking` uses for the Task's first handoff and `task.queryTracking` (reversed) for a row's handoffs, so every read of a Task's handoffs agrees.
- **Bounds.** Each leg is a fixed size, so the reply does not grow with a Task's history. `liveRunIds` is a sample, capped at `MAX_LEG_LIVE_RUNS` (20): a leg with more runs going at once is not expected.
- **Grants.** As `task.queryTracking`: the operation's row names `task.read`, the service also checks `run.read`, and a caller that lacks one is refused with `forbidden` naming it.
- **How it reads.** The same port, `TaskTrackingRuns`, with three more methods (`readTaskIds`, `readWorkflowNames`, `readLegRuns`) that the controller daemon answers from the runs repository. It opens no transaction. Each step is one statement for all the ids: the runs' Tasks by primary key; for each (run, Task), the handoff entry of that run on `task_provenance_handoff_run`, a partial index on `(run_id, task_id)` of the entries that name a signal (migration 90), then the Task by key, and the next entry by seeking `task_provenance_handoff` just after the entry by `(at, rowid)`, which reads one entry; one recursive statement that walks the legs from the handoffs' runs on the primary key and on `runs_original_run_id`, so it reads the runs of the legs and never a Task's other runs; and the workflow names of the next handoffs' runs by primary key. A handoff's run always exists, because runs are never deleted. The cost follows the size of the legs asked for (a wide fan-out of re-runs is linear) and does not follow the Task's number of handoffs. `tracking.speed.test.ts` measures it: 50 handoffs of Tasks with 100 handoffs and one leg of 200 re-runs took 1.6 ms (9.9 ms before the index), and 50 handoffs on one Task of 10,000 handoffs took 1.1 ms (140 ms before, when the Task's handoffs were walked once per handoff).
- Its CLI row is `hercule task legs --run <id>...`.

*(Added 2026-10-21, [#803](https://github.com/theagenticage/hercule/issues/803).)* **`task.readTracking`** returns what the Tracking pane of one Task draws, in one read, so the pane needs no read per run and no read of a session's transcript. It is owned by the tasks domain, like `task.queryTracking`:

```ts
interface TrackingDetail {
  firstHandoff: { signalId: string; runId: string; at: string; workflowName: string }   // the Task's oldest handoff: the signal "You asked" shows
  runs: TrackingDetailRun[]                                                             // the Task's newest runs, at most 20, oldest first
  output?: TrackingOutput                                                               // what the newest run's last completed agent step produced
  endingActionStepName?: string                                                         // the action step the newest run ended on
}
interface TrackingDetailRun extends TrackingRun {                 // the same facts as a Tracking row's run
  sessionId?: string                                              // the session of the run's last agent step: its thread
}
type TrackingOutput =
  | { kind: "text";   stepName: string; sessionId?: string; text: string }
  | { kind: "fields"; stepName: string; sessionId?: string; fields: { label: string; value: TrackingOutputValue }[] }
type TrackingOutputValue = string | number | boolean | null | { items: number } | { fields: number }
```

- **The runs.** The Task's newest `MAX_TRACKING_DETAIL_RUNS` (20) runs by creation time, then id, listed oldest first. A run's `sessionId` is the session of its step record that started last (`startedAt`) and has one. Only agent steps have sessions, so it is the session of the run's last agent step, and the run's thread. A run that never started an agent step has none.
- **The output.** It comes from the newest run's last completed agent step: the step record with the latest `finishedAt`, then the latest record, among the records of steps whose kind in the run's plan is `agent`. A text generation step is not an agent step. `stepName` is the step's `name`, else its id. The output is absent when the run completed no agent step, or the step left nothing to draw.
  - A step with **no `outputSchema`** gives `kind: "text"`: the output's `text`, trimmed. It is absent when `text` is missing, not a string, or blank. A text longer than `MAX_TRACKING_OUTPUT_TEXT` (1000 characters) is cut at the last paragraph break within the limit, else the last line break, else the last space, else just short of the limit, and ends with "…". The cut, "…" included, has at most 1000 characters. A break counts only in the second half of the limit, so a paragraph break at character 5 does not throw away almost the whole text: such a text is cut at a later line break or space, or just short of the limit. The cut never splits a surrogate pair. Lengths are counted in UTF-16 code units, as the contract counts them.
  - A step with an **`outputSchema`** gives `kind: "fields"`: the output's top-level fields, in the order of the schema's `properties` (the output's own order when the schema lists none), at most `MAX_TRACKING_OUTPUT_FIELDS` (12). A property the output does not hold is skipped. A field's `label` is its property's `title` in the schema, else the property's name, cut as the text is to `MAX_TRACKING_OUTPUT_LABEL` (80 characters), because a title is as long as its author wrote it and a name is whatever key the agent put in its output (the contract bounds `label` at 80). A string value longer than `MAX_TRACKING_OUTPUT_VALUE` (300 characters) is cut as the text is. An array is sent as its length, `{ items }`, and an object as its field count, `{ fields }`, so the reply never grows with the output. The output is absent when the output is not an object or holds none of the schema's properties.
- **Step names.** `stepName` of the output and `endingActionStepName` are cut as the text is, to `MAX_TRACKING_STEP_NAME` (80 characters, "…" included), because a workflow may give a step a name of any length, and a step's id or an action's id stands in for a missing name. The contract bounds both fields at 80. Other strings of the reply have a bound already: `workflowName` is a workflow's name, at most 128 characters wherever a workflow is written, and the title of a Task is bounded by the Task's own contract.
- **The ending action step.** `endingActionStepName` is set when the newest run has completed and its last completed step, of any kind, is an action step: its `name`, else its action's id. It is absent when that last step is an agent step, so a run that ended on its agent step has an output and no ending action step. It is absent for a run that is live, which has not ended on anything, and for a run that failed, which its failure cause explains. No record keeps a summary of what an action step did, so none is sent.
- **First handoff.** The oldest provenance entry of the Task that names a signal, with `workflowName`, the name of the workflow of the run that entry names, as it was when that run started (as `TrackingRun.workflowName`). The run may be older than the 20 newest, so the name is read from that one run, never taken from `runs`. A Task that does not exist, is deleted, or has no such entry fails with `not_found`: the pane follows handed-off work only. The Task need not be in progress.
- **Grants.** As `task.queryTracking`: the operation's row names `task.read`, the service also checks `run.read`, and a caller that lacks one is refused with `forbidden` naming it.
- **How it reads.** The same port, `TaskTrackingRuns`, with two more methods (`readRunHistory`, and `readWorkflowName` for the first handoff) that the controller daemon answers from the runs repository. It opens no transaction. The first handoff is one lookup on `task_provenance_handoff`, and its workflow name one lookup of its run by id (one more method of the port, `readWorkflowName`). The runs are one lookup of the Task's newest runs on `runs_task_id`, one probe of each run's session on `run_steps_session`, a partial index of the step records that have a session, which holds the session itself so no step record and no output is read, and for the newest run two statements that each return one step record (the last completed record, and the last completed agent record with its output and its step's `outputSchema`). They walk the run's plan once and probe the records on the primary key of `run_steps`. Nothing reads a transcript, a Task's other runs, or any output but the one. The reply is bounded by the limits above whatever the Task's history, the plan or the output, and `tracking.speed.test.ts` measures it.
- Its CLI row is `hercule task read-tracking <id>`, with the id or an id tail resolved through `task.query`, as `task read`. Purpose: "Shows what Intake's Tracking pane draws for one handed-off task." The spelling is a verb and its object, as `connection list-choices`, and `hercule task tracking` stays the list of every followed task.

`task.query` sorts over `updatedAt | createdAt | priority | status`, default `updatedAt desc`, keyset. *(Amended 2026-10-03, [#300](https://github.com/theagenticage/hercule/issues/300).)* `priority` ascends `low, normal, high, urgent`, and `status` ascends `open, in-progress, done, cancelled`. With `text` the order is relevance and the walk pages by offset; `text` together with an explicit `sort` is `validation` naming both ([./09-tasks.md](./09-tasks.md) Search). `task.update` never takes a whole `labels` array: labels move one at a time through `addLabels` and `removeLabels`, so a concurrent edit by the user and a triage agent cannot clobber each other.

- **`trigger.resume` is usable in `notification.answer`** (section 2, `notification`), so the breaker's decision binds two answers: Resume, and Resume and discard held events.
- **Held matches are listed** by `event.query` with `workflowId` and `triggerId` together (section 2, `event`).

*(Added 2026-10-29, [#898](https://github.com/theagenticage/hercule/issues/898).)* **Retrying a call.** `session.spawn`, `session.continue` and `session.input` take `dedupKey?`, a string of 1 to 200 characters (`MAX_DEDUP_KEY_LENGTH`, the limit of `event.emit`'s key). - **A repeat does nothing.** A call with the same key, by the same actor, on the same operation returns the first call's result and changes nothing. It runs no placement, writes nothing and sends nothing to a runner.

- **The CLI** takes `--dedup-key <key>` on `hercule session spawn`, `session input` and `session continue`.

It is counted as `Subagent.toolCalls` is, from one set of tool-call kinds: every stored `item.started` of a tool-call kind adds one, whichever agent reported it, and a replayed frame adds nothing. The controller keeps the count in a column updated as each event is stored, and migration 0067 counted the sessions stored before it from their stream. `hercule session read` prints it as the `toolCalls` line beside the Token Usage, and `hercule session list` as a column.
- **`session.interrupt { sessionId, subagentId }`** stops that subagent and every subagent below it, and leaves the rest of the session running. It is `not_found` for a subagent the session does not have. Like an interrupt of the session's own agent, it is sent whatever the subagent's recorded status, because the record lags behind the runner; the adapter ignores it for a subagent with no open turn. Without `subagentId` it stops all work in the session: its own agent's turn and every running subagent ([./06-providers.md](./06-providers.md) section 13.4). `session.respondToApprovalRequest` and `session.respondToQuestion` are unchanged: they are keyed by request id, and any open Request can be answered, in any order.
- **`transcript.query`** searches every agent's transcript. A `Passage` from a subagent carries its `subagentId`.
- **The CLI rows:**
  - `hercule transcript read <session-id> --subagent <id>`. Human output of a filtered read leaves out `subagentId`, which is the same on every row. A `subagent` item's row prints `subagentIds=...`, so an agent sees which id to pass.

*(Added 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768).)* **The skills a session has.** A session's skills are its library skills and its repository skills ([./06-providers.md](./06-providers.md) section 9.4). Two operations return them, and the composer's skill lists read both ([#769](https://github.com/theagenticage/hercule/issues/769)). They are two operations because one operation carries one grant: a session's skills are a read of the session, and a preview is a read of the workspaces of repos on a runner.

- **`session.querySkills`** returns the skills of one session. It is `not_found` when the session or its runner does not exist.
  - The library part is what the controller saved when it last claimed the session's start (a start, a resume or a fork), so a Skill added to the library later is absent until the session is resumed. It is read from the session row, not from the library ([./04-state-store.md](./04-state-store.md) Skill rows).
  - A session whose start is still queued, a queued resume included, gets the library as it is now, which is what its start will carry.
  - A Thread that started before the controller recorded library skills (migration `0087`) has no saved list. Its library part is left out and `incompleteReason` says so. The part shows after the Thread is resumed.
  - The repository part is read live from the session's workspace on its runner. A session without a workspace has no repository part.
- **`session.previewSkills`** returns the skills a new Thread would have, for a draft that has no session yet: the library as it is now, plus the repository skills of each repo's ready main workspace on the runner. It is `not_found` when the runner or a repo does not exist, and `validation` when only one of `runnerId` and `resourceId` is given, `resourceId` has none or more than 32 repos, or the resources cannot be checked out together (a resource that is not a repo, a repo listed twice, two repos with the same name, or a repo name that is not a valid directory name: `.`, `..` or `.git`, or, when there are two or more repos, `.claude` or `.agents`, in any letter case), with the same error as `session.spawn` for those repos. The wire schema refuses a lone `runnerId` or `resourceId` and an empty or oversized `resourceId`; the controller refuses `.claude` and `.agents` when it lays out the workspace ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 6.3).
  - *(Amended 2026-10-19, [#769](https://github.com/theagenticage/hercule/issues/769).)* With neither `runnerId` nor `resourceId`, the draft opens no repo and the answer is the library part alone: the same Skills, with the same descriptions, that a Thread started now would record, so a Skill without a current revision is left out. No runner is asked and `skipped` is empty. A `runnerId` alone is refused rather than ignored, so a client that meant to list a runner's repository skills learns it sent no repos.
  - The controller runs the checks of a spawn, finds each repo's ready main workspace on the runner (or none), and sends the runner one request ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2, `RepositorySkillsPreview`) with every repo in the order the Thread would open them. The runner lists the workspace the Thread would get, with the rules it applies to a real one. So names, clashes, caps and paths are the ones a start gets, and the controller changes none of them.
  - The answer shows the Thread's workspace, not the main workspace. With more than one repo, each checkout sits in a folder named after its repo, so every `path` starts with that folder.
  - A later repo whose checkout name an earlier repo already has is skipped, as a real start skips it: its skills are listed in `skipped`, not in `items`.
  - A repo with no ready main workspace on the runner, or whose checkout folder the runner cannot read, keeps its checkout name and appears as one entry in `skipped`, named by its folder (`.` for a single repo at the workspace root).
  - The runner reads at most 4 previews or inspections at a time, whoever asks, and answers within 9 seconds of the request, the wait for a permit included.
- **The answer** is `{ items, skipped, incompleteReason? }`, the same for both operations. It is not paged: a session has few skills, and the composer needs the whole list.
  - `items` holds the library skills first, then the repository skills, each part sorted by name. A library item is `{ source: "library", name, description }`. A repository item is `{ source: "repository", name, description, path }`. Its `name` is `<checkout>:<skill>`, such as `hercule:release`. Its `path` is the skill's folder relative to the workspace root, such as `web/.agents/skills/release`, or `.agents/skills/release` for a checkout at the root. A library skill and a repository skill with the same part after the prefix are both listed.
  - `skipped` holds `{ path, reason }` for each skill folder or checkout the runner found but could not offer. `path` is written as in `items`. `reason` is plain text of at most 512 characters, and says what is wrong with the folder, so a user whose skill is missing can find out why ([./06-providers.md](./06-providers.md) section 9.4 lists the reasons).
  - `incompleteReason` is present when `items` may not hold all the skills of the session, and holds the reason in plain words. A client shows it, so a missing part is never mistaken for an empty one. When more than one reason applies, they are joined into one message. The reasons:
    - the session started before its library skills were recorded (`session.querySkills` only);
    - the runner is too old to list repository skills, because it did not list the `repositorySkills` capability ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2);
    - the runner is offline, or did not answer in 10 seconds;
    - the runner failed to read the workspace, with its message. This includes a listing that took longer than 9 seconds ("reading the workspace's skill folders took longer than 9 seconds") and a request that got no permit to read in time ("the runner is still busy reading skill folders for earlier requests; try again in a moment"). The runner gives up on both before the controller's 10 seconds are over;
    - the runner left an entry out at a cap (`truncated`): a list was full, or the walk budget of the listing was used up (10,000 entries, every file and folder the runner reads counting one). The runner stops listing once both lists are full and an entry was left out. The text is: "Not every skill folder of the workspace is shown: a listing holds at most 256 skills and 256 skipped folders, and reads a limited number of files and folders." (`truncated` in the runner's answer, [./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2).
  - The repository part never fails the call. When it cannot be read, the library part is still listed. With several repos, the skills of the repos that were read are kept.
- **The CLI rows**, by the nested-noun rule of section 6.3:
  - `hercule session skill list <session-id>`. Purpose: "Lists the skills a session has: the Skill Library's, then the repositories'. Prints the folders that are not offered, each with its reason, and the reason the list may be incomplete."
  - `hercule session skill preview --runner <id> --resource <id>...`. Purpose: "Lists the skills a new thread would have, before it starts. Repeat `--resource` for each repository, at most 32." It prints the same extra lines as `list`.

*(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* **Images in prompts.** An Attachment is an image the user attaches to a prompt ([./04-state-store.md](./04-state-store.md) section What is in the store).

- **`attachment.create`** uploads one image and answers `201` with the `Attachment`. The body is the raw bytes, never base64 JSON, which would add a third to a 10 MiB body. The request declares no media type: the controller reads the file's first bytes, and that is the only type it records. Accepted types are `image/png`, `image/jpeg`, `image/gif` and `image/webp` (`IMAGE_MIME_TYPES`); any other file is refused as `validation` with a message that names the accepted types. A file is at most 10 MiB (`MAX_ATTACHMENT_BYTES`, section 1.5) and a name at most 255 characters (`MAX_ATTACHMENT_NAME_LENGTH`), with no control characters. One actor may hold at most 200 MiB of uploads that no input references yet. The limit counts only such uploads younger than the sweep's 24 hours, and the check and the insert run in one transaction, so two parallel uploads cannot both slip under it. An upload past it is refused as `validation`, with a message that says how long to wait, for example "try again in about 3 hours", or to send or remove some images first. The row is stamped with the caller's actor.
- **`attachment.readContent`** streams the bytes with the image's `content-type`, plus the headers in [./13-security.md](./13-security.md) section 1. It serves an attachment that some input references, or one that no input references yet and that the caller's actor uploaded; anything else is `not_found`. *(Amended 2026-10-10, [#478](https://github.com/theagenticage/hercule/issues/478).)* It also serves an image an agent's tool returned, which a transcript references as a `ToolResultImage` ([./06-providers.md](./06-providers.md) section 6.3). Its grant is `session.read`, the grant that reads the transcript, so whoever may read a session's transcript may read its images. No second operation is needed: an Attachment owned by a tool result is stored and served like one owned by an input ([./04-state-store.md](./04-state-store.md)). The bearer never goes into a URL: `@hercule/client-core` fetches the bytes with the bearer and returns a `Blob`, and a UI makes an object URL from it and revokes the URL when the image leaves the screen.
- **`attachment.delete`** deletes an upload of the caller's actor that no input references yet, row and file, and answers `{}`. Any other id is `not_found`, including an image an agent's tool returned: it belongs to the session's transcript and lives as long as the transcript does ([./04-state-store.md](./04-state-store.md)). A client calls it when the user removes an image from the composer's shelf, so the image stops counting against the 200 MiB limit at once.
- **`attachments`** is an optional list of `AttachmentId`s, at most 10 (`MAX_ATTACHMENTS_PER_INPUT`), on `session.spawn`, `session.input`, `session.continue` and `input.update`. Their order is the order the agent sees them in. `input.steer` takes none: it sends a row that already exists. On `input.update`, `attachments` replaces the row's list, and when it is absent the list is kept; an attachment dropped from the list becomes sweepable.
- **Text or images.** `prompt` and `text` may be empty when at least one image is attached. A payload with neither is `validation`: "A prompt needs text or at least one image." `MAX_PROMPT_LENGTH` still holds, and still fits one runner frame, because a frame carries references only. A Thread's title falls back to the first image's name, for example `image.png`, when the prompt text is blank. *(Amended 2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282): that cut-short title is the immediate one, and a generated title may replace it once; [./02-domain-model.md](./02-domain-model.md), the Session's `title`.)*
- **The claim.** The ids are checked inside the transaction that stores the input: each must exist and must have been uploaded by the caller's actor. Otherwise the whole input fails as `validation` and nothing is stored. An id that the 24-hour sweep has deleted fails with an issue at path `["attachments", i]` and the message "This image expired; attach it again." A composer maps that path to the image's tile.
- **The model and runner gates.** In the same transaction the input is refused as `validation` when the session's runner did not negotiate images or the model the turn runs on does not accept them, with the messages of [./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2. A queued input is checked again when it is sent.
- **`session.continue`** (fork) references the parent's attachment rows; no file is copied.
- **What reads return.** The `Input` record (`input.query`, `input.update`) carries `attachments: Attachment[]` in order; `input.query` reads the attachments of every listed row in one batched query. A transcript's `user_message` item carries `detail.attachments` ([./06-providers.md](./06-providers.md) section 6.3). *(Amended 2026-10-10, [#511](https://github.com/theagenticage/hercule/issues/511).)* A `user_message` that another session's agent sent also carries `detail.senderSessionId`, the sending session's id (same section).
- **The CLI rows.** The three attachment operations are `hidden: true`, with the reason "images are uploaded through `--image` on `session spawn`, `session input` and `session continue`" (section 6.3).
  - `hercule session interrupt <session-id> --subagent <id>`.
  - `--subagent` takes the harness's full id, or a tail of eight or more characters matched within that session.

### subscription

Semantics: [./08-events-and-connections.md](./08-events-and-connections.md) section 7; the session-side behaviour is section 7 of this document.

| Operation | Input | Grant | Route |
|---|---|---|---|
| `subscription.create` | `{ target: SubscriptionTarget }` -> `{ subscriptionId }` | `subscription.write` | `POST /subscriptions` |
| `subscription.query` | `{ holder?: { kind: "session" \| "run", id }, target?: SubscriptionTarget }` | `subscription.read` | `GET /subscriptions` |
| `subscription.cancel` | `{ subscriptionId }` | `subscription.write` | `DELETE /subscriptions/{id}` |

```ts
type SubscriptionTarget =
  | { kind: "run";     runId: string }       // run.* events for that run
  | { kind: "session"; sessionId: string }   // session.* events for that session (ended, needs approval)
  | { kind: "ref";     ref: string }         // any event whose refs include this External Ref (a PR's checks, reviews, merge)
  | { kind: "request"; requestId: string }   // the decision on a Permission Request
```

The controller expands a target into the pipeline's matching condition and stores both, so the web app shows "waiting on run r_3" without parsing anything. A session token with no `holder` lists its own subscriptions; a user credential must name a holder. `subscription.cancel` accepts session-held subscriptions only; a run-held one (instantiated from a signal trigger) ends with its run, and cancelling it directly is 409 `invalid_state` *(amended 2026-10-04, [#83](https://github.com/theagenticage/hercule/issues/83): built; the message says the subscription ends when its run ends, and to cancel the run instead)*. No free-form CEL target in v1: the four kinds already compose into everything the tickets asked for, and CEL is the escape hatch if dogfooding proves them short.

*(Amended 2026-09-27, [#81](https://github.com/theagenticage/hercule/issues/81).)* **Targets as built.** `subscription.create` accepts two of the four kinds:

- `ref`, as above.
- `run:<id>`, which receives that run's `run.completed`, `run.failed` or `run.cancelled` event ([./08-events-and-connections.md](./08-events-and-connections.md) section 5.5). The controller reads the run through the runs domain's own read, so the caller also needs the `run.read` grant, and is refused with `forbidden` without it. An unknown run is refused with `not_found`. A run that has already ended is refused with `invalid_state`, because no event of it would ever come. A run id that is not a UUID is refused with `validation`. The stored condition also requires `event.source == "platform"`, so an event a plugin emits under a `run.` kind cannot pass for the run's own.

`session` and `request` targets are still refused with `invalid_state`: no `session.*` events are emitted yet, and ~~Permission Requests do not exist yet~~ `permission.request` registers the `request` subscription itself, so no caller needs to *(amended 2026-10-10, [#86](https://github.com/theagenticage/hercule/issues/86))*.

*(Amended 2026-10-04, [#83](https://github.com/theagenticage/hercule/issues/83).)* **Run-held subscriptions as built.**

- **The holder** is `{ kind: "session", id }` or `{ kind: "run", id }`, written `session:<id>` or `run:<id>`. Example: `hercule subscription list --holder run:<run id>` lists what a run waits on.
- **The target union** has a fifth kind, `{ kind: "signal", triggerId }`, which only a run-held subscription has. It names the signal trigger in the run's plan. `subscription.create` never accepts it: only a run opens a run-held subscription, when it starts ([./08-events-and-connections.md](./08-events-and-connections.md) section 7.1).
- **`subscription.cancel`** refuses a run-held subscription with 409 `invalid_state`, as above.

A Signal is its own record, never a Notification, and the two families of operations share nothing but the shape of a Bound Action.

- *(Added 2026-10-21, [#802](https://github.com/theagenticage/hercule/issues/802).)* **`signal.queryYourWork`** returns Your work, the Tasks Intake's Your work section draws ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#95-blocks)): the open Tasks (status `open` or `in-progress`, never a deleted one) whose provenance carries the thread ref of an open signal, on To do or snoozed. A snooze plays no part, on purpose: the client keeps the Tasks whose `signalIds` meet its own read of To do, so To do alone decides which signals show Your work, and a snooze that runs out between the two reads cannot make them disagree. It is owned by the signals domain, which reads Tasks through the tasks domain's repository. It is worked out on every read and never stored, so a client needs no read of Tasks by ref:

  ```ts
  interface YourWorkTask {
    id: string
    title: string
    status: "open" | "in-progress"
    updatedAt: string
    signalIds: string[]   // the open signals the Task belongs to, ascending; never empty
  }
  ```

  - **One row for each Task.** A Task that carries the thread refs of several open signals, or one ref several times, appears once with every signal id. Only a signal raised from an event has a thread ref, so a signal of a core kind (`proposal`, `offer`, `unsure`, `fyi`) brings no Task.
  - **Order.** `updatedAt`, newest first, then `id`. Not paged: a client counts every row, and a row holds no description or provenance.
  - **Grants.** The operation's row names `signal.read`, and the service also checks `task.read`, because a row holds Task titles and `task.query` is what gives them. A session needs both; a caller that lacks one is refused with `forbidden` naming it, so signal access alone never reveals a Task.
  - **How it reads.** No transaction, so it reads on the read-only connection and never waits for a writer. It is two statements, which are not an atomic snapshot: the thread refs of the open signals (a scan of a partial index that holds the open signals only, so no resolved signal is read), then the open Tasks that carry those refs, starting from `task_provenance_ref`, so no Task and no provenance entry that carries none of the refs is read. A signal resolved between the two still counts, and the push that change makes brings the next read.
  - Its CLI row is `hercule signal your-work`. Purpose: "Lists Your work: the open and in-progress tasks that belong to an open signal, snoozed or not." It takes no field.
- **The grants bind sessions only in v1.** A run's action steps and a plugin are ungated, as for every grant (section 3.1); the shipped profiles that hold `signal.read` and `signal.write` are in [./13-security.md](./13-security.md#62-shipped-profiles).
- **User only.** `signal.act`, `signal.markDone`, `signal.handOff` *(added 2026-10-20, [#801](https://github.com/theagenticage/hercule/issues/801))* and `signal.lowerPriority` refuse a session or a run with `forbidden`, even when its profile holds `signal.write`: an answer is the user's act, as with `notification.act`, and an agent must not quietly lower what the user was told is urgent. Snooze is not an answer, so any holder of `signal.write` may snooze and unsnooze, and an assistant can do it when the user asks.
- **Reads.** `signal.query` and `signal.read` return `snooze?: { until, snoozedAt }` beside each signal. The `to-do` view is not paged: it returns every open signal on To do in one reply, because the list is short by nature and every client's To do count, per tab and in all, must take in every row (section 1.6's second exception). The view sets the order: `later` is soonest first, `done` is newest first ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#97-snooze-and-not-urgent)). `source` is the id of the plugin whose kind the signal is. A read by a session or a run carries no describe lines, as for Notifications: only the user takes an answer. A Hand to an agent run reads its signal and the signal's events through `signal.read` ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#94-actions-done-and-hand-to-an-agent)).
- **`signal.raise`** follows [./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#93-core-kinds-and-signalraise). A kind that is not a core kind, the priority `urgent`, and a `proposal` without `task` are refused with `validation`. Each action is checked as `notification.create` checks an answer, against `signal.answer` in `usableIn`, and a named Connection must exist, have the action's Connection type and be enabled; a failed check is a `validation` error naming the action's path. *(Amended 2026-10-12, [#532](https://github.com/theagenticage/hercule/issues/532).)* An action that runs `ignoreRule.create` is refused the same way, at `actions.<n>.operation.op`, because only the core binds it, on its own Ignore Rule offer. The core fills in `origin` from the caller, never from the input.
- **`signal.screen`** accepts a decision only for a pending Screening of that event and kind ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#98-screening-and-the-screener)). The first decision wins; a second is refused with `invalid_state` and the message names the first ("already screened: yes, by run 0193…"). An event that was never sent to the Screener is `not_found`. It is an API operation as well as a built-in action so that the user or a test can stand in for a run.
- **`signal.act`** runs the action's frozen operation as the user and resolves the signal at the click. It refuses `actionId: "done"` with `validation`, and the message says to call `signal.markDone`. `text` on an action without `field` is `validation`. On an action with `field`, the core puts `text` into the field the action names, decodes the input again with the operation's schema, checks the Connection again, then runs it. A failed check is `validation`; a failed operation returns the operation's own error; in both cases the signal stays open. A signal already resolved is `invalid_state`. *(Amended 2026-10-12, [#532](https://github.com/theagenticage/hercule/issues/532).)* The operation's own errors include `conflict`: Ignore on the core's offer binds `ignoreRule.create`, which refuses a rule equal to an existing one with `conflict`.
  - *(Amended 2026-10-11, [#524](https://github.com/theagenticage/hercule/issues/524).)* **Two answers never run at once.** A core operation runs in the transaction that resolves the signal, so both commit or neither does. A plugin action reaches outside the controller, so it runs outside any transaction ([ADR 0004](../adr/0004-controller-state-lives-in-one-sqlite-database.md)) and the signal resolves once the action succeeds. While it runs, any other `signal.act` on the same signal is refused with `invalid_state`, so a second click cannot resolve the signal under an action whose effect is already on its way. The same holds while a core operation runs. A `signal.withdraw` that arrives while an action on the signal runs is refused with `invalid_state` too, with the message "an action on this signal is running; withdraw it once it finishes".
- **`signal.handOff`** *(Added 2026-10-20, [#801](https://github.com/theagenticage/hercule/issues/801).)* starts a workflow on a signal and puts the work on a Task, as the user ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#94-actions-done-and-hand-to-an-agent), [ADR 0046](../adr/0046-handing-a-signal-off-tracks-the-work-on-a-task.md)). The Hand to an agent answers bind it, and it lists `signal.answer` in `usableIn`. A session or a run is refused with `forbidden`, as for `signal.act`. In one transaction it:
  1. finds the open Tasks (status `open` or `in-progress`) whose provenance carries the signal's thread ref (`origin.threadRef` of a plugin signal). A core signal has no thread ref, so it finds none;
  2. with none, decides the id of a new Task;
  3. starts the run with `taskId` set to the Task found or decided, as `run.start` starts a stored workflow, with the signal as the workflow's signal input;
  4. writes the Task in one write, with the provenance entry `{ signalId, runId, ref?, eventId?, actor: user }`, where `ref` is the thread ref and `eventId` is the signal's origin event. A new Task has the signal's title and priority and is created `in-progress` with the entry, so the handoff emits one `task.created` that carries the entry and no `task.updated` ([./08-events-and-connections.md](./08-events-and-connections.md)). A Task found is set `in-progress` if it was `open`, and gets the entry: one `task.updated`. The run is started first so that a run that cannot start writes no Task; the Task's id is decided in step 2 because the run names the Task and the Task's first entry names the run;
  5. resolves the signal `decided` with the `actionId` of the Hand to an agent answer for this workflow, the outcome "Handed to *workflow name*", and `resolution.runId`. It returns the resolved signal. The run's id is `resolution.runId`.

  It acts on the signal's own Hand to an agent answer for the workflow. A signal raised before this change has a frozen `run.start` answer instead, and handing it off takes that one: the run starts untracked, with no Task ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#94-actions-done-and-hand-to-an-agent)).

  - **One transaction, no waiting.** The transaction creates the run and does not wait on a runner: placing the run's first session happens after the commit, as for `run.start` ([ADR 0004](../adr/0004-controller-state-lives-in-one-sqlite-database.md)). If any step fails, nothing is written and the signal stays open.
  - **Every caller is checked.** The handoff itself, not its callers, checks that the caller is the user, that the signal is open, and that the signal offers a Hand to an agent answer for the workflow that binds `signal.handOff` on this signal. A caller inside the controller cannot skip these. Writing the Task is a narrow path of the tasks domain, `recordHandoff`, which is also user only; `task.create` and `task.update` keep their ordinary contract (no chosen id, no starting status, no `signalId` in an entry).
  - **Only the core binds it.** `signal.raise` and a plugin's draft refuse an action whose operation is `signal.handOff` with `validation`, as they refuse `ignoreRule.create`, so a raiser cannot make one signal's answer hand off another. For a signal stored with such an answer, `signal.act` refuses it with `validation` when its `signalId` is not the signal it sits on, and writes nothing.
  - **Called through `signal.act`,** the operation's step 5 is the one resolution of the signal. `signal.act` does not write a second.
  - **The describe line** is worked out when it is read, from the signal, the workflow and the open Tasks at that moment: "Starts *Implement* on *PAY-212*, tracked as a new Task", or "Starts *Implement* on *PAY-212*, continues *Retry failed webhooks*". The Task's name is the marked part in the second form.
  - **Errors.**
    - `forbidden`: a session or a run called it.
    - `not_found`: no such signal, or the signal does not offer a Hand to an agent answer for this workflow. The message lists the workflows the signal offers.
    - `invalid_state`: the signal is resolved, or another action on it is running (the rule of `signal.act`, above).
    - `validation`: the workflow has no input for the signal's kind, or the run cannot start (`run.start`'s own checks refuse it: the workflow is invalid or disabled, or its inputs do not fit).
- **`signal.withdraw`** is refused with `forbidden` for any actor but the one that raised the signal, so a plugin's kind, which no actor raised, is never withdrawn this way: it ends through its kind's `ends` ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#96-when-a-signal-leaves)). A resolved signal is `invalid_state`.
- **Operations that take a list of ids.** `signal.snooze` is the first contract operation that takes a list of ids, and `markDone`, `unsnooze` and `lowerPriority` follow it: one user action, such as a bulk snooze, is one call. Each returns the ids it changed and `skipped: { signalId, reason: "resolved" }[]` for the signals that had resolved before the call; a skipped signal is normal, not an error, because a signal may end on its source while the user clicks. Unknown ids are `not_found` for the whole call. None of the four is bulk-destructive ([./13-security.md](./13-security.md#61-grant-families)).
  - `signal.markDone` fails the whole call with `validation`, naming the ids, when a signal's kind has no `done` action. Only a client bug or a hand-typed command sends one, and skipping it would hide that. It is the only way to Done, from every surface, and the place where the core suggests Ignore Rules ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#99-ignore-rules)).
  - *(Amended 2026-10-11, [#525](https://github.com/theagenticage/hercule/issues/525).)* `signal.markDone` fails the whole call with `invalid_state`, and changes nothing, while an action or a withdrawal on one of the signals runs. The signal is not skipped, because the running action may still fail and leave it open, so it has not resolved yet.
  - `signal.snooze` refuses an `until` in the past with `validation`, and replaces the time of a signal that is already snoozed.
  - `signal.unsnooze` changes nothing and writes nothing for a signal that is not snoozed.
  - `signal.lowerPriority` moves `urgent` to `high`. An open signal of any other priority is left as it is and is not listed in `skipped`, whose only reason is `resolved`. It sends nothing to the source.
- **The live topic `signal`.** Every committed write that raises, resolves, snoozes, unsnoozes or lowers a signal publishes on the topic `signal`, and the push carries the ids of the signals that changed ([./14-web-app.md](./14-web-app.md)). When a snooze runs out no record changes and nothing is published: the client sets its own timer.
- **No chat delivery.** Signals are not delivered to chat sinks in v1, so no answer comes from a chat click.

**The CLI rows.** Ids are positional and repeatable where the operation takes a list, and `hercule signal list` is the listing that resolves short ids. *(Amended 2026-10-11, [#525](https://github.com/theagenticage/hercule/issues/525).)* Each id of a repeated positional resolves as a single one does. `hercule signal unsnooze` resolves its tails through `hercule signal list --view later`, because only a snoozed signal can be unsnoozed; the other commands resolve through the To do view.

- `hercule signal list [--view to-do|later|done] [--kind <kind>] [--source <pluginId>]`. Purpose: "Lists signals: what asks for your move now, what is snoozed, or what is done." Example: `hercule signal list --view later`. The human rendering prints each signal's blocks as text through the same `client-core` function every client uses.
- `hercule signal read <id>`. Purpose: "Shows one signal: its blocks, its actions and where it came from."
- `hercule signal raise --kind <kind> --title <text> --reason <text> --event-id <id>... [--priority <p>] [--blocks-stdin] ~~[--actions '<json>']~~ [--action '<json>'...] [--task '<json>']` *(Amended 2026-10-11, [#524](https://github.com/theagenticage/hercule/issues/524).)* `--action` takes one action as JSON and repeats for each, as `--event-id` repeats, so a long list never has to be one quoted argument. Purpose: "Puts a proposal, an offer, an unsure item or an FYI on the user's Intake." Example: `hercule signal raise --kind fyi --title "Release 4.2 shipped" --reason "Tagged and published by the release workflow" --event-id 81234 --blocks-stdin < blocks.json`. `blocks` is the signal's content, so it comes from stdin as JSON, under section 6.3's one content channel rule. `--action` ~~`--actions`~~ and `--task` take the field's value as JSON, as `hercule run start --inputs` does.
- `hercule signal screen <eventId> --kind <kind> --decision yes|no --reason <text>`. Purpose: "Records the Screener's decision for one event." Example: `hercule signal screen 81234 --kind gmail/mail --decision yes --reason "Marta asks you to sign the lease by Friday"`.
- `hercule signal act <id> --action <actionId> [--text-stdin]`. Purpose: "Takes one of a signal's actions, as you." The typed reply of an action with a field comes from stdin, under section 6.3's one content channel rule: `hercule signal act 0b1c2d3e --action reply --text-stdin < reply.md`.
- *(Added 2026-10-20, [#801](https://github.com/theagenticage/hercule/issues/801).)* `hercule signal hand-off <id> --workflow <id>`. Purpose: "Hands a signal to a workflow, as you, and tracks the work on a Task." Example: `hercule signal hand-off 0b1c2d3e --workflow 9f8e7d6c`. `--workflow` takes a full id or a tail of eight or more characters, as `hercule run start` does. The command prints the resolved signal's line, such as "signal 0b1c2d3e decided: Handed to Implement", then the run's id and the subscription hint (section 8), as `hercule run start` does. It does not print the Task's id.
- `hercule signal withdraw <id> --reason <text>`. Purpose: "Takes back a signal you raised, when its question no longer exists."
- `hercule signal done <id>...`. Purpose: "Takes signals off your To do list as done. Their source is not told." Example: `hercule signal done 0b1c2d3e 9f8e7d6c`. *(The verb is `done`, not `mark-done`, as [#387](https://github.com/theagenticage/hercule/issues/387) decided; it departs from section 6.3's rule that a custom verb is the kebab-cased operation verb.)*
- `hercule signal snooze <id>... --until <time>`. Purpose: "Hides signals from To do until a time. They stay open, and their source is not told." Example: `hercule signal snooze 0b1c2d3e 9f8e7d6c --until 2026-10-13T09:00+02:00`. `--until` takes an ISO 8601 time with its offset and nothing else: the CLI adds nothing of its own, and the menu's choices belong to `client-core`. An agent reads the user's timezone with `hercule settings read`.
- `hercule signal unsnooze <id>...`. Purpose: "Puts snoozed signals back on To do now."
- `hercule signal lower-priority <id>...`. Purpose: "Moves urgent signals out of Now. Their source is not told."

### ignoreRule

*(Added 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395), [#398](https://github.com/theagenticage/hercule/issues/398).)* Model: [./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#99-ignore-rules). An Ignore Rule has no grant family of its own: it is a part of how signals are raised, so it sits under `signal`.

| Operation | Input | Grant | Route |
|---|---|---|---|
| `ignoreRule.query` | `{ kind? }` -> rules, each with its caught count and its last catch | `signal.read` | `GET /ignore-rules` |
| `ignoreRule.create` | `{ kind, match }` -> the rule; user only; usable as `signal.answer` | `signal.write` | `POST /ignore-rules` |
| `ignoreRule.delete` | `{ id }`; user only | `signal.write` | `DELETE /ignore-rules/{id}` |

- **User only.** `create` and `delete` refuse a session or a run with `forbidden`, even when its profile holds `signal.write`: a rule hides things from the user, so an agent may only suggest one ([ADR 0022](../adr/0022-proposing-is-not-doing.md)). The core's own suggestion is an `offer` whose Ignore action binds `ignoreRule.create`, which runs as the user at the click.
- **`ignoreRule.create`** refuses with `validation`:
  - a `match` with no values, and the message points to the kind's switch: `hercule plugin update-intake`;
  - a field the kind does not declare;
  - a core kind;
  - a kind no plugin declares.

  A rule equal to an existing one is `conflict`, and the message names the existing rule's id. Creating a rule also resolves, in the same transaction, the open signals it matches. *(Amended 2026-10-12, [#532](https://github.com/theagenticage/hercule/issues/532).)* It resolves the open core offer of the same rule too, and leaves open a signal an action is running on, which that action then resolves ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#99-ignore-rules)).
- **The describe line** of `ignoreRule.create` says what the rule does and what it does not: ~~"Ignores **review requests** from **dependabot[bot]** in **acme/webshop**. GitHub still sends them; they show in Everything. Also takes matching open signals off your list."~~ "Ignores **Review requested** where Repository is **acme/webshop** and Author is **dependabot[bot]**. GitHub still sends them; they show in Everything. Also takes matching open signals off your list." *(Amended 2026-10-12, [#532](https://github.com/theagenticage/hercule/issues/532).)* The line uses the kind's label and each field's label as the plugin declares them, and the labels are nouns, so the line reads "where *field* is *value*" ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md#99-ignore-rules)). For a kind no loaded plugin declares any more, the line shows the kind's id and the fields' names, and "The source" in place of the plugin's name.
- **`ignoreRule.query`** counts the catch rows for each rule, so the count covers the events still in the log ("caught 142 in the last 90 days"), and returns the time of the last catch.
- **`ignoreRule.delete`** works forward only: it brings nothing back.

**The CLI rows.**

- `hercule ignore-rule list [--kind <kind>]`. Purpose: "Lists your Ignore Rules and how many events each has caught."
- `hercule ignore-rule create <kind> --match <field>=<value>...`. Purpose: ~~"Stops signals of one kind with these values from being raised, and takes the matching open ones off your list."~~ "Stops signals of one kind with these values from being raised. It also takes the matching open ones off your list." *(Amended 2026-10-12, [#532](https://github.com/theagenticage/hercule/issues/532): a CLI purpose opens with a sentence of at most 100 characters.)* Example: `hercule ignore-rule create github/review-requested --match repo=acme/webshop --match author=dependabot[bot]`. The kind is positional, by its row.
- `hercule ignore-rule delete <id>`. Purpose: "Deletes an Ignore Rule. Events it already caught stay caught." `hercule ignore-rule list` resolves short ids.

### event

Pipeline: [./08-events-and-connections.md](./08-events-and-connections.md).

### harness, provider, providerAccount, modelProfile (grant family `infra`)

*(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)* These four groups replace the `provider.*` operations on Provider Instances ([ADR 0048](../adr/0048-harnesses-and-provider-accounts-are-separate.md)). A **Harness** is the agent program (Claude Code, Codex, pi), a **Provider** is the company that serves the models and bills for them, a **Provider Account** is one account at one Provider, and a **Model Profile** is a named model menu picked from the accounts ([GLOSSARY](../../GLOSSARY.md)). The records' shapes and what they mean are [./06-providers.md](./06-providers.md)'s; this section owns the operations. Reads need `infra.read` and writes `infra.write`, as `provider.*` did, so no Permission Profile changes. Harnesses and Providers are plugin contributions with qualified ids such as `pi/pi` ([ADR 0034](../adr/0034-a-catalog-contribution-is-identified-by-its-qualified-id.md)). Each is read as one whole list, like `workflowAction.query`, so a qualified id, which holds a `/`, never has to be a path segment.

- **`providerAccount.create`.** `kind` is one of the Provider's Account Kinds ([./06-providers.md](./06-providers.md)), and is refused `validation` otherwise. `credentials` holds the fields of the kind's `credentials` step, such as `apiKey`. It is required for a kind that has that step and refused `validation` for a kind that has not. The values are stored as Secrets owned by the account and are never returned. *(Amended 2026-10-31, [#406](https://github.com/theagenticage/hercule/issues/406).)* A key is checked with the provider before anything is stored ([./06-providers.md](./06-providers.md) section 15.2): a key the provider refuses fails the call with `validation` carrying the provider's own words, and a provider that cannot be reached fails it with `invalid_state`, so the user tries again. A kind whose setup is a `harness-login` step (`subscription-per-machine`, `subscription-token`) is created without credentials and then signed in with `signIn`.
  - `label` is required when an account at that Provider already exists, with the message "Give this one a name, so you can tell them apart." It is refused `conflict` when another account at that Provider has the same label.
  - `defaultHarnessId` defaults to the Provider's own harness, else pi ([./06-providers.md](./06-providers.md)). A harness the account cannot run in is refused `validation`, with the reason.
  - Creating an account starts a read of its Model Catalog, and nothing waits for it (section 8). The outcome arrives on topic `provider`. A key the Provider refuses makes the account `failed`, with the Provider's words.
- **`providerAccount.update`.** `providerId` and `kind` never change: another kind is another account. New `credentials` are checked as on `create` *(Amended 2026-10-31, [#406](https://github.com/theagenticage/hercule/issues/406).)*, then replace the stored ones, start a new catalog read and clear the account's expiry warnings. Sessions started afterwards use them; running sessions keep what they started with. A `subscription-token` account takes no `credentials`: it gets a new token only through `signIn`, because Hercule runs the token flow itself and accepts no pasted token ([./06-providers.md](./06-providers.md)).
- **`providerAccount.delete`** is refused `invalid_state` while something would be left pointing at nothing: an Agent or an assistant, `textGeneration.model`, the user's `thread.providerAccountId`, or a session on the account that is queued, starting, idle or busy. The message names each of them, and says to point them elsewhere, or to let the sessions end, first. A Model Profile never blocks it: the account leaves every profile in the same transaction, which raises each profile's revision, and a client's confirm names those profiles. The account's Secrets, Model Catalog, Account Usage and Capability Snapshots go with it. Ended sessions keep the account's id as history, and continuing one is refused `invalid_state`, with a message that says the account was deleted.
- **`providerAccount.signIn`** starts a sign-in on one runner, through the harness that holds the kind's login ([./06-providers.md](./06-providers.md)). It keeps the two steps of `provider.login`.
  - For `subscription-per-machine`, the harness signs that machine in, inside the account's Harness Home there.
  - For `subscription-token`, the runner runs `claude setup-token`, and the controller keeps the token it prints, so the token works on every runner. Its expiry is one year from that moment.
  - The answer is the URL to open. A device login adds the one-time `userCode` to type there and `expiresAt`, when that code stops working, at most a day after the call. A device login finishes by itself: when the runner reports that it ended, the controller reads the account on that runner again and announces it on topic `provider`.
  - It is refused `invalid_state` when the runner is offline, when the harness is not installed there, when the kind has no `harness-login` step, or when the runner printed no URL. A runner that goes offline ends the sign-in; the next call starts a new one.
- **`providerAccount.submitSignInCode`** sends the code the browser showed to the harness that waits for it, and answers the account once the sign-in is done. A code the vendor refuses is `validation` carrying the vendor's own words, and the sign-in stays up for another paste. One account is one vendor identity ([./06-providers.md](./06-providers.md)). The first sign-in of an account sets its identity. A sign-in that reports someone else is refused `conflict`, with a message such as "This account is rogier@work.com, and that sign-in was rogier@gmail.com. Sign in again on this machine as rogier@work.com." The wrong login stays in the Harness Home, and that runner counts as not signed in for the account until a sign-in as the right person replaces it.
- **`providerAccount.refresh`** reads the account's Model Catalog and Account Usage again, and answers at once (section 8). The outcome arrives on topic `provider`. A failed read keeps the last good catalog and records the error ([./06-providers.md](./06-providers.md)).
- **`modelProfile.create`** is refused `conflict` when another profile has the name. A copy takes every account, entry and harness choice of `copyFromId`, and its default entry.
- **`modelProfile.update` replaces the whole profile.** It carries all of `name`, `accounts` (in order, each with its `harnessId` and its `entries` in order), `defaultEntry` and `dismissedNewModels`, and the stored profile becomes exactly that. One exception: an account that is new to the profile and is sent without `entries` gets its Provider's Default Selection; `entries: []` means none. A profile with no default entry then takes that account's default model ([./06-providers.md](./06-providers.md) section 17). Every write raises `revision` by one. It is refused:
  - `conflict` when the profile's revision is not `expectedRevision`, with the message "The profile changed since you read it (now revision <current>). Read it again and make your change on that." Nothing is merged for the caller: a client reads the profile again and applies the user's one change to it.
  - `validation` when an account appears twice, an entry (account, model, harness) appears twice, `defaultEntry` is not one of the entries, an account does not exist, or a harness is one the account cannot run in, with the reason.

  An entry whose model the account's catalog no longer lists is kept, and shows that it cannot run ([./06-providers.md](./06-providers.md)).
- **`modelProfile.delete`** is refused `invalid_state` for the last profile: "This is your only Model Profile. Create another before you delete this one." Otherwise every project that named the profile gets `modelProfileId: null` in the same transaction, so its new Threads start on the thread default; a client's confirm names those projects.
- **Audit.** Every write appends its own audit row: `providerAccount.created`, `providerAccount.updated`, `providerAccount.deleted`, `providerAccount.signedIn`, `modelProfile.created`, `modelProfile.updated` and `modelProfile.deleted`. No credential value ever enters one.
- **Live updates.** One topic, `provider`, covers all four groups ([./14-web-app.md](./14-web-app.md) Live model). The controller publishes on it after every write above, and after every change that alters what they read without a write: a runner's harness facts or Capability Snapshots changing, a runner connecting or disconnecting, a catalog or usage read ending, a sign-in ending, and a harness or provider plugin being enabled or disabled. So a sign-in on one machine, a failed account or a runner going offline reaches the composer's entries without Settings being open. A client that shows the Text Generation status reads `controller.read` again on it, because what `automatic` resolves to depends on the same facts.

*(Amended 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), [ADR 0039](../adr/0039-workspaces-preserve-runner-local-git-state-and-human-work.md).)* The table records the accepted contract; operations ship with their implementation, never with success stubs. Each operation has its CLI row beside the owning Effect Schema operation table, including purpose, examples and every input field. `workspace.attach` persists external path intent for exactly one runner; no other spawn input accepts an external path. `workspace.inspect` is a controller daemon use case, while `workspace.read` remains a persisted read. Mutation services enforce permissions and stamp actors, and transport handlers remain one line.

`Workspace.ownership`, `retentionPolicy` and `observedAt`, and Checkout `headCommit`, `startingRevision` and `baseCommit` are owned by [spec 02](./02-domain-model.md). Unobserved facts are null. A manual workspace has no automatic deletion deadline; a deadline for an automatic workspace is eligibility for safe cleanup, never proof files were removed. The later lifecycle supersedes the managed-only, implicit primary branch-switch and lease-only rules in the historical amendments below. Thread main-workspace starts preserve the actual branch. Workflow primary policies that explicitly choose a branch retain that behavior. Ephemeral checkouts accept the `startingRevision` union of spec 03 section 6.8; deprecated `baseBranch` is an explicit remote choice and supplying both is validation failure.

Disposal reserves `disposing` before runner I/O and returns deletion success only after a successful outcome. Safe refusal leaves files available with its reason; a lost acknowledgement leaves durable intent for retry. Only a user may request force through `discardChanges: true`, and automatic cleanup cannot request it. Detachment tells the user about derived worktrees while preserving their source bindings and every attached file. Capability negotiation rejects unsupported new semantics visibly. Derived clients and OpenAPI are regenerated by their owning tools.

Workspaces otherwise appear as side effects of session and run placement; `lost` is set by runner retirement, never by an operation.

*(Amended 2026-09-27, [#263](https://github.com/theagenticage/hercule/issues/263); [ADR 0036](../adr/0036-a-workspace-is-kept-by-leases-its-holders-release.md).)* **A workspace says how long it is kept, and `workspace.dispose` names what still uses it.**

- **`Workspace.keptUntil`** (`Timestamp | null`) is when the sweep may delete the workspace: the latest kept-until time of its Workspace Leases, fixed when its last holder released it. A settings change does not move it. It is null for a primary, for a workspace that is gone, and while a session or a run still holds it. Example: a run that failed on 24 Sep leaves its workspace with `keptUntil` 8 Oct, fourteen days by default.
- **`Workspace.sessionIds`** are the sessions holding an active lease on it.
- **`run.cancel`'s `keepWorkspace`** picks the retention the run releases its lease with: `inspection`, kept for `workspace.inspectionTtlDays` from the cancel, or `none`.
- **`workspace.dispose`** refuses a workspace with an active lease with `invalid_state`, and the message names what to stop: `cancel run <id> first` for an unfinished run, `stop sessions <ids> first` for sessions that have not exited, and both when a run and sessions both hold it.
- **The setting `workspace.failedRunTtlDays` is renamed `workspace.inspectionTtlDays`.** Its default stays 14 days.

*(Amended 2026-09-16, [#72](https://github.com/theagenticage/hercule/issues/72).)* Three sentences the rows above only sketched.

- `session.spawn`'s `workspace` is one of four, and a caller writes exactly one of them: absent (the thread runs with no workspace, `workspaceId: null`; *amended 2026-10-14, [#688](https://github.com/theagenticage/hercule/issues/688):* for a session's spawn on its own runner, absent joins the calling session's workspace); `{kind: "primary", resourceId, branch?}` (the repo's main workspace on the placing machine, made if it is not there yet, with `branch` the one the machine switches it to before the harness starts - a one-shot pick, never replayed when the thread is resumed); `{kind: "ephemeral", checkouts: [{resourceId, baseBranch?}]}` (a workspace of the thread's own, one worktree per repo on ~~`hercule/run-<last 8 of the session id>`~~ `hercule/thread-<last 8 of the session id>` *(amended 2026-09-25, [#257](https://github.com/theagenticage/hercule/issues/257): renamed so a thread's branch never looks like a run's, which is `hercule/run-<runId>`)*, an empty list making a scratch workspace); `{kind: "existing", workspaceId}` (join one that stands - it must be `ready`, it pins the machine, and every repo in it must be filed under the `projectId` the thread carries).

Every resource any of the above reaches has to be filed under it, whether the workspace is made or joined. *(Amended 2026-10-13, [#593](https://github.com/theagenticage/hercule/issues/593).)* Without `projectId`, a Thread a session starts is filed under the calling session's project, or under none if that project was deleted. A copied project limits `workspace` like a named one. To use a repo from another project, the caller names that project.

- **Names and revision hashes.** A Skill's `name` is its identity and its key in every route: it matches `^[a-z0-9]+(-[a-z0-9]+)*$` and is at most 64 characters, the rule of the Agent Skills format. `hercule` is the built-in skill's name (`BUILT_IN_SKILL_NAME`) and is refused. The built-in skill is not in the Skill Library: no operation returns or changes it, and runners add it themselves ([./06-providers.md](./06-providers.md) section 9.3). A `revisionHash` is a Skill Revision's full hash, 64 lowercase hex characters (`^[0-9a-f]{64}$`; how it is computed is in [./02-domain-model.md](./02-domain-model.md) Skill Revision). Neither a name nor a hash is a UUIDv7, so neither has a tail form (section 1.4). An unknown name, or a hash that is not a revision of that Skill, is `not_found`.
- **Which revisions wait.** A revision is *available* while the Skill's `availableRevisionHash` names it: an update check found it and nobody has applied it yet. A revision is *proposed* while its `origin` is `session` and it was never applied (`appliedAt` is null). These two are the only revisions `skill.apply` takes.
- **The Skill record.** `skill.query`'s items, `skill.read`'s `skill`, and the `skill` in every answer of this group are one record, built from the Skill and its revisions:
  - `name`.
  - `source`: the Skill Source, `{ kind: "github", repo, path, branch }`, with `branch` null for the default branch, or `{ kind: "upload" }`.
  - `currentRevisionHash`: the revision sessions get, or null for a Skill that exists only as proposed revisions.
  - `currentApprovalEffects`: the current revision's `approvalEffects` (below), or null when there is no current revision.
  - `currentFileCount` and `currentSizeBytes`: the current revision's `fileCount` and `sizeBytes` (below), or null when there is no current revision. The desktop list shows them.
  - `availableRevisionHash`: the available revision, or null when no update waits.
  - `availableApprovalEffects`: the available revision's `approvalEffects`, or null. A client compares it with `currentApprovalEffects`, so the list can say "Update may change approvals" before anyone applies the update ([./17-desktop-app.md](./17-desktop-app.md) §The sections, Skills).
  - `proposedCount`: how many proposed revisions the Skill has.
  - `lastCheckedAt`: when the last update check ended, or null. `checkError`: that check's error message, or null when it succeeded. Both stay null for a Skill with an `upload` source.
  - `createdAt`, `createdBy`, `updatedAt`, `updatedBy`.
- **The Skill Revision record.** `skill.read`'s `history`, `availableRevision` and `proposedRevisions` hold this record:
  - `revisionHash`.
  - `origin`: how the revision arrived. `import`: read from a folder and sent with `skill.import`, by an import or by "Upload new version". `github`: an update check found it. `session`: a session proposed it.
  - `fileCount`, and `sizeBytes`, the total bytes of its files' content. This is not the archive's size, which the 10 MiB cap measures.
  - `description`: the `description` in its `SKILL.md` frontmatter, so a client shows it without parsing YAML.
  - `createdAt`, `createdBy`.
  - `appliedAt`, `appliedBy`: the last time the revision was made current, and by whom, or null if it never was.
  - `includesThirdPartyContent`: true when a tainted session proposed it (slice 5; [./13-security.md](./13-security.md) section 10).
- **`skill.read`'s answer.**
  - `skill`: the Skill record.
  - `files`: the current revision's files, sorted by path, each `{ path, mode, sizeBytes }`, where `mode` is `644` or `755`. Empty when there is no current revision.
  - `skillMd`: the text of the current revision's `SKILL.md`, at most 1 MiB by the content rules, or null when there is no current revision.
  - `history`: every revision that has been current, each once, sorted by `appliedAt`, newest first. The one whose hash is `currentRevisionHash` is the current one.
  - `availableRevision`: the available revision, or null.
  - `proposedRevisions`: the proposed revisions, newest first.
  - No operation reads any other file of a revision. That waits for the skill editor ([#741](https://github.com/theagenticage/hercule/issues/741)).
- **No paging.** `skill.query` answers the whole library, as `plugin.query` does, because the library is short.
- **Caps.** The Skill Library holds at most 256 Skills (`MAX_SKILLS`). `skill.import` or `skill.propose` of a new name past it is `cap_exceeded`: "The Skill Library holds 256 skills, the most it can hold. Delete a skill you no longer use, then try again." At most 20 proposed revisions wait in the library at once. `skill.propose` past it is `cap_exceeded`, and the message names every Skill with a proposed revision: "20 proposed revisions already wait for review, in `grilling`, `teach` and `write-docs`. Ask the user to apply or reject them on the Skills screen before you propose another."
- **The transfer format.** `skill.import` and `skill.propose` carry one skill as one uncompressed ustar tar archive, as raw bytes, never as base64 JSON, for the reason `attachment.create` gives. The archive's paths are relative to the skill's root. It holds regular-file entries. A directory entry is accepted and ignored, because a folder is not content: an empty folder is dropped, and a runner creates parent folders as it writes files ([./02-domain-model.md](./02-domain-model.md) Skill Revision). The archive as built is at most 10 MiB (`MAX_SKILL_BYTES`), and that is the length of the body: a larger body gets the bare `413` of section 1.5, so the CLI and the desktop app measure the archive they built before they send it. The controller reads and checks the whole archive in memory before it writes any file. The CLI and the desktop app build the archive from a folder (section 6.3, [./17-desktop-app.md](./17-desktop-app.md)).
- **`approvalEffects`.** The two `SKILL.md` frontmatter fields that change approvals on Claude Code ([./13-security.md](./13-security.md) section 8): `allowedTools`, the text of `allowed-tools` or null, and `hooks`, the value of `hooks` as canonical JSON (keys sorted, no spaces) or null. The controller reads them when it checks the content, so a client shows the warning line without parsing YAML. `hooks` is the value and not a flag, so two revisions' effects compare as text: a changed hook counts as a change even when both revisions have hooks.
- **The content rules.** The controller checks every skill's content with one function, whatever its origin: an archive sent to `skill.import` or `skill.propose`, and a tree an update check fetches. No client checks them first; the CLI and the desktop app show the controller's refusal. On `skill.import` and `skill.propose` a broken rule is `validation`, and every broken rule is listed at once. On an update check the broken rules become the Skill's `checkError`, and no revision is stored. Each issue says what was wrong and what to do:
  - The skill's root holds `SKILL.md`, and its YAML frontmatter has a `name` equal to the skill's name and a `description`. For example: "`teach/SKILL.md` has `name: teaching`. A skill's name must match its folder name; rename the folder or the name." And: "`teach/SKILL.md` has no `description`. Add one to its frontmatter: the agent reads it to decide when to use the skill." For an update check, the skill's name is the Skill's name. *(Amended 2026-10-18, [#734](https://github.com/theagenticage/hercule/issues/734).)* A `description` that is only white space counts as missing, because Codex 0.163.0 silently drops a skill with one. Checked live, Codex refuses nothing else these rules accept: descriptions of 1,024, 1,025 and 5,000 characters, a description over several lines, a 900 KB body, unicode, CRLF line ends and extra frontmatter keys all load.
  - The frontmatter is a YAML mapping, and no key appears twice. Two YAML parsers can disagree on which of two equal keys counts, so a duplicate could hide an `allowed-tools` from `approvalEffects`. For example: "`teach/SKILL.md` has `allowed-tools` twice in its frontmatter. Each key may appear once."
  - The frontmatter is plain YAML: it uses no anchor, no alias and no tag, and every key is text. Two YAML parsers can disagree on what an alias or a tag reads as, just as they can on a duplicate key, so either could hide an `allowed-tools` from `approvalEffects`; an alias can also make the frontmatter a cycle or blow it up in size. No real skill's frontmatter needs them. For example: "`teach/SKILL.md` uses a YAML alias at line 4. Write each value out in full: anchors, aliases and tags are not allowed in a skill's frontmatter." *(Amended 2026-10-18, [#732](https://github.com/theagenticage/hercule/issues/732).)*
  - `SKILL.md` is at most 1 MiB. For example: "`teach/SKILL.md` is 1.4 MiB. A `SKILL.md` may be at most 1 MiB; move long material into files beside it."
  - The name follows the rule above. For example: "`hercule` is the built-in skill's name. Rename the folder and the `name` in its `SKILL.md`."
  - Every entry is a regular file, or a directory, which is ignored. For example: "`teach/notes` is a symbolic link. A skill archive holds only files and folders; read the folder with `hercule skill import` or the desktop app, which put a link's target in the archive when the target is inside the skill's folder."
  - Every file's mode is `644` or `755`. For example: "`teach/run.sh` has mode `700`. A file's mode must be `644` or `755`."
  - At most 1,000 files. For example: "`teach` has 1,204 files. A skill holds at most 1,000; remove the files it does not need."
  - Every path is relative and uses `/`. It has no leading `/`, no empty segment, no `.` or `..` segment, and no control character. For example: "`teach/../x` is not a path inside the skill. Paths must stay inside the skill's folder."
  - No two paths are equal, also when compared ~~ignoring case after Unicode NFC normalization~~ folded, because a runner on a disk that ignores case, as macOS's does by default, can hold only one of them. Folded means: each segment in Unicode NFKD, upper-cased and then lower-cased, with default-ignorable code points such as a zero-width space dropped. Disks fold names in different ways, and this fold is wider than any of them, so `SKILL.md` and `ſKILL.md`, `ß` and `SS`, and `ﬀ` and `ff` count as equal. For example: "`teach/Notes.md` and `teach/notes.md` differ only in case. Rename one of them." And: "`teach/ſKILL.md` and `teach/SKILL.md` name one file on a disk that ignores case, such as macOS's. Rename one of them." *(Amended 2026-10-18, [#732](https://github.com/theagenticage/hercule/issues/732): paths were compared ignoring case after NFC normalization, which let `ſKILL.md` stand beside `SKILL.md`.)*
  - No file's path is a folder of another file's path, compared the same way, ~~ignoring case after NFC normalization,~~ folded segment by segment. For example: "`teach/docs` is a file, and `teach/docs/intro.md` needs it to be a folder. Rename one of them."
  - Every folder has one spelling. Two paths that name the same folder, compared ~~ignoring case after NFC normalization~~ folded, spell it the same way, because a disk that ignores case merges the two folders, and the tree read back from it would hash differently. For example: "`teach/Docs/a.md` and `teach/docs/b.md` spell one folder two ways. Use one spelling."
  - Every path fits a ustar header: at most 100 bytes, or split at a `/` into a part of at most 155 bytes and a name of at most 100 bytes. For example: "`teach/reference/...` is too long for a tar archive. Shorten its folder names or its file name."
  - The archive as built is at most 10 MiB. ~~An import or a proposal past it gets the `413` above and never reaches this check; a tree an update check fetches is measured here.~~ The check measures the archive the controller builds from the files, which is what it stores, not the body. A body sent without the archive's two 512-byte end blocks still reads, so it can pass the `413` above and build to up to 1 KiB more. A tree an update check fetches is measured here too. For example: "`teach` is 10.1 MiB as a tar archive. A skill's archive may be at most 10 MiB; remove the files it does not need, or make them smaller." *(Amended 2026-10-18, [#732](https://github.com/theagenticage/hercule/issues/732): the body limit alone let a stored archive pass 10 MiB.)*
- **`skill.import`** puts the user's own files into the Skill Library. It serves Import from a folder and "Upload new version" on the Skills screen, and `hercule skill import`.
  - **User only.** A session is refused with `forbidden`, whatever grants its profile holds, as `signal.markDone` refuses one. Otherwise a session could change what every future Thread loads without the user ever seeing the change. The message: "Only the user imports skills, so a session token is refused whatever grants its profile holds. Propose the skill instead with `hercule skill propose <folder>`; the user applies it on the Skills screen." The CLI row gives the same meaning for `forbidden`.
  - **What it does.** With no Skill of that name, it creates the Skill with the content as its current revision, and answers `created`. Otherwise these steps run in order, and the first that applies decides:
    1. The content's hash equals the current revision's: nothing is stored, and the call answers `unchanged`, with or without `replace`.
    2. The Skill has no current revision, because it exists only as proposed revisions: the content becomes current, and the call answers `revised`. It needs no `replace`, because there is no content to replace. The proposed revisions stay.
    3. `replace` is not `true`: the call is `conflict`, with the message "`grilling` exists with different content (current revision `<hash>`, imported content `<hash>`). Import with --replace true to make the imported content current." The desktop app asks the user to confirm and sends again with `replace: true`.
    4. `replace` is `true`: the content becomes current, and the call answers `revised`.
  - **Which revision becomes current.** A Skill holds one revision per hash. When the content becomes current, a revision of the Skill with that hash is reused, whether it was current before, is available or is proposed. Else a new revision with origin `import` is stored. Either way the revision records `appliedAt` and `appliedBy`, as `skill.apply` does. So importing an earlier version's files again is how a user goes back to it.
  - **Source.** Every import sets the Skill's source from the request, also one that answers `unchanged`, so a user fixes a wrong source by importing again. `sourceRepo` and `sourcePath` together give a GitHub Skill Source, with `sourceBranch` as its branch (absent: the default branch). None of the three gives an `upload` source. Any other combination is `validation`. `sourceRepo` must match `^[A-Za-z0-9-]+/[A-Za-z0-9._-]+$`, and `sourcePath` and `sourceBranch` may hold no `..`, `?`, `#` or control character, because the update check puts them into GitHub URLs. "Upload new version" sends no source fields, so it turns a GitHub-sourced Skill's source into `upload` ([./16-open-items.md](./16-open-items.md) B).
  - **A changed source.** When the source changes, the change is audited, `availableRevisionHash` is cleared, and every revision with origin `github` that was never current and is not available is deleted, because the old source produced it. An import that changes neither the content nor the source writes nothing and appends no audit entry.
- **`skill.delete`** deletes the Skill and every revision it has. A running session keeps the copy its runner gave it ([./06-providers.md](./06-providers.md) section 9.4).
- **`skill.check`** answers at once and never waits for GitHub. A `name` whose Skill has no GitHub source is `invalid_state`. The controller also checks every GitHub source every 3 hours ([./02-domain-model.md](./02-domain-model.md) Skill Source); ~~how a check downloads from GitHub is open ([./16-open-items.md](./16-open-items.md) B)~~ a check asks GitHub's REST API for the branch's commit and downloads the codeload tarball at that commit ([./16-open-items.md](./16-open-items.md) B) *(amended 2026-10-18, [#735](https://github.com/theagenticage/hercule/issues/735))*. The rules of a check:
  - One check runs at a time per Skill. A request for a Skill whose check is running joins that check when the Skill's source is still the one that check began with. After a source change, the request starts a new check once the running one ends, because the running check's result will be dropped (below).
  - A check that finds the same upstream commit as the last one downloads nothing.
  - *(Added 2026-10-18, [#735](https://github.com/theagenticage/hercule/issues/735).)* **What is decided since.**
    - **The 3-hourly pass.** It runs when the controller starts and every 3 hours after. It checks each GitHub-sourced Skill whose last check ended 3 hours ago or more, or that was never checked.
    - **One lookup per repository.** The Skills of one pass, or of one `skill.check` without `name`, that share a repository and a branch share one commit lookup and at most one download.
    - **The same commit.** A check that finds the commit of the last tree it downloaded and checked sets `lastCheckedAt` and keeps `checkError` as it is, because the result for that commit has not changed. The stored commit is cleared when the source changes, when the current revision changes, and when a check fails before it has a tree to check, so the next check downloads again ([./04-state-store.md](./04-state-store.md) §Skill rows, `upstream_commit`).
    - **Stamps.** A check changes the Skill record's `updatedAt` and `updatedBy` only when it changes `availableRevisionHash`, and then stamps `system`. Setting `lastCheckedAt` and `checkError` alone leaves them as they were.
    - **Announcing the result.** Every check that ends announces the Skill on the live topic `skill` (below), so an open screen shows the result.
  - The download is bounded: it stops reading past a byte cap, gives up after a timeout, and follows redirects only to GitHub hosts.
  - The fetched tree passes the content rules above, or becomes the Skill's `checkError` and never a revision.
  - When the check ends, it sets `lastCheckedAt`, and sets `checkError` to its error or clears it.
  - A check publishes its result only when the Skill's source is unchanged since the check began, compared in the write transaction. Otherwise the result is dropped.
  - The result: when the tree's hash equals the current revision's, `availableRevisionHash` is cleared. When it equals another revision of the Skill, `availableRevisionHash` points at that revision, so an upstream revert to content applied before reuses its row. Else a new revision with origin `github`, stamped `system` (section 3.1), is stored and `availableRevisionHash` points at it. A `github` revision that was never current and is no longer available is deleted.
- **`skill.diff`** compares a revision with the Skill's current revision. When the Skill has no current revision, as for a new Skill a session proposed, every file is `added`. `patch` is a unified diff, with the whole text for an added file. *(Amended 2026-10-18, [#735](https://github.com/theagenticage/hercule/issues/735).)* `patch` holds the hunks only, each starting at `@@`, with no `---` and `+++` file headers, because the entry's `path` already names the file. An added file's patch is one hunk, `@@ -0,0 +1,N @@`, and a removed file's has every line as `-`. A file whose mode alone changed (`modeChanged`) has an empty patch. `mode` is the file's mode in the revision, `644` or `755`, or null for a removed file, so a client can say whether a file becomes executable. `patchOmitted` is null when `patch` is given. Otherwise `patch` is null and `patchOmitted` says why: `binary` when either side is binary, and `tooLarge` when either side is over 1 MiB, or when its patch would bring the patches given so far, in path order, past 1 MiB in total. A client shows "too large to show" for `tooLarge`. The 1 MiB total keeps the answer small whatever the revision holds. *(Amended 2026-10-18, [#735](https://github.com/theagenticage/hercule/issues/735).)* The work is bounded too, so a hostile revision cannot stall the controller: the line-by-line comparison stops at 1,000 changed lines in one file and 4,000 in one answer, and past either a file's patch is one hunk that removes every old line and adds every new one, which is still a correct unified diff. `approvalEffects` lets a client show the revision's warning line ([./13-security.md](./13-security.md) section 8) when `SKILL.md` did not change.
- **`skill.apply`** makes the Skill's available revision, or one of its proposed revisions, current, and records `appliedAt` and `appliedBy` on it. The revision that was current stays in the history. Applying the available revision clears `availableRevisionHash`. Any other revision, the current one included, is `invalid_state`: there is no rollback. *(Amended 2026-10-18, [#735](https://github.com/theagenticage/hercule/issues/735).)* A hash that is no revision of the Skill is `not_found`; when the Skill has an available revision, because a check replaced the one the caller saw, the message says so: "`teach` has a newer update than the one you chose. Read the skill again and apply that one." For an earlier revision the message says how to get its content back: "`<hash>` is an earlier revision of `grilling`, not one waiting to be applied. To go back to it, import its files again with `hercule skill import <folder> --replace true`."
- **`skill.applyUpdates`** makes each named Skill's available revision current, each as `skill.apply` would, in one transaction. The caller names each Skill with the available revision it showed the user. When a named Skill's `availableRevisionHash` is no longer that hash, because a check found something newer since, the call is `conflict` and applies nothing, so Update all never applies a revision its confirmation did not show. The message: "`grilling` has a newer update than the one you confirmed. Read the updates again and confirm." It is bulk, but not destructive: it deletes nothing, and every previous current revision stays in its Skill's history, so the rule that withholds bulk-destructive operations ([./13-security.md](./13-security.md) section 6.1) does not withhold it.
- **`skill.propose`** files a proposed Skill Revision, with origin `session`, of an existing Skill or of a new one. A new one is a Skill whose `currentRevisionHash` is null and whose source is `upload`; it reaches no session until a revision is applied. When the content's hash equals any revision of the Skill, the call answers `unchanged` and files nothing. The caps above apply. Only a session proposes: the user is refused with `forbidden`, although the user holds every grant, as `notification.create` refuses the user (section 2, `notification`). A proposal waits for the user to apply it, so one the user files for themselves is a detour around an import, and its origin `session` and the Skills screen's "Proposed by" line would name no session. The message: "Only a session proposes a skill revision. Import your own skills instead, with `hercule skill import <folder>` or Import from a folder in Settings > Skills; an import applies at once."
- **`skill.reject`** deletes a proposed revision. Any other revision is `invalid_state`. When the proposed revision is also the available one, because an update check found the same content, rejecting it clears `availableRevisionHash` too. Rejecting the last proposed revision of a Skill whose `currentRevisionHash` is null deletes the Skill too.
- **Grants.** `skill.read` covers `query`, `read` and `diff`; `skill.write` covers `propose` and `check`; `skill.apply` covers `apply`, `applyUpdates`, `reject` and `delete`, and `import` for the user. `unrestricted` holds `skill.read` only: `skill.write` and `skill.apply` are the first grants user parity leaves out, because `unrestricted` is the default Thread profile and a skill steers every future Thread. `assistant` holds `skill.read` and `skill.write`, so an assistant can propose. No shipped profile holds `skill.apply` ([./13-security.md](./13-security.md) sections 6.1 and 6.2). A user who wants a session to propose or apply skills adds the grant to a profile in Settings > Permission profiles. Only the user gives these two grants: a session is refused when `profile.create` or `profile.update` would add either to a profile, and when it calls `permission.decide` on a request for either, because `unrestricted` holds `permission.write` ([./13-security.md](./13-security.md) section 6.2).
- **Taint.** A tainted session is refused `skill.apply`, `skill.applyUpdates`, `skill.reject` and `skill.delete`, even when it holds `skill.apply` ([./13-security.md](./13-security.md) section 10; slice 5 builds the stored taint flag the check reads). `skill.propose` and `skill.check` still work, and a revision a tainted session proposes has `includesThirdPartyContent`. `skill.import` needs no taint rule, because no session may call it.
- *(Added 2026-10-18, [#735](https://github.com/theagenticage/hercule/issues/735).)* **The live topic `skill`.** Every committed write that changes a Skill record publishes on the topic `skill`, and the push carries the names of the Skills that changed, not ids ([./14-web-app.md](./14-web-app.md)). The writes are `skill.import`, `skill.delete`, `skill.apply`, `skill.applyUpdates`, and every update check that ends, since it sets `lastCheckedAt`. A client holding the topic reads the list, or the open Skill, again ([./16-open-items.md](./16-open-items.md) A).

## 3. Actor stamping

### 3.1 Actor values

Every mutation through the service layer is stamped with an actor in the append-only event log ([./04-state-store.md](./04-state-store.md)):

```
actor: "user" | "session:<sessionId>" | "run:<runId>" | "plugin:<pluginId>"
```

- `user`: an API key or the web app's login token. Full parity; no profile applies.
- `session:<id>`: a session token. Bounded by the agent's permission profile (section 5).
- `run:<id>`: an action step executing inside a run (`task.create` on a cron tick). **Ungated**: the workflow was authored by the user, and its action steps run with the user's parity. A plugin action's `ctx.api` mutations are also `run:<id>`, with the `stepId` carried in the audit entry ([ADR 0026](../adr/0026-workflow-actions-may-call-the-public-api-as-the-run.md)). *(Amended 2026-10-04, [#89](https://github.com/theagenticage/hercule/issues/89).)* For a workflow sent with `run.start` the caller authored the steps, so `run.start` checks `connection.use` on the caller before the run starts (section 2); the run's steps are then ungated as for a stored workflow. *(Amended again 2026-10-04, [#89](https://github.com/theagenticage/hercule/issues/89).)* The same check runs wherever a caller chooses a step's Connection: when a workflow is saved, when a Connection input is given a value, and when a sent workflow is replayed (section 2, `connection`). Agent steps are sessions and act as `session:<id>` under their own profile, which is what keeps a `worker` session from fanning out.
- `plugin:<id>`: a plugin calling the service layer in-process through the public-API client capability. **Ungated**: the user enabled the plugin and granted the capability ([./05-plugins.md](./05-plugins.md)).

*(Amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79).)* Two more facts about the values:

- **`run:<id>` is built.** Every mutation a built-in action step makes is stamped `run:<runId>`, and no grant check refuses it. The step's id is not yet written to the audit entry; the step record shows what each step returned ([./07](./07-workflows.md) section 7.2). `ctx.api` for plugin actions is not built yet ([./05-plugins.md](./05-plugins.md) section 4.4). *(Amended 2026-10-04, [#89](https://github.com/theagenticage/hercule/issues/89): it is left to a follow-up ticket.)*
- **`system`** is a fifth value, which the contract already accepts. It stamps a change the controller made on nobody's behalf: enlisting a runner that presented a join token, and what that runner reports about itself afterwards. *(Amended 2026-10-18, [#312](https://github.com/theagenticage/hercule/issues/312).)* It also stamps a Skill Revision that an update check stores (section 2, `skill`). It is only a stamp, never a caller: no credential resolves to it, so no grant check ever sees it.

An envelope's `actor` is `Actor | null`, and `null` means no actor caused the row: an ingested or cron event, and **`auth.login.failed`**, which is stamped `null` rather than `user` because nobody has been authenticated at the moment it is written. *(Amended 2026-09-04, [#59](https://github.com/theagenticage/hercule/issues/59).)*

The event log is the audit log; there is no separate audit subsystem. Multi-user later widens the `user` value to a user id and never restructures the field. Security events and actor-stamped mutations keep 90-day retention ([./13-security.md](./13-security.md)).

The actor also appears wherever the domain records who did something: task provenance entries (`{ref?, eventId?, runId?, at, actor}`), the `actor` field of the event envelope (platform events such as `task.created` carry it there, never duplicated in the payload; [./08-events-and-connections.md](./08-events-and-connections.md)), permission requests, memory writes (a provenance line on writes distilled from tainted conversations).

The actor is derived from the credential or the in-process caller, never supplied by the caller: an API key resolves to `user`, a session token resolves to `session:<id>` (section 4), the run engine and the plugin host supply theirs.

## 4. Credentials

Two credential kinds resolve to the same actor-stamped API. Both are opaque random tokens, hashed in the controller database, resolved by one indexed lookup. No JWTs, no OAuth machinery for Hercule's own auth. Details: [./13-security.md](./13-security.md).

### 4.1 Session tokens

- **Minting:** at session start the controller mints a session token whose subject is the Session row. The token carries no claims of its own; the session's permission profile is reached by resolution `token -> session -> profile`: the profile id was copied onto the Session at spawn ([./02-domain-model.md](./02-domain-model.md) rule 9), so a Thread (no agent) resolves the same way.
- **Injection:** the runner injects `HERCULE_API_URL`, `HERCULE_TOKEN` and `HERCULE_SESSION=1` into the harness process environment. Nothing is written to runner disk.
- **Lifetime:** the token dies with the session. It is revoked when the session ends. A rotated assistant conversation continues in a fresh session and therefore under a fresh token; the old session's subscriptions migrate to the successor ([./12-assistants.md](./12-assistants.md)). *(Amended 2026-09-12, [#162](https://github.com/theagenticage/hercule/issues/162).)* "Ends" is the process exiting: the token is revoked on every exit, and a resume mints a fresh one for the same session id ([./13-security.md](./13-security.md) section 5).
- **Latency constraint (hard rule):** resolving token to profile MUST NOT meaningfully add endpoint latency. One indexed lookup on the hashed token plus a cached or joined profile read satisfies it; a per-request chain of separate queries does not.
- **`HERCULE_SESSION=1`:** the marker that makes the CLI refuse file-held user credentials (section 6.2 and [./13-security.md](./13-security.md)). It defends against accidental fallback to the user's identity, not against a malicious local process; sessions are bare processes as the same OS user ([ADR 0003](../adr/0003-sessions-run-as-bare-processes.md)).

### 4.2 User API keys

Long-lived, opaque, revocable, minted in the web app or via `hercule login` (password in, token out, stored with mode 0600 in the CLI credential file; its location inside Hercule Home is **Open** in [./15-packaging-and-operations.md](./15-packaging-and-operations.md)). Always the user's identity; the user has unrestricted parity. The web app's bearer token comes from the same password login. Full auth model: [./13-security.md](./13-security.md).

## 5. Permission enforcement

Every Session carries a permission profile, copied from its Agent at spawn, or for a Thread from the `thread.profileId` setting when the user starts it and from the calling session's profile when a session does; its session token carries it. Enforcement happens in the service layer, so it binds HTTP callers and in-process session callers alike (run and plugin actors are ungated, section 3.1). Parity with the user is the ceiling, not the default.

Grant families and verbs, the operation-to-grant table's vocabulary, and the three shipped profiles (`assistant`, `worker`, `unrestricted`) are specified in [./13-security.md](./13-security.md) section 6; this document does not restate them. Section 2 names the grant beside every operation.

**Grants are unscoped in v1 (hard rule):** a grant on a family covers every entity in that family. `session.read` reads every session's transcript, including other assistants' conversations; "the sessions I spawned" is a filter (`actor: "me"`), not a boundary. Scoped grants are the post-v1 "finer grants inside a family" that [./13-security.md](./13-security.md) reserves room for. The sole v1 exception is `memory` (section 6.4): a session token's memory operations are pinned to that session's assistant.

**403 rule (hard rule):** a denied operation returns 403 and the response names the missing grant (section 1.5). The CLI surfaces that name verbatim so the agent can ask for exactly it.

**Escalation:** `permission.request { grant, reason, operation? }` is granted to every profile. It creates a Permission Request notification, and, when the caller is a session, registers a `{ kind: "request" }` subscription for that session as part of the same operation: nobody asks for a grant without wanting the answer, so the response carries `subscriptionId` and the CLI has nothing to teach. `operation` is optional and informational in v1: it lets the notification say "wants to run ~~`connection.create`~~ `task.delete` with {...}" *(amended 2026-10-10, [#86](https://github.com/theagenticage/hercule/issues/86): an operation needing `connection.manage` is refused, see below)* instead of only naming a grant. The user decides `session` (overlay that dies with the session), `profile` (edit the agent's profile) or `deny`; the decision arrives as queued input and the agent retries the original call itself, so the actor stays `session:<id>`. A one-call outcome (`once`) is post-v1 (section 10). Escalation UX: [./13-security.md](./13-security.md) section 6.4. *(Amended 2026-10-10, [#86](https://github.com/theagenticage/hercule/issues/86).)* As built, only a session may ask: the user, a run and a plugin hold every grant, so their `permission.request` is refused with `validation`, and the response always carries `subscriptionId`. A request for a grant the session already holds, or already has an open request for, or from a session that has exited, is refused with `invalid_state`. An `operation` whose input can carry a credential or a secret (one needing a `credential`, `secret` or `infra` grant, or `connection.manage`) is refused with `validation`, because the notification shows its input in full; the agent describes such a call in `reason` instead ([./13-security.md](./13-security.md) section 6.4). `profile` adds the grant to the asking session's current profile, not to its Agent's: a Thread has no Agent, and the two can differ.

## 6. The `hercule` CLI

### 6.1 One binary, ~~three~~ five roles

`hercule` is the single self-contained binary ([ADR 0018](../adr/0018-hercule-ships-as-one-self-contained-binary.md)). `hercule serve` runs the controller, `hercule runner` runs a runner, and every other verb is an API client. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* `hercule service` and `hercule promote` are roles of their own too, not API clients: the first acts on this machine's OS supervisor, the second writes this machine's Hercule Home ([./15-packaging-and-operations.md](./15-packaging-and-operations.md) section 2). Role subcommands (`serve`, `runner`, `runner join`, `service install`, `upgrade`, `login`, `promote`, export/import) are specified in [./15-packaging-and-operations.md](./15-packaging-and-operations.md). Mode isolation is CI-enforced: the runner entrypoint imports no controller packages.

The CLI never prompts interactively: onboarding lives wholly in the web app + API, and the runner join exchange is fully programmatic.

`hercule login` takes the password docker-style (resolved 2026-09-01, [#44](https://github.com/theagenticage/hercule/issues/44)): `--password-stdin` is the canonical scripted form; on a TTY with no flag it prompts with echo off, **one of two documented exceptions** to the never-prompts rule *(amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103); the other is `hercule promote` without `--yes`)*. The rule's purpose is that automation and the future desktop installer never wedge on a hidden prompt - `--password-stdin` preserves programmatic drivability, and the desktop app never runs `hercule login`. A bare `--password` flag does not exist (it would leak into `ps` and shell history).

### 6.2 Credential resolution

The CLI resolves its credential in this order:

1. `HERCULE_TOKEN` from the environment (with `HERCULE_API_URL`).
2. The CLI credential file, `~/.hercule/credentials.json` (written by `hercule login`; [./15-packaging-and-operations.md](./15-packaging-and-operations.md)).

When `HERCULE_SESSION=1` is set, step 2 is skipped: the CLI refuses file credentials outright. This is what makes the ops CLI and hercule-as-a-tool the same binary: identical commands, different credential.

### 6.3 Hercule-as-a-tool

Inside a session the `hercule` CLI is the whole of hercule-as-a-tool in v1. It ships built-in (not a plugin contribution), is uniform across Claude Code, Codex and pi, and needs no per-adapter wiring. The runner makes the binary available to the session process and materializes the skill (below) into it.

*(Rewritten 2026-09-15, [#126](https://github.com/theagenticage/hercule/issues/126). Until then this section pinned "Command = operation id": `hercule <entity> <verb>` was `<entity>.<verb>` spelled exactly as the contract spells it, which produced `hercule apiKey query` and `hercule auth wsTicket` and left the agent-addressed help nowhere to live.)*

**The command tree is spelled for a terminal and written in the contract.** `packages/contract` holds, beside the operation table, one CLI table with a row per operation: the command's words, its purpose, its examples, and one entry per field with its flag name and one line of help; or `hidden: true` for an operation only programmatic clients call. The row type is keyed by operation id, so an operation without a row does not compile. The `hercule` CLI derives its whole tree, its argument parsing and its help from that table plus the operation's schemas; nothing per-operation lives in the CLI package. A test proves the tree and the visible operations are one-to-one.

What survives of the one-vocabulary rule (section 1.3, [ADR 0021](../adr/0021-one-operation-vocabulary-coarse-grants-explicit-routes.md)): the operation id names the endpoint, the contract key and the built-in workflow action; a 403 names the grant; `--json` prints the output schema verbatim; and every command's `--help` names its operation id, route and grant on one line, so an agent holding a workflow action id or a 403 can find the command, and the other way round.

Spelling rules:

- A command is `hercule <noun>... <verb>`, every word kebab-case. The first noun is the operation's entity in kebab-case, singular as the id is (`api-key`, `session`).
- Standard verbs: `query` is `list`; `read`, `create`, `update` and `delete` keep their names. `hercule task list`, `hercule task read <id>`.
- A custom verb is kebab-cased as a verb phrase: `hercule runner refresh-facts`, `hercule user set-password`, `hercule connection start-oauth`, `hercule connection start-device-flow`.
- A custom verb of the form `<action><Thing>`, where the things have ids and a listing of their own, becomes a nested noun with standard verbs: `runner.createJoinToken`, `runner.queryJoinTokens` and `runner.revokeJoinToken` are `hercule runner join-token create | list | revoke <id>`.
- An owned sub-resource that is its own operation entity keeps its own root noun: `hercule input list <session-id>`, `hercule transcript read <session-id>`.
- One spelling per command. No aliases, no second spelling; the operation id is not accepted as a command.
- A hidden operation has no command at all: not in the tree, not in help, not callable. `auth.login`, `auth.logout` and `auth.wsTicket` are hidden; `hercule login` is the human form of login.
- Path parameters are positional, in route order. A payload field may be positional when its row says so (`hercule permission request <grant>`, `hercule subscription create <target>`), after the path parameters. Every other field is a flag, kebab-case, named in the row; a repeatable flag is singular (`--label bug --label ui`).
- Ids: a full id, or a tail of eight or more characters where the row names the listing that resolves it (section 1.4). A positional whose row names no listing takes the full id, and its help says so.
- The CLI adds no default of its own. A common case that needs no flags gets there through the operation's own defaults, never through a value the CLI invents.

Rules the CLI follows on every command:

- **Agent-addressed help.** `--help` works at any position on every subcommand, `hercule runner --help` included. Three levels. `hercule --help` lists every visible noun with its verbs and one line, then the conventions that hold everywhere (ids, `--json`, stdin, paging, exit codes, what a 403 means). `hercule <noun> --help` lists the noun's verbs with one line and the grant each needs, and a flow line naming the usual order. `hercule <noun> <verb> --help` prints, in this fixed order: purpose (what it does and when to use it), usage, examples, arguments, flags, stdin, returns, errors, next, and the operation line (`operation <id> · <METHOD> <path> · grant <g>`). Purpose, examples, the line per field, the noun's summary and flow line, and optional per-error meanings are written in the table; usage, placeholders, allowed values, required or optional, the stdin note, paging, the returns fields, the error code list and the operation line are derived from the contract. Examples are stored as arguments plus stdin and are parsed by a test, so they cannot go stale; every command any help text names must exist, by test. Static help plus 403s that name the missing grant are the two teaching channels.
- **Output.** Human-readable by default; `--json` on every command emits the contract's output schema (or error envelope) verbatim. Teaching lines ("read the reply with ...") exist only in the human rendering.
- **Progressive disclosure.** The skill is a minimal skeleton pointing at the CLI's own help. It names no command beyond the three help forms, and the ticket that writes it carries a test that every command it names exists. *(Amended 2026-10-14, [#665](https://github.com/theagenticage/hercule/issues/665).)* One exception: after the help forms, the skill has a short section, "Discussions and the wiki", that names the `discussion` and `wiki-page` commands with an example each ([./19-agent-coordination.md](./19-agent-coordination.md) section 7.2). The reason: agents spend several tool calls in the help before they can run a command, and a session told about a Discussion should be able to read it and post at once. The same test covers the commands it names. *(Amended 2026-10-14, [#687](https://github.com/theagenticage/hercule/issues/687).)* The session orientation every session starts with ([./06-providers.md](./06-providers.md) section 9.3) follows the same rule and the same test: it names `hercule --help`, `hercule session spawn --help` and `hercule session input --help`, nothing else. The list of "commands an agent uses most" that this section used to carry is the root help, generated.
- **One content channel (hard rule).** A field the row marks `stdin` has no inline flag: a password, a secret's value, credentials, a task's or project's description, a session's prompt or input text, a config that is the whole payload. Required, it is read from stdin unasked: `echo "carry on" | hercule session input <id>`. Optional, it is read only when its `--<flag>-stdin` marker is given (`hercule task update <id> --description-stdin < notes.md`), so an empty pipe never blanks a field. The whole of stdin is the value, one trailing newline removed, which is what a heredoc produces. At most one stdin field per command, because a document has newlines and cannot share the stream; `hercule user set-password` is the one exception and reads two lines, current then next. At a terminal the CLI never blocks on a stdin field: it exits 2 and shows the piped form (the echo-off prompt of section 6.1 is `hercule login`'s exception). There is no inline content flag and no `--file` flag. [Assemble the v1 spec](https://github.com/theagenticage/hercule/issues/21) delegated the pick between stdin-only and `--file` to the spec; the spec picks stdin-only. Rationale: a model mixed `--content` with a heredoc in the memory experiment ([Prototype: assistant memory interface](https://github.com/theagenticage/hercule/issues/31)).
- **Never blocks.** No `--wait` on any command (section 8).
- **Pagination.** ~~`list` commands page with `--limit`, `--cursor` and `--sort`;~~ *(Amended 2026-10-03, [#300](https://github.com/theagenticage/hercule/issues/300).)* `list` commands page with `--limit`, `--cursor` and `--sort`, and `--sort` repeats, one flag per key in order; `--all` follows `nextCursor` to the end.

*(Amended 2026-09-23, [#78](https://github.com/theagenticage/hercule/issues/78).)* A workflow's source is the first document the CLI carries both ways, and five rules changed so that a file round-trips byte for byte:

- **stdin is strict UTF-8.** A byte that is not part of a UTF-8 character is refused with exit 2, and nothing is sent, because a replacement character would change the value before any operation sees it. A leading byte order mark is kept, because it is part of what was sent.
- **`\r\n` is a newline.** The one trailing newline removed from stdin may be `\r\n`, as a file saved on Windows ends, and `hercule user set-password` splits its two lines on `\r\n` too.
- **A read prints the document.** `hercule workflow read` prints the source as it is, not as key/value lines, and ends it with the line break the source uses (`\r\n` when the source's first line break is one). What a read prints can be edited and piped back into `hercule workflow update`. `--json` prints the whole record. `workflow create` and `workflow update` print the id, whether the workflow is on, and one line per warning, and not the source the caller has just sent.
- **A check that finds an error exits 1.** `hercule workflow validate` prints one line per error and per warning, each named by its place in the definition, or one line that says the source is valid. It exits 1 when there is an error, as a refused save does, so a script can stop on it; warnings alone exit 0.
- **A field row may be hidden.** A row can hide one field of a visible operation (`hidden: true`, with the reason in a comment), and the field is then not on the command line at all. `definition` is hidden on `workflow create`, `update` and `validate` (and `submit`, *amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79)*), because on the command line the source is the text and stdin carries it. On `create` and `validate` (and `submit`) the `source` row is marked `required`, so the command reads stdin unasked although the operation lets the field be absent. A row that names a field the operation does not take fails the tree test, hidden or not.

*(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* **`--image <path>` ~~is the one flag that names a file~~ names an image file to upload.** *(Amended 2026-10-18, [#312](https://github.com/theagenticage/hercule/issues/312): it is no longer the only way the CLI reads files from disk. `hercule skill import` and `hercule skill propose` read a whole folder, named by their argument; see the next paragraph.)* `hercule session spawn`, `session input` and `session continue` take `--image <path>`, repeatable, in the order the agent should see the images. It is a CLI-side step, not a content flag: the CLI uploads each file with `attachment.create`, and puts the returned ids in the operation's `attachments` field. The image bytes are binary and there can be several, so they cannot share stdin with the prompt; the prompt text still comes from stdin as the content channel rule says. `hercule session input <id> --image a.png --image b.jpg < note.txt` sends the note with two images. With at least one `--image`, the prompt is optional: an empty stdin from a pipe or a file sends the images alone, and at a terminal the CLI does not wait for stdin and sends the images with empty text. Without `--image` the prompt is required as before. The CLI row marks the field as `{ upload: true, flag: "image" }`, so the CLI package still holds nothing per operation. Before it sends anything, the CLI checks every file without reading its bytes, and refuses more than 10 files, a missing file, a file that is not a PNG, JPEG, GIF or WebP by its name, or a file over 10 MiB; it uploads only after every id tail has resolved, and a refused upload names the file. `input update` takes no `--image`: its row keeps `attachments` hidden, so from the command line a queued input keeps the images it has. The attachment operations are hidden, so `--image` is the only way the CLI uploads an image. A desktop or web client gives an upload or an image download more time than other requests: the desktop app allows 120 seconds ([./17-desktop-app.md](./17-desktop-app.md) §Reaching the controller).

*(Added 2026-10-18, [#312](https://github.com/theagenticage/hercule/issues/312).)* **`hercule skill import <folder>` and `hercule skill propose <folder>` read a folder.** Like `--image`, reading it is a CLI-side step. One folder becomes one request per skill it holds: the CLI reads the folder, builds one tar archive per skill, and sends each archive as the body of its own `skill.import` or `skill.propose` (section 2, `skill`). The rules:

- **Which folders are skills.** A folder that holds a `SKILL.md` is one skill, named by the folder's name. For `import`, a folder without one is a folder of skills: every subfolder that holds a `SKILL.md` is a skill. To import one skill of a folder of skills, pass that skill's own folder. `propose` takes one skill folder only.
- **Symbolic links.** The skill folder itself may be a symbolic link, as the `skills` tool makes them; the reader resolves it first. A link inside the skill folder is followed only when its target is inside that resolved folder, and the archive then holds the target, so the controller never sees a link. A link whose target is outside it refuses the skill, with a message that names the link: "`teach/shared` points outside the skill's folder. A skill holds only its own files; copy what it needs into its folder." A cycle of links refuses the skill too. This keeps a link from carrying a file from elsewhere on the disk, such as an SSH key, into the Skill Library.
- **What the archive holds.** The reader skips `.DS_Store`, `Thumbs.db` and `.git/`, and writes no directory entries, so an empty folder is left out. It keeps the owner's execute bit: a file with it set gets mode `755`, any other file `644`.
- **Where a skill comes from.** `import` reads the nearest `.skill-lock.json`: in the folder, in its parent, or in its parent's parent. The `skills` tool keeps the file beside the skills folder (`~/.agents/.skill-lock.json`), so the parent finds it for `~/.agents/skills` and the parent's parent for a single skill such as `~/.agents/skills/grilling`. An entry for the skill with `sourceType: "github"` gives it a GitHub Skill Source: `sourceRepo` is the entry's `source`, `sourcePath` is the folder of its `skillPath`, and there is no `sourceBranch`, because the file names no branch. Any other entry, or none, sends no source fields, which gives the skill an `upload` source. A lock file the CLI cannot read is ignored and named in one line of the summary; it never fails the import. *(Amended 2026-10-18, [#732](https://github.com/theagenticage/hercule/issues/732).)* So is a `github` entry whose source `skill.import` would refuse, such as a `source` written as a URL: that skill gets an `upload` source, and the same line names it.
- **`--replace true`** is passed on every import of the folder.
- **Before it sends a skill,** the CLI builds the skill's archive and refuses the skill by name when the archive is over 10 MiB, because the controller would answer it with a bare `413` (section 1.5). It checks no content rule: the controller does, and the CLI prints its refusal.
- **Sending.** It sends one skill per request, one at a time, and prints one line per skill: created, revised, unchanged, or the refusal with its message. Under a skill whose current revision now has approval effects, `import` prints the warning line (section 2, `skill`). A refused skill does not stop the others, and the command fails when any skill was refused. *(Amended 2026-10-18, [#732](https://github.com/theagenticage/hercule/issues/732).)* An answer about the credential rather than the skill, `forbidden` or `unauthenticated`, does stop the command at that skill, and so does a controller that stops answering, or an answer that is not the controller's, such as a proxy's error page: every later skill would get the same. `import` prints the lines of the skills before it, then one line naming the skill it stopped at and why.
- **The row.** The row marks `name` as `{ skillFolder: true, help }`, a field row of its own kind, as `{ upload: true, flag: "image" }` marks `attachments`. The command then takes one positional `<folder>`, and the CLI fills `name` from each skill folder's name and the body with that skill's archive. On `skill.import`, `sourceRepo`, `sourcePath` and `sourceBranch` are `{ hidden: true }`, because the lock file fills them, and `replace` is an ordinary flag. So the CLI tree is still derived from the table, and the CLI package still holds nothing per operation. The package of the shared folder reader, which the desktop app uses too, is an implementer's choice ([./16-open-items.md](./16-open-items.md) B).
- Neither command blocks: each request answers when its archive is stored.

*(Added 2026-10-23, [#827](https://github.com/theagenticage/hercule/issues/827).)* **`hercule session spawn --role <role>`** is how an agent learns about roles: from the `session spawn` row's help and its example with `--role`, not from the skill or the session orientation, which name only the help commands (Progressive disclosure, above). The flag's help names the cap and adds: "make it specific when a role is already taken, e.g. `refunds review`". Two Threads of one Workspace may share a role; clients number them on screen ([./02-domain-model.md](./02-domain-model.md) Session, `role`), and the spawn does not look for duplicates.

*(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)* **A command that changes its spelling takes its teaching text with it.** `hercule provider` changes meaning and `--instance` becomes `--account` and `--harness` (section 2, "harness, provider, providerAccount, modelProfile"). The skill, the session orientation and every help example that names `hercule provider` or `--instance` change in the ticket that changes the command, not later, and the test that every command named in help exists fails on any left behind.

**Standing rule.** An operation added to the contract lands its CLI row in the same change: spelling, purpose, examples and a line per field, or `hidden: true` with the reason in a comment. The row type and the tree tests refuse a contract without it; no ticket ships an operation the CLI cannot explain.

**The skill.** One harness-agnostic skill source describes the CLI; each harness adapter materializes it in that harness's native instruction format ~~(Codex takes instructions only as `AGENTS.md` in the cwd, so a Codex session needs a cwd even when workspace-less)~~. *(Amended 2026-09-30: Codex takes it as `developerInstructions` since [#68](https://github.com/theagenticage/hercule/issues/68); a Codex session still gets a scratch cwd, because `thread/start` requires one.)* Materialization and harness-home isolation are specified in [./06-providers.md](./06-providers.md).

### 6.4 `hercule memory`

Assistant memory is reached only through these operations ([ADR 0020](../adr/0020-assistant-memory-is-reached-only-through-the-api.md)); nothing is materialized on runner disk and assistant sessions stay workspace-less. Memory tiers (`core` plus named topics), the two-line topic header, the size and count caps, injection at session start and rotation are specified in [./12-assistants.md](./12-assistants.md); the operations and their enforcement are specified here.

| Operation | Behaviour |
|---|---|
| `list me` | Returns the index: per document, name, size and gist. This is the same index injected at session start. |
| `read me <name>` | Returns the full body of `core` or one topic. |
| `search me --text <words>` | SQLite FTS5 over `core` and every topic; returns per matching document `{ name, snippets[] }`. The API's substitute for `grep`. |
| `write me <name> [--gist "..."] [--confirm-shrink true] [--expected-version <n>]` | Replaces the whole body of `core` or a topic; creates the topic if absent. Content on stdin; `--gist` sets the topic's one-line gist (optional, unchanged when omitted, ~~ignored for `core`~~ refused with `validation` on `gist` for `core`, which has none *(amended 2026-10-11, [#93](https://github.com/theagenticage/hercule/issues/93))*). `--expected-version` writes only if the document is still at that version *(amended 2026-10-11, [#93](https://github.com/theagenticage/hercule/issues/93))*. |
| `append me <name>` | Appends content to an existing document. Content on stdin, and not empty: empty text is `validation` on `body` *(amended 2026-10-11, [#93](https://github.com/theagenticage/hercule/issues/93))*. Never touches the gist. |
| `delete me <name>` | Removes a topic. `delete core` is refused (`core` is seeded and always injected; `write core` with an empty body clears it). |

Enforcement at the write seam (hard rules):

- A `write` or `append` whose resulting size exceeds the document's cap fails with `cap_exceeded`, naming the current size and the cap so the agent can consolidate. The over-cap write is a visible event, never a silent truncation.
- A `write` that would exceed the topic count cap fails with `cap_exceeded`, naming the topic count and its cap.
- **Shrink guard.** A `write` that would shrink a document of 1,000 or more characters by more than 50% fails with `shrink_rejected`, naming old and new sizes, unless the call carries `confirmShrink: true`. The error is the teaching channel ([./12-assistants.md](./12-assistants.md) section 6.4).
- **Versions** *(amended 2026-10-11, [#93](https://github.com/theagenticage/hercule/issues/93))*. Every document carries `version`, which goes up on every `write` and `append`. The numbers come from one counter per assistant, so a topic deleted and created again never reuses a version; an absent document is at version 0. `PUT` takes an optional `expectedVersion`: the write fails with `conflict` (409) unless the document is still at that version, and `0` fails it unless the document does not exist yet. The message names the stored and the expected version and says to read the document again and redo the edit; for `0` on an existing topic it says the topic exists and how to replace it. The check runs in the write's transaction, after the document lookup and before the caps and the shrink guard. Without `expectedVersion` a write replaces whatever is there.
- Memory text (`body` of `write` and `append`) refuses control characters other than tab, line feed and carriage return, with `validation` on `body` *(amended 2026-10-11, [#93](https://github.com/theagenticage/hercule/issues/93))*: search marks its hits with control characters, and memory is text.
- Every write is actor-stamped (section 3). Writes from a tainted session (one that has been delivered third-party lines) get provenance metadata *on* the document, set by the core, rendered by `read` as a trailing `> provenance:` line ([./12-assistants.md](./12-assistants.md) section 6.7, [./13-security.md](./13-security.md) section 10).

**Scope (hard rule, the one scoped family in v1):** memory operations from a session token act on the memory of that session's assistant and on nothing else; `assistantId` (`/assistants/{id}/memory`) is honoured for user credentials only, and a session token naming another assistant gets 403 `forbidden`. A session under a profile without `memory` (the `worker` profile) reaches no memory at all. The user reaches every assistant's memory through the same operations; the web app's memory view is a client of them.

*(Amended 2026-10-11, [#93](https://github.com/theagenticage/hercule/issues/93).)* Every command names the assistant first, the way every command takes its path parameters (`/assistants/{id}/memory/{name}`) as positionals in route order: `me` from a session, an id or a tail from the user. `search` takes its words as `--text`, because a query field is never positional; `--confirm-shrink` takes `true`, because every flag takes a value. The CLI accepts `me` wherever a field holds an id and passes it to the controller unresolved. A size counts characters as Unicode code points, and `size` is stored on the document at the write seam. `delete core` is a `validation` error on `name`. `append` to a topic that does not exist is `not_found`: `write` creates topics, `append` never does. A topic name is one line of at most 64 characters with no slash and no space at either end; `search`, `.` and `..` are refused because they collide with the routes. The audit log records each memory write, append and delete with the assistant, the name and the size, never the body. A missing assistant is `not_found` before the scope check, but a missing document is `not_found` only after it, so a session cannot learn another assistant's topic names from which reads fail.

There is no header convention to validate: the gist is a field (`--gist`), the body is pure content ([./12-assistants.md](./12-assistants.md) section 6.2).

## 7. Session subscriptions

A session may hold Subscriptions directly, without a run. Two use cases justify it: mid-session artifacts (an agent opens PR #87 and subscribes to its CI) and assistants (long-lived, no run to hold claims).

- **Registration** is the ordinary `subscription.create` operation (section 2), invoked from the session as `hercule subscription create <target>`, where `<target>` is `<kind>:<id>` (`run:r_3`, `session:s_12`, `request:pr_7`) or a bare External Ref (`github:pr:owner/repo#87`, taken as `ref:`).
- **Matching** runs in the single persisted pipeline like every subscription ([./08-events-and-connections.md](./08-events-and-connections.md)).
- **Delivery** is queued input on a turn boundary: rendered text plus the structured payload. Never steering by default. The agent's next turn opens with the match.
- **Lifetime:** dies with its holder session, or with `subscription.cancel`. On assistant rotation the subscriptions migrate to the successor session. No timeouts.
- **No polling surface for matches** in v1: there is no "any news?" operation; the event wakes the session. Listing *registrations* (`subscription.query`) exists for cancellation and for the session view.

Platform-auto detection ("this session opened PR #87, subscribe it") is not specified; explicit registration is the primitive.

## 8. The no-blocking rule

Every endpoint returns fast. No operation waits for a run, session, approval or permission decision to finish. Consequences:

- Spawn-type operations (~~`workflow.run`, `workflow.submit`~~ `run.start` *(amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79))*, `session.spawn`) return a handle immediately, and the CLI's human rendering teaches the follow-up: `subscribe for updates: hercule subscription create run:r_3`. *(Amended 2026-09-24, [#79](https://github.com/theagenticage/hercule/issues/79).)* ~~Until run events land ([#81](https://github.com/theagenticage/hercule/issues/81)) nothing would ever match a subscription on a run, so the controller refuses the target `run:<id>`.~~ ~~`hercule workflow run` and `hercule workflow submit`~~ ~~`hercule run start` therefore teaches `see how far it got with hercule run read <id>`. The subscription hint returns with [#81](https://github.com/theagenticage/hercule/issues/81).~~ *(Amended 2026-09-27, [#81](https://github.com/theagenticage/hercule/issues/81).)* Run events are emitted and the controller accepts the target `run:<id>` (section 2), so `hercule run start` and `hercule run rerun` print the subscription hint again.
- There is no `--wait` flag anywhere in the CLI.
- The canonical long-wait pattern for an agent is: start the thing, subscribe to it, end the turn. The matching event arrives as queued input and wakes the session.
- Permission escalation (section 5) subscribes the caller automatically; the assistant heartbeat is a Scheduled Wake delivering queued input ([./12-assistants.md](./12-assistants.md) section 8).

## 9. The ops CLI

The ops CLI is the same `hercule` binary under a user credential: `hercule login` writes the API key to the CLI credential file, after which every API verb runs as actor `user` with unrestricted parity. Commands are identical to what a session sees; only the credential and therefore the profile differ. Role subcommands are specified in [./15-packaging-and-operations.md](./15-packaging-and-operations.md); runner join in [./03-controller-and-runners.md](./03-controller-and-runners.md).

## 10. Post-v1

- **Hercule MCP server** - the public API exposed to sessions as typed MCP tools (t3-code-style self-injection). High on the revisit list. V1 keeps the `SessionSpec.mcpServers` passthrough ([./06-providers.md](./06-providers.md)) so it lands without redesign; the operation catalogue maps one-to-one onto tools.
- **Scoped grants** ("the sessions you spawned", "this project's tasks") - finer grants inside a family; v1 grants are unscoped except `memory`.
- **One-call permission outcome (`once`)** - a fourth decision on a Permission Request that carries an `operation`: an overlay row on the session with `remainingUses: 1`, consumed by the first successful call of the named operation, so "may I do X once?" is answerable without a session-wide grant. `permission.request` already carries the `operation` field this needs. Its CLI sugar (`hercule <failed command> --request "<reason>"`, packing the failed call into the request) lands with it.
- **Bulk operations** (delete-many, cancel-all) - none exist in v1; when they do, they are tagged in the contract and withheld from every profile but `unrestricted` by default, per [./13-security.md](./13-security.md). *(Amended 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395).)* The signal operations that take a list of ids (`signal.markDone`, `snooze`, `unsnooze`, `lowerPriority`) are not bulk operations in this sense: none deletes or cancels anything, and the reasons are in [./13-security.md](./13-security.md#61-grant-families).
- **Offset pagination and totals** - bolted on beside cursors if usage shows a real need for random access.
- **CEL subscription targets** - a fifth `SubscriptionTarget` kind carrying a filter over `event`, if the four shorthand kinds prove short.
- **Read-only memory materialization on runners** (memory as files for native grep, writes still via API) - a pure read convenience addable without touching the write path.
- **Memory version history** - ruled post-v1; the retrofit is additive (history table beside the live document). V1 ships the shrink guard on the write seam instead, and every rewrite is a visible actor-stamped event.
- **Platform-auto subscription detection** - the controller subscribing a session to artifacts it created; explicit registration stays the primitive.
- **Multi-user** - widens the actor field to a user id; no restructuring.
- **Per-agent git identity** - a policy addition on unchanged plumbing ([./13-security.md](./13-security.md)).
