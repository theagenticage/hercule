# Providers

A provider wraps one interactive coding harness (Claude Code via the Agent SDK, Codex via `codex app-server`, pi via its RPC mode) behind two surfaces: a **ProviderDefinition** on the controller (static self-description, registered by the provider plugin) and a **ProviderAdapter** on the runner (execution: probe plus five session methods, one normalized event stream). The controller authors a `SessionSpec` that names ids, never paths; the runner resolves it and drives the adapter; the adapter normalizes vendor traffic into one event vocabulary at the runner, with a tagged raw passthrough. Degradation is declared, never silent: per-mode and per-feature support are pure facts on the definition, and the controller substitutes an unsupported access mode by a hardcoded, strictly downward fallback before the session starts. Rationale lives in [ADR 0007](../adr/0007-provider-adapter-is-a-thin-interface-behind-a-normalized-event-stream.md).

## 1. Shape

| Surface | Where | Registered by | Owns |
|---|---|---|---|
| ProviderDefinition | controller | provider plugin, into the `provider` extension point ([./05-plugins.md](./05-plugins.md)) | identity, config schema, declared capabilities |
| ProviderAdapter | runner | built-in runner code in v1, written plugin-shaped (one narrow interface per provider, no cross-provider leakage); lifted into the plugin post-v1 | probing, session execution, event normalization |

A **provider instance** is a definition plus decoded config (t3-code's driver/instance split). The instance id, not the provider id, is the routing key everywhere: snapshots, session specs, placement. `supportsMultipleInstances` providers get multi-account by config-dir isolation (one login per instance).

**Default instances exist from first run** (resolved 2026-09-01, [Web app details](https://github.com/theagenticage/hercule/issues/45)): the controller creates one provider instance per shipped provider plugin (Claude Code, Codex, pi) with default config - subscription auth, no overrides - named after the provider, so the first-session onboarding ([./14-web-app.md](./14-web-app.md) §Onboarding) can offer "Log in to Claude Code" without the user ever meeting the instance concept; a second instance appears only when they want a second account.

The runner never sees Hercule domain state and the controller never sees runner paths ([./03-controller-and-runners.md](./03-controller-and-runners.md), ADR 0002). Provider-native session state (transcripts, thread rollouts, session trees) lives on the runner's disk; the controller's normalized per-session stream ([./04-state-store.md](./04-state-store.md)) is the observable record.

## 2. ProviderDefinition and declared capabilities

```ts
interface ProviderDefinition {
  id: string                                  // "claude-code" | "codex" | "pi"
  displayName: string
  supportsMultipleInstances: boolean          // multi-account via config-dir isolation
  configSchema: Schema                        // per-instance logical settings, in Effect Schema: env, model defaults - never paths (§2.1)
  defaultConfig: unknown                      // a plain JSON value, not a function (2026-09-06)
  declared: DeclaredCapabilities              // static facts of the pinned adapter version
}

interface DeclaredCapabilities {
  steering: "native" | "unsupported"          // unsupported degrades to queue
  fork: "native" | "unsupported"
  modelSwitch: "in-session" | "new-session"
  accessModes: Record<AccessMode, "native" | "unsupported">
  mcpPassthrough: "native" | "unsupported"    // pi: unsupported (2026-09-06)
  disallowedTools: "native" | "unsupported"   // Claude disallowedTools, pi excludeTools; Codex unsupported
  structuredOutput: "supported" | "unsupported"
}

type AccessMode = "approval-required" | "auto-accept-edits" | "auto" | "full-access"
```

Rules:

- Every value is a pure fact about the pinned adapter version. No value expresses a fallback; what an unsupported mode falls back to is controller policy (section 8.4). The earlier `asks-instead` value is withdrawn.
- ~~`steering: "unsupported"` means input sent to a busy session is queued by the controller instead (section 5); it never fails.~~ Steering is a guarantee of every session, not of the provider: `steering: "unsupported"` only changes how the controller keeps it. A steer on such a session interrupts the running turn and sends the input as the next turn (section 5) *(amended 2026-09-26, [#92](https://github.com/theagenticage/hercule/issues/92))*.
- `structuredOutput` is declared per [structured output research](https://github.com/theagenticage/hercule/issues/28): the mechanism differs per harness (section 7) but the graph sees one capability. A harness with no mechanism declares `unsupported`; the controller then rejects agent steps that declare an output schema on that provider at plan validation, never emulating with a closing prompt.
- The UI derives every affordance from declared facts plus policy, never from the provider name.

Declared values for the three v1 providers:

| Capability | Claude Code | Codex | pi |
|---|---|---|---|
| `steering` | native (stream-append into the running `query()`) | native (`turn/steer`) | native (`steer()`) |
| `fork` | native (`resume` + `forkSession: true`) | native (`thread/fork`) | native (`fork()`) |
| `modelSwitch` | in-session (`setModel()`) | in-session (per-turn `model` override on `turn/start`) | in-session (RPC `set_model`) |
| `accessModes` | all four native | all four native | approval-required, auto-accept-edits, full-access native; `auto` unsupported |
| `mcpPassthrough` | native (`mcpServers` option) | native (MCP servers, `mcpToolCall` items) | unsupported (2026-09-06, below) |
| `disallowedTools` | native (`disallowedTools`) | unsupported | native (`excludeTools`) |
| `structuredOutput` | supported (native `outputFormat`) | supported (native `outputSchema`) | supported (adapter-owned `submit_result` tool) |

*(Amended 2026-09-06, [#63](https://github.com/theagenticage/hercule/issues/63).)* `configSchema` is an **Effect Schema**, like every other schema crossing the host API ([./05](./05-plugins.md) section 5), and the catalog persists the JSON Schema derived from it. `defaultConfig` reaches the host as a **plain JSON value**, not a function: the plugin calls its own default-building code and passes the result, because nothing that cannot be serialized crosses the host boundary ([./05](./05-plugins.md) section 3).

pi's `auto` is unsupported because `auto` means a harness-side reviewer judges routine actions; parking (section 8.2) fixes pi's approval mechanics but gives it no reviewer.

### 2.1 Instance config

`configSchema` covers, per instance, **logical settings only**: extra environment for the spawned process (API keys, `ANTHROPIC_BASE_URL`-style routing, `CLAUDE_CODE_USE_BEDROCK=1`), model defaults, and provider-specific options. It never holds paths. The runner derives both paths itself: the provider home is `<storage dir>/providers/<instanceId>/` under the runner's material state ([./15-packaging-and-operations.md](./15-packaging-and-operations.md)), and the binary is the runner-installed harness ([15 §12](./15-packaging-and-operations.md)); both reach the adapter on `ProviderRunnerContext` (section 4). Per-runner path overrides ("use my own `claude`") are post-v1. This resolves ticket 12's "binary path, config dir" wording against the no-runner-paths rule (ADR 0005): those two were the runner's to resolve all along (resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)). ~~The one path-shaped fact that does exist lives per instance × runner, not in instance config: `userMaterialDir` (§9.1 User Material), an opaque runner-scoped string stored beside the capability snapshot.~~ *(Amended 2026-10-04, [#75](https://github.com/theagenticage/hercule/issues/75).)* User Material stores no path either: the runner reads it from each harness's default install locations on its own machine (§9.1 User Material).

Instance config is validated against `configSchema` and stored on the controller; the runner receives the instance's config with each probe and session request. Secret-valued entries are `provider-instance`-owned rows in the secrets table ([./13-security.md](./13-security.md)): the controller decrypts them and sends them inline with each probe or session request over the runner WebSocket; they are held in memory for the operation and never land on runner disk (the same posture as git credentials, 13 §9). They are never logged and never returned by the API.

## 3. Capability snapshots

```ts
interface CapabilitySnapshot {
  instanceId: string; runnerId: string; probedAt: string
  declared: DeclaredCapabilities              // copied from the definition
  harnessVersion: string | null               // probed: claude --version, initialize.userAgent
  auth: { status: "ok" | "unauthenticated" | "error"
          identity?: string; planLabel?: string; backend?: string }
  models: ModelDescriptor[]
}

interface ModelDescriptor {
  slug: string; name: string
  isDefault?: boolean; isLegacy?: boolean
  options: OptionDescriptor[]                 // select | boolean, with per-model choices and defaults
}

interface OptionDescriptor {                  // field names beyond kind/choices/default are not pinned
  id: string                                  // well-known ids below, or provider-specific
  label: string
  kind: "select" | "boolean"
  choices?: { value: string; label: string }[]
  default: string | boolean
}
```

### 3.1 Scope and cadence

- **Scope is instance x runner.** Harness binaries live on runners with potentially different versions, so catalogs, auth and capabilities differ per runner. The controller stores one snapshot per (instance, runner) in its DB. Harness version skew across the fleet is a surfaced fact, not an error (the hook for later fleet-managed harness updates).
- **The composer resolves the snapshot against the placement target.** Switching the target runner in the composer triggers an on-demand probe of that runner; the cached snapshot is shown meanwhile.
- **Cadence** (copied from t3-code): a background interval, demand-gated (probe only while something is watching), on instance config change, and on placement change.
- The probe runs on the runner through `ProviderAdapter.probe(config)`; the runner reports the `ProbeResult` as a runner fact over the runner protocol ([./03-controller-and-runners.md](./03-controller-and-runners.md)); the controller stamps `instanceId`, `runnerId`, `probedAt` and copies `declared` from the definition to form the snapshot.

### 3.2 Probing is side-effect-free

Discovery never creates, resumes, or mutates a provider conversation, and never reads credential files. Per provider:

| Provider | Probe |
|---|---|
| Claude Code | a throwaway SDK `query()` with **no prompt at all**, then `accountInfo()` and `supportedModels()` over the control protocol: account identity, subscription/plan label, `apiProvider` (first-party vs Bedrock etc.). The CLI version comes from `claude --version`. No API call is made. |
| Codex | `initialize` (user-agent carries the version) + `account/read` + `model/list` over a probe-only app-server process |
| pi | `pi auth check --provider <id> --json` per configured upstream provider; `pi --version` for the harness version |

`auth.status` is `unauthenticated` when the harness reports no usable login, `error` when the probe itself failed (binary missing, protocol error), `ok` otherwise. A provider instance with `auth.status !== "ok"` on a runner is filtered out of placement for that runner ([./03-controller-and-runners.md](./03-controller-and-runners.md)).

*(Corrected 2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64), against the real SDK 0.3.263 and CLI 2.1.263.)* The Claude row above described a probe that cannot work. The init message carries **no** identity; a prompt that never yields produces no init message at all; and a prompt that does yield makes a real `/v1/messages` call at the same instant as the init message, so a probe with one would bill the user's account for opening a Fleet page. `hooks: {}` does not disable hooks and `mcpServers: {}` does not strip MCP; what does the isolating is `settingSources: []` and `strictMcpConfig: true`. Even under `persistSession: false` the CLI writes `.claude.json`, `backups/` and `sessions/` into its config directory, which is why that directory is the instance's own and never the user's `~/.claude`. `HOME` is never overridden.

### 3.3 Catalog policy

Probe-first, curated overlay where introspection falls short:

- **Codex**: models, reasoning efforts and service tiers come fully probed from `model/list`.
- **Claude Code**: probed. *(Corrected 2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64).)* `supportedModels()` reports the CLI's own list with per-model option support (`supportsEffort`, `supportedEffortLevels`, `supportsFastMode`), so the catalog is the probed list plus a small hand-authored **legacy overlay** for slugs the CLI has stopped listing; a probed entry always wins. There are no per-model CLI-version gates: the CLI forwards any slug to the API unchanged, so which models it lists is the CLI's own gate, and an unlisted model keeps working for as long as Anthropic serves it.
- **pi**: models come from RPC `get_available_models` for the authenticated upstream providers, treated as probed.
- **Custom-model entries** are the user's escape hatch on every provider: a user-typed slug with no descriptor, rendered generically.

**Well-known option ids** are documented conventions, not an enum: `effort`, `thinking`, `contextWindow`, `fastMode`. The composer renders dedicated controls for them and workflows can reference them portably across providers; unknown ids render generically from the descriptor. Reasoning effort is a per-model `effort` option: probed per model for Codex, curated per model for Claude.

## 4. ProviderAdapter

```ts
interface ProviderAdapter {
  providerId: string
  probe(config: InstanceConfig): Effect<ProbeResult>
  startSession(spec: SessionSpec, ctx: ProviderRunnerContext): Effect<SessionBinding>
  sendInput(sessionId: string, input: TurnInput): Effect<SendResult>
  interrupt(sessionId: string, subagentId?: string): Effect<void>   // subagentId added 2026-10-05, #355: section 13.4
  respondToApprovalRequest(sessionId: string, requestId: string, decision: ApprovalDecision): Effect<void>   // was respondToRequest; renamed 2026-10-01, #309
  respondToQuestion(sessionId: string, requestId: string, answers: QuestionAnswers): Effect<void>             // added 2026-10-01, #309
  stopSession(sessionId: string): Effect<void>
  listSessions(): Effect<SessionBinding[]>    // reconciliation after runner restart
  events: Stream<ProviderEvent>               // the one output channel
}
// Effect-typed natively (ADR 0031): methods return Effects and `events` is a Stream, so session supervision,
// interruption and subprocess cleanup on the runner use Effect's structured concurrency directly.
// Vendor SDK boundaries (the Agent SDK's async generator, Codex stdio JSONL, pi's RPC) are wrapped at the edge.
// A promise-shaped facade is a post-v1 option if runner-side plugin loading wants one.

interface SessionSpec {                       // controller-authored - carries ids, never paths
  instanceId: string
  workspaceId: string | null                  // null = workspace-less session
  modelSelection: { model: string; options: Record<string, string | boolean> }
  accessMode: AccessMode                      // always a mode the target provider declares native
  systemPrompt?: string
  mcpServers?: McpServerConfig[]              // the decided passthrough field (#11)
  disallowedTools?: string[]                  // harness tool families to remove, Hercule vocabulary (rules below); copied from the Agent
  continue?: { nativeSessionId: string; mode: "resume" | "fork"; subagents?: { subagentId: string; itemId?: string }[] }   // subagents added 2026-10-05, #355: section 13.2
  outputSchema?: JsonSchema                   // structured result contract, section 7
}

interface ProviderRunnerContext {             // the facts the runner resolved for this session on this machine
  cwd: string | null                          // workspace or scratch dir; null only as the controller-side "no workspace" marker (§9.1)
  env: Record<string, string>                 // session env: HERCULE_*, GH_TOKEN, GIT_CONFIG_*, PATH prepend (§9.3)
  home: string                                // this instance's provider home on this runner (CLAUDE_CONFIG_DIR / CODEX_HOME / PI_CODING_AGENT_DIR)
  binary: string                              // resolved harness binary path on this runner (§11)
}

interface SendResult { turnId: string; delivery: "opened" | "steered" }

interface SessionBinding {
  sessionId: string                           // Hercule session id
  nativeSessionId: string                     // Claude session id | Codex thread id | pi session file id
  instanceId: string
}

type ApprovalDecision = "allow" | "allow_always" | "deny" | "cancel"
```

Rules:

- **No merged spec type.** `startSession` takes the controller-authored `SessionSpec` byte-for-byte (auditable, storable, comparable) plus a `ProviderRunnerContext` holding exactly the facts the runner resolved: cwd, session env, provider home, binary. Nothing here ever moves to `SessionSpec`. (Renamed from ticket 12's `RunnerContext`, 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43): the old name read as "facts about the runner", which it is not.)
- **Ids in, paths out.** The runner's session supervisor resolves `workspaceId` to a path and hands the adapter the context. The adapter never sees workspace ids; the controller never sees paths (runner paths are runner-owned opaque facts, ADR 0005).
- `accessMode` on the spec is post-fallback (section 8.4); adapters carry no fallback logic and may reject a mode they do not declare native as a programming error.
- `mcpServers` is the per-session MCP-config passthrough decided in [plugin architecture](https://github.com/theagenticage/hercule/issues/11): it carries self-injection and, later, plugin-contributed MCP tools. In v1 hercule-as-a-tool is the `hercule` CLI, not MCP ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)), so v1 core passes nothing here by default.
- `disallowedTools` names harness tool *families* in a small Hercule vocabulary (`edit`, `write`, `shell`, `web`, ...); the adapter owns the mapping to its harness's tool names and declares `disallowedTools: native | unsupported` in its capabilities. Unsupported is honest, not silent: the controller passes the field anyway, the adapter ignores it, and the UI shows "not enforced on <provider>" from the snapshot. The value is the Agent's `disallowedTools` copied at spawn ([./02-domain-model.md](./02-domain-model.md) rule 9); assistants default to `["edit"]` ([./12-assistants.md](./12-assistants.md) section 7). Resolved 2026-09-01, [Domain model residue](https://github.com/theagenticage/hercule/issues/46).
- `outputSchema` carries the agent step's declared schema ([./07-workflows.md](./07-workflows.md)); the adapter applies it by the provider's mechanism (section 7).
- **Deliberately absent:** `readThread` / `rollbackThread` (return with the checkpoint/revert feature; fork covers branching), a separate steer method, any queue surface, a mode-switch method (so a session's access mode locks at start; the composer shows it read-only, [./14-web-app.md](./14-web-app.md) §App shell, 2026-09-01).

*(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* The `disallowedTools` vocabulary is closed and is spelled ~~(`edit`, `write`, `shell`, `web`, ...)~~ `edit`, `write`, `shell`, `web-search`, `web-fetch`; a value outside those five is refused as `validation` rather than carried to an adapter that would have to guess at it. The mappings: Claude maps all five; pi maps `edit`, `write` and `shell` onto its own `edit`, `write` and `bash`, and has no web tool at all, so a web family is honoured by absence rather than dropped; Codex declares `disallowedTools: "unsupported"` and the reply says so. `mcpServers` is deferred to [#222](https://github.com/theagenticage/hercule/issues/222): v1 as shipped carries no such field on the Agent.

*(Amended 2026-09-10, [#67](https://github.com/theagenticage/hercule/issues/67).)* `stopSession(sessionId: string): Effect<void>` becomes `stopSession(sessionId, reason: ExitReason): Effect<void>`: the caller - a controller `SessionStop`, the runner's inactivity or absolute timer, or an announced shutdown - names why, and the adapter emits exactly that reason on `session.exited`. First reason wins where a session is stopped twice.

### 4.1 Session identity and binding

The Hercule session id and the provider-native id are separate concepts joined explicitly by `SessionBinding`. `startSession` returns the binding once the native id is known (Claude: init message; Codex: `thread/started`; pi: session file created). The controller stores `nativeSessionId` on the Session record ([./02-domain-model.md](./02-domain-model.md)) and passes it back in `continue` for resume and fork.

Amended 2026-09-07 ([#65](https://github.com/theagenticage/hercule/issues/65)): on Claude the native id is **minted by the adapter and passed as `options.sessionId`**, not read off the init message, because the CLI in streaming-input mode emits nothing at all - `init` included - until a first turn arrives, so a `startSession` that waited for it would block until somebody sent input. The two ids stay separate concepts joined only by `SessionBinding`; only where the native one comes from changes, and Codex and pi keep reading theirs off `thread/started` and the session file.

- A session is pinned to the runner where it starts (ADR 0002). Resume and fork target the same runner and the same instance.
- `listSessions()` enumerates the adapter's live and resumable sessions after a runner restart; the runner reconciles them against the controller's Session records over the runner protocol. Sessions the runner cannot account for are marked exited with `reason: "runner_restart"`.
- If a runner dies unrecoverably, its sessions' resumability dies with it; history survives in the controller's normalized stream. Accepted v1 trade.

*(Amended 2026-09-22, [#200](https://github.com/theagenticage/hercule/issues/200).)* The runner is not the only source of `exited`. The controller also ends a session without a report in two cases: a runner that is retired (reason `runner_retired` in the audit entry), and a runner that stays away past the session's absolute timeout (reason `runner_lost`, rule in [./03-controller-and-runners.md](./03-controller-and-runners.md) section 6.2). Neither writes a `session.exited` event to the stream; the status move and the audit entry carry the reason, as the `runner_restart` reconciliation above does.
*(Amended 2026-09-08, [#66](https://github.com/theagenticage/hercule/issues/66).)* `session.continue` guards on the derived `resumable` above and nothing of its own for the session side, plus three facts about the machine: it is not draining ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 7 - ~~a continued session is a new session on that machine~~ *a forked session is a new session on that machine; a resume is not, see the #162 amendment below*), it is online, and it holds a capability snapshot for the parent's provider instance saying it is logged in - the stored snapshot, never a probe, and the same check placement makes for a spawn. `resumable` stays a fact about the provider-native transcript; each machine-side refusal names its own reason, which is what keeps the field and the operation from reading as a contradiction.

- Codex allows only one app-server process to hold a thread open for writing (`-32600` on a second `thread/resume`). ~~The process topology is not pinned; the suggested topology is one app-server process per instance per runner, with thread ownership serialized through it.~~ *(Amended 2026-09-30.)* Hercule runs one app-server per session (section 10.2), so each thread has exactly one writer by construction.

**Session status** (consolidated from pinned lifecycle facts, not pinned by a ticket; [./02-domain-model.md](./02-domain-model.md) mirrors it):

```ts
type SessionStatus = "queued" | "starting" | "idle" | "busy" | "exited"
// derived, not stored: resumable = exited && the session's runner still holds its native state
```

`queued` = placement accepted, runner full or unreachable; `starting` = `startSession` sent, no `session.started` yet; `idle` = no running turn; `busy` = a turn is running (including while parked on an open request); `exited` = `session.exited` received or the runner reported it gone. `session.exited.reason` values are the spec's vocabulary: `stopped` (via `stopSession`), `process_exit`, `idle_unload` (Codex `thread/closed`, or the runner's own idle timer when the spec carries `timeouts.idleMs`, [./03-controller-and-runners.md](./03-controller-and-runners.md) section 6.2 *(amended 2026-09-25, [#92](https://github.com/theagenticage/hercule/issues/92))*), `runner_restart`, `crash`. *(Amended 2026-09-25, [#92](https://github.com/theagenticage/hercule/issues/92).)* An `idle_unload` exit is otherwise an exit like any other: what it does to the session's input depends on the session, not on the reason (section 5). *(Amended 2026-09-27, [#92](https://github.com/theagenticage/hercule/issues/92).)* A turn is running from the moment the runner answers that an input opened it, so that answer moves ~~an `idle` session~~ an `idle` or `starting` session *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431))* to `busy`, before `turn.started` arrives. The answer is applied in the order the runner sent it among the session's events, so an exit that follows it is an exit while `busy`. A harness can start its turn after it answers (Codex answers `turn/start` before it reports the turn), and without this rule a session that exits in between would read as idle, and the message would get neither a reply nor a notice. *(Amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431).)* A start carries the session's first input and the runner answers it the same way (section 4.2), so a session can go from `starting` straight to `busy`. ## 5. Steering and queued input

Steering is implicit in `sendInput`: a busy session steers (input folds into the running turn), an idle session opens a new turn. `SendResult.delivery` reports which happened and is the only authority; consumers never infer steering from event order. A steered input appears in the stream as `item user_message { steered: true }` inside the running turn.

Vendor mechanisms: Claude appends to the streaming input of the live `query()`; Codex calls `turn/steer` with `expectedTurnId`; pi calls `steer()`. When Codex rejects `turn/steer` because the turn just ended, the adapter opens a new turn with the same input and reports `opened` - input is delivered unconditionally, never bounced. If `turn/steer` proves flaky, t3-code's approach (queue a `turn/start` and relabel it) is the documented fallback.

**The input queue is controller-owned domain state.** When the user or a workflow sends input to a busy session and steering is not wanted (or the provider declares `steering: "unsupported"`), the controller stores Queued Input and flushes it with `sendInput` on `turn.completed`. Queued input is editable and cancelable until flushed, except that the input a session starts with cannot be cancelled before the session starts: `input.cancel` refuses it `invalid_state` and says to stop the session instead, because that input is the session's only reason to start. While the session is `queued`, that input is its oldest waiting row and can still be edited; while it is `starting`, it is on the wire with the start and can be neither edited nor cancelled. An input the runner refused and put back to waiting is an ordinary waiting row and can be cancelled ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)) *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431))*; subscription deliveries to sessions arrive this way ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)). Vendor-native queues (Codex follow-up `turn/start`, pi `followUp()`) go unused: they are process-local and uneditable. The cost is sub-second flush latency over the runner WebSocket, riding the ordinary seq/ack + outbox protocol.

## 6. Normalized event taxonomy

Normalization happens at the runner, closest to the vendor protocol. Every event carries the base fields; every event may carry `raw` (the untouched vendor payload tagged with its source, e.g. `claude.sdk.message`, `codex.app-server.notification`, `pi.session.event`). Enums are open for consumers: unknown kinds render generically, never crash.

```ts
interface ProviderEventBase {
  eventId: string; sessionId: string; at: string
  turnId?: string; itemId?: string; requestId?: string
  providerRefs?: Record<string, string>       // native ids (thread id, item id, tool_use id ...)
  raw?: { source: string; payload: unknown }
}
```

*(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); decided by [#351](https://github.com/theagenticage/hercule/issues/351) and [#377](https://github.com/theagenticage/hercule/issues/377).)* **An event names the subagent it belongs to.** `turn.started`, `turn.completed`, `item.started`, `item.updated`, `item.completed`, `content.delta`, `request.opened`, `request.resolved`, `session.usage.updated`, `runtime.warning` and `runtime.error` carry an optional `subagentId`: the harness's own id for the subagent whose event it is. Absent means the session's own agent. `session.started` and `session.exited` never carry it. One more event, `subagent.started`, introduces a subagent before any of its events. Section 13 owns both.

### 6.4 Streaming

`content.delta { itemId, streamKind: "assistant_text" | "reasoning_text" | "command_output", delta }`

- Deltas are append-only text per (item, streamKind). Where the vendor sends cumulative snapshots (pi `tool_execution_update.partialResult`), the adapter diffs by common prefix before emitting.
- `command_output` deltas exist only where the harness streams them (Codex `outputDelta`, pi); on Claude the output arrives whole on `item.completed`. Degradation, not distortion.
- **Reasoning-summary precedence rule**: where a vendor streams raw and summarized reasoning as separate channels (Codex `item/reasoning/textDelta` and `summaryTextDelta`), the adapter picks one channel per reasoning item, raw preferred, and emits it as `reasoning_text`; the unpicked channel stays raw-only. No fourth stream kind (`reasoning_summary_text` remains an additive option later).
- The store coalesces deltas in memory and flushes at message/turn boundaries; nothing is persisted per token ([./04-state-store.md](./04-state-store.md)). Watched sessions receive an ephemeral token-delta passthrough ([./14-web-app.md](./14-web-app.md)).

### 6.5 Requests (approvals and questions)

- ~~`request.opened { kind, detail }`~~ *(Amended 2026-09-13, [#70](https://github.com/theagenticage/hercule/issues/70).)* `request.opened { request: { requestId, itemId, kind, decisions, detail } }` with kind `command_approval` | `file_change_approval` | `file_read_approval` | `tool_approval` | ~~`user_input`~~ `question` *(renamed 2026-09-14, [#70](https://github.com/theagenticage/hercule/issues/70), D-28)*. The request is nested so the record the controller stores and hands out is exactly what arrived. `itemId` is the item the request is about, which is what a surface overlays; `decisions` is the non-empty set of `ApprovalDecision` values this request accepts, so a request that may persist no rule, or has nothing for an allow to carry, offers fewer rather than leaving a surface to offer an answer the adapter would have to substitute for. `detail` is one closed shape per kind - `command_approval { command }`, `file_change_approval { paths }`, `file_read_approval { paths }`, `tool_approval { toolName }`, `question { questions }` - and the adapter truncates `command`, `paths` and `questions` to the protocol's bounds, because an oversized frame is an undecodable one and costs the runner its socket and every session on it. *(Amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309): only an approval carries `decisions`; a question takes answers only and carries none.)*
- `request.resolved { requestId, decision: ApprovalDecision }`, or `request.resolved { requestId, answers: QuestionAnswers }` for an answered question *(amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309))*

`file_read_approval` renders as a path list, not a diff or a command (native in Codex `item/fileRead/requestApproval`). A request is one of two different things ~~sharing one slot~~ *(amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355): a session can have several open at once, section 13.3)*: an **approval** (`command_approval`, `file_change_approval`, `file_read_approval`, `tool_approval`) names what would be run and is resolved by one of the four `ApprovalDecision` values and never by free text, while a **question** carries one to many questions and is resolved by answers, each either one or more of the options offered or a custom string the user types. *(Amended 2026-09-14, [#70](https://github.com/theagenticage/hercule/issues/70), D-28: the kind is `question`; ~~`user_input`~~ named the transport, not the thing.)* `question` carries structured questions in `detail` (Claude `AskUserQuestion`, Codex `item/tool/requestUserInput`); ~~it resolves with the answers~~, and the taxonomy needs no separate question event pair. *(Amended 2026-09-13, [#70](https://github.com/theagenticage/hercule/issues/70).)* ~~Answering a question with its answers is not built; until `session.respond` carries answers the request offers `deny` and `cancel`. The future shape is pinned: `session.respond` will take `{ sessionId, requestId, answers: Record<header, string | string[]> }` in place of `decision`, keyed by each question's `header`, where a value is one or more of the offered option labels or a custom string the user typed ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md) section 2).~~ *(Amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309).)* **A question is answered with its answers.** `session.respondToQuestion` takes `{ sessionId, requestId, answers: Record<header, string | string[]> }`, keyed by each question's `header`, where a value is one or more of the offered option labels or a custom string the user typed ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md) section 2). As built:

- **A question takes answers only.** It offers no decision, so a `question` request carries no `decisions`. The user who wants to say something else types their own answer. To turn a question down, the user stops the turn (`session.interrupt`), which resolves it as `cancel`, as it resolves any open request. Claude Code is then denied and its turn interrupted; Codex gets a JSON-RPC error reply, because its reply to a question has no way to decline, and its turn is interrupted.
- **It resolves with what the user said.** The runner frame `sessionRespondToQuestion` carries the answers, and the event `request.resolved` carries `answers` in place of `decision`. An answered question resolves with its answers, never with a substituted `allow`. A decision goes in the frame `sessionRespondToApprovalRequest`.
- **The adapter maps the answers back to the harness.** `apps/runner/src/providers/questions.ts` finds each header's key in the harness's own input, with the parser that built the request, so a header or a question truncated in the request still leads back to the untruncated key. Claude Code gets `canUseTool`'s `{ behavior: "allow", updatedInput: { ...input, answers } }`, keyed by each question's full text, a list joined with `", "`. Codex gets the reply `{ answers: { <question id>: { answers: [...] } } }`, a string as a one-item list, and its turn goes on.
- **A repeated header is numbered:** the second "Approach" is shown as "Approach (2)". Answers come back keyed by header, so two questions showing one header could not both be answered, and Claude Code checks only that question texts are unique.
- **What cannot be answered is dropped when the request is built:** a question with no key in the harness's input (its full text on Claude, its id on Codex), because its answer could not be sent back; a question whose key repeats an earlier question's, because the harness reads one answer per key; and an option whose label repeats an earlier option's, because a picked option is sent back as its label. A Codex question with `options: null` is a question with no options, answered with text.
- **A secret question is kept, with a warning.** A Codex question with `isSecret: true` is marked `secret`. Nothing hides or protects its answer, so the dock says so before the user types: the answer is stored in the thread like any other.
- **pi raises no question.** pi has no built-in tool that asks the user, and the one extension a pi session runs is Hercule's own, which asks only `confirm`. [#316](https://github.com/theagenticage/hercule/issues/316) gives a pi session a tool that asks.
- **The answers to one request hold at most `MAX_ANSWERS_LENGTH` characters, headers included** (four messages' worth), so a full set of answers always fits the 2 MiB frame.

*(Amended 2026-09-14, [#70](https://github.com/theagenticage/hercule/issues/70).)* The structured questions are pinned: `question { questions }` carries one to many `{ question, header, options: [{ label, description }], multiSelect }` - `header` the short chip the question is labelled with, `question` its prose, `options` what each answer would have meant, `multiSelect` whether more than one may be chosen. Provider-neutral: Claude's `AskUserQuestion` (1-4 questions, 2-4 options, an optional `preview` the protocol drops) and Codex's `item/tool/requestUserInput` both map into it. A question a harness sends without prose or a chip is dropped rather than guessed at, and an ask from which no question survives becomes `tool_approval { toolName }` rather than a `question` with no question on it, which would be an undecodable frame. *(Amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309): a question also carries `secret?: true` when the harness asked to keep its answer secret, Codex's `isSecret`; the field is absent otherwise.)*

`ApprovalDecision` scope semantics: `allow` = this call only; `allow_always` = the vendor's for-session persistence, never persistence on disk (Codex `acceptForSession`, Claude `updatedPermissions` with every rule rewritten to `destination: "session"`~~, pi: the adapter's hook remembers the rule for the session~~ *(amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355): the pi adapter offers `allow`, `deny` and `cancel` only, so a pi approval never offers `allow_always`; [#353](https://github.com/theagenticage/hercule/issues/353))*); `deny` = refuse with a reason the model sees; `cancel` = refuse and end the turn. The four values and their vendor mappings are pinned; that `cancel` ends the turn is the spec's consolidated reading of the vendors' `cancel` options. Vendor exotics (Codex execpolicy / network amendments) are not offered; the chosen native option is recorded in `raw` / `providerRefs`.

*(Amended 2026-09-14, [#73](https://github.com/theagenticage/hercule/issues/73).)* No adapter emits `file_read_approval` in v1: `item/fileRead/requestApproval` is not in the app-server's ServerRequest set at codex 0.154.0, and Codex was the one provider that had it natively. The protocol kind stays as specced, for the adapter or the Codex release that first opens such a request.

A request stays open until ~~`respondToRequest`~~ `respondToApprovalRequest` or `respondToQuestion` *(amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309))*; the controller surfaces it as a Notification and in the session view ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md)). *(Amended 2026-09-28, [#85](https://github.com/theagenticage/hercule/issues/85): an approval surfaces as a `core.approval` decision, and a `question` surfaces in the session view only, ~~because an answer cannot yet carry answers to questions~~ *(amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309))* because none of a notification's bound answers fits a set of answers; [#317](https://github.com/theagenticage/hercule/issues/317) decides how a question is announced ([./10-triage-intake-and-notifications.md](./10-triage-intake-and-notifications.md) section 7.6).)* `interrupt` on a session with an open request resolves it as `cancel` (spec's consolidated semantics; follows from the park-and-resume abort caveat in section 8.2). *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)* With several agents asking, a stop resolves as `cancel` the Requests of every agent it stops, and no others (section 13.4).

### 6.6 Usage and ops

- `session.usage.updated { ... }` - a cumulative token snapshot for the session, taken from Claude `context_usage`, Codex `thread/tokenUsage/updated` and pi `message_end.usage`. Cadence differs per harness; the snapshot shape absorbs that. The field set is below.
- `runtime.warning` - retries (Claude `api_retry`, pi `auto_retry_*`), model rerouting or drift mid-turn, mirror errors.
- `runtime.error { class }` - Codex `codexErrorInfo` is the reference class enum (`ContextWindowExceeded`, `UsageLimitExceeded`, `Unauthorized`, `SandboxError`, ...); other adapters map to the same classes where they can, else `unknown`.

~~**Open:** the exact field set of the `session.usage.updated` snapshot is not pinned beyond "token snapshot plus context usage".~~ *(Resolved 2026-09-07, [#65](https://github.com/theagenticage/hercule/issues/65).)* The snapshot is `{ inputTokens, outputTokens, cacheReadTokens?, cacheWriteTokens?, costUsd? }`, cumulative for the session, with the three optional fields present only where the harness reports them. Context usage against the model's window is **not** in the v1 shape: no consumer reads it yet, and the assistant rotation threshold (section 9.2) adds the field it needs when it ships, rather than the shape carrying a number nothing checks.

*(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); decided by [#377](https://github.com/theagenticage/hercule/issues/377).)* **Usage events feed Token Usage on the records,** and screens read only the records ([CONTEXT.md](../../CONTEXT.md) Token Usage). The snapshot keeps its shape, the protocol's `Usage`, with three changes:

- **It counts since this process started,** ~~cumulative for the session~~, for one agent: the session's own agent, or the subagent its `subagentId` names. The controller adds each process's count to the record's running total, so a record holds the whole life of the session and never goes down, not on a resume and not on a compaction. For example, a session spends 50k tokens, exits, resumes and spends 20k more: the adapter reports 20k, and the record says 70k.
- **The four parts never overlap.** `inputTokens` is input not read from cache, `cacheReadTokens` and `cacheWriteTokens` are the cache reads and writes, and `outputTokens` is the output. The tokens used are their sum. An adapter whose harness counts cached reads inside its input subtracts them ([#428](https://github.com/theagenticage/hercule/issues/428) fixes the Codex adapter).
- **A snapshot with no `subagentId` covers the session's own agent and every subagent.** One with a `subagentId` covers that subagent alone. The adapter does the adding where the harness counts each agent apart (Codex), so the controller never knows which harness counts how. Section 13.5 says how, per harness.

`costUsd` follows the same rules where the harness reports a cost.

### 6.7 Trimmed on purpose

Auth, account, rate-limit and MCP-status events are snapshot material (section 3), not session events; rate-limit pushes arriving mid-session lag the probe cadence, accepted for v1. `turn.aborted`, `turn.diff.updated` (diffs come from workspace checkpoints), hooks, realtime audio, files-persisted, and vendor-specific items (review mode, image generation) are dropped; all are additive later via new kinds or `raw`. Claude's long informational tail (`tool_use_summary`, `prompt_suggestion`, 20+ system subtypes) is whitelisted-in and raw-logged otherwise. Claude's task lifecycle system messages (`task_started`, `task_progress`, `task_updated`, `task_notification`) are among the trimmed: a task's command already shows as its tool item, and a stopped task shows as that item failing *(amended 2026-09-27, [#92](https://github.com/theagenticage/hercule/issues/92))*. *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); [#351](https://github.com/theagenticage/hercule/issues/351).)* Except `task_started` and `task_notification` with `task_type: local_agent`, which are a subagent's turn boundaries and are kept (section 13.6). ## 7. Structured output

An agent step may declare an output schema; the graph routes on the schema-conforming result ([./07-workflows.md](./07-workflows.md), ADR 0008). The runner obtains it by the provider's native-enough mechanism; a closing prompt with parse-and-retry is never used.

| Provider | Mechanism | Result location | Failure signal |
|---|---|---|---|
| Claude Code | `outputFormat: { type: "json_schema", schema }` on `query()`; SDK validates and re-prompts | `structured_output` on the final `result` message | `subtype: "error_max_structured_output_retries"`, or `success` with no `structured_output` (treated as failure per SDK docs) |
| Codex | `outputSchema` on `turn/start` (stable, not experimental-gated); enforced server-side as strict constrained decoding | text of the turn's final `agentMessage` item | turn `failed`, or turn completed with a final item that is not an `agentMessage` (missing output; ~~the adapter may retry with a fresh `turn/start`, default once~~) |
| pi | `submit_result` tool registered by the Hercule extension file (section 10.3): Typebox parameters = output schema, ~~`terminate: true`~~, `constrainedSampling: { type: "json_schema", strict: "prefer" }`; pi validates args and feeds violations back to the model | the tool's captured args (~~carried on `tool_execution_end`~~; a trailing assistant message is ignored) | agent settled without calling the tool: adapter re-prompts ("You must call submit_result with ...") a bounded number of times (default 2 retries, the research's example figure), then schema-failure |

*(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* Four corrections: three to the pi row, from building it against pi 0.85.1, and one to the Codex row. **Where the args come from:** a call's arguments are carried on `tool_execution_start` and on nothing else, so the adapter captures them there and reads them when the matching `tool_execution_end` arrives; the end frame alone would answer the turn with nothing. **Where `terminate` lives:** it is a field of the tool's execute result, returned by the call, not a field of the registration - the same in section 10.3's extension-file paragraph. **Two bounds on the failure signal, one per harness**, both named in `apps/runner/src/providers/pi/adapter.ts` - `MAX_REPROMPTS` for the re-prompts and `MAX_REFUSED_ANSWERS` for the refused answers. pi stops asking after three answers pi's own argument validation refused: a model argues with the validator indefinitely on a schema no value can satisfy, so the settle the re-prompt bound waits for never comes; the adapter ends pi's run and reports the last answer's schema-failure on a `completed` turn. On Codex the API refuses an unsatisfiable schema before any sampling happens - `invalid_json_schema` on `response_format 'codex_output_schema'` - and the adapter reports that as a schema-failure carrying the API's own sentence, on a `failed` turn. **No retry on Codex:** the Codex row's struck clause promised a fresh `turn/start` after a turn that ended without a value, and the adapter as shipped never retries - a turn that answered nothing is reported as a schema-failure at once, because the one failure seen live is the API refusing the schema, which a second identical `turn/start` would only be refused for again.

Normalized outcome, carried as `structuredResult` on `turn.completed` when the session has an `outputSchema`:

```ts
type StructuredResult =
  | { outcome: "ok"; value: unknown }
  | { outcome: "schema-failure"; reason: string }   // validation/retries exhausted, tool never called
// ordinary run failure = turn.completed { state: "failed" } with no structuredResult
```

The runner re-validates `value` against the declared schema before routing, on every provider (cheap, catches harness regressions, one uniform error surface). *(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* More precisely: the runner re-validates `value` against the declared schema on every provider before it reports `ok`, whatever the harness claims about having validated it already, so `ok` means one thing everywhere. Schemas are linted at workflow validation ([./07-workflows.md](./07-workflows.md)) against the common strict subset, regardless of which provider the step runs on: OpenAI's strict subset is the binding constraint (`additionalProperties: false`, all properties required), within JSON Schema draft-07 (Claude) and pi-ai's strict-transform subset (no `$ref`, `oneOf`, `patternProperties`). pi string enums compile to `StringEnum`, not unions of literals.

`outputSchema` lives on `SessionSpec` only, and the adapter applies it to **every turn** of that session by the provider's mechanism (Codex re-sends it on each `turn/start`, Claude on each `query()`, pi's extension registers the tool at session start). `TurnInput` never carries it. This works because a session belongs to exactly one agent step and the schema is that step's: iterations re-enter the same session and each yields its own `structuredResult` ([Workflow execution semantics](https://github.com/theagenticage/hercule/issues/36)).

## 8. Access modes

`AccessMode` is the session-level permission axis the adapter enforces, ordered `approval-required < auto-accept-edits < auto < full-access`. Meaning: approval-required asks for every side-effecting action; auto-accept-edits allows file edits, asks for the rest; auto lets a harness-side reviewer judge routine actions; full-access allows everything.

### 8.1 Mapping table (normative)

| Hercule mode | Claude Code | Codex | pi |
|---|---|---|---|
| approval-required | SDK default mode + `canUseTool` parks -> `request.opened`, resumes on decision | `approvalPolicy: "untrusted"` + `sandbox: "read-only"`; approvals arrive as server-to-client requests | `tool_call` handler parks -> `request.opened`, resumes on decision (native park-and-resume) |
| auto-accept-edits | `permissionMode: "acceptEdits"` | `approvalPolicy: "on-request"` + `sandbox: "workspace-write"` | handler allows edit/write tools, parks the rest |
| auto | `permissionMode: "auto"` (native) | `approvalsReviewer: "auto_review"` (native) | unsupported (falls back, section 8.4) |
| full-access | `permissionMode: "bypassPermissions"` + `allowDangerouslySkipPermissions: true` | `approvalPolicy: "never"` + `sandbox: "danger-full-access"` | handler allows all |

Claude and pi are park-and-resume providers: the approval seam is an awaited callback (`canUseTool`; pi's `tool_call` extension handler, awaited with no timeout, verified in source at v0.84.x) that the adapter does not return from until ~~`respondToRequest`~~ `respondToApprovalRequest`, or `respondToQuestion` for a question, *(amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309))* arrives; `undefined` / allow lets the call execute as-is, deny returns a reason the model sees. Codex is the RPC-approval provider: `item/commandExecution/requestApproval`, `item/fileChange/requestApproval`, `item/fileRead/requestApproval`, `item/tool/requestUserInput`, `mcpServer/elicitation/request` and `item/permissions/requestApproval` are server-to-client JSON-RPC requests the adapter MUST answer or the turn hangs; each maps to a `request.opened` and is answered from the decision (`accept` / `acceptForSession` / `decline` / `cancel`).

On Claude the callback is supplied in every mode but `full-access` - which actions a mode asks about is the harness's own judgement, and with `allowDangerouslySkipPermissions` the SDK ignores the callback and warns once per session - and a decision maps to one `PermissionResult` (verified against `@anthropic-ai/claude-agent-sdk` 0.3.263):

| Decision | `PermissionResult` |
|---|---|
| allow | `{ behavior: "allow", decisionClassification: "user_temporary" }` |
| allow always | `{ behavior: "allow", updatedPermissions: <the callback's own `suggestions`, every one rewritten to `destination: "session"`>, decisionClassification: "user_permanent" }`; offered only where the callback handed suggestions over. The rewrite is what keeps the answer about this thread: a click never writes a rule to the user's settings files on disk |
| deny | `{ behavior: "deny", message, decisionClassification: "user_reject" }` |
| cancel | the same deny with `interrupt: true`, which ends the turn with it |

*(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); [#353](https://github.com/theagenticage/hercule/issues/353).)* **A Claude park is keyed by its `toolUseID`,** so several `canUseTool` calls can be parked at once: the main agent's and each subagent's (the callback names a subagent in `agentID`). The adapter never denies a call because another is parked. **To verify in the Claude build:** what `interrupt: true` does when the asker is a subagent. The earlier pi degradation (deny-with-reason and retry after approval) is withdrawn.

### 8.2 Park-and-resume build caveats

From `research/pi-approval-parking.md` (branch `research/pi-approval-parking`), binding for the pi adapter and analogous for Claude:

- **Race the parked decision against `ctx.signal`.** pi's `abort()` only flips the AbortController; the loop checks it after the handler resolves. The handler returns promptly on abort so `interrupt` passes through a parked approval.
- **A park serializes the tool batch**: preflights run sequentially and sibling calls wait for all preflights. Same shape as Claude; accepted.
- **Handler exceptions deny fail-safe**: wrap the wait so an IPC failure produces a clear deny reason, never a silent allow.
- **No contractual guarantee** (pre-1.0): pin the pi version and ship a regression test asserting that a pending `tool_call` handler delays execution.
- **The park is bridged in-band over RPC**: the Hercule extension's `tool_call` handler blocks on `ctx.ui`, which RPC mode surfaces as an `extension_ui_request` on stdout; the adapter answers with `extension_ui_response` when ~~`respondToRequest`~~ `respondToApprovalRequest` *(amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309))* arrives. No side channel.
- While parked no LLM connection is held open; the turn stays active; `tool_execution_start` has already fired, so the UI overlays "awaiting approval" on the started item.
- On Claude, `canUseTool` is reached only when the pipeline falls through to a prompt; auto-approved tools never hit it. That is the intended behaviour for the mapped modes. A `PreToolUse` hook is the seam if every call must be observed. In `approval-required`, which actions are asked about is the harness's own judgement: Claude Code decides read-only shell itself, so only mutating commands park - `ls -la` ran without the callback being called at all, while `touch proof.txt` parked *(observed 2026-09-14, [#70](https://github.com/theagenticage/hercule/issues/70), CLI 2.1.270)*.

### 8.3 Codex sandbox caveats

Sandboxing is enforced by Codex (Seatbelt on macOS, bubblewrap on Linux; WSL1 unsupported). `thread/shellCommand` and `process/spawn` bypass it entirely; the adapter never calls them. `thread/start` with `workspace-write` marks the cwd trusted in the instance's `config.toml`; with `CODEX_HOME` isolated per instance (section 9) this touches no user config.

### 8.4 Fallback policy

- The definition declares support per mode; the controller resolves any unsupported mode to a supported one **before session start**. `SessionSpec.accessMode` therefore always names a natively supported mode and adapters carry no fallback logic.
- The fallback chain is **hardcoded in v1**, not configurable, and **strictly downward** on `approval-required < auto-accept-edits < auto < full-access`: the substitute is the nearest less-permissive supported mode. Shipped result: `auto -> auto-accept-edits` (auto always allows edits, so ask-everything was overly punitive). If no equal-or-less-permissive supported mode exists, session start fails with a clear error. Guardrail owned by [./13-security.md](./13-security.md).
- The UI keeps every mode selectable and annotates the substitution from declaration plus policy ("runs as Auto-accept edits on this provider", by the mode's name, [./14-web-app.md](./14-web-app.md), amended 2026-09-30). The Session record stores both `requestedAccessMode` and the effective `accessMode` ([./02-domain-model.md](./02-domain-model.md)); the fallback chain is stated in ADR 0007 and the glossary ([../../CONTEXT.md](../../CONTEXT.md)) as amended.

### 9.3 Session environment and skills

The runner injects, per session: `HERCULE_API_URL`, `HERCULE_TOKEN` (the session token; dies with the session), `HERCULE_SESSION=1` (makes the `hercule` CLI refuse file credentials), plus the git credential material (`GH_TOKEN`, `GIT_CONFIG_*`) whose mechanics [./13-security.md](./13-security.md) owns (session token: [./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)). The runner makes the `hercule` binary reachable from the session by prepending its own bin directory to `PATH` ([./15-packaging-and-operations.md](./15-packaging-and-operations.md) §2), so `which hercule` works and the skill text stays portable. One provider-agnostic skill source describes hercule-as-a-tool, and each adapter has exactly one function mapping it to its harness's own channel.

*(Amended 2026-10-03, [#310](https://github.com/theagenticage/hercule/issues/310).)* Before it adds the variables above, the runner removes every `HERCULE_*` variable it inherited from its own environment, the same way it removes git's own variables (`GIT_*`, `SSH_ASKPASS`).

- **Why.** Those variables configure the runner itself. The controller starts the local runner with `HERCULE_HOME` set to its own Home, usually the user's live one, so a `hercule serve` an agent ran in a session without `--home` would open the live database. Others, such as `HERCULE_BIND_PORT` or `HERCULE_DATA_DIR`, change what any `hercule` command in the session does.
- **Nothing in a session needs them.** The CLI authenticates with `HERCULE_API_URL` and `HERCULE_TOKEN`, and the git credential helper reads only variables the runner sets.
- **Every child of the runner loses them.** A repository's setup command and a workspace action step start from the same environment as a session.
- **The default Home.** Without `HERCULE_HOME`, a `hercule` command falls back to `~/.hercule`. When the session's controller runs on a scratch Home, for example while an agent tests Threads or an end-to-end run is live, that default is the user's live Home. So `HERCULE_SESSION=1` gets a second effect: the commands [15 §5](./15-packaging-and-operations.md) lists refuse the default Home and ask for `--home` or `HERCULE_HOME`.
- **Instance config still applies.** Instance config `env` (section 2.1) is applied after the removal, so a `HERCULE_*` variable the user sets there still reaches the session. The variables this section lists are set after instance config, so it cannot replace them.
- **Not sessions.** Probes, logins and installs still run with the runner's own environment (section 10.1).

**Amended 2026-09-15 ([#68](https://github.com/theagenticage/hercule/issues/68)),** replacing "Claude skill file under the session's project settings, Codex `AGENTS.md` section": nothing is materialized per session any more.

- **Claude**: the runner writes the skill once at start into a Claude plugin directory under its own storage - `<runner storage>/claude-plugin/`, holding `.claude-plugin/plugin.json` and `skills/hercule/SKILL.md` - overwritten at every start so an upgraded binary's skill text takes over, exactly like the `bin/hercule` symlink. Every session loads it by path through the Agent SDK's `plugins` option (`[{ type: "local", path }]`). Hercule owns the directory, so a Thread's own `.claude/` is never collided with and no session is written into.
- **Codex**: `developerInstructions` on `thread/start`, `thread/resume` and `thread/fork` (the channel [#73](https://github.com/theagenticage/hercule/issues/73) found), which retires the scratch-cwd `AGENTS.md` channel, consistent with the #73 note in section 9.1. The scratch cwd itself stays and stays empty.
- **pi**: ~~unchanged and pending - no pi adapter exists yet ([#74](https://github.com/theagenticage/hercule/issues/74)).~~ *(Amended 2026-09-30.)* The pi adapter exists ([#74](https://github.com/theagenticage/hercule/issues/74)), but it does not read `herculeTool` yet, so a pi session is not told about the `hercule` CLI. ## 10. Per-provider build notes

### 10.1 Claude Code (Agent SDK)

- **Surface**: `query()` async generator of typed `SDKMessage` plus the `Query` control object (`interrupt`, `setPermissionMode`, `setModel`, `streamInput`, `getContextUsage`, `close`). One long-lived `query()` per session in streaming-input mode (required for the control methods and for steering); `includePartialMessages: true` for deltas. Session id on the init message and every `result`.
- **Process**: each session is one Claude Code CLI subprocess, about 1 GiB RAM as a starting point, memory growing over long sessions; no built-in timeout, no per-subagent deadline. The runner's supervisor owns deadlines and recycling; `maxConcurrentSessions` derives from RAM (~1 session per 2 GiB, [./03-controller-and-runners.md](./03-controller-and-runners.md)). Subagent caps via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` / `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and `maxBudgetUsd`. *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)* Hercule sets none of them in v1, so the harness defaults hold (section 13.7).
- **Binary**: `pathToClaudeCodeExecutable` points at the runner-installed `claude` (`ctx.binary`; the SDK spawns it without a shell). The SDK's bundled per-platform CLI packages are excluded from the Hercule build; the installed CLI is floor-pinned to the SDK's own version - SDK 0.3.N pairs with CLI 2.1.N, and newer CLI with older SDK is the supported direction ([ADR 0028](../adr/0028-provider-harnesses-are-runner-installed-executables.md), [./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12).
- **Probe** *(2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64))*: `query({ prompt: <an input stream that closes at once>, options: { pathToClaudeCodeExecutable: ctx.binary, settingSources: [], strictMcpConfig: true, persistSession: false, env } })`, then `accountInfo()` and `supportedModels()`, then close, under a 15 s deadline. `env` is the runner's own with `CLAUDE_CONFIG_DIR` set to the instance home and `DISABLE_AUTOUPDATER=1`; `HOME` is untouched. Zero API calls; about 460 ms against a warm CLI.
- **Login** *(2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64))*: `claude auth login` with stdin piped, `CLAUDE_CONFIG_DIR` set to the instance home and `BROWSER` set to a command that exits non-zero. The failing browser launch is what makes the CLI print the paste-a-code authorize URL; a launch that succeeds switches it to a `localhost` callback no remote browser can reach. The runner holds one login child per instance, relays the first `https://` URL it prints, writes the pasted code and a newline to its stdin, and kills a child left idle for ten minutes. `claude setup-token` needs a PTY and is not usable; `claude auth status --json` is the cheapest auth check.
- **Auth**: delegation only. The CLI holds its own login in the instance's `CLAUDE_CONFIG_DIR` (Linux: `.credentials.json` in that dir; macOS: a Keychain item keyed per config dir - `Claude Code-credentials-<hash of dir>` - so instance logins never collide with each other or with the user's personal login; when the Keychain rejects the write, e.g. locked over SSH, the CLI falls back to `.credentials.json` in the config dir. `HOME` is never overridden). Hercule never reads, extracts, or refreshes vendor tokens. API-key / Bedrock / Vertex routes are instance env (`ANTHROPIC_API_KEY`, `CLAUDE_CODE_USE_BEDROCK=1`, ...), not separate code paths. The read-only probe reads `AccountInfo` (email, subscription type, `apiProvider`) over the control protocol; the init message carries none of it (see the Probe note above).

**Risk:** Claude subscription auth. Research #2 (`research/claude-agent-sdk.md`) read Anthropic's Agent SDK policy as forbidding it ("Claude.ai subscription login is not permitted ... Hercule must design around API-key billing"); tickets 22 and 23 and the charting decision accept the t3-code posture (the user's own tool driving the user's own login through the unmodified vendor CLI; the prohibition targets products offering claude.ai login to other users). The decision stands; the risk that Anthropic reads it the other way is on record. API-key / Bedrock / Vertex remain first-class on the same instance config.
- **Resume / fork**: `resume: <id>` (+ `forkSession: true`); transcripts under `$CLAUDE_CONFIG_DIR/projects/<encoded-cwd>/`; same-runner only (the alpha `sessionStore` mirror is not used in v1). `persistSession: false` for probes.
- **hercule-as-a-tool** *(2026-09-15, [#68](https://github.com/theagenticage/hercule/issues/68))*: `plugins: [{ type: "local", path: <runner storage>/claude-plugin }]` on every session. `settingSources: []` above still holds and the plugin loads independently of it: a plugin named by path is not discovered through a setting source. Verified live against CLI 2.1.272 - a session with no setting source at all read the plugin's `SKILL.md` and answered with a marker only that file carried.
- **Sharp edges**: the SDK's eight per-platform packages bundle a 196 MB CLI and are excluded from the build; single-shot `query()` throws after yielding an error result (wrap iteration); `env` replaces the subprocess env; MCP tools need explicit allow rules (`acceptEdits` does not auto-approve them); `AskUserQuestion` and `ExitPlanMode` are intercepted in `canUseTool` and mapped to `question` / `plan`.
- **Stability**: 0.x semver, weekly releases version-locked to the CLI, several breaking changes shipped. Pin the exact SDK version; the installed CLI floats above the floor (version policy in [./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12); treat CLI-version-gated behaviour as part of the adapter contract; keep the SDK entirely behind the adapter seam.

### 10.2 Codex (app server)

- **Transport**: spawn `codex app-server` (CLI from npm `@openai/codex` or the static-binary installer), newline-delimited JSON-RPC 2.0 over stdio with the `jsonrpc` field **omitted on the wire**; a thin Hercule-owned codec, not a strict JSON-RPC library. One `initialize` + `initialized` per connection; `capabilities.experimentalApi` stays off - the stable surface keeps deprecated fields for compatibility, the experimental surface promises nothing, and t3code's opting into experimental is prior art to avoid, not follow (pinned, [#43](https://github.com/theagenticage/hercule/issues/43)). WebSocket transport is explicitly unsupported.
- **Model**: Thread > Turn > Item maps 1:1 onto Session > Turn > Item. `thread/start` (`model`, `cwd`, `approvalPolicy`, `sandbox`, `ephemeral`), `thread/resume`, `thread/fork`, `turn/start` (per-turn `model`, `outputSchema`), `turn/steer`, `turn/interrupt`. Notifications `turn/started` -> `item/started` -> deltas -> `item/completed` -> `turn/completed`; usage via `thread/tokenUsage/updated`. Unknown notifications are ignored for forward compatibility.
- **Approvals**: server-to-client requests (section 8.1); the adapter implements every request handler even where the answer is always decline.
- **Subagents** *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)*: a collab agent is a child thread on the session's own app-server, and each child thread is a subagent (section 13.6). The adapter keeps its state per thread.
- **Process ownership**: ~~topology unpinned; suggested one app-server process per instance per runner (section 4.1).~~ Pinned below. Single-writer per thread; the server unloads idle unsubscribed threads after 30 minutes and emits `thread/closed` (maps to `session.exited`, resumable).
- **Process ownership, pinned** *(2026-09-14, [#73](https://github.com/theagenticage/hercule/issues/73))*: ~~one app-server host per provider instance on a runner, reference-counted over the sessions using it and shut down with its last one.~~ *(Amended 2026-09-30, recording what [#68](https://github.com/theagenticage/hercule/issues/68) built.)* One app-server per session, not per instance, killed when the session ends. The session token is in the environment the app-server was started with, and every shell command it runs inherits that environment. A shared host would run a second session's work under the first session's token, grants and actor stamp, and would stop working for both once the first token was revoked (section 9.3). So the auth refresh and the model catalog are per process too. A probe runs on a host of its own. A device-code login is an exception to the host's request/response rhythm: its completion is confirmed by a later probe rather than awaited, because Bun's HTTP server cuts an idle request at 10 seconds and the user needs longer than that in the browser. *(Amended 2026-10-02, [#313](https://github.com/theagenticage/hercule/issues/313).)* That later probe is no longer left to the user. When the login's child exits, or its code's 15 minutes run out, the runner sends `LoginEnded`, and the controller probes the instance on that runner at once and announces `provider` / `updated` ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2). `provider.login` answers a device-code login with `expiresAt` beside `userCode`. A client finishes the login by itself once a snapshot for that runner, probed after the login started, has `auth.status` `ok`, and shows the code as expired once `expiresAt` has passed. The web app has no "Done" button any more. A failed login is not told apart from one still waiting: a newer snapshot that is not `ok` may come from any probe, so the client waits until the login is done or the code expires.
- **Errors**: `-32001` overload -> retry with exponential backoff and jitter; mid-turn `error` notifications with `codexErrorInfo` feed `runtime.error { class }`.
- **Auth**: ChatGPT OAuth or API key via `account/*`; credentials in `$CODEX_HOME/auth.json` (file store default); tokens auto-refresh. `cli_auth_credentials_store` stays `file` on runners.
- **Stability**: no cross-version protocol guarantee. Pin the CLI release, generate types with `codex app-server generate-ts` for that release, regenerate and re-verify on every upgrade.

### 10.3 pi (standalone binary, RPC mode)

- **Hosting**: pi runs as its own executable - the official standalone Bun-compiled binary, installed per runner ([./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12) - one `pi --mode rpc` child process per session, LF-delimited JSONL over stdio. This supersedes the earlier SDK-in-a-child-host consolidation (decided 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)): an external binary keeps pi independently updatable like the other two harnesses, the RPC protocol is the contract instead of a pre-1.0 TypeScript API, and no pi code compiles into the Hercule binary. Launch: ~~`--mode rpc --no-context-files --no-extensions --no-skills --no-prompt-templates --no-themes --no-approve -e <hercule extension>`~~ `--mode rpc --no-extensions --no-skills --no-prompt-templates --no-themes --no-approve -e <hercule extension>`, `--session-dir` under the instance home, `--session-id` so Hercule picks the session id up front. *(Amended 2026-10-04, [#75](https://github.com/theagenticage/hercule/issues/75).)* A workspace-less session adds `--no-context-files`, as section 9.1 has said since [#307](https://github.com/theagenticage/hercule/issues/307), and a Thread with User Material adds the flags of section 9.1 User Material.
- **The Hercule extension file**: one TypeScript file materialized into the instance home at session start and loaded with `-e` (explicit paths load even under `--no-extensions`; jiti and typebox ship inside pi's binary, so the extension's imports resolve). It carries the two seams RPC lacks: the awaited `tool_call` hook for approvals (section 8.2: parks on `ctx.ui`, bridged as `extension_ui_request` / `extension_ui_response`) and the `submit_result` structured-output tool (`pi.registerTool`, ~~`terminate: true`~~; section 7). *(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* `terminate: true` is returned by the tool's execute result, not declared on the registration.
- **Surface**: `prompt` / `steer` / `follow_up` / `abort`; events `agent_start` .. `agent_settled`, `turn_*`, `message_*` deltas, `tool_execution_*`, compaction and retry events; `set_model`, `set_thinking_level`, `set_auto_compaction`; `get_session_stats` (tokens, cost, context usage). Sessions are tree-structured JSONL files under the instance dir; resume via `--session <id>`, fork via `--fork <id>` or in-process `fork {entryId}`.
- **Absent by design**: ~~subagents,~~ plan mode, MCP (verify). Declared, not emulated. *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)* pi has no subagents of its own, but Hercule's pi extension gives a session a subagent tool, so a pi session has subagents like the other two (section 13.6).
- **Auth**: multi-provider. The pinned v1 path is API-key auth - z.ai coding plan: provider `zai` (or `zai-coding-cn`), the key a `provider-instance` secret injected as `ZAI_API_KEY`. OAuth logins exist but are TUI-only (`/login`, no headless command); the fleet UI shows the copy-paste command as the fallback ([./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12). `auth.json` in the instance dir holds raw vendor tokens (plain file on every OS); Hercule never touches it. ## 11. Provider install portability and per-runner login

Installs are one command per provider (all three are self-contained binaries: Claude Code and Codex native, pi Bun-compiled) and are installed at runner join with a floor-pinned version policy ([ADR 0028](../adr/0028-provider-harnesses-are-runner-installed-executables.md), [./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12); credentials are not distributed. Per-runner login is the durable model: refresh-token rotation with reuse detection (documented for Codex, structurally identical in pi, undocumented for Claude) makes two live copies of one credential log each other out. Hercule therefore drives each provider's own headless login on the runner as a post-join step from the fleet UI ([./03-controller-and-runners.md](./03-controller-and-runners.md) §3.3), relaying the device code or login URL to the user's browser. The per-provider login flows are listed in [./15-packaging-and-operations.md](./15-packaging-and-operations.md) section 12. Copying a credential file remains a bootstrap shortcut owned by exactly one runner afterwards. All three vendors permit the user's own account on the user's own machines; prohibitions target sharing with other people. Credential posture: [./13-security.md](./13-security.md). Findings: `research/provider-portability.md` (branch `research/provider-portability`).

## 12. Cost and usage

v1 records, per session, every `session.usage.updated` snapshot and, per turn, `usage` and `costUsd` on `turn.completed` when the harness reports them: Claude `total_cost_usd`, pi `usage.cost.total`; Codex reports token usage but no cost (subscription plans), so `costUsd` is absent there. There is **no rate-table pricing in v1**: Hercule never multiplies tokens by a price list, and unpriced usage stays unpriced. `costUsd` is the slot a later cost dashboard reads; t3-code's transcript-scanning usage subsystem is the reference for that later work. *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)* The Session and Subagent records carry Token Usage and `costUsd` (section 6.6), and those records are what a later cost dashboard reads, never the usage events.

## 13. Subagents

*(Added 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); decided by [#350](https://github.com/theagenticage/hercule/issues/350), [#351](https://github.com/theagenticage/hercule/issues/351), [#352](https://github.com/theagenticage/hercule/issues/352), [#353](https://github.com/theagenticage/hercule/issues/353) and [#377](https://github.com/theagenticage/hercule/issues/377).)* A **Subagent** is an agent a session's harness delegated work to while the session runs ([CONTEXT.md](../../CONTEXT.md)). It is not a Session: it lives inside its session's process and settings, and is owned by its session the way a Turn is ([ADR 0038](../adr/0038-a-subagent-is-part-of-its-session-not-a-session.md); the record is in [./02-domain-model.md](./02-domain-model.md) Subagent). This section says how an adapter reports subagents, and what the user can do to them.

### 13.1 The one rule

**An event attributed to a subagent never changes the session's own state.** That covers the session's status, the Requests its own agent waits on, an assistant's reply ([./12-assistants.md](./12-assistants.md) section 9) and the session's turn notifications. Every place that reads the stream for the session's own state reads only the events with no `subagentId`:

- the controller's status and open-Request bookkeeping, the assistant observer, and the walk that finds an assistant's reply;
- the runner's supervisor, whose open turn and park become a set of open turns and a set of parks ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 6.2).

These readers change in the same build as the adapters. An adapter that sends subagent events to a controller that still reads every event as the main agent's would corrupt the session's state; that is why the runner protocol version goes up with this change ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2).

### 13.2 How a subagent appears in the stream

- **`subagent.started { subagentId, parentSubagentId?, itemId?, description?, agentType? }`** introduces a subagent, once per process, before any event of that subagent. `parentSubagentId` is the subagent that started it, absent when the session's own agent did. The event belongs to the parent, so it carries no attribution field of its own: it is stored in the parent's transcript, the one `parentSubagentId` names. `itemId` is the `subagent` item that started it in its parent's transcript. `description` is the short task name the parent gave it. *(Amended 2026-10-05, [#435](https://github.com/theagenticage/hercule/issues/435): the record's agentType needs a source.)* `agentType` is the harness's name for the kind of agent, which the record's `agentType` copies ([./02-domain-model.md](./02-domain-model.md) Subagent): Claude's `subagent_type` on the `Agent` call, Codex's role from `thread/read`.
- **The controller upserts the record** by `(session, subagentId)`. A field is filled when it is empty and never overwritten, so a resumed process that knows less never erases what an earlier one recorded. Two fields are filled at ingest when the event leaves them empty:
  - `itemId`, from the first `subagent` item whose `detail.subagentIds` lists the subagent. *(Amended 2026-10-05, [#435](https://github.com/theagenticage/hercule/issues/435).)* Every id an adapter lists in `detail.subagentIds` is a subagent it introduces with `subagent.started` in that process, before or after the item, so a listed subagent the controller has not heard of yet gets its record at the item's time and keeps the link when its introduction comes later;
  - `description`, from the first line of the input of the subagent's first turn: the brief its parent gave it.
- **There is no end event.** A subagent's status is computed from its turns (section 6.2): `running` while one is open, else the ending of its last turn, `completed`, `failed` or `stopped` (the turn's `interrupted`). A subagent the parent continues goes back to `running`.
- **An event from a subagent not yet introduced is held back,** bounded, and never handed to the session's own agent. Each adapter's bound is in section 13.6. When the bound is reached, the events are dropped with a `runtime.warning` that gives their count. Released events take the same path as any other, so a grandchild first named in a child's events is picked up.
- **On a resume,** `SessionSpec.continue.subagents` carries the session's known subagents, `{ subagentId, itemId }`, from the controller's records. The adapter seeds its map from it, so a subagent continued in the new process lands on its record. A fork carries none: a forked session starts with no subagents.
- **When the process exits,** any subagent turn still open is read as cut off, the same rule the main turn follows, and the record's `running` becomes `stopped`. No event is made up for it. A subagent never outlives its session's process.

### 13.3 Several open Requests

- **A session holds a list of open Requests,** each from its own asker: the session's own agent, or a subagent, named by the `subagentId` on its `request.opened`. The controller holds the list (`Session.openRequests`, [./02-domain-model.md](./02-domain-model.md) Session), so every surface sees the same Requests.
- **The runner never holds a Request back.** Every Request the harness asks is reported at once:
  - Claude parks are keyed by `toolUseID` (section 8.1), and a second `canUseTool` is no longer denied with "ask again";
  - pi no longer denies a second dialog;
  - Codex no longer queues a second request inside the runner, out of the user's sight.
- **The user answers any Request, in any order.** The respond operations are keyed by request id.
- **`allow_always` resolves only the Request it answers.** Other open Requests stay open, even when the new rule would cover them: Hercule does not know how the harness matches its rules, and guessing would answer for the user. A request the harness asks after the grant may never be asked at all.
- **A Request closes** when it is answered, when its own agent's turn ends, when its agent is stopped (a stop that cascades down from a parent included, section 13.4), or when the session exits. The main agent's turn ending closes only the main agent's Requests. `cancel` on an approval ends only the asking agent's turn.
- **Questions come from the session's own agent today.** Claude denies `AskUserQuestion` to every subagent, and Codex's `request_user_input` is root-only. Nothing in the shape stops a subagent's question.
- **"Waiting on you" means the list is not empty,** whoever asked. The session's status still follows its own agent only, so an `idle` session whose subagent asks is idle and waiting on you at once.

### 13.4 Stopping

- **`interrupt(sessionId, subagentId)` stops one subagent and every subagent below it.** The adapter stops each descendant itself, in any order, because no harness cascades reliably: Claude's `stopTask` stops a foreground child but not a background one, and Codex never cascades. Each stopped subagent ends `stopped`, and its Requests close as `cancel`. On Claude it is `stopTask(agentId)`, and the subagent cannot be continued afterwards. On Codex it is `turn/interrupt` on the child's thread; the parent may give the child work again later, which opens a new turn.
- **`interrupt(sessionId)` stops all work in the session:** the main agent's turn and every running subagent, even while the main agent is idle and only background subagents run.
  - Claude: `interrupt()` with the default options (no `perTaskStopAffordance`) already stops every subagent and its shells. The adapter keeps that default.
  - Codex: the root's `turn/interrupt` does not stop children. The adapter interrupts every child thread with an open turn, and interrupts at once a child turn that starts after the stop.
- **Known limit (Claude):** after a stop, the main model is never told that its background subagents were stopped, and it may go on believing one still runs. Two fixes were rejected: stopping each subagent with `stopTask` instead starts a new main turn per stop, so Stop would set the agent working again; and a note added to the model's next input is text the user never wrote.
- **A subagent takes no messages.** Hercule offers no way to message a subagent: Claude has no host route to one, and Codex V2 refuses it. The shape agreed before it was dropped is recorded in [#353](https://github.com/theagenticage/hercule/issues/353).

### 13.5 Token Usage per harness

The meaning is section 6.6's. Per harness:

- **Claude.** The session's snapshot is `result.modelUsage`, which already includes every subagent and compaction. A subagent's count is **exact or absent**. `task_notification.usage.total_tokens` is not what the subagent spent: it adds the last call's input to the output of every call. The candidate source is the sum of the subagent's own frames' `message.usage`, counting each `message.id` once. The Claude build probes whether the main agent's count plus its subagents' equals the growth of `modelUsage`. If it does not, a Claude subagent carries no count, and a screen shows it as not reported, never as 0. The session's count is exact either way. A subagent's `turn.completed` carries no `usage`, `costUsd` or `structuredResult`.
- **Codex.** Each thread counts alone, so the root's count leaves out its children. The adapter sends each child's count with its `subagentId`, and the session's snapshot as the root's count plus every child's. ~~Each thread is counted from the total it starts from in this process: on its first report, `total - last`. That one rule covers a resume, and a forked child, which probably starts at its parent's total; the Codex build probes a fork.~~ *(Amended 2026-10-05, [#435](https://github.com/theagenticage/hercule/issues/435).)* Each thread counts how much its `total` grows from one report to the next. Codex repeats an unchanged total after a cancelled call, a stream error or a compaction, so counting from the first report after a turn started would count a resumed thread's history whenever that first call is cancelled. The rules:
  - The report Codex sends right after a resume or a fork, before any turn starts, is the restored history. It sets where counting starts and counts nothing.
  - With no earlier report, counting starts from `total - last`: zero on a fresh thread, the parent's total on a forked child.
  - A repeated total adds nothing.
  - A total that went down adds nothing, and counting continues from the new total. Codex resets its total to zero when the context window overflows, and a snapshot never goes down (section 6.6).
- **pi.** The same meaning. How a child reports is the pi build's to decide.

### 13.6 Per provider

**Claude Code.**

- `forwardSubagentText: true`, sent in the `initialize` request. The CLI floor of section 10.1 already supports it.
- `task_started` and `task_notification` with `task_type: local_agent` are kept (section 6.7). A frame is mapped to its subagent through `parent_tool_use_id`, which names the original `Agent` call even for a continued run, to the agent id.
- A `task_started` for an agent with no open turn opens a turn for it, with an id the adapter mints. Its `prompt` is the turn's `user_message`; the subagent's own prompt frames are ignored, so nothing shows twice. A `task_started` for an agent whose turn is open does nothing. The adapter never reads a later `task_started` as a `SendMessage`: a subagent also wakes by itself when its background shell finishes.
- `task_notification` closes the turn: `completed`, `failed` or `stopped` becomes `completed`, `failed` or `interrupted`. One with no open turn is ignored (an orphan, or `worker_restart` on a resume).
- Subagent turns live in their own map, from agent id to turn id, and never touch the main turn's state or its stream maps, so a main agent streaming at the same time is undisturbed. Steering, interrupting and changing the model act on the main turn as before.
- A `canUseTool` call with `agentID` set never opens a main turn; its Request carries that agent's id. `system:permission_denied` is attributed to its `agent_id`.
- `SendMessage` is a `subagent` item. Its `subagentIds` is set only when `to` names a known subagent; `to` may be a name the `Agent` call gave it, which the adapter records.
- A frame whose `parent_tool_use_id` is unknown is held until the next `task_started` or `task_notification`, then dropped with a warning if it is still unknown.
- **Known limit:** `compact_boundary` and `api_retry` name no agent, so a subagent's compaction or retry is attributed to the main agent.

**Codex.**

- One app-server runs per session, so a thread other than the root is a subagent of the session: `subagentId` is its thread id, and its turn and item ids are native.
- The parent is the thread a V1 spawn `collabAgentToolCall` or a V2 `subAgentActivity` `started` is on, or `parentThreadId` from `thread/read`. The root maps to none. A V2 `completed` is never used to find the parent, because it lands on the initiating thread's old turn.
- The description is a V1 spawn's `prompt`, cut short. V2 has none, so it is `agentNickname`, or the last part of `agentPath`.
- The first event of an unknown thread starts a `thread/read` (parent, nickname, role; no experimental API needed). That thread's notifications and server requests wait in one queue, in arrival order, for the round trip. If the read fails, `subagent.started` goes out with no parent, and a warning.
- A child's approvals are Requests carrying its `subagentId` ([#362](https://github.com/theagenticage/hercule/issues/362) fixes the refusal that denied them silently). They arrive at the same time and can be answered in any order.
- Adapter and normalizer state are kept per thread. `thread/closed`, the tracked `turnId`, cancelling parks on `turn/completed`, the structured result, reasoning buffers and the model follow the root only. Each child has its own parks, and a child's `turn/completed` cancels only that child's.

**pi.** pi has no subagents of its own. Hercule's pi extension gives a session a subagent tool, and its children report with the event shape above. **Where a child runs is open** ([./16-open-items.md](./16-open-items.md) A): in pi's own process through its SDK, as a `pi --mode rpc` child the extension spawns, or as a child the runner spawns at the extension's request. The pi build decides it after a research step; it also forwards a child's approvals and questions, and stops one child. The facts so far are on [#351](https://github.com/theagenticage/hercule/issues/351) and in `docs/research/subagents-pi.md` (branch `research/subagents-pi`).

### 13.7 Limits and failure

- **Hercule sets no subagent limit in v1,** so each harness's defaults hold. Claude: 3 levels deep and 20 running at once. Codex 0.154.0: one level below the root and 6 children (V1), or 3 children (V2), from its own `[agents]` config, which the instance's `CODEX_HOME` leaves unset. A per-Agent limit later is additive: a field on the Agent, copied onto the session spec.
- **A failed subagent needs nothing new.** Its parent sees the failure as the result of its tool call, its record is `failed`, and its Requests are announced like any other.
- **A Hercule session another session spawns is not a subagent.** It would be a Session of its own with a link to the session that spawned it, left open here; a client could later list it beside the subagents by merging `session.querySubagents` with `session.query { actor }`.

## Post-v1

- Runner-side provider execution lifted into the provider plugin (v1: built-in, plugin-shaped).
- `readThread` / `rollbackThread` with the checkpoint/revert feature (v1 keeps fork and the normalized stream as the record).
- Plugin-contributed MCP tools through `SessionSpec.mcpServers` (v1 keeps the field).
- Rate-table cost pricing and a cost dashboard (v1 keeps `costUsd` and usage snapshots).
- Cross-runner session resumability via transcript mirroring (v1 pins sessions to their runner).
- Additional stream kinds (`reasoning_summary_text`, tool-argument streaming) and item kinds (review mode, image generation) as open-enum additions.
- Hercule-level OS sandboxing as a probed runner capability (ADR 0003).
- ACP-based adapters (Cursor and similar) need an extension-method seam beyond `sessionUpdate` mapping.
- **Reusing the user's existing local login, and moving logins between runners** - strongly wanted (noted 2026-09-01 by [Web app details](https://github.com/theagenticage/hercule/issues/45)): adopting the `claude` / `codex` / `pi` login already on the user's laptop instead of a fresh paste-a-code per instance, `claude setup-token` (one year, no rotation to race) as the Claude path, and Hercule shuffling tokens so a new runner needs no login at all; together with the instance-level "use my own binary and my own login" opt-in that skips home isolation (section 2.1 lists the binary half). The blocker to reopen is the refresh-token rotation fact from ticket #23; `setup-token` is why it may be solvable for Claude specifically.
