# Providers

A provider wraps one interactive coding harness (Claude Code via the Agent SDK, Codex via `codex app-server`, pi via its RPC mode) behind two surfaces: a **ProviderDefinition** on the controller (static self-description, registered by the provider plugin) and a **ProviderAdapter** on the runner (execution: ~~probe plus five session methods, one normalized event stream~~ the probe, install and login, six session methods with one normalized event stream, and a one-shot `generateText` for text generation, section 14 *(amended 2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282))*). The controller authors a `SessionSpec` that names ids, never paths; the runner resolves it and drives the adapter; the adapter normalizes vendor traffic into one event vocabulary at the runner, with a tagged raw passthrough. Degradation is declared, never silent: per-mode and per-feature support are pure facts on the definition, and the controller substitutes an unsupported access mode by a hardcoded, strictly downward fallback before the session starts. Rationale lives in [ADR 0007](../adr/0007-provider-adapter-is-a-thin-interface-behind-a-normalized-event-stream.md).

## 1. Shape

| Surface | Where | Registered by | Owns |
|---|---|---|---|
| ProviderDefinition | controller | provider plugin, into the `provider` extension point ([./05-plugins.md](./05-plugins.md)) | identity, config schema, declared capabilities |
| ProviderAdapter | runner | built-in runner code in v1, written plugin-shaped (one narrow interface per provider, no cross-provider leakage); lifted into the plugin post-v1 | probing, session execution, event normalization, text generation (section 14, *added 2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282)*) |

A **provider instance** is a definition plus decoded config (t3-code's driver/instance split). The instance id, not the provider id, is the routing key everywhere: snapshots, session specs, placement. `supportsMultipleInstances` providers get multi-account by config-dir isolation (one login per instance).

**Default instances exist from first run** (resolved 2026-09-01, [Web app details](https://github.com/theagenticage/hercule/issues/45)): the controller creates one provider instance per shipped provider plugin (Claude Code, Codex, pi) with default config - subscription auth, no overrides - named after the provider, so the first-session onboarding ([./14-web-app.md](./14-web-app.md) §Onboarding) can offer "Log in to Claude Code" without the user ever meeting the instance concept; a second instance appears only when they want a second account.

The runner never sees Hercule domain state and the controller never sees runner paths ([./03-controller-and-runners.md](./03-controller-and-runners.md), ADR 0002). Provider-native session state (transcripts, thread rollouts, session trees) lives on the runner's disk; the controller's normalized per-session stream ([./04-state-store.md](./04-state-store.md)) is the observable record.

## 2. ProviderDefinition and declared capabilities

```ts
interface ProviderDefinition {
  id: string                                  // "claude-code" | "codex" | "pi"
  displayName: string
  supportsMultipleInstances: boolean          // multi-account via config-dir isolation
  configSchema: Schema                        // per-instance logical settings, in Effect Schema: env, model defaults - never paths (§2.1)
  defaultConfig: unknown                      // a plain JSON value, not a function (2026-09-06)
  declared: DeclaredCapabilities              // static facts of the pinned adapter version
  suggestedTextGenerationModel?: string       // added 2026-10-11, #282: a small, cheap model slug for text generation (section 14)
}

interface DeclaredCapabilities {
  steering: "native" | "unsupported"          // unsupported degrades to queue
  fork: "native" | "unsupported"
  modelSwitch: "in-session" | "new-session"
  accessModes: Record<AccessMode, "native" | "unsupported">
  mcpPassthrough: "native" | "unsupported"    // pi: unsupported (2026-09-06)
  disallowedTools: "native" | "unsupported"   // Claude disallowedTools, pi excludeTools; Codex unsupported
  structuredOutput: "supported" | "unsupported"
}

type AccessMode = "approval-required" | "auto-accept-edits" | "auto" | "full-access"
```

Rules:

- Every value is a pure fact about the pinned adapter version. No value expresses a fallback; what an unsupported mode falls back to is controller policy (section 8.4). The earlier `asks-instead` value is withdrawn.
- ~~`steering: "unsupported"` means input sent to a busy session is queued by the controller instead (section 5); it never fails.~~ Steering is a guarantee of every session, not of the provider: `steering: "unsupported"` only changes how the controller keeps it. A steer on such a session interrupts the running turn and sends the input as the next turn (section 5) *(amended 2026-09-26, [#92](https://github.com/theagenticage/hercule/issues/92))*.
- `structuredOutput` is declared per [structured output research](https://github.com/theagenticage/hercule/issues/28): the mechanism differs per harness (section 7) but the graph sees one capability. A harness with no mechanism declares `unsupported`; the controller then rejects agent steps that declare an output schema on that provider at plan validation, never emulating with a closing prompt.
- The UI derives every affordance from declared facts plus policy, never from the provider name.

Declared values for the three v1 providers:

| Capability | Claude Code | Codex | pi |
|---|---|---|---|
| `steering` | native (stream-append into the running `query()`) | native (`turn/steer`) | native (`steer()`) |
| `fork` | native (`resume` + `forkSession: true`) | native (`thread/fork`) | native (`fork()`) |
| `modelSwitch` | in-session (`setModel()`) | in-session (per-turn `model` override on `turn/start`) | in-session (RPC `set_model`) |
| `accessModes` | all four native | all four native | approval-required, auto-accept-edits, full-access native; `auto` unsupported |
| `mcpPassthrough` | native (`mcpServers` option) | native (MCP servers, `mcpToolCall` items) | unsupported (2026-09-06, below) |
| `disallowedTools` | native (`disallowedTools`) | unsupported | native (`excludeTools`) |
| `structuredOutput` | supported (native `outputFormat`) | supported (native `outputSchema`) | supported (adapter-owned `submit_result` tool) |

*(Amended 2026-09-06, [#63](https://github.com/theagenticage/hercule/issues/63).)* The table gained the `disallowedTools` row, which the interface above has always declared and the table simply omitted, and pi's `mcpPassthrough` is settled. ~~**Verify at build time:** pi `mcpPassthrough` - the taxonomy matrix records no MCP support in pi; declare `unsupported` unless the pinned version has it.~~ Checked against pi 0.84.x/0.85.1: its README states "No MCP" and MCP is an extension rather than part of the core, so the pinned version passes nothing through and pi declares `mcpPassthrough: "unsupported"`. `excludeTools` and the `set_model` RPC are native, so `disallowedTools: "native"` and `modelSwitch: "in-session"` stand.

*(Amended 2026-09-06, [#63](https://github.com/theagenticage/hercule/issues/63).)* `configSchema` is an **Effect Schema**, like every other schema crossing the host API ([./05](./05-plugins.md) section 5), and the catalog persists the JSON Schema derived from it. `defaultConfig` reaches the host as a **plain JSON value**, not a function: the plugin calls its own default-building code and passes the result, because nothing that cannot be serialized crosses the host boundary ([./05](./05-plugins.md) section 3).

pi's `auto` is unsupported because `auto` means a harness-side reviewer judges routine actions; parking (section 8.2) fixes pi's approval mechanics but gives it no reviewer.

### 2.1 Instance config

`configSchema` covers, per instance, **logical settings only**: extra environment for the spawned process (API keys, `ANTHROPIC_BASE_URL`-style routing, `CLAUDE_CODE_USE_BEDROCK=1`), model defaults, and provider-specific options. It never holds paths. The runner derives both paths itself: the provider home is `<storage dir>/providers/<instanceId>/` under the runner's material state ([./15-packaging-and-operations.md](./15-packaging-and-operations.md)), and the binary is the runner-installed harness ([15 §12](./15-packaging-and-operations.md)); both reach the adapter on `ProviderRunnerContext` (section 4). Per-runner path overrides ("use my own `claude`") are post-v1. This resolves ticket 12's "binary path, config dir" wording against the no-runner-paths rule (ADR 0005): those two were the runner's to resolve all along (resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)). ~~The one path-shaped fact that does exist lives per instance × runner, not in instance config: `userMaterialDir` (§9.1 User Material), an opaque runner-scoped string stored beside the capability snapshot.~~ *(Amended 2026-10-04, [#75](https://github.com/theagenticage/hercule/issues/75).)* User Material stores no path either: the runner reads it from each harness's default install locations on its own machine (§9.1 User Material).

Instance config is validated against `configSchema` and stored on the controller; the runner receives the instance's config with each probe and session request. Secret-valued entries are `provider-instance`-owned rows in the secrets table ([./13-security.md](./13-security.md)): the controller decrypts them and sends them inline with each probe or session request over the runner WebSocket; they are held in memory for the operation and never land on runner disk (the same posture as git credentials, 13 §9). They are never logged and never returned by the API.

## 3. Capability snapshots

```ts
interface CapabilitySnapshot {
  instanceId: string; runnerId: string; probedAt: string
  declared: DeclaredCapabilities              // copied from the definition
  harnessVersion: string | null               // probed: claude --version, initialize.userAgent
  auth: { status: "ok" | "unauthenticated" | "error"
          identity?: string; planLabel?: string; backend?: string }
  models: ModelDescriptor[]
}

interface ModelDescriptor {
  slug: string; name: string
  isDefault?: boolean; isLegacy?: boolean
  imageInput: { maxBytes: number | null } | null  // required; added 2026-10-08, #465: section 3.3
  options: OptionDescriptor[]                 // select | boolean, with per-model choices and defaults
}

interface OptionDescriptor {                  // field names beyond kind/choices/default are not pinned
  id: string                                  // well-known ids below, or provider-specific
  label: string
  kind: "select" | "boolean"
  choices?: { value: string; label: string }[]
  default: string | boolean
}
```

### 3.1 Scope and cadence

- **Scope is instance x runner.** Harness binaries live on runners with potentially different versions, so catalogs, auth and capabilities differ per runner. The controller stores one snapshot per (instance, runner) in its DB. Harness version skew across the fleet is a surfaced fact, not an error (the hook for later fleet-managed harness updates).
- **The composer resolves the snapshot against the placement target.** Switching the target runner in the composer triggers an on-demand probe of that runner; the cached snapshot is shown meanwhile.
- **Cadence** (copied from t3-code): a background interval, demand-gated (probe only while something is watching), on instance config change, and on placement change.
- The probe runs on the runner through `ProviderAdapter.probe(config)`; the runner reports the `ProbeResult` as a runner fact over the runner protocol ([./03-controller-and-runners.md](./03-controller-and-runners.md)); the controller stamps `instanceId`, `runnerId`, `probedAt` and copies `declared` from the definition to form the snapshot.

### 3.2 Probing is side-effect-free

Discovery never creates, resumes, or mutates a provider conversation, and never reads credential files. Per provider:

| Provider | Probe |
|---|---|
| Claude Code | a throwaway SDK `query()` with **no prompt at all**, then `accountInfo()` and `supportedModels()` over the control protocol: account identity, subscription/plan label, `apiProvider` (first-party vs Bedrock etc.). The CLI version comes from `claude --version`. No API call is made. |
| Codex | `initialize` (user-agent carries the version) + `account/read` + `model/list` over a probe-only app-server process |
| pi | `pi auth check --provider <id> --json` per configured upstream provider; `pi --version` for the harness version |

`auth.status` is `unauthenticated` when the harness reports no usable login, `error` when the probe itself failed (binary missing, protocol error), `ok` otherwise. A provider instance with `auth.status !== "ok"` on a runner is filtered out of placement for that runner ([./03-controller-and-runners.md](./03-controller-and-runners.md)).

*(Corrected 2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64), against the real SDK 0.3.263 and CLI 2.1.263.)* The Claude row above described a probe that cannot work. The init message carries **no** identity; a prompt that never yields produces no init message at all; and a prompt that does yield makes a real `/v1/messages` call at the same instant as the init message, so a probe with one would bill the user's account for opening a Fleet page. `hooks: {}` does not disable hooks and `mcpServers: {}` does not strip MCP; what does the isolating is `settingSources: []` and `strictMcpConfig: true`. Even under `persistSession: false` the CLI writes `.claude.json`, `backups/` and `sessions/` into its config directory, which is why that directory is the instance's own and never the user's `~/.claude`. `HOME` is never overridden.

### 3.3 Catalog policy

Probe-first, curated overlay where introspection falls short:

- **Codex**: models, reasoning efforts and service tiers come fully probed from `model/list`.
- **Claude Code**: probed. *(Corrected 2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64).)* `supportedModels()` reports the CLI's own list with per-model option support (`supportsEffort`, `supportedEffortLevels`, `supportsFastMode`), so the catalog is the probed list plus a small hand-authored **legacy overlay** for slugs the CLI has stopped listing; a probed entry always wins. There are no per-model CLI-version gates: the CLI forwards any slug to the API unchanged, so which models it lists is the CLI's own gate, and an unlisted model keeps working for as long as Anthropic serves it.
- **pi**: models come from RPC `get_available_models` for the authenticated upstream providers, treated as probed.
- **Custom-model entries** are the user's escape hatch on every provider: a user-typed slug with no descriptor, rendered generically.

*(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* **`imageInput` is required on every model.** It is required so that every adapter must answer, and "unknown" never passes as yes. `null` means the model takes no images. Otherwise `maxBytes` is the largest image the harness takes, or `null` when it sets no limit below the controller's 10 MiB. The capability is per kind of input because harnesses declare it per modality and limits differ per kind; a later `documentInput` would sit beside it. Each adapter sets it in its probe:

- **Codex**: `{ maxBytes: null }` when the model's `inputModalities` includes `"image"`, else `null`. Every current Codex model reports `["text", "image"]`.
- **pi**: `{ maxBytes: 3.375 MiB }` when the model's `input` from `get_available_models` includes `"image"`, else `null` (section 10.3). pi reports no `"image"` for `glm-5.3`, so it is text-only.
- **Claude Code**: the CLI reports no such field, so the adapter declares `{ maxBytes: null }` for every model, each `LEGACY_MODELS` entry included. Every current Claude model accepts images.
- **Custom-model entries** have no descriptor, so a prompt with images on one fails closed: the controller refuses it because the model is not in the snapshot ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2).

The composer reads `imageInput` to disable Attach and refuse pasted or too-large images; the controller reads it to refuse input with images, or with an image over `maxBytes`, ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2).

**Well-known option ids** are documented conventions, not an enum: `effort`, `thinking`, `contextWindow`, `fastMode`. The composer renders dedicated controls for them and workflows can reference them portably across providers; unknown ids render generically from the descriptor. Reasoning effort is a per-model `effort` option: probed per model for Codex, curated per model for Claude.

## 4. ProviderAdapter

```ts
interface ProviderAdapter {
  providerId: string
  probe(config: InstanceConfig): Effect<ProbeResult>
  install?(env: Environment): Effect<InstallOutcome>                     // per machine, not per instance
  login?(ctx: ProviderRunnerContext, binary: string): LoginCommand      // the harness's own headless login
  generateText(ctx: ProviderRunnerContext, config: InstanceConfig, spec: TextGenerationSpec): Effect<TextGenerationOutcome>   // added 2026-10-11, #282: section 14; never fails
  startSession(spec: SessionSpec, ctx: ProviderRunnerContext): Effect<SessionBinding>
  sendInput(sessionId: string, input: TurnInput): Effect<SendResult>
  interrupt(sessionId: string, subagentId?: string): Effect<void>   // subagentId added 2026-10-05, #355: section 13.4
  respondToApprovalRequest(sessionId: string, requestId: string, decision: ApprovalDecision): Effect<void>   // was respondToRequest; renamed 2026-10-01, #309
  respondToQuestion(sessionId: string, requestId: string, answers: QuestionAnswers, modelSelection: ModelSelection): Effect<void, AnswerNotDelivered>   // added 2026-10-01, #309; can fail and takes the model, 2026-10-26, #770
  stopSession(sessionId: string): Effect<void>
  listSessions(): Effect<SessionBinding[]>    // reconciliation after runner restart
  events: Stream<ProviderEvent>               // the one output channel
}
// Effect-typed natively (ADR 0031): methods return Effects and `events` is a Stream, so session supervision,
// interruption and subprocess cleanup on the runner use Effect's structured concurrency directly.
// Vendor SDK boundaries (the Agent SDK's async generator, Codex stdio JSONL, pi's RPC) are wrapped at the edge.
// A promise-shaped facade is a post-v1 option if runner-side plugin loading wants one.

interface SessionSpec {                       // controller-authored - carries ids, never paths
  instanceId: string
  workspaceId: string | null                  // null = workspace-less session
  modelSelection: { model: string; options: Record<string, string | boolean> }
  accessMode: AccessMode                      // always a mode the target provider declares native
  systemPrompt?: string
  mcpServers?: McpServerConfig[]              // the decided passthrough field (#11)
  disallowedTools?: string[]                  // harness tool families to remove, Hercule vocabulary (rules below); copied from the Agent
  continue?: { nativeSessionId: string; mode: "resume" | "fork"; subagents?: { subagentId: string; itemId?: string; parentSubagentId?: string; lastUsageReport?: { source: string; payload: JsonValue } }[] }   // known subagents, parent links and saved provider reports: section 13.2
  outputSchema?: JsonSchema                   // structured result contract, section 7
}

interface ProviderRunnerContext {             // the facts the runner resolved for this session on this machine
  cwd: string | null                          // workspace or scratch dir; null only as the controller-side "no workspace" marker (§9.1)
  env: Record<string, string>                 // session env: HERCULE_*, GH_TOKEN (as set at start), GIT_CONFIG_*, PATH prepend with the `hercule` and `gh` shims (§9.3)
  home: string                                // this instance's provider home on this runner (CLAUDE_CONFIG_DIR / CODEX_HOME / PI_CODING_AGENT_DIR)
  binary: string                              // resolved harness binary path on this runner (§11)
  attachmentsDir: string | null               // added 2026-10-08, #465: this session's attachment cache, below; null outside a session
}

interface SendResult { turnId: string; delivery: "opened" | "steered" }

interface SessionBinding {
  sessionId: string                           // Hercule session id
  nativeSessionId: string                     // Claude session id | Codex thread id | pi session file id
  instanceId: string
}

type ApprovalDecision = "allow" | "allow_always" | "deny" | "cancel"
```

Rules:

- **No merged spec type.** `startSession` takes the controller-authored `SessionSpec` byte-for-byte (auditable, storable, comparable) plus a `ProviderRunnerContext` holding exactly the facts the runner resolved: cwd, session env, provider home, binary. Nothing here ever moves to `SessionSpec`. (Renamed from ticket 12's `RunnerContext`, 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43): the old name read as "facts about the runner", which it is not.)
- **Ids in, paths out.** The runner's session supervisor resolves `workspaceId` to a path and hands the adapter the context. The adapter never sees workspace ids; the controller never sees paths (runner paths are runner-owned opaque facts, ADR 0005).
- `accessMode` on the spec is post-fallback (section 8.4); adapters carry no fallback logic and may reject a mode they do not declare native as a programming error.
- `mcpServers` is the per-session MCP-config passthrough decided in [plugin architecture](https://github.com/theagenticage/hercule/issues/11): it carries self-injection and, later, plugin-contributed MCP tools. In v1 hercule-as-a-tool is the `hercule` CLI, not MCP ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)), so v1 core passes nothing here by default.
- `disallowedTools` names harness tool *families* in a small Hercule vocabulary (`edit`, `write`, `shell`, `web`, ...); the adapter owns the mapping to its harness's tool names and declares `disallowedTools: native | unsupported` in its capabilities. Unsupported is honest, not silent: the controller passes the field anyway, the adapter ignores it, and the UI shows "not enforced on <provider>" from the snapshot. The value is the Agent's `disallowedTools` copied at spawn ([./02-domain-model.md](./02-domain-model.md) rule 9); assistants default to `["edit"]` ([./12-assistants.md](./12-assistants.md) section 7). Resolved 2026-09-01, [Domain model residue](https://github.com/theagenticage/hercule/issues/46).
- `outputSchema` carries the agent step's declared schema ([./07-workflows.md](./07-workflows.md)); the adapter applies it by the provider's mechanism (section 7).
- **Deliberately absent:** `readThread` / `rollbackThread` (return with the checkpoint/revert feature; fork covers branching), a separate steer method, any queue surface, a mode-switch method (so a session's access mode locks at start; the composer shows it read-only, [./14-web-app.md](./14-web-app.md) §App shell, 2026-09-01).

*(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* The `disallowedTools` vocabulary is closed and is spelled ~~(`edit`, `write`, `shell`, `web`, ...)~~ `edit`, `write`, `shell`, `web-search`, `web-fetch`; a value outside those five is refused as `validation` rather than carried to an adapter that would have to guess at it. The mappings: Claude maps all five; pi maps `edit`, `write` and `shell` onto its own `edit`, `write` and `bash`, and has no web tool at all, so a web family is honoured by absence rather than dropped; Codex declares `disallowedTools: "unsupported"` and the reply says so. `mcpServers` is deferred to [#222](https://github.com/theagenticage/hercule/issues/222): v1 as shipped carries no such field on the Agent.

*(Amended 2026-09-10, [#67](https://github.com/theagenticage/hercule/issues/67).)* `stopSession(sessionId: string): Effect<void>` becomes `stopSession(sessionId, reason: ExitReason): Effect<void>`: the caller - a controller `SessionStop`, the runner's inactivity or absolute timer, or an announced shutdown - names why, and the adapter emits exactly that reason on `session.exited`. First reason wins where a session is stopped twice.

~~**Open:** `TurnInput` is pinned only as "the user input for one turn" (text). Whether it carries attachments or images in v1 is not decided.~~ *(Resolved 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* **`TurnInput` carries images as references.** `TurnInput.attachments?: AttachmentReference[]` lists the images of the turn in order, each `{ id, name, mimeType, sizeBytes, sha256 }`; the frame never carries bytes ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2). An input with images may have empty text.

- **The supervisor fetches, the adapter never does.** The runner's session supervisor fetches each image into the session's attachment cache before it calls `startSession` with a first input or `sendInput`. The adapter never talks to the controller.
- **The adapter receives local files, not references.** `sendInput` takes an `AdapterTurnInput`: the `TurnInput` with `attachments?: LocalAttachment[]` in place of the references, where a `LocalAttachment` is `AttachmentReference & { path }`: the reference as the frame carried it, plus `path`, which points at the cached copy. The wire type and the adapter's type stay separate.
- **`ProviderRunnerContext.attachmentsDir`** is the session's cache directory, `<runner storage>/attachments/<sessionId>/`. The session context resolver (`apps/runner/src/sessions/context.ts`) creates it before `startSession`. It is `null` in the contexts of a probe, an install and a login, which have no session and so no images. It is a field of the context because Claude Code's `--add-dir` is a spawn flag (section 10.1). It is never in the workspace, so git stays clean.
- **Each adapter maps the files to its harness's image input** (section 10) and adds one path line per image after the text, separated by a blank line: `[Attached image "image.png" is saved at: <path>]`. The line lets the agent use the file itself, for example to copy a screenshot into the repository. One shared helper, `appendAttachmentPaths`, writes the lines for all three adapters. The line is added only when the adapter sends the prompt: the stored input and the user's bubble keep the original text.
- ~~**An image over a harness's limit refuses the turn before anything is sent**, by the adapter.~~ *(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* **An image over the model's `imageInput.maxBytes` is refused by the controller**, when the input is created or updated, as `validation`, for example `"photo.png" is 4 MB; this model accepts images up to 3.375 MB. Send a smaller image or pick another model.` The rule: anything knowable before sending is checked before the input is accepted. The adapter checks no limit of its own. Only pi declares a limit (section 10.3); Claude Code and Codex rely on the controller's 10 MiB cap ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md) section 1.5).
- **No resizing in v1.** The client uploads the original bytes and the adapter hands those bytes to the harness. Claude Code and Codex shrink large images themselves, and pi resizes some (section 10.3).

*(Amended 2026-10-10, [#511](https://github.com/theagenticage/hercule/issues/511).)* **`TurnInput` names the agent that sent it.** `TurnInput.senderSessionId?` is the session whose agent sent the input, set by the controller only for a message from another session's agent ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2, which owns the rule and why no protocol version bump is needed).

- **The harness learns who sent it.** Each adapter puts one fixed line before the text the harness gets: `[Message from session <id>, another agent. To reply: hercule session input <id>]`. One shared runner helper builds the text the harness gets, this line and the attachment path lines included, for all three adapters. It names the id only, because the runner does not know session titles; the agent reads more with `hercule session read <id>`.
- **Only the harness gets the line**, like the attachment path lines: the stored input and the `user_message`'s `detail.text` keep the original text.
- **The `user_message` carries the sender** as `detail.senderSessionId` (section 6.3).

## 5. Steering and queued input

Steering is implicit in `sendInput`: a busy session steers (input folds into the running turn), an idle session opens a new turn. `SendResult.delivery` reports which happened and is the only authority; consumers never infer steering from event order. A steered input appears in the stream as `item user_message { steered: true }` inside the running turn.

Vendor mechanisms: Claude appends to the streaming input of the live `query()`; Codex calls `turn/steer` with `expectedTurnId`; pi calls `steer()`. When Codex rejects `turn/steer` because the turn just ended, the adapter opens a new turn with the same input and reports `opened` - input is delivered unconditionally, never bounced. *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* That fallback holds only when Codex refuses the steer with a JSON-RPC error that has a `code`, which proves it did not take the input (section 10.2). A failure with no `code` (a timeout, a lost connection, a failed write) fails the input and starts no turn. If `turn/steer` proves flaky, t3-code's approach (queue a `turn/start` and relabel it) is the documented fallback.

**The input queue is controller-owned domain state.** When the user or a workflow sends input to a busy session and steering is not wanted (or the provider declares `steering: "unsupported"`), the controller stores Queued Input and flushes it with `sendInput` on `turn.completed`. Queued input is editable and cancelable until flushed, except that the input a session starts with cannot be cancelled before the session starts: `input.cancel` refuses it `invalid_state` and says to stop the session instead, because that input is the session's only reason to start. While the session is `queued`, that input is its oldest waiting row and can still be edited; while it is `starting`, it is on the wire with the start and can be neither edited nor cancelled. An input the runner refused and put back to waiting is an ordinary waiting row and can be cancelled ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)) *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431))*; subscription deliveries to sessions arrive this way ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)). Vendor-native queues (Codex follow-up `turn/start`, pi `followUp()`) go unused: they are process-local and uneditable. The cost is sub-second flush latency over the runner WebSocket, riding the ordinary seq/ack + outbox protocol.

A delivery the runner refuses, or one nobody answers in time, puts the row back to `queued` with `sentAt` null and `reason` set, rather than ending it; it is sent again at the session's next transition to idle, steered by hand, or cancelled by the user. *(Amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431).)* A row can also be left waiting on an idle session, for example by a refused start input, which leaves the session idle with no turn to end. The controller's recurring delivery pass sends such a row: it sends the oldest waiting row of every idle session that has no row on the wire. Only the user, the session's exit, or a controller restart ends a row for good: exit cancels a row still waiting outright, and leaves a row already on the wire until its answer arrives, at which point that same answer is what ends it, recording why on `reason` rather than dropping it; a restart cancels a row still on the wire at that moment, a start's input included *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431))*, since whether the runner took it is unknown.

*(Amended 2026-10-05, [#83](https://github.com/theagenticage/hercule/issues/83).)* **An agent step's prompt is never sent again once it may have reached the harness.** A step prompt the runner refuses while the controller still waits for the answer goes back to `queued`, like any input. So does a step prompt the controller could not send because the runner had no connection: it never left the controller, and it is sent when the runner connects. A step prompt that gets no answer is not put back to `queued`. No answer means that a `SessionInput`'s deadline passed, or that the runner's connection ended first. A start has no deadline, so the end of the connection is the only way a start's prompt goes unanswered. The prompt moves to the status `sent`, keeps its `sentAt` as the lasting record that it left the controller, and gets no `reason`, because the status says it. A controller restart that finds a step prompt on the wire marks it `sent` the same way. So the statuses of an input are `queued`, `sent`, `delivered` and `cancelled`, and only a step prompt reaches `sent`. `sent` is final, except that a confirmation that arrives later still marks the row `delivered`. Sending the prompt again could run the step's turn twice, and that turn may push or comment. When no answer comes, the controller does not fail the step. It asks the runner for the step's result right away. If the runner has no connection, it asks when the runner connects. The runner handles that request only after every earlier frame of the step's session, so the request never overtakes the prompt ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2). The runner's answer settles the step:

- If the runner took the prompt, it answers with the step's result when the turn ends. A confirmation that arrives later marks the row `delivered`.
- A refusal that arrives later leaves the row `sent`, and the prompt is not sent again. The controller sends no second request: the runner ran no turn for the prompt, so it answers the waiting one `interrupted`, and the step fails from that answer.
- If the prompt never reached the runner, the runner answers `interrupted` too.

## 6. Normalized event taxonomy

Normalization happens at the runner, closest to the vendor protocol. Every event carries the base fields; every event may carry `raw` (the untouched vendor payload tagged with its source, e.g. `claude.sdk.message`, `codex.app-server.notification`, `pi.session.event`). Enums are open for consumers: unknown kinds render generically, never crash.

```ts
interface ProviderEventBase {
  eventId: string; sessionId: string; at: string
  turnId?: string; itemId?: string; requestId?: string
  providerRefs?: Record<string, string>       // native ids (thread id, item id, tool_use id ...)
  raw?: { source: string; payload: unknown }
}
```

*(Amended 2026-10-08, [#476](https://github.com/theagenticage/hercule/issues/476).)* **No event the runner sends is larger than one frame.** The runner's socket carries at most `MAX_FRAME_BYTES` (2 MiB) per message, and the controller closes the socket on a bigger one, which would end the stream of every session on that runner ([./13-security.md](./13-security.md) section 1). Adapters already truncate the fields the protocol bounds (section 6.5), but `raw`, the native ids in `providerRefs`, an item's `detail`, a `content.delta` and a turn's structured result have no bound of their own: a Claude `Read` of a large image puts its bytes in `detail` and again in `raw`. So the runner's supervisor checks every event before it numbers it, and shrinks one that would not fit, in this order, stopping as soon as it fits:

1. It drops `raw`. This overrides "every event may carry `raw`" above for an oversized event: its `raw` is not untouched but gone.
2. It splits a `content.delta` into consecutive deltas, each of which fits. The stream is append-only, so nothing is lost.
3. It drops the `detail` of an `item.started` or `item.completed`.
4. It replaces the `structuredResult` of a `turn.completed` with a `schema-failure` whose reason gives the result's size and the limit, so an agent step fails with a reason instead of never finishing (section 7).
5. It drops `providerRefs`.
6. It drops the event. Every field left on a `turn.completed` or a `session.exited` after step 5 is bounded, so neither reaches this step: a turn or a session left open would never end.

*(Added 2026-10-14, [#665](https://github.com/theagenticage/hercule/issues/665).)* Step 3 keeps an `item.completed`'s `editedFiles`, the edited files Edit Overlaps count ([./19-agent-coordination.md](./19-agent-coordination.md) section 4.1). That field is bounded (256 paths of at most 1,024 characters), so such an event never reaches step 6.

Whenever something is left out, the runner sends a `runtime.warning` right after the event, on the same turn and subagent, that says in plain words what the event was, its size, the limit and what was left out, with the item's id at the end, for example "A tool call result was 4.03 MiB, too large to send (the limit is 2 MiB), so its output and raw data were left out. Item toolu_01." The loss is never silent: the warning is stored in the transcript like any other event, and the desktop draws it in the thread (spec 17). A step's result frame is held to the same limit by its own failure code, `output_too_large` ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2). Image tool results by reference ([#478](https://github.com/theagenticage/hercule/issues/478)) remove the most likely trigger; this rule is the guard for every other oversized event.

*(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); decided by [#351](https://github.com/theagenticage/hercule/issues/351) and [#377](https://github.com/theagenticage/hercule/issues/377).)* **An event names the subagent it belongs to.** `turn.started`, `turn.completed`, `item.started`, `item.updated`, `item.completed`, `content.delta`, `request.opened`, `request.resolved`, `session.usage.updated`, `runtime.warning` and `runtime.error` carry an optional `subagentId`: the harness's own id for the subagent whose event it is. Absent means the session's own agent. `session.started` and `session.exited` never carry it. One more event, `subagent.started`, introduces a subagent before any of its events. Section 13 owns both.

### 6.4 Streaming

`content.delta { itemId, streamKind: "assistant_text" | "reasoning_text" | "command_output", delta }`

- Deltas are append-only text per (item, streamKind). Where the vendor sends cumulative snapshots (pi `tool_execution_update.partialResult`), the adapter diffs by common prefix before emitting.
- `command_output` deltas exist only where the harness streams them (Codex `outputDelta`, pi); on Claude the output arrives whole on `item.completed`. Degradation, not distortion.
- **Reasoning-summary precedence rule**: where a vendor streams raw and summarized reasoning as separate channels (Codex `item/reasoning/textDelta` and `summaryTextDelta`), the adapter picks one channel per reasoning item, raw preferred, and emits it as `reasoning_text`; the unpicked channel stays raw-only. No fourth stream kind (`reasoning_summary_text` remains an additive option later).
- *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* **A completed assistant message that streamed no text still shows its text.** Codex writes some messages in one piece (an async question, section 6.5), so their text arrives only inside `item/completed`, and a client builds a message's text from deltas. When an `agentMessage` completes with text and no non-empty `assistant_text` delta came for that item, the Codex adapter emits the text as one `content.delta` before `item.completed`. A message that streamed is never emitted again, and a repeated `item/completed` for an item adds nothing.
- The store coalesces deltas in memory and flushes at message/turn boundaries; nothing is persisted per token ([./04-state-store.md](./04-state-store.md)). Watched sessions receive an ephemeral token-delta passthrough ([./14-web-app.md](./14-web-app.md)).

An answered question resolves with its answers, never with a substituted `allow`. A decision goes in the frame `sessionRespondToApprovalRequest`.
- **The adapter maps the answers back to the harness.** `apps/runner/src/providers/questions.ts` finds each header's key in the harness's own input, with the parser that built the request, so a header or a question truncated in the request still leads back to the untruncated key. Claude Code gets `canUseTool`'s `{ behavior: "allow", updatedInput: { ...input, answers } }`, keyed by each question's full text, a list joined with `", "`. Codex gets the reply `{ answers: { <question id>: { answers: [...] } } }`, a string as a one-item list, and its turn goes on.
- **A repeated header is numbered:** the second "Approach" is shown as "Approach (2)". Answers come back keyed by header, so two questions showing one header could not both be answered, and Claude Code checks only that question texts are unique.
- **What cannot be answered is dropped when the request is built:** a question with no key in the harness's input (its full text on Claude, its id on Codex), because its answer could not be sent back; a question whose key repeats an earlier question's, because the harness reads one answer per key; and an option whose label repeats an earlier option's, because a picked option is sent back as its label. A Codex question with `options: null` is a question with no options, answered with text.
- **A secret question is kept, with a warning.** A Codex question with `isSecret: true` is marked `secret`. Nothing hides or protects its answer, so the dock says so before the user types: the answer is stored in the thread like any other.
- **pi raises no question.** pi has no built-in tool that asks the user, and the one extension a pi session runs is Hercule's own, which asks only `confirm`. [#316](https://github.com/theagenticage/hercule/issues/316) gives a pi session a tool that asks.
- **The answers to one request hold at most `MAX_ANSWERS_LENGTH` characters, headers included** (four messages' worth), so a full set of answers always fits the 2 MiB frame.

Codex offers the tool to the root agent only, so an async item of a subagent opens no Request and the session gets a `runtime.warning`. An async item opens a Request only when it belongs to the root agent's current turn and that turn was not stopped. Any other item (a late item of an ended, stopped or replaced turn) opens nothing, and its id is remembered, so it never opens later either.
  - *Shape.* `question` is the whole title, cut to the protocol's bound. `header` is "Question", or "Question 1" to "Question n" when there are several. Options are bare labels (an empty label and a repeated label are dropped). `options: null` is a question with no options, answered with text. `multiSelect` is false.
  - *The answer* is one ordinary text input holding Codex's reply envelope (the format of Codex 0.163, which the Codex terminal sends): `<send_user_message_question_reply>`, a JSON array with one entry per question, then `</send_user_message_question_reply>`. An entry is `{ answer, question, questionItemId }`. `answer` is the picked label or the typed text, with a list joined by ", ". `question` is the original title, cut to 512 UTF-8 bytes, with line breaks replaced by spaces. `questionItemId` is the JSON text of `["request_user_input_async", <native item id>, <question index>]`. The question closes when Codex has taken the input. A second answer while one is on its way is refused. If the question was closed while the answer was on its way and Codex then took it, the transcript shows the answer and no second `request.resolved` is reported.
  - *The transcript* shows the answer once, as a `user_message`, the way the Codex terminal shows it: for each question `> <question>`, a blank line and the answer, with a blank line between questions. `<question>` is the same flattened text the envelope carries (line breaks replaced by spaces, cut to 512 UTF-8 bytes), so a title cannot end the quote. The envelope is never shown.
  - *Stopping* the session's own agent cancels its async questions, including one whose answer is on its way (that answer then fails as *Closed* above if Codex did not take it). Cancelling a root approval ends the root's turn, so it closes them as an interrupt of the root does. Stopping a subagent, or cancelling a subagent's approval, leaves them.

### 6.6 Usage and ops

- `session.usage.updated { ... }` - a cumulative token snapshot for the session, taken from Claude `context_usage`, Codex `thread/tokenUsage/updated` and pi `message_end.usage`. Cadence differs per harness; the snapshot shape absorbs that. The field set is below.
- `runtime.warning` - retries (Claude `api_retry`, pi `auto_retry_*`), model rerouting or drift mid-turn, mirror errors, and an event the runner shrank or dropped because it was larger than a frame (section 6, amended 2026-10-08, [#476](https://github.com/theagenticage/hercule/issues/476)).
- `runtime.error { class }` - Codex `codexErrorInfo` is the reference class enum (`ContextWindowExceeded`, `UsageLimitExceeded`, `Unauthorized`, `SandboxError`, ...); other adapters map to the same classes where they can, else `unknown`.

~~**Open:** the exact field set of the `session.usage.updated` snapshot is not pinned beyond "token snapshot plus context usage".~~ *(Resolved 2026-09-07, [#65](https://github.com/theagenticage/hercule/issues/65).)* The snapshot is `{ inputTokens, outputTokens, cacheReadTokens?, cacheWriteTokens?, costUsd? }`, cumulative for the session, with the three optional fields present only where the harness reports them. Context usage against the model's window is **not** in the v1 shape: no consumer reads it yet, and the assistant rotation threshold (section 9.2) adds the field it needs when it ships, rather than the shape carrying a number nothing checks.

*(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); decided by [#377](https://github.com/theagenticage/hercule/issues/377).)* **Usage events feed Token Usage on the records,** and screens read only the records ([GLOSSARY.md](../../GLOSSARY.md) Token Usage). The snapshot keeps its shape, the protocol's `Usage`, with three changes:

- **It counts since this process started,** ~~cumulative for the session~~, for one agent: the session's own agent, or the subagent its `subagentId` names. The controller adds each process's count to the record's running total, so a record holds the whole life of the session and never goes down, not on a resume and not on a compaction. For example, a session spends 50k tokens, exits, resumes and spends 20k more: the adapter reports 20k, and the record says 70k.
- **The four parts never overlap.** `inputTokens` is input not read from cache, `cacheReadTokens` and `cacheWriteTokens` are the cache reads and writes, and `outputTokens` is the output. The tokens used are their sum. An adapter whose harness counts cached reads inside its input subtracts them ([#428](https://github.com/theagenticage/hercule/issues/428) fixes the Codex adapter).
- **A snapshot with no `subagentId` covers the session's own agent and every subagent.** One with a `subagentId` covers that subagent alone. The adapter does the adding where the harness counts each agent apart (Codex), so the controller never knows which harness counts how. Section 13.5 says how, per harness.

`costUsd` follows the same rules where the harness reports a cost.

*(Amended 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)* Token Usage can be incomplete when a required historical baseline cannot be restored or discovery drops events. `session.usage.updated` has two exclusive forms: the existing exact `{ usage: Usage }`, or `{ usageReport: { status: "incomplete", counts: Usage } }` with no `usage`. The controller derives each record's `usageReport: { status: "complete" | "incomplete", counts }` from these process reports. Counts remain monotonic known subtotals; once an interval is missing, the lifetime report stays incomplete across resumes. The legacy record field `usage` is present only for a complete report. Screens show incomplete counts with an incomplete label and never reuse an earlier exact count. Missing reports remain absent, distinct from a reported zero.

| Provider | Mechanism | Result location | Failure signal |
|---|---|---|---|
| Claude Code | `outputFormat: { type: "json_schema", schema }` on `query()`; SDK validates and re-prompts | `structured_output` on the final `result` message | `subtype: "error_max_structured_output_retries"`, or `success` with no `structured_output` (treated as failure per SDK docs) |
| Codex | `outputSchema` on `turn/start` (stable, not experimental-gated); enforced server-side as strict constrained decoding | text of the turn's final `agentMessage` item | turn `failed`, or turn completed with a final item that is not an `agentMessage` (missing output; ~~the adapter may retry with a fresh `turn/start`, default once~~) |

*(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* Four corrections: three to the pi row, from building it against pi 0.85.1, and one to the Codex row. **Where the args come from:** a call's arguments are carried on `tool_execution_start` and on nothing else, so the adapter captures them there and reads them when the matching `tool_execution_end` arrives; the end frame alone would answer the turn with nothing. **Where `terminate` lives:** it is a field of the tool's execute result, returned by the call, not a field of the registration - the same in section 10.3's extension-file paragraph. **Two bounds on the failure signal, one per harness**, both named in `apps/runner/src/providers/pi/adapter.ts` - `MAX_REPROMPTS` for the re-prompts and `MAX_REFUSED_ANSWERS` for the refused answers. pi stops asking after three answers pi's own argument validation refused: a model argues with the validator indefinitely on a schema no value can satisfy, so the settle the re-prompt bound waits for never comes; the adapter ends pi's run and reports the last answer's schema-failure on a `completed` turn. On Codex the API refuses an unsatisfiable schema before any sampling happens - `invalid_json_schema` on `response_format 'codex_output_schema'` - and the adapter reports that as a schema-failure carrying the API's own sentence, on a `failed` turn. **No retry on Codex:** the Codex row's struck clause promised a fresh `turn/start` after a turn that ended without a value, and the adapter as shipped never retries - a turn that answered nothing is reported as a schema-failure at once, because the one failure seen live is the API refusing the schema, which a second identical `turn/start` would only be refused for again.

Normalized outcome, carried as `structuredResult` on `turn.completed` when the session has an `outputSchema`:

```ts
type StructuredResult =
  | { outcome: "ok"; value: unknown }
  | { outcome: "schema-failure"; reason: string }   // validation/retries exhausted, tool never called
// ordinary run failure = turn.completed { state: "failed" } with no structuredResult
```

The runner re-validates `value` against the declared schema before routing, on every provider (cheap, catches harness regressions, one uniform error surface). *(Amended 2026-09-19, [#76](https://github.com/theagenticage/hercule/issues/76).)* More precisely: the runner re-validates `value` against the declared schema on every provider before it reports `ok`, whatever the harness claims about having validated it already, so `ok` means one thing everywhere. `outputSchema` lives on `SessionSpec` only, and the adapter applies it to **every turn** of that session by the provider's mechanism (Codex re-sends it on each `turn/start`, Claude on each `query()`, pi's extension registers the tool at session start). `TurnInput` never carries it. This works because a session belongs to exactly one agent step and the schema is that step's: iterations re-enter the same session and each yields its own `structuredResult` ([Workflow execution semantics](https://github.com/theagenticage/hercule/issues/36)).

## 8. Access modes

`AccessMode` is the session-level permission axis the adapter enforces, ordered `approval-required < auto-accept-edits < auto < full-access`. Meaning: approval-required asks for every side-effecting action; auto-accept-edits allows file edits, asks for the rest; auto lets a harness-side reviewer judge routine actions; full-access allows everything.

### 8.2 Park-and-resume build caveats

From `research/pi-approval-parking.md` (branch `research/pi-approval-parking`), binding for the pi adapter and analogous for Claude:

- **Race the parked decision against `ctx.signal`.** pi's `abort()` only flips the AbortController; the loop checks it after the handler resolves. The handler returns promptly on abort so `interrupt` passes through a parked approval.
- **A park serializes the tool batch**: preflights run sequentially and sibling calls wait for all preflights. Same shape as Claude; accepted.
- **Handler exceptions deny fail-safe**: wrap the wait so an IPC failure produces a clear deny reason, never a silent allow.
- **No contractual guarantee** (pre-1.0): pin the pi version and ship a regression test asserting that a pending `tool_call` handler delays execution.
- **The park is bridged in-band over RPC**: the Hercule extension's `tool_call` handler blocks on `ctx.ui`, which RPC mode surfaces as an `extension_ui_request` on stdout; the adapter answers with `extension_ui_response` when ~~`respondToRequest`~~ `respondToApprovalRequest` *(amended 2026-10-01, [#309](https://github.com/theagenticage/hercule/issues/309))* arrives. No side channel.
- *(Added 2026-10-10, [#516](https://github.com/theagenticage/hercule/issues/516).)* **The approval card describes the call pi will run.** pi validates and converts a call's arguments after `tool_execution_start` and before the `tool_call` hook, so the arguments on `tool_execution_start` can differ from what runs: a `write` whose `path` the model sent as the number `42` writes the file `42`. The hook's dialog message is the JSON `{ toolCallId, toolName, command?, path? }`, where `command` and `path` come from the hook's validated `event.input` and are present only when they are strings. The adapter finds the call's item by `toolCallId` and builds the card's command or paths from the message, never from `tool_execution_start`. The rest of the input stays out of the message, because a `write`'s content can be megabytes and the message is one RPC frame.
- While parked no LLM connection is held open; the turn stays active; `tool_execution_start` has already fired, so the UI overlays "awaiting approval" on the started item.
- On Claude, `canUseTool` is reached only when the pipeline falls through to a prompt; auto-approved tools never hit it. That is the intended behaviour for the mapped modes. *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* In `full-access` the callback is passed, and only a question and a call that always needs approval fall through to it (section 8.1); the question is the reason it is there. A `PreToolUse` hook is the seam if every call must be observed. In `approval-required`, which actions are asked about is the harness's own judgement: Claude Code decides read-only shell itself, so only mutating commands park - `ls -la` ran without the callback being called at all, while `touch proof.txt` parked *(observed 2026-09-14, [#70](https://github.com/theagenticage/hercule/issues/70), CLI 2.1.270)*.

### 8.3 Codex sandbox caveats

Sandboxing is enforced by Codex (Seatbelt on macOS, bubblewrap on Linux; WSL1 unsupported). `thread/shellCommand` and `process/spawn` bypass it entirely; the adapter never calls them. `thread/start` with `workspace-write` marks the cwd trusted in the instance's `config.toml`; with `CODEX_HOME` isolated per instance (section 9) this touches no user config.

### 8.4 Fallback policy

- The definition declares support per mode; the controller resolves any unsupported mode to a supported one **before session start**. `SessionSpec.accessMode` therefore always names a natively supported mode and adapters carry no fallback logic.
- The fallback chain is **hardcoded in v1**, not configurable, and **strictly downward** on `approval-required < auto-accept-edits < auto < full-access`: the substitute is the nearest less-permissive supported mode. Shipped result: `auto -> auto-accept-edits` (auto always allows edits, so ask-everything was overly punitive). If no equal-or-less-permissive supported mode exists, session start fails with a clear error. Guardrail owned by [./13-security.md](./13-security.md).
- The UI keeps every mode selectable and annotates the substitution from declaration plus policy ("runs as Auto-accept edits on this provider", by the mode's name, [./14-web-app.md](./14-web-app.md), amended 2026-09-30). The Session record stores both `requestedAccessMode` and the effective `accessMode` ([./02-domain-model.md](./02-domain-model.md)); the fallback chain is stated in ADR 0007 and the glossary ([../../GLOSSARY.md](../../GLOSSARY.md)) as amended.

*(Amended 2026-10-03, [#310](https://github.com/theagenticage/hercule/issues/310).)* Before it adds the variables above, the runner removes every `HERCULE_*` variable it inherited from its own environment, the same way it removes git's own variables (`GIT_*`, `SSH_ASKPASS`).

- **Why.** Those variables configure the runner itself. The controller starts the local runner with `HERCULE_HOME` set to its own Home, usually the user's live one, so a `hercule serve` an agent ran in a session without `--home` would open the live database. Others, such as `HERCULE_BIND_PORT` or `HERCULE_DATA_DIR`, change what any `hercule` command in the session does.
- **Nothing in a session needs them.** The CLI authenticates with `HERCULE_API_URL` and `HERCULE_TOKEN`, and the git credential helper reads only variables the runner sets.
- **Every child of the runner loses them.** A repository's setup command and a workspace action step start from the same environment as a session.
- **The default Home.** Without `HERCULE_HOME`, a `hercule` command falls back to `~/.hercule`. When the session's controller runs on a scratch Home, for example while an agent tests Threads or an end-to-end run is live, that default is the user's live Home. So `HERCULE_SESSION=1` gets a second effect: the commands [15 §5](./15-packaging-and-operations.md) lists refuse the default Home and ask for `--home` or `HERCULE_HOME`.
- **Instance config still applies.** Instance config `env` (section 2.1) is applied after the removal, so a `HERCULE_*` variable the user sets there still reaches the session. The variables this section lists are set after instance config, so it cannot replace them.
- **Not sessions.** Probes, logins and installs still run with the runner's own environment (section 10.1).

Until then, the #75 skill links of section 9.1 remain. *(Amended 2026-10-18, #733.)* Built for Claude; ~~Codex and pi still use the #75 links until #734.~~ *(Amended 2026-10-18, [#734](https://github.com/theagenticage/hercule/issues/734).)* Built for Codex and pi too. Every Thread on every harness gets its skills from the library, and no #75 skill link remains.

*(Amended 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768).)* A session's skills are two parts: its **library skills**, which "Who gets what" and "Delivery" below describe, and its **repository skills**, the skills in the checkouts of its workspace ("Repository skills" below). The library part is saved per session. The repository part is read live from the runner.

#### Who gets what

One controller function, `decideSessionSkills(session)`, decides a session's skill list. Today:

- A Thread (`agentId: null`) gets the current revision of every Skill, on every runner, not only the controller's local runner. A Skill whose `currentRevisionHash` is `null` exists only as a proposed Skill Revision and is skipped.
- Assistant sessions and workflow agent steps get none. They stay isolated, as section 9.1 says. Naming skills per Agent or per step is [#737](https://github.com/theagenticage/hercule/issues/737). *(Amended 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768): "none" means no library skills. A session with a workspace of any kind still gets its repository skills, below.)*
- The list never holds the built-in `hercule` skill. The runner always adds that one itself, as section 9.3 says (pi does not get it yet, [#199](https://github.com/theagenticage/hercule/issues/199)).

The controller calls the function again at every start, fork and resume (a fork is a new session and gets a fresh frame, as section 9.1 says), so a resumed or forked Thread picks up library changes. A running session keeps the set it started with. The list names the session's own skills, never "the library", so #737 can later give sessions different sets without changing the runner.

#### Repository skills

*(Added 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768), [#743](https://github.com/theagenticage/hercule/issues/743).)* A **Repository Skill** is a skill folder in a checkout of a session's workspace: `.agents/skills/<name>/` or `.claude/skills/<name>/`, holding a `SKILL.md` in the Agent Skills format. It is a file of the project, and it is not in the Skill Library. The sessions that get one, the harnesses that load one, and the name it has are the same everywhere.

- **Who gets them.** Every session with a workspace, of any kind and on any runner, at every start and resume. They come from the checkout, so they are the same on every runner. A checkout is untrusted input, so the runner offers a skill only after the checks below, and "Known gaps" lists what a harness can still load that the runner did not offer. A session without a workspace has none. `decideSessionSkills` does not decide them, and the start frame does not carry them: the runner reads them from its own disk.
- **The checkout name.** A repository skill is named `<checkout>:<name>`, such as `hercule:release`. `<checkout>` is the checkout's subdirectory in the workspace, or, for a checkout at the workspace root, the repository name from its remote. The runner converts it to the Agent Skills name rule (`formatCheckoutName` in `@hercule/protocol`): lower case, every run of other characters becomes one hyphen, hyphens at both ends are trimmed, and the result is cut to 64 characters. `My_Repo` becomes `my-repo`. A library skill keeps its plain name. A library skill and a repository skill with the same name are both listed. A checkout in a multi-checkout workspace is never in a folder called `.claude` or `.agents` (or `.git`), in any letter case: the harnesses read those folders from the session's directory, which is the workspace root, and a clone with such a name would put a repository's settings, hooks and skills there as the session's own ([03 section 6.3](./03-controller-and-runners.md)).
- **What is listed.** The runner lists the folders live from the checkouts (`listRepositorySkills` in `apps/runner/src/skills/repository.ts`). It copies nothing and keeps no state, so a skill added to a checkout appears in the next listing. One listing function serves a start, an inspection of an existing workspace and a preview of one that does not exist yet, so the three cannot disagree. In each checkout `.agents/skills` is read before `.claude/skills`: when both hold a folder of the same name, the `.agents/skills` one is listed and the other is skipped. One real folder is one skill: a folder reached twice, such as through a `.claude/skills` link to `.agents/skills`, is listed once. The listing holds at most 256 skills and at most 256 skipped entries (`MAX_REPOSITORY_SKILLS`), and each reason is at most 512 characters (`MAX_SKIPPED_REASON_LENGTH`). `truncated: true` means the runner left an entry out at a cap: the 256 skills, the 256 skipped entries, or the walk budget below. The runner stops listing once both lists are full and an entry was left out. A client then gets an `incompleteReason` sentence ([11 section 2](./11-public-api-and-agent-surface.md)). The runner answers within 9 seconds of the request (`LISTING_TIMEOUT`), just under the 10 seconds the controller waits, and the wait for one of its 4 permits counts toward them. It answers `failed` with "reading the workspace's skill folders took longer than 9 seconds" when the listing ran past that, or with "the runner is still busy reading skill folders for earlier requests; try again in a moment" when no permit came in time ([03 section 2.2](./03-controller-and-runners.md)). The `path` of a skill and of a skipped entry is relative to the workspace root, with `/` between folders: `web/.agents/skills/release` for a checkout in the `web` folder, `.agents/skills/release` for a checkout at the root. A skill has no checkout id: the answer names its checkout by `checkoutName` only.
- **Links and containment.** A checkout is untrusted input, because a repository can commit a link to any place on the runner's disk, such as the user's own `~/.claude/skills`. The runner follows a link only while the target stays inside the checkout: `.claude/skills` pointing at `.agents/skills` is common and works. One function (`resolveWithinCheckout` in `apps/runner/src/skills/files.ts`) resolves every path of a checkout, and it never looks at a place outside the checkout. It follows a path one component at a time, and looks at a component only when the folder before it is already a real folder (no link in its path) inside the checkout. A link's target is read as text and joined to that folder, then walked the same way. The path is refused when:
  - a link has an absolute target ("goes through a link with an absolute target; use a relative link"), because it is only right on the machine that wrote it;
  - a link's target, or a `..` in the path, leaves the checkout ("leads outside its checkout"). This includes a target that climbs above the checkout and comes back in, such as one that names the checkout's folder in another letter case;
  - the path goes through more than 40 links ("goes through more than 40 links"), the same limit as the `ELOOP` error. This also ends a link loop;
  - the path continues past a file ("goes through `plain`, which is not a folder"). A file system cannot open `plain/../x`, `plain/x` or `plain/`, so the runner does not shorten them to `x`.

  The runner looks again at every folder and link it read from a listing before it enters it, with the same function. A folder entry is not trusted as a real folder: it may have become a link out of the checkout since the listing read it.

  The reason names the folder it is about, such as "`.claude/skills` leads outside its checkout". The walk checks two levels.
  - **The three paths to a skill.** The skills folder, the skill folder and the `SKILL.md` must each resolve to a place inside the checkout, and the `SKILL.md` must be a regular file. The runner opens the file without waiting, so a named pipe called `SKILL.md` cannot block the listing. It stages the real folder it checked, not the link, so the link cannot be changed between the check and the use.
  - **Inside the skill folder.** The runner walks each accepted skill folder (`findSkillFolderProblem` in `apps/runner/src/skills/skill-folder.ts`), because a harness does not load only the `SKILL.md` it is pointed at. Codex scans an extra skills root recursively and follows links, so it would also load a skill nested in an accepted one, and every skill behind a link inside the folder. The skill is skipped when the walk finds:
    - a link that `resolveWithinCheckout` refuses (an absolute target, more than 40 links, or a way out of the checkout), or a link that cannot be followed because its target is missing or cannot be read;
    - a file or folder named `SKILL.md`, in any letter case, anywhere below the top level of the skill folder, because a harness would load it as a second skill;
    - more than 1000 files and folders (`MAX_SKILL_FOLDER_ENTRIES`, the skill's own `SKILL.md` included), or folders nested more than 8 levels deep (`MAX_SKILL_FOLDER_DEPTH`), counted from the skill folder, so the walk is bounded.

    All the walks of one listing share one budget of 10,000 entries (`MAX_LISTING_ENTRIES`), counted over every checkout and skill folder, so many large skill folders, or links that lead many skills to one large folder, cannot keep the runner reading. The runner reads every folder one entry at a time, and spends one entry of the budget for each one it reads, plain files and the entries of the top-level skills folders included. It also spends one for each path component it looks at, which is one more for every skill folder and every folder inside it, and more for a link. A folder of any size therefore costs at most the budget, even one with millions of entries. Once the budget is used up, the folder the listing stopped at and everything after it are skipped with one reason, and the answer has `truncated: true`.

    The skill's own top-level `SKILL.md` is not checked for links or for being a second skill, but it counts toward the 1000 entries. Links that stay inside the checkout are followed, as the harness follows them. A folder reached twice is read once, which also ends a link loop. "Twice" means the same folder in the file system (its device and inode numbers), not the same spelling of its path: on a file system that ignores letter case, `demo` and `DEMO` are one folder. Every harness gets the same rule, so a skill means the same on each of them.
- **What is skipped.** A folder the runner cannot offer is skipped with a reason. A skipped folder is never an error. The runner logs one line for each when a session starts, and the inspection and preview answers return them as `skipped` ([03 section 2.2](./03-controller-and-runners.md)). The controller passes them on, so `session.querySkills` and `session.previewSkills` show each skipped folder with its reason. The reasons:
  - the folder name is not a valid Agent Skills name: 1 to 64 characters of `a-z`, `0-9` and hyphens, with no hyphen at either end and no two in a row;
  - the folder has no `SKILL.md`, or its frontmatter is missing or is not valid YAML;
  - the frontmatter `name` is not text, such as `name: 123` (Claude Code would load that skill as `123`, while the runner lists it under its folder name);
  - the frontmatter `name` is text that differs from the folder name, because the harnesses name a skill by its frontmatter `name`, and the Agent Skills format requires the two to be equal;
  - the description is missing, longer than 1024 characters, or holds a control character. Tab, line feed and carriage return are allowed, because a description written as a YAML block has line breaks;
  - the folder cannot be read;
  - the path to the skills folder, the skill folder or the `SKILL.md` leads outside the checkout, goes through a link with an absolute target, goes through more than 40 links, or goes through a file as if it were a folder, or the `SKILL.md` is not a regular file;
  - the skill folder holds a link that leads outside the checkout, has an absolute target, goes through more than 40 links or cannot be followed, a nested `SKILL.md`, or more than the bounds above allow;
  - the listing's walk budget of 10,000 entries was used up before the runner reached the folder;
  - an entry in a skills folder is a link to a file, not to a folder, and its name is a valid skill name;
  - the folder has a name that an earlier folder of the checkout already has;
  - every folder of a checkout whose name converts to nothing, or equals the name of another checkout in the workspace;
  - every folder past the 256th skill of the workspace;
  - a checkout with no folder to read, or whose folder cannot be read. In a preview this is a repo with no ready main workspace on the runner. The checkout is one skipped entry, named by its subdirectory (`.` for the workspace root), and it still takes its checkout name.

  Two kinds of entry in a skills folder are dropped without a `skipped` entry: a plain file, and a link to a file whose name is not a valid skill name. Neither can be a skill. The runner still reads them, so each one spends an entry of the walk budget, and a skills folder with a very large number of them ends the listing at the budget (`truncated: true`). Nothing else is dropped without a trace, except entries left out at a cap, which set `truncated`.

  A reason names the folder by its path from the workspace root and quotes at most 64 characters of any name the repository chose. It has no control characters, and it holds no absolute path of the runner.
- **Staged per start.** At every start and resume the runner stages the listed skills in the start's session skills folder, one Claude plugin folder for each checkout that has skills: `repositories/<checkout>/`, holding `.claude-plugin/plugin.json`, whose name is `repo-<checkout>`, and `skills/<name>`, a symbolic link to the skill's folder in the checkout. They are links because a repository skill belongs to its checkout, so an edit through the link is the project's own edit. The `repo-` prefix keeps the plugin name apart from the `hercule` and `skills` plugins of the runner, because a repository can be called `hercule` or `skills`. The folder is removed with the rest of the session skills folder.
- **Reading a session's skills.** `session.querySkills` and `session.previewSkills` ([11 section 2](./11-public-api-and-agent-surface.md), `hercule session skill list` and `hercule session skill preview`) return both parts for a client, with the skipped folders and the reason the list may be incomplete. The library part is the one saved in `sessions.library_skills` when the controller claimed the session's start, so a Skill added to the library later is absent until the session is resumed. The exception is a session whose start is still queued, a queued resume included: it lists today's library, because that is what its start will carry. The repository part is read live from the runner, through the controller's request to it.
  - For a session, the controller sends an inspect frame that names the session's workspace.
  - For a draft Thread, `session.previewSkills` takes a runner together with repos, or neither (one without the other is refused with `validation`, [11 section 2](./11-public-api-and-agent-surface.md)). With neither, it answers with the Skill Library's skills alone, with their descriptions and without any Skill that has no current revision, as a real start would carry them, and no frame goes to a runner. With both, the controller runs the checks a spawn makes on the repos, finds each repo's ready main workspace on the runner (or none), and sends one preview frame with a `{ remote, subdirectory, workspaceId }` entry per repo ([03 section 2.2](./03-controller-and-runners.md)). The runner lists the planned workspace with the listing function above, so the checkout names, the clash rule, the caps and the paths are the ones a real start gets. The controller prefixes no path and resolves no clash.
  - The runner reads at most 4 inspections, previews or starts at a time, and answers within 9 seconds of the request, the wait for a permit included ([03 section 2.2](./03-controller-and-runners.md)).

  A repository part that cannot be read never fails the call: the answer says why, and still lists the library part.
- **The root boundary.** A session whose working directory is the workspace root, which is when the workspace has no checkout or several, gets an empty regular file named `.git` in the root at every start and resume, unless the root already has a `.git` of any kind (`ensureRootBoundary` in `apps/runner/src/workspaces/root-boundary.ts`).
  - Why. Claude looks for `.claude/` folders in its working directory and in every folder above it, and stops only at a folder with a `.git` entry. A root with none lets the search reach the user's home, so the session would load the user's own skills, commands and agents ([#369](https://github.com/theagenticage/hercule/issues/369)). Section 9.1 has the gap this closes.
  - Why an empty file. A file with no bytes holds no history, so removing it can never lose work. Creating it is one atomic call (`wx`), so two sessions starting in the same root together cannot undo each other. No git process runs, and the root is not made a repository. A root that already has a `.git`, such as a checkout at the root, is never touched. The checkouts under the root are repositories of their own and are not affected.
  - Disposal. Disposing a workspace removes the `.git` of its root only when it is exactly this empty file, and does not count it as a file that blocks cleanup. A `.git` that is a directory or holds any bytes is kept and blocks cleanup like any other root file ([03 section 6.7](./03-controller-and-runners.md)).
  - Failure. When the file cannot be created, for example when the root is not writable, the start is refused: "The runner could not prepare the workspace folder for the session: `<reason>`. The Thread did not start." The reason names the error code and never a path.
  - Checked on a real Claude Code, Codex and pi. With the file, Claude loads none of the skills in a fake user home above the root. Codex reads the file as a broken gitfile and still starts, lists its skills and finishes a turn without a warning. pi starts and leaves the user's skill and instructions out.

The adapters are the only place harness syntax lives (composer rule 2 below).

A bare `/implement` resolves to `skills:implement` when no other skill has that name. The checkouts are listed besides the cwd because Claude Code loads nested `.claude/skills` folders: when a tool reads or edits a file, Claude loads the `.claude/skills` of every directory between that file and the cwd. With several checkouts the cwd is the workspace root, above all of them, so without the checkouts' folders the first read in `web/` would load `web/.claude/skills` by itself. The names of all these folders are merged into one list. An entry turns off only the skill with exactly that name, so each skill lists once, by its folder name. Claude keys a native skill by its folder name, not by the `name` in its `SKILL.md`: for a folder `foo` whose frontmatter says `name: bar`, the entry is `foo`, and an entry `bar` does nothing. Checked on CLI 2.1.302. It keeps folders and links, ignores plain files, and reads nothing inside any folder. It follows a `.claude/skills` that is a link to a place outside the checkout, as Claude does. This is on purpose: the names in such a folder are exactly the skills that would otherwise leak into the session ([#369](https://github.com/theagenticage/hercule/issues/369)), and the names are only used to turn skills off. A `.claude/skills` that is missing or cannot be read gives no names. All the folders share one budget of 10,000 entries (`MAX_LISTING_ENTRIES`), separate from the budget of the repository listing, and every entry counts, plain files included. The read runs under the same 4 permits and the same 9 second limit as the repository listing ([03 section 2.2](./03-controller-and-runners.md)). When the budget is spent, the read takes longer than 9 seconds, or no permit comes in time, the start is refused, because overrides that miss a name would leave that skill turned on. The message is "The runner could not turn off the skills Claude would load natively from `.claude/skills`: `<reason>`. The Thread did not start." The reason is one of: "the workspace's `.claude/skills` folders hold more than 10000 entries in all, plain files included. Keep them to 10000 entries or fewer", "reading the workspace's skill folders took longer than 9 seconds", or "the runner is still busy reading skill folders for earlier requests; try again in a moment". **The settings file.** The overrides hold at most 10,000 names. Passed inline they would still become one command-line argument, which can pass the operating system's limit (128 KiB on Linux), and on macOS a very large inline value was ignored. So when there are overrides, the adapter writes the settings, the fixed ones and the overrides, to `claude-settings.json` in the session skills folder and passes the file's path as the `settings` option. The file is not called `settings.json`, which Claude would read as a setting of the plugin when the folder is also the library skills plugin. The runner removes the file with the folder when the session exits. Without overrides the settings stay inline. A file that cannot be written refuses the start. **The read rule.** The adapter allows `Read(<session skills folder>/**)` whenever the session skills folder exists, which is for every session that has library or repository skills. A skill may tell the agent to read its other files, and a library skill's files are in that folder, while a repository skill's folder is linked into it. The rule lets the agent read there without asking the user and allows nothing else: unlike `additionalDirectories`, it does not let an `acceptEdits` session write there unasked. Claude matches the rule against the resolved path of the file, not the path the agent typed. A link that leads out of the session skills folder is therefore not covered: a read through it goes to `canUseTool` and asks the user, and nothing is read unasked. Checked on the real Claude CLI with a mock API: a read of `<session skills folder>/repo-x/skills/deploy/refs/secret.txt`, where `refs` links outside the checkout, asked for approval and leaked nothing, and a plain file in the folder was read without asking. So the rule does not depend on the containment check above. It matters for library skills. The files of a repository skill are also inside the checkouts, which are in the session's working directory, so Claude can read them without the rule. |

#### Composer rules

These rules hold for the desktop composer ([#743](https://github.com/theagenticage/hercule/issues/743), [#769](https://github.com/theagenticage/hercule/issues/769)) and for anything else that names a skill.

1. **One name per skill everywhere.** The `skills:` prefix, and the `repo-` prefix of a repository skill's plugin, exist only inside the Claude adapter. The user, the API and the screens then see one name for a skill, whatever the harness.
2. ~~**Harness syntax lives only in the adapter.** A skill reference is `{ type: "skill", name }`. The Claude adapter renders it as `/skills:<name>`, the Codex adapter as `{ type: "skill", name, path }`, and the pi adapter in pi's own form. A harness can then change its syntax without the rest of Hercule changing.~~ *(Amended 2026-10-19, [#769](https://github.com/theagenticage/hercule/issues/769).)* **Harness syntax lives only in the adapter, and a message names a skill with a Skill Reference.** A Skill Reference is the text token `$<name>` for a library skill and `$<checkout>:<name>` for a repository skill. No structured part travels in the API: `session.input`, `Input` and `TurnInput` carry text, so the CLI and an agent write `$review` as plain text, and the controller never reads the text for references. Each adapter translates the references of an input into its harness's own form. A harness can then change its syntax without the rest of Hercule changing.
   - **The grammar** is one module in `@hercule/protocol` (`findSkillReferences` and `isSkillReferencePrefix`), which the desktop composer, the desktop transcript and the runner all use, so they cannot disagree.
     - A token is `$` followed by a name that starts with an ASCII letter or digit and continues with letters, digits, `-` and `:` (`[A-Za-z0-9][A-Za-z0-9:-]*`). Each part of the name, the checkout and the skill that `:` separates, must hold at least one letter. A skill and a checkout may start with a digit, so `$3d-modeling` and `$3d:release` are references. `$20`, `$1.50` and `$2024` are text.
     - It counts only at the start of the text or right after whitespace. `x$foo` is not a reference.
     - A trailing `:` or `-` is not part of the name: in `run $review: now` the token is `$review`, and the `:` is text. An inner `:` or `-` is part of the name (`$webshop:release-checklist`).
     - A token inside Markdown code is not a reference, because the transcript draws that code as code. That is an inline code span, a fenced code block and an indented code block (four spaces or a tab, after a blank line or at the start of the text), as CommonMark defines them. A fence or an indented block inside a block quote (`>`) or a list item is code too. An inline code span pairs only inside one paragraph: a blank line, a heading, a thematic break, a fence or a new list item ends it, and a lazy continuation line, which CommonMark counts as part of the paragraph, does not. The module scans lines for this in linear time and is not a Markdown parser, so it does not model everything CommonMark does:
       - containers nested more than 10 deep are not followed;
       - raw HTML and link syntax are read as plain text, so a backtick inside a link destination or an HTML block can still pair with one outside it. A message with such Markdown may get a reference the transcript draws as code, or lose one it draws as text.
     - A path such as `/tmp/x` is not a reference: `/` is not a reference sign.
   - **Resolution.** The grammar only finds tokens. For each input the runner keeps the tokens that name a skill the session's process loaded when it started: the library skills of the start and the repository skills the runner staged for it. A token that names no loaded skill stays text, and so does one for a repository skill added to a checkout after the start. The runner resolves each input once, and every adapter translates the same references.
   - **Recording.** The runner records the names it translated on the `user_message` item as `detail.skills`: each name once, in order of first appearance, without the `$`. The key is absent when it translated none. A client draws a chip only for a name in `detail.skills` ([17](./17-desktop-app.md)).
   - **Values that a workflow template inserts are escaped** *(decided by Rogier, 2026-10-19)*. An agent step's prompt can hold text from outside, such as `CI said: {{ steps.checks.output.payload.summary }}` or the body of a pull request. If that text held `$webshop:release`, the runner would start the skill as if the user had asked for it. So the controller renders the prompt with `renderInputTemplate`, which passes the text of each inserted value through `escapeSkillReferences` (`@hercule/protocol`, beside the grammar): the `$` of each Skill Reference gets a backslash in front, so `$review` becomes `\$review`. A `$` after a backslash does not follow whitespace, so the grammar finds no reference in it, and the transcript draws `\$review` as the text `$review`. The rule is exact, because it uses the grammar itself:
     - Only references are escaped. `$20`, a `$` inside code and text without a reference are not changed. A value that is not a string is inserted as JSON, and the JSON is escaped the same way, so a `\$` in it is no longer valid JSON.
     - The text the template's author wrote keeps its references: `$review {{ inputs.note }}` still starts `review`.
     - A reference that has any text of an inserted value in it is escaped too, so `$webshop:{{ inputs.skill }}` cannot let a value pick the skill. The author's own reference is then plain text as well.
     - The only template whose result becomes an input is an agent step's `prompt`. The other templates do not reach a session: the params of an action step go to the action, and the `instructions` and `input` of a text generation step go to a one-shot model call that loads no skills ([07 §5](./07-workflows.md)). The text of a matched event is not built from a template; the next bullet covers it.
     - This protects the harnesses whose references the runner translates, Claude Code and pi. It does not stop Codex (Known gaps, "Codex finds `$name` itself").
   - **The text of a matched event is escaped too** *(decided by Rogier, 2026-10-19)*. A session-held Subscription delivers an event as input text (`renderEventInput`, [08 section 7.2](./08-events-and-connections.md)): a first line with the event's kind, subject title and URL, then the payload as JSON in a fenced code block. The title is written by someone outside, such as the author of an issue, so an issue titled `$webshop:release` would start that skill. The controller passes the whole text through `escapeSkillReferences`, so the title shows as `\$webshop:release` and starts nothing. The JSON block does not change: a fenced block holds no references, and the JSON is one line, so no value can end the fence early.
   - **Text that people type is not escaped.** A message from a chat user to an assistant, a message in a Thread, and an agent's own input to a session can name a skill. Only text that the controller inserts from outside is escaped.
   - **The mapping.** Each adapter turns a reference into its harness's own form:

   | Harness | `$<name>` (library skill) | `$<checkout>:<name>` (repository skill) |
   |---|---|---|
   | Claude Code | `/skills:<name>` | `/repo-<checkout>:<name>` |
   | Codex | a `skill` item whose `path` is the skill's `SKILL.md` | the same, with the path in the checkout |
   | pi | `/skill:<name>`, or a pointer line (below) | `/skill:<name>`, or a pointer line (below) |

   - **Claude.** The last reference of the text becomes the slash command that runs the skill, and the message is sent as parts.
     - The command is the Claude name above, then a space and the text after the reference without its leading whitespace. It is sent as the last text part of the message, after any images, because Claude runs a command only from the start of the last text part.
     - The leading text part holds the sender header when another session's agent sent the input, the text before the last reference, and the line for each image. Each earlier reference in that text is replaced by its Claude name. Claude does not run those: the model runs one only if it chooses to call that skill. The leading part is left out when it is empty.
     - **Steering.** Claude does not run a slash command that is pushed into a running turn: it holds the message and runs it as the next turn, so the skill would start late. The adapter therefore refuses a steer whose input has a reference. It refuses before it changes anything, so the input stays queued and runs when the turn ends, as section 5 describes for a delivery the runner refuses. The runner answers with this message, which the controller keeps as the row's `reason`, and it reports no `runtime.error`, so the thread gets no error line. The user sees it under the queued input: "Not steered: Claude can't start a skill in the middle of a turn. The input stays queued and runs when this turn ends."
       - **Codex refuses a steer with a skill in the same way,** with "Codex" in place of "Claude" in the message. Its app server accepts the `skill` item on `turn/steer` but does not load the skill: the model gets the text and never the skill's body (checked on Codex 0.163.0; the same item on `turn/start` does load it). Steering it would record a skill, and draw its chip, for a skill that never ran. An input whose references all get no item (the skill folder is gone) carries no skill, so it steers as any other.
       - **pi steers an input with skills as it steers any other.** pi expands a leading `/skill:<name>` on a steer as it does on a prompt: both go through the same expansion in pi's session code (checked on pi 1.3.0).
   - **Codex.** The input has the text item and the image items as before, then one `{ type: "skill", name, path }` item for each distinct skill.
     - `name` is the bare skill name (`release` for `$webshop:release`).
     - `path` is the real path of the skill's `SKILL.md`, with symbolic links resolved, because Codex compares it with the path `skills/list` reports and does not resolve links itself. The item, not the name, tells a library skill and a repository skill of the same name apart.
     - The text keeps `$name` as typed.
     - A skill whose folder no longer exists gets no item.
   - **pi** *(decided by Rogier, 2026-10-19)*. pi expands a skill itself only when the message starts with `/skill:<name> `. pi has no skill tool: its system prompt lists the skills and tells the model to read a skill's file when a task calls for it. So an input is translated in two ways, and Hercule never pastes the body of a `SKILL.md` into a message.
     - The first reference whose skill pi runs natively leads the message as `/skill:<name> `, with its token removed from the text together with the spaces around it. The sender header, the text and the image lines follow.
     - A skill pi runs natively is one that did not lose a name collision. pi keeps the first skill of a name, so the winner is the skill in the first folder, in the order of the `--skill` arguments (the library's folder, then each checkout's in checkout order), that holds `skills/<name>`.
     - Every other distinct skill gets one pointer line after the image lines: `[Skill "$<reference>" is at <folder>/SKILL.md. Read it with the read tool and follow it.]`, where `<reference>` is the reference as typed and `<folder>` is the skill's real folder. A skill that lost a collision is reached this way too, by its own path.
     - A second token of the leading skill stays in the text and gets no pointer, because pi already expanded that skill. The `$name` tokens of the pointed skills stay in the text as typed.
     - With no reference that pi runs natively, there is no `/skill:` command and every skill is a pointer line.
     - pi expands a leading `/skill:` in a steering message as well, so pi never refuses a steer.
3. ~~**The skills slices do not touch message text.** Rewriting what the user typed would change their message without telling them.~~ *(Amended 2026-10-19, [#769](https://github.com/theagenticage/hercule/issues/769).)* **The stored text is never rewritten.** Rewriting what the user typed would change their message without telling them. The text of an input, the `user_message` item and the transcript keep the `$name` as typed, and only what the harness receives is translated. The only record of a translation is `detail.skills`.
4. ~~**One controller function decides a session's skill list:** `decideSessionSkills`. It fills the start frame and will feed autocomplete, so the composer can never offer a skill the session does not have.~~ *(Amended 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768), [#743](https://github.com/theagenticage/hercule/issues/743).)* **A session's skill list has two parts, and one operation returns both.**
   - `decideSessionSkills` decides the library part, fills the start frame, and the controller saves what it decided for the session. ## 10. Per-provider build notes

### 10.1 Claude Code (Agent SDK)

- **Surface**: `query()` async generator of typed `SDKMessage` plus the `Query` control object (`interrupt`, `setPermissionMode`, `setModel`, `streamInput`, `getContextUsage`, `close`). One long-lived `query()` per session in streaming-input mode (required for the control methods and for steering); `includePartialMessages: true` for deltas. Session id on the init message and every `result`.
- **Process**: each session is one Claude Code CLI subprocess, about 1 GiB RAM as a starting point, memory growing over long sessions; no built-in timeout, no per-subagent deadline. The runner's supervisor owns deadlines and recycling; `maxConcurrentSessions` derives from RAM (~1 session per 2 GiB, [./03-controller-and-runners.md](./03-controller-and-runners.md)). Subagent caps via `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` / `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and `maxBudgetUsd`. *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)* Hercule sets none of them in v1, so the harness defaults hold (section 13.7).
- **Binary**: `pathToClaudeCodeExecutable` points at the runner-installed `claude` (`ctx.binary`; the SDK spawns it without a shell). - **Probe** *(2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64))*: `query({ prompt: <an input stream that closes at once>, options: { pathToClaudeCodeExecutable: ctx.binary, settingSources: [], strictMcpConfig: true, persistSession: false, env } })`, then `accountInfo()` and `supportedModels()`, then close, under a 15 s deadline. `env` is the runner's own with `CLAUDE_CONFIG_DIR` set to the instance home and `DISABLE_AUTOUPDATER=1`; `HOME` is untouched. - **Login** *(2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64))*: `claude auth login` with stdin piped, `CLAUDE_CONFIG_DIR` set to the instance home and `BROWSER` set to a command that exits non-zero. The decision stands; the risk that Anthropic reads it the other way is on record. API-key / Bedrock / Vertex remain first-class on the same instance config.

- **Sharp edges**: the SDK's eight per-platform packages bundle a 196 MB CLI and are excluded from the build; single-shot `query()` throws after yielding an error result (wrap iteration); `env` replaces the subprocess env; MCP tools need explicit allow rules (`acceptEdits` does not auto-approve them); `AskUserQuestion` and `ExitPlanMode` are intercepted in `canUseTool` and mapped to `question` / `plan`.

Pin the exact SDK version; the installed CLI floats above the floor (version policy in [./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12); treat CLI-version-gated behaviour as part of the adapter contract; keep the SDK entirely behind the adapter seam.
- **Images in tool results** *(Amended 2026-10-10, [#478](https://github.com/theagenticage/hercule/issues/478).)* A tool result can carry an image's bytes, often twice: a `Read` of a PNG puts an image block in the `tool_result` block's `content`, and the user message's `tool_use_result`, the tool's structured output, repeats the bytes. Before the message is normalized, the adapter finds images by shape in those two places, uploads each distinct image once, and replaces it with its `ToolResultImage` (section 6.3). These shapes are an image:
  - `{ type: "image", source: { type: "base64", data, media_type } }`, the Messages API's image block;
  - `{ type: "image", data, mimeType }`, MCP's image block, as in an MCP tool's `structuredContent`;
  - `{ type: "resource", resource: { blob, mimeType } }`, MCP's embedded resource. With no `mimeType`, which MCP allows, the blob's first bytes decide;
  - `{ base64, type }`, the `file` of a `Read` of an image, and `{ image_data, media_type }`, a cell output's image in a `Read` of a notebook. Only that field is replaced;
  - a `data:image/...;base64,` URL anywhere in text, with or without media type parameters such as `;charset=utf-8` (unquoted MIME tokens, as in RFC 2397), as a `Bash` command that prints an image keeps it in `stdout`. Only the base64 is replaced; the text around it stays.

  A shape counts only when it is an image's, by its declared media type in any letter case, so a PDF, an audio clip or another blob is left as it is. An image the controller does not store, such as a BMP, is uploaded, refused and becomes `unavailable`. The user's own images in a prompt are in neither place, so they are never taken for a tool's. Image data that is empty holds no bytes and is left as it is. **What is guaranteed:** once an image is found, every copy of its base64 spelled exactly the same, in any text or object key, is replaced by `[image <attachment id>]`, or `[image not kept]` for an `unavailable` one; for example the JSON of `structuredContent` that an MCP tool repeats as text. **Known limit:** two kinds of copy are not found, because no list covers them: an image that a tool's structured output holds in a shape of the tool's own invention, and nowhere else, and a copy of a found image encoded differently, for example re-padded, wrapped over lines, or JSON-escaped (`\/` for `/`). Their bytes stay in the event; the supervisor still shrinks an event too large for one frame (section 6, "No event the runner sends is larger than one frame"). An image over 10 MiB is not uploaded and becomes `unavailable`. Up to four uploads of one message run in parallel, so a tool that returns dozens of images never holds them all decoded at once; the session's later events wait for them. A stop aborts the uploads in progress and starts no more, so it never waits for an upload; an image not yet kept becomes `unavailable`. **Known limit:** an upload that fails, for example while the controller restarts, leaves the image `unavailable` for good; the runner does not retry it later.
- **Images** *(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* Verified against CLI 2.1.292 through the Agent SDK. The user message's `content` becomes `[{ type: "text" }, { type: "image", source: { type: "base64", media_type, data } }, ...]`, on a first prompt and on a steer. The adapter starts the session with `--add-dir <ctx.attachmentsDir>`, so the agent can read the cached files the path lines name. Claude Code shrinks large images itself (a 26 MB PNG worked), so the adapter declares no per-image limit. A bad image does not fail the turn: Claude Code emits a synthetic assistant message (`model: "<synthetic>"`, text "API Error: an image in the conversation could not be processed...") and then succeeds. That message stays visible in the transcript and is never filtered. Every Claude model accepts images, so a switch to a text-only model with images in history cannot happen.

### 10.2 Codex (app server)

- **Transport**: spawn `codex app-server` (CLI from npm `@openai/codex` or the static-binary installer), newline-delimited JSON-RPC 2.0 over stdio with the `jsonrpc` field **omitted on the wire**; a thin Hercule-owned codec, not a strict JSON-RPC library. One `initialize` + `initialized` per connection; `capabilities.experimentalApi` stays off - the stable surface keeps deprecated fields for compatibility, the experimental surface promises nothing, and t3code's opting into experimental is prior art to avoid, not follow (pinned, [#43](https://github.com/theagenticage/hercule/issues/43)). WebSocket transport is explicitly unsupported.
- **Model**: Thread > Turn > Item maps 1:1 onto Session > Turn > Item. `thread/start` (`model`, `cwd`, `approvalPolicy`, `sandbox`, `ephemeral`), `thread/resume`, `thread/fork`, `turn/start` (per-turn `model`, `outputSchema`), `turn/steer`, `turn/interrupt`. Notifications `turn/started` -> `item/started` -> deltas -> `item/completed` -> `turn/completed`; usage via `thread/tokenUsage/updated`. Unknown notifications are ignored for forward compatibility.
- **Approvals**: server-to-client requests (section 8.1); the adapter implements every request handler even where the answer is always decline.
- *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* **`turn/steer` falls back to `turn/start` only when Codex says it did not take the input.** Codex refuses a steer it did not take (the turn ended, it is another turn than expected, or it cannot be steered) with a JSON-RPC error, which always has a `code`. Any error with a `code` therefore falls back to `turn/start`, and the adapter reads no message text. A failure with no `code` (a timeout, a lost connection or a failed write) happened on this side of the connection, and Codex may have taken the input. It fails the input and starts nothing, because a new turn would deliver it twice.
- *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* **Async questions** (section 6.5) were built against the reply envelope of Codex 0.163. They were tested on the real binaries 0.154.0, 0.163.0 and 0.164.0, with a local model that asks one: the Request opens, stays open past the turn, and the model receives the exact envelope.
- **Subagents** *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)*: a collab agent is a child thread on the session's own app-server, and each child thread is a subagent (section 13.6). The adapter keeps its state per thread.
- **Process ownership**: ~~topology unpinned; suggested one app-server process per instance per runner (section 4.1).~~ Pinned below. Single-writer per thread; the server unloads idle unsubscribed threads after 30 minutes and emits `thread/closed` (maps to `session.exited`, resumable).
- **Process ownership, pinned** *(2026-09-14, [#73](https://github.com/theagenticage/hercule/issues/73))*: ~~one app-server host per provider instance on a runner, reference-counted over the sessions using it and shut down with its last one.~~ *(Amended 2026-09-30, recording what [#68](https://github.com/theagenticage/hercule/issues/68) built.)* One app-server per session, not per instance, killed when the session ends. The session token is in the environment the app-server was started with, and every shell command it runs inherits that environment. A shared host would run a second session's work under the first session's token, grants and actor stamp, and would stop working for both once the first token was revoked (section 9.3). So the auth refresh and the model catalog are per process too. A probe runs on a host of its own. A device-code login is an exception to the host's request/response rhythm: its completion is confirmed by a later probe rather than awaited, because Bun's HTTP server cuts an idle request at 10 seconds and the user needs longer than that in the browser. *(Amended 2026-10-02, [#313](https://github.com/theagenticage/hercule/issues/313).)* That later probe is no longer left to the user. When the login's child exits, or its code's 15 minutes run out, the runner sends `LoginEnded`, and the controller probes the instance on that runner at once and announces `provider` / `updated` ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2). `provider.login` answers a device-code login with `expiresAt` beside `userCode`. A client finishes the login by itself once a snapshot for that runner, probed after the login started, has `auth.status` `ok`, and shows the code as expired once `expiresAt` has passed. The web app has no "Done" button any more. A failed login is not told apart from one still waiting: a newer snapshot that is not `ok` may come from any probe, so the client waits until the login is done or the code expires.
- **Errors**: `-32001` overload -> retry with exponential backoff and jitter; mid-turn `error` notifications with `codexErrorInfo` feed `runtime.error { class }`.
- **Auth**: ChatGPT OAuth or API key via `account/*`; credentials in `$CODEX_HOME/auth.json` (file store default); tokens auto-refresh. `cli_auth_credentials_store` stays `file` on runners.
- **Stability**: no cross-version protocol guarantee. Pin the CLI release, generate types with `codex app-server generate-ts` for that release, regenerate and re-verify on every upgrade.
- **Images** *(Amended 2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465).)* Verified against `codex` 0.160.1. Each image is an input item `{ type: "localImage", path }` pointing at the cached file, on `turn/start` and on `turn/steer`. Codex shrinks large images itself, so the adapter declares no per-image limit. A bad image does not fail the turn: Codex puts placeholder text in its place. A switch to a text-only model with images in history works: Codex swaps the images for placeholder text.

### 10.3 pi (standalone binary, RPC mode)

- **Hosting**: pi runs as its own executable - the official standalone Bun-compiled binary, installed per runner ([./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12) - one `pi --mode rpc` child process per session, LF-delimited JSONL over stdio. Launch: ~~`--mode rpc --no-context-files --no-extensions --no-skills --no-prompt-templates --no-themes --no-approve -e <hercule extension>`~~ `--mode rpc --no-extensions --no-skills --no-prompt-templates --no-themes --no-approve -e <hercule extension>`, `--session-dir` under the instance home, `--session-id` so Hercule picks the session id up front. *(Amended 2026-10-04, [#75](https://github.com/theagenticage/hercule/issues/75).)* A workspace-less session adds `--no-context-files`, as section 9.1 has said since [#307](https://github.com/theagenticage/hercule/issues/307), and a Thread with User Material adds the flags of section 9.1 User Material.

Each subagent's pi loads a copy of its own instead of this one (section 13.6 pi). ~~one TypeScript file materialized into the instance home at session start~~ *(Amended 2026-10-07, [#438](https://github.com/theagenticage/hercule/issues/438), review.)* Every agent loads a copy of its own, the session's own agent included: `extension-<sessionId>.ts` or `extension-<subagentId>.ts` in the instance home, written before its pi starts and deleted after its pi exits. ## 11. Provider install portability and per-runner login

Installs are one command per provider (all three are self-contained binaries: Claude Code and Codex native, pi Bun-compiled) and are installed at runner join with a floor-pinned version policy ([ADR 0028](../adr/0028-provider-harnesses-are-runner-installed-executables.md), [./15-packaging-and-operations.md](./15-packaging-and-operations.md) §12); credentials are not distributed. Per-runner login is the durable model: refresh-token rotation with reuse detection (documented for Codex, structurally identical in pi, undocumented for Claude) makes two live copies of one credential log each other out. Hercule therefore drives each provider's own headless login on the runner as a post-join step from the fleet UI ([./03-controller-and-runners.md](./03-controller-and-runners.md) §3.3), relaying the device code or login URL to the user's browser. The per-provider login flows are listed in [./15-packaging-and-operations.md](./15-packaging-and-operations.md) section 12. Copying a credential file remains a bootstrap shortcut owned by exactly one runner afterwards. All three vendors permit the user's own account on the user's own machines; prohibitions target sharing with other people. Credential posture: [./13-security.md](./13-security.md). Findings: `research/provider-portability.md` (branch `research/provider-portability`).

## 12. Cost and usage

v1 records, per session, every `session.usage.updated` snapshot and, per turn, `usage` and `costUsd` on `turn.completed` when the harness reports them: Claude `total_cost_usd`, pi `usage.cost.total`; Codex reports token usage but no cost (subscription plans), so `costUsd` is absent there. There is **no rate-table pricing in v1**: Hercule never multiplies tokens by a price list, and unpriced usage stays unpriced. `costUsd` is the slot a later cost dashboard reads; t3-code's transcript-scanning usage subsystem is the reference for that later work. *(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355).)* The Session and Subagent records carry Token Usage and `costUsd` (section 6.6), and those records are what a later cost dashboard reads, never the usage events.

## 13. Subagents

*(Added 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); decided by [#350](https://github.com/theagenticage/hercule/issues/350), [#351](https://github.com/theagenticage/hercule/issues/351), [#352](https://github.com/theagenticage/hercule/issues/352), [#353](https://github.com/theagenticage/hercule/issues/353) and [#377](https://github.com/theagenticage/hercule/issues/377).)* A **Subagent** is an agent a session's harness delegated work to while the session runs ([GLOSSARY.md](../../GLOSSARY.md)). It is not a Session: it lives inside its session's process and settings, and is owned by its session the way a Turn is ([ADR 0038](../adr/0038-a-subagent-is-part-of-its-session-not-a-session.md); the record is in [./02-domain-model.md](./02-domain-model.md) Subagent). This section says how an adapter reports subagents, and what the user can do to them.

### 13.1 The one rule

**An event attributed to a subagent never changes the session's own state.** That covers the session's status, the Requests its own agent waits on, an assistant's reply ([./12-assistants.md](./12-assistants.md) section 9) and the session's turn notifications. Every place that reads the stream for the session's own state reads only the events with no `subagentId`:

- the controller's status and open-Request bookkeeping, the assistant observer, and the walk that finds an assistant's reply;
- the runner's supervisor, whose open turn and park become a set of open turns and a set of parks ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 6.2).

These readers change in the same build as the adapters. An adapter that sends subagent events to a controller that still reads every event as the main agent's would corrupt the session's state; that is why the runner protocol version goes up with this change ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2).

### 13.2 How a subagent appears in the stream

- **`subagent.started { subagentId, parentSubagentId?, itemId?, description?, agentType? }`** introduces a subagent, once per process, before any event of that subagent. `parentSubagentId` is the subagent that started it, absent when the session's own agent did. The event belongs to the parent, so it carries no attribution field of its own: it is stored in the parent's transcript, the one `parentSubagentId` names. `itemId` is the `subagent` item that started it in its parent's transcript. `description` is the short task name the parent gave it. *(Amended 2026-10-05, [#435](https://github.com/theagenticage/hercule/issues/435): the record's agentType needs a source.)* `agentType` is the harness's name for the kind of agent, which the record's `agentType` copies ([./02-domain-model.md](./02-domain-model.md) Subagent): Claude's `subagent_type` on the `Agent` call, Codex's role from `thread/read`.
- **The controller upserts the record** by `(session, subagentId)`. A field is filled when it is empty and never overwritten, so a resumed process that knows less never erases what an earlier one recorded. Two fields are filled at ingest when the event leaves them empty:
  - `itemId`, from the first `subagent` item whose `detail.subagentIds` lists the subagent. *(Amended 2026-10-05, [#435](https://github.com/theagenticage/hercule/issues/435).)* Every id an adapter lists in `detail.subagentIds` is a subagent it introduces with `subagent.started` in that process, before or after the item, so a listed subagent the controller has not heard of yet gets its record at the item's time and keeps the link when its introduction comes later;
  - `description`, from the first line of the input of the subagent's first turn: the brief its parent gave it.
- **There is no end event.** A subagent's status is computed from its turns (section 6.2): `running` while one is open, else the ending of its last turn, `completed`, `failed` or `stopped` (the turn's `interrupted`). A subagent the parent continues goes back to `running`.
- **An event from a subagent not yet introduced is held back,** bounded, and never handed to the session's own agent. Each adapter's bound is in section 13.6. When the bound is reached, the events are dropped with a `runtime.warning` that gives their count. Released events take the same path as any other, so a grandchild first named in a child's events is picked up.
- **On a resume,** `SessionSpec.continue.subagents` carries the session's known subagents, `{ subagentId, itemId?, parentSubagentId?, lastUsageReport? }`, from the controller's records. The adapter seeds its map from it, so a subagent continued in the new process lands on its record. *(Amended 2026-10-05, [#436](https://github.com/theagenticage/hercule/issues/436): the adapter's stop cascade needs the tree.)* `itemId` and `parentSubagentId` are left out when the record has none; `parentSubagentId` is absent for a subagent the session's own agent started. An interrupt of a continued subagent also stops the continued subagents below it (section 13.4). The adapter cannot always rebuild the tree itself: Claude's frames name no parent agent. *(Amended 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)* `lastUsageReport` is the original provider report behind its latest accepted usage snapshot, `{ source, payload }`. The controller stores it unchanged with that snapshot and forwards it without interpreting provider counters. A usage event without `raw` clears it. A fork carries none: a forked session starts with no subagents.
- **When the process exits,** any subagent turn still open is read as cut off, the same rule the main turn follows, and the record's `running` becomes `stopped`. No event is made up for it. A subagent never outlives its session's process.

### 13.3 Several open Requests

- **A session holds a list of open Requests,** each from its own asker: the session's own agent, or a subagent, named by the `subagentId` on its `request.opened`. The controller holds the list (`Session.openRequests`, [./02-domain-model.md](./02-domain-model.md) Session), so every surface sees the same Requests.
- **The runner never holds a Request back.** Every Request the harness asks is reported at once:
  - Claude parks are kept per request (section 8.1), and a second `canUseTool` is no longer denied with "ask again";
  - pi no longer denies a second dialog;
  - Codex no longer queues a second request inside the runner, out of the user's sight.
- **The user answers any Request, in any order.** The respond operations are keyed by request id.
- **`allow_always` resolves only the Request it answers.** Other open Requests stay open, even when the new rule would cover them: Hercule does not know how the harness matches its rules, and guessing would answer for the user. A request the harness asks after the grant may never be asked at all.
- **A Request closes** when it is answered, when its own agent's turn ends, when its agent is stopped (a stop that cascades down from a parent included, section 13.4), or when the session exits. The main agent's turn ending closes only the main agent's Requests. *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* An async question is the exception to the turn: its agent does not wait on it, so the end of that agent's turn leaves it open (section 6.5). Only an accepted answer, the stop of its agent (a `cancel` on one of the root's approvals included), or the session's exit closes it. `cancel` on an approval ends only the asking agent's turn.
- **Questions come from the session's own agent today.** Claude denies `AskUserQuestion` to every subagent, and Codex's `request_user_input` is root-only. Nothing in the shape stops a subagent's question. *(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* Async questions are the root agent's only, because Codex offers the async tool to the root agent alone. An async item of a subagent opens no Request (section 6.5).
- **"Waiting on you" means the list is not empty,** whoever asked. The session's status still follows its own agent only, so an `idle` session whose subagent asks is idle and waiting on you at once.

### 13.4 Stopping

- **`interrupt(sessionId, subagentId)` stops one subagent and every subagent below it.** The adapter stops each descendant itself, in any order, because no harness cascades reliably: Claude's `stopTask` stops a foreground child but not a background one, and Codex never cascades. Each stopped subagent ends `stopped`, and its Requests close as `cancel`. On Claude it is `stopTask(agentId)`, and the subagent cannot be continued afterwards. On Codex it is `turn/interrupt` on the child's thread; the parent may give the child work again later, which opens a new turn. *(Clarified 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)* The adapter keeps a guard for the stopped subtree until the selected subagent starts a new turn. A descendant first discovered before then is interrupted and its Requests are cancelled, even if the selected subagent's stopped turn has already completed. Frames already waiting for metadata retain the stop that applied when they arrived.
- **Stop reaches input preparation.** The runner sends `sessionInterrupt` independently of input delivery, waiting only for the harness binding. Preparation cancelled before native acceptance refuses its input; earlier inputs still queued on the runner are refused too. Native acceptance racing Stop still acknowledges delivery and interrupts the accepted turn. Only a later explicit input can start new work.
- **`interrupt(sessionId)` stops all work in the session:** the main agent's turn and every running subagent, even while the main agent is idle and only background subagents run.
  - Claude: `interrupt()` with the default options (no `perTaskStopAffordance`) already stops every subagent and its shells. The adapter keeps that default.
  - Codex: the root's `turn/interrupt` does not stop children. The adapter interrupts every child thread with an open turn, and interrupts at once a child turn that starts after the stop, including one whose events were waiting for metadata. *(Amended 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)* This whole-session stop guard stays in force until the root accepts the next explicit input. A rejected input leaves the guard in force. Acceptance permits new work by the root and its subagents; it does not interrupt a later continued child merely because an earlier turn was stopped.
- **Known limit (Claude):** after a stop, the main model is never told that its background subagents were stopped, and it may go on believing one still runs. Two fixes were rejected: stopping each subagent with `stopTask` instead starts a new main turn per stop, so Stop would set the agent working again; and a note added to the model's next input is text the user never wrote.
- **A subagent takes no messages.** Hercule offers no way to message a subagent: Claude has no host route to one, and Codex V2 refuses it. The shape agreed before it was dropped is recorded in [#353](https://github.com/theagenticage/hercule/issues/353).

### 13.5 Token Usage per harness

The meaning is section 6.6's. Per harness:

- **Claude.** The session's snapshot is `result.modelUsage`, which already includes every subagent and compaction. A subagent's count is **exact or absent**. `task_notification.usage.total_tokens` is not what the subagent spent: it adds the last call's input to the output of every call. The candidate source is the sum of the subagent's own frames' `message.usage`, counting each `message.id` once. The Claude build probes whether the main agent's count plus its subagents' equals the growth of `modelUsage`. If it does not, a Claude subagent carries no count, and a screen shows it as not reported, never as 0. The session's count is exact either way. *(Resolved 2026-10-05, [#436](https://github.com/theagenticage/hercule/issues/436).)* Probed on CLI 2.1.289: the counts do not add up, so **a Claude subagent carries no Token Usage**. Input, cache read and cache write tokens match the growth of `modelUsage` exactly, but output tokens do not: every frame of a message that ends in a `tool_use` keeps the placeholder output count the message started with, and a subagent streams no `message_delta` that would carry the final one. `modelUsage` also counts a small internal call that no frame shows, and leaves out the last call of a subagent that a denied request ended. A count with the right input and the wrong output is not exact, so it is absent. A subagent's `turn.completed` carries no `usage`, `costUsd` or `structuredResult`.
- **Codex.** Each thread counts alone, so the root's count leaves out its children. The adapter sends each child's count with its `subagentId`, and the session's snapshot as the root's count plus every child's. ~~Each thread is counted from the total it starts from in this process: on its first report, `total - last`. That one rule covers a resume, and a forked child, which probably starts at its parent's total; the Codex build probes a fork.~~ *(Amended 2026-10-05, [#435](https://github.com/theagenticage/hercule/issues/435).)* Each thread counts how much its `total` grows from one report to the next. Codex repeats an unchanged total after a cancelled call, a stream error or a compaction, so counting from the first report after a turn started would count a resumed thread's history whenever that first call is cancelled. The rules:
  - The report Codex sends right after a resume or a fork, before any turn starts, is the restored history. It sets where counting starts and counts nothing.
  - A newly spawned native child starts from zero. *(Verified on Codex 0.154.0 with its default paginated history, for V1 and V2; amended 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)* This differs from the public `thread/fork` operation, which restores its parent's usage history.
  - A resumed child restores its counter baseline from `continue.subagents[].lastUsageReport`, whose payload is its last accepted native usage notification. That report counts nothing in the new process. For children without a usable saved report, the adapter makes one shared initialization attempt before the root accepts new input. It attaches each with `thread/resume`, with at most two attachments at once and one five-second deadline for the complete initialization, so Codex replays its baseline, and keeps listening afterwards. Failure or timeout warns once, marks the affected subagent and Session Token Usage incomplete, and permits input. The failed initialization is not retried for every input. Stop cancels preparation without retrying it; interrupted initialization also leaves usage incomplete. Resuming only the root does not replay child baselines, and a cancelled child's first new call repeats old totals, so `total - last` would incorrectly count history. Saved reports avoid loading every historical child into the app-server.
  - For a root thread without an earlier report, counting starts from `total - last`: zero on a fresh root, its inherited history on a public fork. A restored report before any turn sets the baseline instead.
  - A repeated total adds nothing.
  - A total that went down adds nothing, and counting continues from the new total. Codex resets its total to zero when the context window overflows, and a snapshot never goes down (section 6.6).
- **pi.** ~~The same meaning. How a child reports is the pi build's to decide.~~ *(Resolved 2026-10-07, [#438](https://github.com/theagenticage/hercule/issues/438).)* Each child counts alone, from its own messages' usage, exactly as the main agent does (section 13.6 pi). The adapter sends each child's `session.usage.updated` with its `subagentId`, and the session's snapshot as the main agent's count plus every child's, including children that already ended. When the session stops or exits, each running child's count so far is still sent, attributed to that child. A stopped child's last model call was aborted, so its usage may be missing from the counts. A child's `turn.completed` carries its own `usage` and `costUsd`, and so does the main agent's: its count leaves out its children, as on Codex.

**Codex.**

- One app-server runs per session, so a thread other than the root is a subagent of the session: `subagentId` is its thread id, and its turn and item ids are native.
- The parent is restored from `continue.subagents` on a resume, or learned from the thread a V1 spawn `collabAgentToolCall` or a V2 `subAgentActivity` `started` is on, or `parentThreadId` from `thread/read`. The root maps to none. A saved parent link survives a failed metadata lookup; an absent saved link can still be learned. A V2 `completed` is never used to find the parent, because it lands on the initiating thread's old turn.
- The description is a V1 spawn's `prompt`, cut short. V2 has none, so it is `agentNickname`, or the last part of `agentPath`.
- The first event of an unknown thread starts a metadata-only `thread/read` (`includeTurns: false`; parent, nickname, role; no experimental API needed). That thread's notifications and server requests wait in one queue, in arrival order, for the round trip. If the read fails, the adapter emits a warning and `subagent.started` with the fields already known from its resume record or its parent's item, or without a parent when none is known.
- **Discovery is bounded per session.** *(Added 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)* At most 32 metadata lookups may be pending. Their queues together hold at most 256 frames and 1 MiB of serialized frames. Each lookup times out after five seconds. When these bounds are reached, text deltas are discarded first, with one warning that gives the accumulated count. Turn lifecycle and usage frames take priority over text. If a critical frame cannot fit safely after text is discarded, the adapter warns, marks accounting incomplete and exits the session instead of silently dropping its lifecycle. Any server request that cannot be retained receives an explicit JSON-RPC error instead of leaving Codex waiting. If a parent item lists a subagent while lookup capacity is exhausted, that subagent is introduced immediately with the information available from the item and a warning, so every listed id still has a subagent record. These bounds limit pending discovery work, not the number of subagents in the session. A process exit discards queued frames and cancels outstanding metadata reads.
- A child's approvals are Requests carrying its `subagentId` ([#362](https://github.com/theagenticage/hercule/issues/362) fixes the refusal that denied them silently). They arrive at the same time and can be answered in any order.
- **Each thread owns its adapter and normalizer state:** the tracked native `turnId`, Request map, file-change paths, reasoning buffers, model and usage baseline. A thread's `turn/completed` cancels only that thread's Requests. Child output never changes these values on the root. *(Clarified 2026-10-06, [#437](https://github.com/theagenticage/hercule/issues/437).)*
- **Only the root controls the session.** Input and model-selection changes target the root. The output schema and structured result belong only to the root. Only the root's `thread/closed` exits the session; a child's `thread/closed` leaves the session running.

Hercule's pi extension gives a session a `subagent` tool, and each child is a pi process of its own that reports with the event shape above.

- **Where a child runs: as a `pi --mode rpc` process the runner spawns at the extension's request.** The three candidates were a session inside the parent pi through pi's SDK (1), a `pi --mode rpc` child the extension spawns (2), and a child the runner spawns (3). Compared on the five axes:
  - *Approvals and questions:* a child's `extension_ui_request` arrives on the child's own stdout, so the adapter parks it with that child's `subagentId` directly. Under 2, the extension would re-ask every child dialog through the parent's `ctx.ui`, and a grandchild's twice.
  - *Stopping one child:* the adapter holds the child's pipe and process. Under 2, a stop needs a slash-command bridge into the parent pi, and one more hop per level.
  - *Token Usage:* the adapter normalizes each child's own events, so its count is exact. Under 2, the extension would have to re-serialize the whole child event stream through `tool_execution_update`, inside a file that imports nothing and runs only inside pi.
  - *The runner's process tree:* children are the runner's own children, so session stop and exit end them. Under 2, a parent pi killed after the stop deadline would leave its children orphaned.
  - *pi upgrades:* the extension uses one tool and one dialog call, plus the RPC protocol the adapter already depends on. Candidate 1 builds on the pre-1.0 TypeScript API that section 10.3 chose the RPC binary to avoid, and every in-process extension surveyed reached into pi internals.
  - *Cost:* one pi process per running child, which 2 pays too.
- **The tool.** The extension registers `subagent` with two parameters: `description`, a short task name, and `prompt`, the full brief. Its call is a `subagent` item in the parent's transcript: `detail.description` is the description, and `item.completed` lists the child in `detail.subagentIds`. The call itself never asks for approval: it only starts an agent whose own tools are asked about under the same access mode.
- **The request.** The tool asks the runner with an `input` dialog (`ctx.ui.input`) whose title is a fixed marker and whose placeholder is the JSON `{ toolCallId, description, prompt }`. `toolCallId` is pi's id of the `subagent` call; the adapter uses it to find the call's item. The adapter never reports this dialog as a Request. The call waits for the answer, with the turn's abort signal. The adapter refuses a request, answering with an error that the tool turns into a failed tool result, when:
  - it does not know the call;
  - the asking agent is at the deepest level;
  - the request is over the running limit (section 13.7);
  - the session is stopping, or the asking agent's turn is being aborted.

  Otherwise the adapter:
  - mints the `subagentId` (a UUID) and spawns the child. Once the spawn succeeded, it emits `subagent.started { subagentId, parentSubagentId?, itemId, description }`. A spawn that fails announces nothing: the parent gets the error as its tool result;
  - opens the child's turn with the brief as its `user_message` (attributed to the child), and sends the brief as the child's `prompt`;
  - when the child's turn ends, answers the dialog with the child's final assistant text, or with an error that the tool turns into a failed tool result, and closes the child's stdin, so the child exits.

  So a pi subagent lives exactly as long as its tool call and runs one turn. It is never continued.
- **The child process.** It gets the same binary, and the model and thinking level the session uses at that moment. An input can change those, so they are not always the parent's. It also gets the same access mode, working directory, excluded tools, context-file flags and User Material flags (a Thread's skills, prompt templates and instructions; section 9.1). It gets neither the Agent's appended system prompt nor the output schema: those belong to the session's own agent, and `submit_result` belongs only to the root. It runs with `--no-session`: the child's transcript is the controller's record of its events, and the parent's transcript holds the tool's result. So `continue.subagents` is accepted and ignored on pi, and a resumed session starts with no running child.
- **Each agent's extension file.** Each child loads a fresh copy of the Hercule extension, written for that child alone under a name nobody can guess beforehand, and deleted when the child exits. *(Amended 2026-10-07, [#438](https://github.com/theagenticage/hercule/issues/438), review: the session's own agent loads a copy of its own too, section 10.3.)* The reason: an agent allowed to write files without asking (`auto-accept-edits`) could otherwise rewrite a shared extension file, which holds the approval hook, before a child loads it, and so run that child with no approval hook. The runner enforces the depth limit itself. A child at the deepest level has no `subagent` tool only so the model is not offered it.
- **Requests.** A child's approval dialogs are Requests with its `subagentId`. Every dialog of every agent is reported at once; no second dialog is denied. `cancel` on a child's approval ends only that child's turn. pi asks no questions, so there are none to forward (section 13.3).
- **Stopping.**
  - `interrupt(sessionId, subagentId)` stops the child and every child below it. Their Requests close as `cancel`, their turns end `interrupted`, and their processes are ended. The parent's dialog is answered with an error saying the user stopped the subagent, so the parent sees a failed tool call and carries on.
  - `interrupt(sessionId)` stops every child and aborts the main turn.
  - A parent whose tool call ends while its child still runs, because the parent's turn was aborted, has that child's subtree stopped the same way.
  - When the session's pi exits or is stopped, every child is ended with it. As section 13.2 says, no event is made up for an open child turn.
  - *(Added 2026-10-07, [#438](https://github.com/theagenticage/hercule/issues/438), review.)* **What an agent's bash calls left running ends with the agent.** pi starts each bash call as a process group of its own, and on an abort it kills only the call that is running. So a background process started by a call that has completed, such as `npm run dev &`, would outlive the agent. When an agent's pi exits, for any reason, the runner kills with `SIGKILL` every process that still holds the agent's extension copy open, then deletes the copy. Every process a bash call starts inherits that open file (section 10.3). The runner lists the processes with `lsof` on macOS and reads `/proc` on Linux, and lists again after each round of kills, for at most three rounds, because a process may start another one before it is killed. This applies to the session's own agent on a session Stop as much as to a stopped subagent.
  - **Known limit:** a process that closes file descriptor 9 escapes, as does a daemon that closes every inherited file. Reuse of a process ID cannot make the runner kill an unrelated process, because a process is killed only while it holds the copy open.
- **Token Usage** is in section 13.5.
- **pi-durable** (`@earendil-works/pi-durable`), pi upstream's experimental subagents, is the thing to re-check when Hercule pins a new pi version. Nothing in it is reachable through `pi --mode rpc` today.

### 13.7 Limits and failure

- **Hercule sets no subagent limit in v1,** so each harness's defaults hold. Claude: 3 levels deep and 20 running at once. Codex 0.154.0: one level below the root and 6 children (V1), or 3 children (V2), from its own `[agents]` config, which the instance's `CODEX_HOME` leaves unset. *(Amended 2026-10-07, [#438](https://github.com/theagenticage/hercule/issues/438).)* pi: the `subagent` tool's own defaults, which Hercule does not let an Agent change. At most 4 children run at once per session, because each is a whole pi process. Children go two levels below the session's own agent: a child may start children, and a grandchild has no `subagent` tool. A request over the running limit is answered at once with an error that the model sees as a failed tool call; it says how many children run and to wait for one to finish. *(Amended 2026-10-07, [#438](https://github.com/theagenticage/hercule/issues/438), review.)* A stopped child counts against the limit until its pi has exited and what its bash calls left running has been killed, so a child that is slow to stop never lets a fifth pi process run. The running limit is per session, and each child is a whole pi process (about 110 MB idle), so a runner with several busy sessions pays that cost once per session; a runner-wide limit later is additive. A per-Agent limit later is additive: a field on the Agent, copied onto the session spec.
- **A failed subagent needs nothing new.** Its parent sees the failure as the result of its tool call, its record is `failed`, and its Requests are announced like any other.
- **A Hercule session another session spawns is not a subagent.** It would be a Session of its own with a link to the session that spawned it, left open here; a client could later list it beside the subagents by merging `session.querySubagents` with `session.query { actor }`.

## 14. Text generation

*(Added 2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282).)* A **text generation** is one model call: instructions, one input and an output schema go in, and a value that matches the schema comes out. It has no tools, no workspace, no transcript and no turn. It is not a Session: it has no Session row, takes no session slot, and emits no events. Work that needs tools stays an agent step. The reasons are in [ADR 0041](../adr/0041-text-generation-is-one-model-call-on-a-runner.md).

### 14.1 Who calls it

- **The controller's `TextGeneration` service** is the one entry point. Its `generate` method takes a caller, a purpose, the instructions, the input and an output schema ~~in Effect Schema, and returns the decoded value~~ *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* as JSON Schema in the strict subset of section 7, and returns a value that matches the schema, checked by the controller, or a `TextGenerationError`. Thread titles derive the JSON Schema from an Effect Schema, and decode the value with it.
- **The caller** is `core:<domain>` for a domain of the controller, such as `core:sessions`, or `plugin:<id>` for a plugin. *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* A workflow run's text generation step calls as `run:<runId>` ([./07-workflows.md](./07-workflows.md) section 4). Plugins reach the service later, through a host capability ([#285](https://github.com/theagenticage/hercule/issues/285)), under the usage rule in [./05-plugins.md](./05-plugins.md) section 8. Agents and sessions never call it: they are already model calls. It is not a public operation in v1 ([#287](https://github.com/theagenticage/hercule/issues/287)).
- **The purpose** names what the call is for, such as `thread.title`. The service qualifies it with the caller's domain or plugin id, so the record shows `sessions/thread.title`, and one caller cannot claim another's purpose. *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* A run's step passes its step id as the purpose, qualified with the run id, as `<runId>/<stepId>`. The model never sees it. There is no registry of purposes.

### 14.2 The text generation model

The controller setting `textGeneration.model` ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md) section 2) picks the provider instance and model every text generation runs on. It has three values:

- **`automatic`**, the default, and what an unset key reads as. The controller walks a fixed order of providers, Codex, then pi, then Claude Code, and picks the first one whose `suggestedTextGenerationModel` (section 2) is in the model catalog of an instance that is logged in on a runner that could take the call (section 14.3). Today the suggestions are Codex `gpt-6-luna`, pi `glm-5.3-flash`, and the Haiku model the Claude Code definition names. A provider with no suggestion is skipped. With no match, text generation is off and every call fails as `unavailable`. The order is a controller constant, not a setting.
- **`{ instanceId, model }`**, a model the user chose. `model` is the name the instance's model list gives it, at most 512 characters. Every call runs there. A call that cannot run there fails; it never falls back to another instance or provider.
- **`off`.** Every call fails at once as `unavailable`. Nothing is recorded and the last failure (section 14.5) is not changed, because nothing was tried.

The adapter runs the model at its provider's cheapest reasoning setting: lowest effort, or thinking off. The controller sends no model options.

### 14.3 Where it runs

The controller holds no provider login ([./13-security.md](./13-security.md) section 8), so every text generation runs on a runner. The runner is chosen per call, in this order:

1. the controller's local runner, when it could take the call;
2. otherwise any other runner that could.

A runner could take the call when it is placeable, is not reserved, has negotiated the `textGeneration` capability, has the instance logged in, and lists the model among the instance's models. A reserved runner is never chosen ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 5.5): nobody placed this work on it. A runner whose negotiated capabilities lack `textGeneration` is never chosen ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2). `automatic` and the runner choice use this one rule, so `automatic` never picks a model that no runner could run.

**At most 10 text generations run at once on one runner.** The limit is the protocol constant `MAX_CONCURRENT_TEXT_GENERATIONS_PER_RUNNER` in `@hercule/protocol`, and both sides enforce it. It only guards against a burst, such as 50 events arriving together; normal use never reaches it. It is separate from `maxConcurrentSessions` ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 5.3): a text generation takes no session slot, and a full runner's session queue does not hold one back.

- **The controller queues.** A call over the limit waits in the controller until a slot on that runner is free. ~~The wait counts against the caller's timeout (section 14.5).~~ *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* The wait does not count against the caller's timeout: the 60 seconds start when the call holds a slot (section 14.5). So a burst queued overnight waits for slots instead of timing out. Once a call holds its slot, the setting is read again before the call is sent. When the setting no longer names the instance and model the call queued for, the call is not sent and looks again with the setting as it is now: it fails with `off` when text generation was turned off, and runs on the new model when another one was chosen.
- **The runner refuses.** A runner that already runs 10 calls answers an 11th as `failed` at once. The controller never sends one, so this only guards against a controller that does.

**A slot is held until the runner answers**, not until the caller stops waiting. The runner always answers within its own deadline of 60 seconds (`TEXT_GENERATION_DEADLINE_MS`), or its connection ends. The runner in turn frees its own slot only after the harness process has exited (section 14.4). If the caller's timeout freed the slot first, a burst during a provider outage would start new harnesses on a runner whose earlier harnesses still run, and the limit would not hold. The controller also stops holding a slot 10 seconds after that deadline, so a runner that never answers cannot keep a slot for good. A caller that gives up while still waiting for a slot, such as a cancelled run, never sends its call. A caller that gives up after the call was sent stops waiting, but the call runs to its end. *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* The controller sends a call only to a runner whose connection it holds, so a call never goes to a runner that has already gone away.

### 14.4 The adapter's one-shot method

`generateText(ctx, config, spec)` on the `ProviderAdapter` (section 4) makes the call. `spec` is a `TextGenerationSpec`: the model name, a string as the instance's model list gives it (a text generation takes no model options), the instructions, the input and the output schema as JSON Schema ([./03-controller-and-runners.md](./03-controller-and-runners.md) section 2.2).

- **One harness process per call.** It starts, answers and exits before the method returns. Starting takes about 0.5 to 2 seconds, and Claude Code uses about 1 GiB of memory while it runs. A warm process per runner is an optimization to make only after measuring.
- **The instructions are the system prompt and the input is the one user message.**
- **No workspace.** The runner makes a scratch folder for each call under `<runner storage>/scratch`, readable by its user only (mode 0700), and passes it to the adapter as `ctx.cwd`. The adapter runs the harness there, so no repository's instructions or settings reach the call. The runner removes the folder on every path, whatever the outcome, and wipes the whole `scratch` folder when it starts, so a crash leaves nothing behind.
- **The runner owns the deadline and the limit.** `answerTextGeneration` (`apps/runner/src/socket.ts`) handles the request frame and calls the runner's text generator, `makeTextGenerator` (`apps/runner/src/text-generation.ts`).
  - It stops a call that runs past 60 seconds and answers `timeout`.
  - It catches any error once and answers `failed` with a message that is never empty. A failure message never contains model output or the harness's error output, because the controller stores and shows it, and error output can hold a credential or quote the input. A harness that exits early is reported by its exit code, or by a fixed sentence.
  - It runs at most `MAX_CONCURRENT_TEXT_GENERATIONS_PER_RUNNER` (10) calls at once and answers an 11th `failed` at once. The controller never sends an 11th (section 14.3), so this only guards against a controller that does.
  - **It releases a slot only after the harness has exited.** When a call ends, the runner waits for the harness process to exit before the slot is free for the next call. The wait is bounded. Codex and pi get SIGTERM, then 2 seconds to exit, then SIGKILL. Claude Code gets the SDK's own close first, which closes its input and waits about 2 seconds for the exit, and then the same SIGTERM, 2 seconds and SIGKILL. The runner starts the Claude Code process itself, through the SDK's `spawnClaudeCodeProcess` option, so that it stops and awaits that exact process: the SDK's close returns after its 2 second wait whether or not the process has exited, and the SDK's own SIGKILL comes only after about 7 seconds. So the runner can answer up to about 64 seconds after the request, which is why the controller holds a slot for up to 70. This keeps the count of 10 a count of live harness processes, not of calls.
- **Nothing persisted.** The harness writes no session or transcript into the instance home.
- **The output schema** follows the strict subset of section 7, so it works on every provider.
- **It can fail.** `generateText` returns an Effect that can fail with an error, for example when the harness cannot be started, and the runner turns that into `failed` as above. When the harness runs, it returns one outcome:
  - `ok` with the value, re-validated against the schema by the runner as in section 7, and `usage` when the harness reported it: token counts, and cost when the provider reports cost;
  - `invalid-output` with a reason, when the harness answered with no value that matches the schema;
  - `timeout`, when the harness ran past the runner's deadline of 60 seconds (`TEXT_GENERATION_DEADLINE_MS`) and the runner stopped it;
  - `failed` with a message, when there was no answer: the harness would not start, was not logged in, or errored.

How each provider makes a call with no tools, nothing persisted and a structured answer:

- **Claude Code.** One `query()` with the input as the prompt and these options: `systemPrompt` set to the instructions, `tools: []`, `outputFormat: { type: "json_schema", schema }`, `persistSession: false`, `settingSources: []`, `cwd` set to the scratch folder, and the binary and environment of the probe (section 10.1). The value is `structured_output` on the `result` message. Usage and `total_cost_usd` come from the same message.

  **Verified at build time** *(2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282))*: yes, `outputFormat` works with `tools: []`. The CLI's init message then lists exactly one tool, `StructuredOutput`, and the result carries a valid `structured_output`. The adapter also sets `thinking` disabled, `effort: "low"` and `maxTurns: 2`; the second turn only exists so the SDK can retry one structured output that did not match. A retry cut short ends as `error_max_turns`, which the adapter reports as `invalid-output`. No session file was written. The suggested model is the `haiku` alias, which the probe lists and which follows the newest Haiku. Haiku 5.5 still spends about 100 to 140 thinking tokens with both settings; neither switches it off alone. Proven on CLI 2.1.296, not the 2.1.263 the SDK pins: the SDK bundles no CLI and runs the machine's own `claude`.

- **Codex.** A `codex app-server` of its own. `thread/start` with `ephemeral: true`, `cwd` set to the scratch folder, and the built-in tools turned off through config. Then one `turn/start` with the input and `outputSchema`. The value is the text of the turn's final `agentMessage` item, parsed as JSON. Usage comes from `thread/tokenUsage/updated`; Codex reports no cost (section 12).

  **Verified at build time** *(2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282))*, on the pinned 0.154.0: only partly. The thread config turns off `features.shell_tool`, `features.view_image`, `features.multi_agent`, `features.apps`, `features.plugins`, `features.image_generation`, `web_search`, `skills.bundled.enabled` and `include_environment_context`. Four `-c` process overrides (`features.plugins`, `features.shell_snapshot`, `features.memories`, `skills.bundled.enabled`) stop what Codex writes while it starts, before any thread exists. Four tools cannot be turned off: `apply_patch` and `request_user_input` have no setting, and `exec` and `wait` come from the model's own catalog entry (`tool_mode: code_mode_only`). With the shell off, `exec` runs JavaScript with no file system, network or shell. The adapter therefore fails a call on any item other than a user message, an agent message or reasoning, and refuses every server request, in a read-only sandbox that never asks. With `ephemeral: true` no session or rollout file is written. `gpt-6-luna` is listed by Codex 0.162 and later but not by 0.154.0, so on the pinned release `automatic` passes over Codex; the proof ran on `gpt-5.6-luna`.

- **pi.** One `pi --mode rpc` process started with `--no-session --no-builtin-tools`, the system prompt set to the instructions, and the Hercule extension file loaded for `submit_result` (section 7). The extension file also registers `bash` and, when `HERCULE_SUBAGENTS` is set, `subagent` (section 10.3). The call passes `--exclude-tools bash` and leaves `HERCULE_SUBAGENTS` unset, so `submit_result` is the only tool the model can call. `--no-tools` is not used: it would remove `submit_result` too. The call runs under `approval-required`, and the adapter fails the call at once on any tool other than `submit_result`, or on any approval dialog. The value is the arguments of the `submit_result` call. Usage and cost come from `get_session_stats`.

  **Verified at build time** *(2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282))*, on the pinned 0.85.1: pi's active tools were `["submit_result"]` and only that tool was sent to the model. No session file was written. pi still writes `models-store.json` and an empty `auth.json` into its agent directory with `--no-session`, so the adapter points `PI_CODING_AGENT_DIR` at the scratch folder (`ctx.cwd`). `--thinking off` is clamped to the lowest level the model supports, which is `low` for `glm-5.3-flash`. The turn is aborted after three answers that do not match the schema, which ends as `invalid-output`.

### 14.5 How a call ends

~~The caller waits for at most 60 seconds in all, counting the wait for a free slot (section 14.3). It gets the value, or fails with one of three reasons:~~ *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* The caller waits for a free slot (section 14.3), and then for at most 60 seconds from the moment the call holds it. It gets the value, or fails with one of ~~four~~ five reasons:

- **`unavailable`**: no runner can take the call now~~, or the harness gave no answer~~. This covers ~~the setting `off`,~~ `automatic` with no match, a chosen instance that is logged in on no runner that could take the call, ~~every `failed` outcome from the runner, whatever its message,~~ a call the controller could not send, and a runner whose connection ended before it answered. The same call may work later.
- **`failed`** *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)*: the runner took the call and the harness gave no answer, or the controller could not prepare it. This covers every `failed` outcome from the runner, whatever its message, credentials the controller cannot read, and any unexpected error. Calling again at once will not help. A provider's rate limit ends here too, until [#625](https://github.com/theagenticage/hercule/issues/625) makes it a reason to wait.
- **`off`** *(Added 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)*: the setting is `off`, so no runner was asked. It is a reason of the service's error only: the call writes no audit entry and no last failure, so `controller.read` never shows it.
- **`timeout`**: the caller's wait ran out before an answer came, or the runner reported that it stopped the harness at its own deadline. The slot of a call whose caller gave up stays held until the runner answers (section 14.3).
- **`invalid-output`**: the harness answered, but the value does not match the schema, by the runner's check or by the controller's decode.

The error carries a message a user can act on, such as "No runner has Codex logged in." It never holds the prompt or the output.

The caller decides its own fallback. Nothing is retried by the service, except a waiting call looking for a runner again (below), and no call is kept anywhere that survives a restart. A call waits in memory for a runner or a free slot (section 14.3), so a controller restart that loses a call in flight leaves nothing to clean up. *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* ~~A workflow's text generation step is a caller with a fallback of its own: it waits on `unavailable` and calls again ([./07-workflows.md](./07-workflows.md) section 7.2).~~ *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* **The caller picks what happens when no runner can take the call,** with `whenNoRunner`:

- **`fail`**: the call fails at once with `unavailable`. A Thread title passes it, because it has a fallback of its own (section 14.6).
- **`wait`**: the call waits in the service, with no time limit, until a change may let a runner take it, and then looks again. A workflow's text generation step passes it ([./07-workflows.md](./07-workflows.md) section 7.2). The changes are: a provider snapshot stored, `textGeneration.model` written, a runner connecting, placements changing, and a runner retired. A call sent to a runner whose connection then ended looks again at once, one time, because an ended connection announces no change; if that finds no runner either, the call waits for a change. The setting is checked on every look, so the setting turned `off` while a call waits fails it with `off`. A waiting call writes no audit entry and no last failure. Its one entry is written when it ends, with the duration of its last attempt.

Either way, a call that ends writes its record even when its caller is interrupted at that moment. Interrupting a call that waits for a runner or a slot withdraws it, and a withdrawn call writes no record, even when the controller stops before its slot comes free; interrupting one already sent stops the wait, and the record is written once the runner answers (section 14.3).

**The last failure** is held in memory: its reason, its message and when it happened. Its message is trimmed and never empty. It is kept with two things: the value of `textGeneration.model` the call started under, and the target it actually ran on, which is the instance and model, or none when no target was found. The next call that succeeds clears it, and a controller restart forgets it. `controller.read` returns it only when both still match what the setting and its resolution are now. So a failure of the previous model never shows beside the new one, whether the user chose another model, or `automatic` began to resolve to another instance or model (for example because a login expired). A failure that ends after such a change is kept under the values it started with, so it stays hidden too. `controller.read` returns it beside the model `automatic` resolves to now ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md)), so Settings can show "Automatic - currently Codex gpt-6-luna" and why the last call failed ([./14-web-app.md](./14-web-app.md)). Nothing switches provider silently: `automatic` is a choice the user can see, not a hidden fallback.

*(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* **Why no call can run now.** `controller.read` also returns `unavailableReason`: the sentence that says why no text generation can run now, in words the user can act on, or null when one can. It is set when the setting is `off`, when `automatic` finds no match or the chosen instance is gone, and when no placeable runner is logged in to the instance. Unlike the last failure, it is worked out from the setting and the runners as they are now, so Settings can show it before any call has failed. A workflow step that waits for text generation shows it ([./14-web-app.md](./14-web-app.md)).

**The record.** Every call except one refused before the controller looks for a runner writes an audit entry, `textGeneration.completed` or `textGeneration.failed`. The entry is never routed and never holds the prompt or the output ([./13-security.md](./13-security.md) section 11). *(Amended 2026-10-14, [#286](https://github.com/theagenticage/hercule/issues/286).)* Two refusals write none: the setting is `off`, and the output schema is outside the strict subset of section 7, which fails as `failed`. A call whose caller gave up after it was sent writes its entry when the runner answers.

### 14.6 Thread titles

Thread titles are the first use. The title rules are in [./02-domain-model.md](./02-domain-model.md) (the Session's `title`). For the call itself:

- **Caller and purpose:** `core:sessions`, `thread.title`.
- **When:** at a Thread's first submission, in the background, beside the turn rather than after it. *(Amended 2026-10-23, [#827](https://github.com/theagenticage/hercule/issues/827).)* A fork of a Thread gets the call too, on its first message (its continuation prompt), so its title and role are generated like any Thread's. A session spawned from an Agent, an agent step session and an assistant session get no call.
- **Input:** the first message only.
- **Output:** `{ title, needsRefinement, role }`. `needsRefinement` is true when the subject is still unclear from the first message alone, such as "pick this up" with an issue URL, or "fix this". *(Amended 2026-10-23, [#827](https://github.com/theagenticage/hercule/issues/827).)* `role` is the Thread's job in a word or two, such as "migration", "fix", "feature" or "review". The prompt allows an empty `role` when the message is too vague to name a job.
  - **No length limit in the schema.** The `role` schema, like `title`'s, has no `maxLength`. `maxLength` may be outside the strict subset every provider shares (section 7), and a schema miss fails the whole call as `invalid-output`, which would lose a good title over a long role.
  - **The controller cleans the role like the title:** line breaks and runs of spaces become one space, and control and format characters are removed, except the zero-width non-joiner and joiner. It then keeps the role only when it passes the same rule as a spawn role (not empty, at most 24 characters, `MAX_ROLE_LENGTH`, counted as Unicode code points), and only when the Thread has no role yet. When spawn gave a role, the generated one is ignored and the spawn role stays. It never cuts a role, because a cut role reads as a broken phrase. A generated role that is dropped changes nothing: a session that has no role keeps `null`, and clients show its title.
  - **Title and role are accepted on their own.** A valid role is stored even when the title is empty after cleaning, and the other way round. `needsRefinement` is stored only together with a generated title, so a role-only answer leaves it null.
- **On failure:** the cut-short title stays. The failure shows in the setting's status and in the record, never as an error in the Thread.

## Post-v1

- Runner-side provider execution lifted into the provider plugin (v1: built-in, plugin-shaped).
- `readThread` / `rollbackThread` with the checkpoint/revert feature (v1 keeps fork and the normalized stream as the record).
- Plugin-contributed MCP tools through `SessionSpec.mcpServers` (v1 keeps the field).
- Rate-table cost pricing and a cost dashboard (v1 keeps `costUsd` and usage snapshots).
- Cross-runner session resumability via transcript mirroring (v1 pins sessions to their runner).
- Additional stream kinds (`reasoning_summary_text`, tool-argument streaming) and item kinds (review mode, image generation) as open-enum additions.
- Hercule-level OS sandboxing as a probed runner capability (ADR 0003).
- ACP-based adapters (Cursor and similar) need an extension-method seam beyond `sessionUpdate` mapping.
- **Reusing the user's existing local login, and moving logins between runners** - strongly wanted (noted 2026-09-01 by [Web app details](https://github.com/theagenticage/hercule/issues/45)): adopting the `claude` / `codex` / `pi` login already on the user's laptop instead of a fresh paste-a-code per instance, `claude setup-token` (one year, no rotation to race) as the Claude path, and Hercule shuffling tokens so a new runner needs no login at all; together with the instance-level "use my own binary and my own login" opt-in that skips home isolation (section 2.1 lists the binary half). The blocker to reopen is the refresh-token rotation fact from ticket #23; `setup-token` is why it may be solvable for Claude specifically.
