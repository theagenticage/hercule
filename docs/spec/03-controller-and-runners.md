# Controller and Runners

The controller is the single brain: it holds all domain state, interprets execution plans, schedules steps, and decides where sessions run. Runners are daemons on machines that host sessions and workspaces on the controller's behalf and own only material state (files, harness-native session data, an event outbox). This document specifies the split between the two, the protocol they speak, how a runner joins and leaves the fleet, how work is placed, what a runner executes sessions in and how it provisions and tears down workspaces, and how the controller itself moves to another machine (promotion). Rationale lives in [ADR 0002](../adr/0002-orchestration-stays-on-the-controller.md), [ADR 0003](../adr/0003-sessions-run-as-bare-processes.md) and [ADR 0005](../adr/0005-promotion-is-migration-behind-a-stable-controller-identity.md).

## 1. The controller/runner split

### 1.1 What lives where

| Concern | Owner |
|---|---|
| Domain state: Tasks, Runs, Sessions as records, Workflows, Subscriptions, event log, queued input, queues and scheduling rows, capability snapshots | Controller ([04-state-store](./04-state-store.md)) |
| Run orchestration: interpreting execution plans, scheduling steps, placement decisions | Controller |
| Material state: workspace files, checkouts, bare caches, harness-native session data (transcripts, harness homes), the event outbox, process logs | Runner disk |
| Runner-local paths | Runner; opaque to the controller, keyed by id |

The unit of placement is the Session and the Workspace. Runners never interpret execution plans; plan-shipping to runners is a possible later optimization enabled by protocol capability negotiation (section 2.2), not v1.

Runners are semi-stateful: wiping a runner loses its workspaces and the resumability of its sessions, never history. The controller's normalized session streams remain the observable record ([06-providers](./06-providers.md)).

### 1.2 Disconnect semantics

A runner that loses its controller connection stays autonomous: its running sessions continue, their events buffer in the disk outbox, and everything replays on reconnect. Plan progression waits for the controller: a step cannot complete, and no new step can start, while the controller cannot see the runner.

### 1.3 Ids cross the boundary, paths do not

The controller authors a `SessionSpec` that carries `workspaceId` (or `null` for a workspace-less session), never a path. The runner's session supervisor resolves the id to a directory and hands the adapter a `HarnessRunnerContext` (cwd, session env, harness home, harness binary - the facts the runner resolved for this session on this machine); the adapter never sees workspace ids and the controller never sees paths. Full shapes in [06-providers](./06-providers.md). *(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)* The Harness Home is the one folder the controller names: frames carry `harnessHome`, a path relative to the runner's storage directory: `providers/homes/<accountId>/<harnessId>`, or `providers/<legacyHomeFolder>` for an account migrated from a Provider instance, for its original harness only. The runner joins it to its storage directory. It names no machine path, so the rule holds ([06-providers](./06-providers.md), section 2.2 below).

## 2. The runner protocol

### 2.1 Transport

- The runner dials the controller and holds one persistent WebSocket. Runners accept no inbound connections from the controller.
- The controller MUST be reachable by every runner (LAN, tailnet, or public address; the user's choice). Reachability tricks such as pairing codes, tunnels and short-lived WS tickets belong to client-to-controller connections ([14-web-app](./14-web-app.md)), not to this link.
- The runner authenticates with its durable per-runner credential (section 3.2). The runner authenticates the controller's logical identity (section 8.1), not its address.
- The local runner on the controller machine joins over a loopback WebSocket as a supervised child process of the controller (`hercule runner --local`); it is an ordinary fleet member with no special code path ([15-packaging-and-operations](./15-packaging-and-operations.md)).

### 2.2 Framing and hello

- Messages are versioned typed JSON.
- The first exchange on every connection is `hello`. It carries, in both directions: the protocol version, the negotiated capability list (the protocol's extensibility seam: later features such as plan-shipping or OS sandboxing are advertised here and used only when both sides list them), and, from the runner, its probed facts (section 4).
- The hello exchange settles protocol compatibility. A hard refusal happens only on protocol incompatibility; any other version skew between controller and runner is warn-don't-block (section 2.4).

*(Amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431).)* **The runner keeps each session's frames in order, and nothing else waits for them.** A start now runs until the harness has its input, which can take as long as the harness takes to come up, so it must not hold up the rest of the connection:

- The frames of one session (`SessionStart`, `SessionInput`, `SessionInterrupt`, and the answers to its approval requests and questions) are handled one at a time, in the order they arrived. A `SessionInput` sent right after a `SessionStart` is handed to the harness after the start's input, never refused because the session is not up yet.
- Frames of different sessions are handled at the same time, so one slow start never delays another session.
- `Ping` is answered at once, and so are the frames that are not about a session. A slow start can never make a healthy runner miss the silence threshold (section 7).
- `SessionStop` does not wait behind its session's frames, and no frame waits behind it. It takes effect the moment it arrives, at any point of a start, so a start that has not handed over its input yet answers that input refused ([./06-providers.md](./06-providers.md) section 4.2). A start the stop reaches before it has spawned the harness spawns none, and reports `session.exited` with reason `stopped` itself. A `SessionInput` handled after the stop has arrived, including one still waiting behind earlier frames of the session, is refused without reaching the harness. An input refused this way does not restart the idle wait (section 6.2), because the session is already stopping.
- The controller can send a `SessionStart` for the same session right after a stop: when a sessions report lists a session the controller holds as `exited`, it sends `SessionStop`, and a resume can queue the session again before the old process is gone. A start that finds its session still held by the adapter, with a stop requested, waits until the old harness has exited, for at most 30 seconds, instead of being refused as a duplicate, and the earlier stop does not stop it. If the old harness is still running after that bound, the runner logs a warning and refuses the new start's input as still stopping. The controller puts that input back to waiting, like any refused input ([./06-providers.md](./06-providers.md) section 4.2), and the old harness's exit, when it comes, ends the session.

*(Amended 2026-09-25, [#257](https://github.com/theagenticage/hercule/issues/257); [ADR 0035](../adr/0035-an-action-declares-where-it-runs.md).)* **Workspace steps add four frames.** A workspace step is a step of a run whose action runs in the run's workspace on a runner, such as `git.commit` ([./07-workflows.md](./07-workflows.md) section 4.4). Every frame names its step by the **step key** `{ runId, stepId, iteration }`.

- Controller to runner: `WorkspaceStepStart { runId, stepId, iteration, workspaceId, action, input, resourceId?, gitIdentity? }`. It carries everything the runner needs, because the runner holds no Hercule state: the action's id, its `input` as the controller stored it on the step record, the checkout to work in when the workspace has more than one, and who a commit is made as (the workspace's designated Connection, as `SessionStart` carries it; absent when no Connection backs the workspace).
- Controller to runner: `WorkspaceStepSettle { steps }`: the controller no longer owes these steps, because their records have ended. Settling a step means more than stopping it: the runner stops the step if it is still running, deletes its result file, and remembers its key so a start of it that arrives late is ignored. There is no reply. The controller sends it when a run ends with a workspace step running, once it has recorded a step's result, and for every reported step whose record has ended.
- Runner to controller: `WorkspaceStepResult { runId, stepId, iteration, outcome }`, sent once the step has finished. `outcome` is `{ status: "completed", output }` or `{ status: "failed", code, message }`. `code` is one of `action_failed` (the action ran and failed), `timeout` (it ran past its deadline and was stopped), `unsupported_action` (this runner's build does not implement it) and `interrupted` (it was stopped before it finished). *(Amended 2026-10-08, [#476](https://github.com/theagenticage/hercule/issues/476).)* `output_too_large`: the step completed, but the result frame would be larger than `MAX_FRAME_BYTES` (2 MiB), the largest message the controller accepts. The runner sends this failure in place of the output, with a message that gives the size, such as "The step's output was 2.31 MiB, too large to send (the limit is 2 MiB)." It also saves this failure, not the output, in the step's result file, so a start sent again after a reconnect gets the same small answer. Without it, the controller would close the socket on the result, which ends the stream of every session on the runner, and would close it again on every reconnect. The run fails with `step-failed`. An older controller cannot decode the new code, so it raises the protocol version to 5, and a runner and a controller on different versions refuse each other at hello.
- Runner to controller: `WorkspaceStepsReport { steps }`: the steps the runner is running now, sent on connect like `SessionsReport`. The controller settles each one whose record is no longer `running`.
- A frame lists at most 256 step keys, which only refuses a nonsense frame.

Delivery is idempotent by the step key, not sequenced. The controller sends a `WorkspaceStepStart` again whenever it cannot know whether the runner has the step: on every connect, for every workspace step still `running` in a run pinned to that runner. The runner ignores a repeated start while the step runs, answers it with the stored result once the step has finished, and runs it only when it has no trace of it. So a result lost with a dropped socket is answered again on the next connect. While the run's workspace is still `provisioning`, the controller sends the workspace's provision frame before the start. ~~It rebuilds that frame from the workspace's rows, the checkout's base branch included, so a repeated provision is identical to the first.~~ *(Amended 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), section 6.8.)* The controller resends the stored preparation instruction, including the frozen checkout and setup choices; later Resource edits do not change it. The runner keeps each step's result in a file outside every checkout, `<runner storage>/step-results/<workspaceId>/<runId>-<stepId>-<iteration>.json`, so a commit never picks it up. The files of a workspace are deleted when the workspace is disposed. *(Amended 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), section 6.8.)* A primary workspace may remain registered after a step ends, so its step's file is deleted once the controller no longer owes the step: the report's answer shows its record ended, or a `WorkspaceStepSettle` for it arrives.

The route authenticates with the runner credential, answers `401` to a bad one, and `404` unless the session is placed on the calling runner, so a runner cannot write into another runner's sessions. It refuses an image over 10 MiB, or one that is not a PNG, JPEG, GIF or WebP, as `validation`. It answers `201` with `{ id, mimeType, sizeBytes }`: a new Attachment, or the one already stored for the same bytes in that session ([./04-state-store.md](./04-state-store.md)). The upload runs on its own HTTP connection, like a fetch, and the runner waits at most `ATTACHMENT_UPLOAD_TIMEOUT` (30 seconds) for it: the session's later events wait behind it. Like the fetch, the route sits behind the promotion gate (section 8): a frozen controller answers `promotion_in_progress` and a sealed one `controller_sealed`, because B would never receive an image A stored after the copy. The runner then keeps that image as unavailable, with the reason.
- **Ordering.** The controller sends a frame only after the transaction that stored the input commits, and the upload wrote the file before its row. So by the time the runner sees a reference, the file, its row and the reference from the input are all committed, and the route can always serve it.
- **The runner fetches before it calls the adapter**, on both paths: a session's first input on `SessionStart` and later input on `SessionInput`. Fetches run in parallel. Each download goes to a temp file, is checked against its `sha256`, and is renamed into the runner's attachment cache at `<runner storage>/attachments/<sessionId>/<attachmentId>`. The cache is never in the workspace, so git stays clean. A session's cache is removed when the session ends, and the whole cache is wiped when the runner daemon starts, so no image outlives the session that needed it. One fetch runs per attachment id at a time, and a cached file is reused while the session runs, so a redelivered input fetches nothing twice. A resumed session starts with an empty cache and fetches its images again. A failed fetch refuses the input with a clear message; the runner never sends the text without its images. The controller waits `SESSION_INPUT_DEADLINE` (10 seconds) for the answer to a `SessionInput` or a steer, and `ATTACHMENT_DOWNLOAD_TIMEOUT` (2 minutes) longer when it carries images, the time the runner has to download them. Both constants live in `@hercule/protocol`. What the adapter receives is in [06-providers](./06-providers.md) section 4.

*(Added 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768).)* **Repository skills.** A repository skill is a skill folder in a checkout of a workspace ([06-providers](./06-providers.md) section 9.4). Three frames let the controller read them, all in `@hercule/protocol` and modelled on the workspace inspection:

- **`RepositorySkillsInspect { requestId, workspaceId }`**, controller to runner. It asks the runner to list the skills in the checkouts of one existing workspace. It changes nothing on disk.
- **`RepositorySkillsPreview { requestId, checkouts }`**, controller to runner. It asks which skills a workspace would have before it exists, for a draft Thread. `checkouts` holds 1 to 32 (`MAX_CHECKOUTS`) entries, in the order the Thread would open them. Each is `{ remote, subdirectory, workspaceId }`:
  - `remote` is the repo's remote.
  - `subdirectory` is the folder the checkout would get in the workspace, or null for the one checkout of a single-repo workspace, which sits at the root. It follows the rules of section 6.3.
  - `workspaceId` is the repo's ready main workspace on this runner, or null when the repo has none there.

  The runner lists the planned workspace with the code that lists a real one, so the checkout names, the clash rule, the caps and the paths are the ones a real start gets. The controller prefixes no path and resolves no clash. A main workspace is one repo, so the folder the runner reads for a checkout is the only checkout of its main workspace. A repo with no ready main workspace, or a checkout folder the runner cannot read, still takes its checkout name, so the later checkouts keep the names they would have. It appears as one skipped entry, named by its `subdirectory` (`.` for the workspace root). A preview changes nothing on disk.
- **`RepositorySkillsInspection { requestId, workspaceId?, outcome }`**, runner to controller. It answers either request, matched by `requestId`. `workspaceId` repeats the one an inspect asked about and is absent from the answer to a preview. `outcome` is `listed { skills, skipped, truncated }` or `failed { message }`.
  - Each of the at most 256 (`MAX_REPOSITORY_SKILLS`) `skills` is `{ checkoutName, name, description, path }`: `checkoutName` is the prefix of the skill's qualified name, and `path` is the skill's folder relative to the workspace root, such as `web/.agents/skills/release`.
  - Each of the at most 256 `skipped` entries is `{ path, reason }`: a skill folder or a checkout the runner found but cannot offer, and why, with `path` relative to the workspace root and `reason` at most 512 characters (`MAX_SKIPPED_REASON_LENGTH`). The limit keeps 256 reasons inside the frame size limit.
  - `truncated` is true when the runner left an entry out at a cap: a list was full (256 skills or 256 skipped entries), or the walk budget was used up (10,000 entries across all the checkouts and skill folders of one listing, `MAX_LISTING_ENTRIES`; every file and folder the runner reads from a folder counts, plain files and the top-level skills folders included, and so does every path component it looks at while it follows a link; the folders not reached are skipped with one reason). Either list may then be missing entries. The runner stops listing once both lists are full and an entry was left out. The controller turns it into the `incompleteReason` of the client's answer, so a client never mistakes a cut list for a complete one.
  - `failed` is for a workspace the runner does not hold or cannot read. The runner also sends it in three other cases. Each has its own message, so the user can tell them apart:
    - A listing that runs longer than 9 seconds (`LISTING_TIMEOUT`): "reading the workspace's skill folders took longer than 9 seconds". The 9 seconds count from the request, and the wait for a permit (see the next point) counts toward them. This is just under the 10 seconds the controller waits, so the controller gets the runner's message and not a plain timeout.
    - A request that gets no permit to read within those 9 seconds: "the runner is still busy reading skill folders for earlier requests; try again in a moment". Nothing was read.
    - An encoded answer that would pass the frame size limit, with a message that tells the user to shorten the skill descriptions: a frame over the limit would make the controller close the socket, which ends every session on the runner.
- **The runner reads at most 4 inspections, previews or session starts at the same time**, whoever asks (a read needs a permit, and there are 4; a start reads the repository skills of its workspace under the same permit and 9 second limit, and is refused with the same two messages when it is slow or finds no permit). A request waits for a permit, and the wait counts toward its 9 seconds. Each one walks the files of up to 32 checkouts, and the limit keeps a burst of requests from taking the disk away from the sessions the runner hosts.
  - A listing that runs past 9 seconds is told to stop, and the request is answered `failed`. The listing keeps its permit until its work has really stopped, which is after the file system call it was in returns. A call that hangs, such as a read on a stalled network mount, cannot be cancelled, so a hung file system holds a permit and later requests answer "busy". It does not pile up more work than 4 listings, and it is not hidden.
- **The controller waits 10 seconds for the answer**, with the same request-and-answer call as the workspace inspection. An unanswered request is not retried, and no frame is replayed (section 2.3): the answer is written straight to the socket. The controller passes `skills`, `skipped` and `truncated` on to the client ([11 section 2](./11-public-api-and-agent-surface.md), `session.querySkills` and `session.previewSkills`).
- **This amends the capability list above: it also holds `repositorySkills`**, `REPOSITORY_SKILLS_CAPABILITY` in `@hercule/protocol`. Both sides list it. The controller sends `RepositorySkillsInspect` and `RepositorySkillsPreview` only to a runner whose negotiated capabilities hold it, because a runner that does not know a frame closes the socket on it.
- **`PROTOCOL_VERSION` does not change.** The capability keeps the frames away from a runner built before it, and that runner stays online for everything else.
- **`SessionStart` carries nothing about repository skills.** The runner lists and stages them from its own disk at every start and resume ([06-providers](./06-providers.md) section 9.4). The capability only covers reading them for a client.

### 2.3 Sequencing, acks and the outbox

- Every runner-to-controller event carries a monotonic sequence number. The controller acknowledges sequence numbers.
- The runner keeps a disk-backed outbox of unacknowledged events. On reconnect it replays everything after the last acknowledged sequence number. This is the only disconnect buffer; there is no separate replay protocol.
- The runner reconnects with exponential backoff, 1 s doubling to a 30 s cap, retrying forever. The backoff resets to zero on an OS wake or network-change signal, so a laptop lid-open reconnects immediately.
- Seq/ack state is keyed by the controller's logical identity, so it survives the controller changing address (section 8).
- Controller-to-runner traffic on the same socket includes placement commands (start, resume, fork, stop, interrupt a session; provision or tear down a workspace), input delivery (queued input flushed on `turn.completed`, a session's first input carried by its start *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431))*, and steering, both controller-owned domain state riding this channel; *(amended 2026-09-26, [#92](https://github.com/theagenticage/hercule/issues/92))* steering is a guarantee of every session: where the harness cannot steer, the controller sends `SessionInterrupt` and delivers the input as the next turn, and a conversation's session keeps its waiting input through an exit and is resumed for it, [./06-providers.md](./06-providers.md) section 5), approval decisions, probe requests, the reachability probe used during promotion (section 8.2), and the remote upgrade command (section 2.4).

### 2.4 Fleet version skew

- Controller and runner ship as the same binary ([15-packaging-and-operations](./15-packaging-and-operations.md)); skew is expected and surfaced, never hidden.
- Policy is warn-don't-block: a runner on a different binary version stays online and accepts placements; the fleet UI shows the skew. The only hard refusal is protocol incompatibility at hello.
- The controller can upgrade a runner remotely with one WS command that reuses the runner's own self-update path. Upgrade the controller first, then runners, as a UI-nudged convention.
- Harness versions differ per runner as well; that skew is a fact in the capability snapshot (section 4.2), not a protocol concern.

*(Amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431).)* Putting a session's first input on `SessionStart` raised `PROTOCOL_VERSION` from 1 to 2 (section 2.2), so a runner on protocol 1 is refused at hello and stays offline until it is upgraded. This is a deliberate exception to warn-don't-block: the change could have been a capability with a fallback for older runners, but an older runner would decode the new `SessionStart`, drop the input it does not know, and start a session with nothing to do. Nobody runs a fleet yet, and one delivery path is simpler than two. The policy above is unchanged for any other skew.

A runner on protocol 2 is refused at hello and stays offline until it is upgraded.

The top-level `message` is gone: the `error` carries one, written for the user. The controller reacts to the tag, so a refused steer, a missing harness and a lost connection to the harness are told apart without reading words. This raised `PROTOCOL_VERSION` from 9 to 10 (section 2.2) under the same exception. The two shapes of a refused answer do not decode on the other side, so a refused input would be lost or misread. A runner on protocol 9 or older is refused at hello and stays offline until it is upgraded. `SessionRespondToQuestionResult` is unchanged.

## 3. Registration and join

### 3.1 The join exchange

1. The user mints a single-use join token in the web app or the ops CLI.
2. On the new machine the user runs one command: `hercule runner join <controller-url> --token <token>`.
3. The exchange upgrades the token to a durable per-runner credential. It is fully programmatic: no interactive prompts, so a future auto-installer can drive it end to end. A one-line installer is acceptable in v1.
4. Join then installs the harness CLIs (section 3.3) and registers the machine's service unit by default (`--no-service` skips it; [15-packaging-and-operations](./15-packaging-and-operations.md)); a `--reserved` flag marks the runner reserved (section 5.5). A harness-CLI install failure never fails the join: the harness simply reports as absent in the runner's facts, with an "Install" retry in the fleet UI.
5. The controller records the new runner (identity, credential, name, probed facts) and the runner appears in the fleet as `online`.

The fleet UI reserves an "Add machine" spot showing the join command with a freshly minted token; fleet auto-discovery and push-install are post-v1.

*(Amended 2026-09-07, [#64](https://github.com/theagenticage/hercule/issues/64).)* Step 4 no longer installs the harness CLIs. Installing a harness is the user's decision per machine and per harness - a user with only a Claude subscription has no use for a Codex binary - so it is an **Install** action on the runner's fleet page and nothing else. Join stays prompt-free and installs nothing; a machine with no harness reports it as absent in its facts, which is what puts the Install button in front of the user.

The join token is single-use and expires after **1 hour**. Outstanding tokens are listable and revocable, and the "Add machine" spot mints a fresh one each time it is opened, so an expired token costs one page refresh.

### 3.2 What the runner sets up on enrollment

- A random storage directory for all its workspaces, caches and other material state, under the runner area of Hercule Home (`~/.hercule/runner/`, [15-packaging-and-operations](./15-packaging-and-operations.md)). A re-enlisted machine therefore never overwrites a previous life's folders. Legacy folders from earlier lives MAY surface very discreetly in the UI for manual recovery; Hercule never adopts them automatically.
- Its durable credential: an opaque random token, stored locally on the runner in `~/.hercule/runner/runner.json` (mode 0600, alongside the controller URL, the controller's logical identity and public key, and the storage-directory name; [15-packaging-and-operations](./15-packaging-and-operations.md)) and stored hashed on the controller ([13-security](./13-security.md)). It is not a secrets-table entry.
- A name. The controller MAY auto-assign a fun name (mythological names are the suggested scheme); the user can rename at any time.

## 4. Runner capabilities

A Runner Capability is a fact about a runner used for placement. Two kinds:

- **Probed facts**, self-reported by the runner at hello and refreshed on change: OS and architecture, RAM (feeds the session cap default), docker presence, toolchains (section 6.6), ~~provider binaries and their auth state~~ harness binaries and their versions *(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)*. Sign-in state is not a runner fact: it belongs to a Provider Account and is probed per account (section 4.2). Probing is credential-file-free: auth state comes from each ~~provider's~~ harness's own side-effect-free probe, never from reading credential files. The controller never probes a runner actively.
- **Labels**, free-form strings the user applies to a runner (`gpu`, `office`, `fast-disk`). Labels are placement filters and nothing more.

### 4.1 Reporting

Probed facts are runner facts, not session events: they arrive in hello and in subsequent fact updates, not in a session's normalized event stream.

*(Amended 2026-09-05, [#61](https://github.com/theagenticage/hercule/issues/61).)* The two reports are **latest-wins state, sent unsequenced and never buffered**: a report older than the newest one is worthless, so one that finds no socket is dropped rather than queued. Their shapes, every size in bytes because the session-cap rule is arithmetic on them:

- `RunnerFacts { os, arch, totalMemoryBytes, docker: boolean, toolchains: [{ name, version, path }], ~~providers: [{ name, present, path? }]~~ harnesses: [{ name, present, path?, version? }] *(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)*, adapters: [qualified harness id] *(Amended 2026-10-31, [#932](https://github.com/theagenticage/hercule/issues/932).)*, identityPort }`. A harness's version is a runner fact, because it does not depend on the account. `adapters` lists the qualified harness ids (such as `claude-code/claude-code`) that this runner build has an adapter for. It is a fact about the binary rather than the machine, so the fleet view can show "no adapter in this runner build" instead of finding out by trying and failing. `identityPort` is a probed fact because only the runner knows which port it got (section 5.4).
- `RunnerWatermark { diskFreeBytes, availableMemoryBytes, acceptingPlacements: boolean }`, sent right after every hello and on the 60-second check.

The controller stores each whole, as one JSON document on the runner row, and hands it back on the fleet read. A toolchain whose `--version` cannot be parsed reports the raw string; one that is absent produces no entry and no error.

*(Amended 2026-09-10, [#67](https://github.com/theagenticage/hercule/issues/67).)* `RunnerWatermark` is `{ diskFreeBytes, availableMemoryBytes }`; ~~`acceptingPlacements: boolean`~~ leaves the wire. Whether a machine accepts placements is the controller's decision, made from the reported free bytes against a per-runner watermark it holds (10 GiB unless overridden by `runner.update { diskWatermarkBytes }`), checked at every placement and on every report. The `runner.placementsChanged` audit entry is recorded on the crossing, from a report or from an update.

## 5. Placement

### 5.1 Policy

Placement is deliberately dumb and runs in this order:

1. **Capability filter.** Runners lacking a required probed fact or label are excluded (e.g. an agent step requiring `git`, or a label the workflow names).
2. **Explicit choice.** If the request names a runner, use it - including a reserved one (section 5.5).
3. **Default runner.** Otherwise the fleet-level default runner. Never a reserved runner (the default runner cannot be flagged reserved).
4. **Controller's local runner.** If no default is set, the local runner on the controller machine - unless it is flagged reserved.

No load balancing, no migration, no failover.

*(Amended 2026-09-17, [#208](https://github.com/theagenticage/hercule/issues/208).)* Steps 3 and 4 are **not implemented as written**: a request that names no runner is placed on any placeable runner holding a logged-in snapshot for the instance, and neither the fleet default nor the controller's local runner is consulted. The ladder above is what the system is to do; tracked in [#210](https://github.com/theagenticage/hercule/issues/210).

*(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)* **Which runners can run a Provider Account in a harness.** Wherever this section says a runner hosts, or holds a logged-in snapshot for, a provider instance, the test is now this:

- the harness is installed on the runner (its facts, section 4.1), and
- the account works there: a key or token account works on every runner, because the controller sends its secret with the frame; a per-machine account works only where its snapshot says it is signed in, as the account's identity (section 3.3).

Placement ignores models. A session whose harness on that runner does not know the model fails to start with the harness's own error; the harness version warnings of [ADR 0028](../adr/0028-provider-harnesses-are-runner-installed-executables.md) already flag an old harness.

*(Amended 2026-09-25, [#257](https://github.com/theagenticage/hercule/issues/257).)* **Run pinning until the ladder is built.** A run is pinned to a runner in the transaction that starts its first workspace step ([./07-workflows.md](./07-workflows.md) section 4.4). Until [#210](https://github.com/theagenticage/hercule/issues/210) replaces it with the ladder above, the rule is:

- The run is pinned to a **placeable** runner: `online`, `active`, and not reserved. A reserved runner is never picked, because a run names no runner (section 5.5).
- For a `primary` policy, a placeable runner that already holds a `ready` main workspace of the policy's resource is preferred, so the run works in the clone the user already has there.
- When no runner is placeable, the step record stays `pending` and the run sleeps. It is not failed: the controller wakes every run that waits for a runner when a runner connects, and when a connected runner may have become placeable (it is undrained, no longer reserved, or given more room). [#258](https://github.com/theagenticage/hercule/issues/258) adds the capability part: a runner must also implement every workspace action in the plan.
- From then on the run is pinned, as section 5.2 says of any work: every later workspace step goes to the same runner. A run whose runner is `offline` or `unreachable` waits for it with no time limit. Cancelling the run, or retiring the runner, are the only ways out; retiring fails the run with `workspace-failed`.

*(Amended 2026-09-25, [#258](https://github.com/theagenticage/hercule/issues/258).)* **The capability filter in run pinning.** A run is pinned only to a runner whose negotiated capabilities (section 2.2) hold every workspace action in the plan, not just the one about to run, because every later workspace step goes to the same runner.

- **At `run.start`**, a plan whose workspace actions no runner that is neither retired nor reserved offers is refused with `validation`, naming the missing actions: "No runner can run git.commit; update a runner to this version." When each action is offered by some runner but no runner offers them all, every workspace action in the plan is named. An offline or draining runner still counts, because it may take the run later. A reserved runner does not count: a run names no runner, so it is never pinned to a reserved one (above), and counting one would let the run wait forever. A plan that only reserved runners offer is refused with the same message.
- A plan that some runner offers, but no placeable one, starts, and its step record stays `pending` until a capable runner is placeable, as above.
- **At pinning time**, if every runner that offered the plan's workspace actions has been retired or reserved since the run started, the run fails with `workspace-failed` at the step about to start, with the same message. Retiring a runner wakes every run waiting for a runner, so such a run fails at once rather than waiting for a runner that will never come.
- A run that is already pinned is not checked again. If its runner comes back on a build without the action, the runner answers the step with `unsupported_action`.

*(Amended 2026-10-04, [#83](https://github.com/theagenticage/hercule/issues/83).)* **Pinning a run with an agent step.** An agent step is a workspace step, so the run is pinned in the transaction that starts its first agent step or workspace action, by the rules above, with two more conditions on the runner:

- ~~it hosts the provider instance of the step's Agent;~~ it can run the step Agent's Provider Account in the Agent's harness (above) *(Amended 2026-10-30, [#406](https://github.com/theagenticage/hercule/issues/406).)*;
- its negotiated capabilities hold `agentSteps` (section 2.2).

A run with an agent step and no workspace policy is still pinned. Its sessions have no workspace, and all of them run on that runner.

### 5.2 Pin once landed

- A Workspace is pinned to the runner it was provisioned on.
- A Session is pinned to the runner it started on: harness session state lives on that disk. Resume and fork happen on the same runner.
- A session that names a workspace is placed on that workspace's runner; the filter and choice steps above apply only to the runner selection that happens before a workspace exists.

### 5.3 Per-runner session cap

- Each runner has `maxConcurrentSessions`. Default: derived from probed RAM at roughly one session per 2 GiB, floor 1. User-overridable per runner.
- A full runner queues its placements. Queued placements are visible in the UI. Work never spills to another runner.
- A runner below its disk-space watermark (section 6.2) also stops accepting placements; they queue the same way.
- Placements pinned to a runner that is `offline` or `unreachable` wait for its return.
- *(Added 2026-10-11, [#282](https://github.com/theagenticage/hercule/issues/282).)* A text generation is not a placement and takes no slot of this cap. It has a limit of its own, `MAX_CONCURRENT_TEXT_GENERATIONS_PER_RUNNER` (10) at once per runner, which the controller and the runner both enforce ([./06-providers.md](./06-providers.md) section 14.3).

*(Amended 2026-09-10, [#67](https://github.com/theagenticage/hercule/issues/67).)* The queue is the Session rows in status `queued`, oldest first; there is no separate placement-queue table. One dispatch function per runner moves them to `starting` when the runner is online, active, above its watermark and has a free slot, and runs after a spawn, a session exit, the runner's `sessionsReport`, a watermark report, a cap or watermark change, and undrain. A spawn or continue pinned to an offline or unreachable runner ~~waits for its return~~ succeeds immediately as `queued`. Retiring a runner ends its queued sessions.

### 5.4 The "local" alias

"Local" is a client-resolved placement alias meaning "the runner on the machine the user is operating". It is distinct from the default runner, is a UI convenience only, and is not offered when that machine has no runner. Resolution: the runner serves `GET /identity` on a loopback-only port it owns and reports as a probed fact (`identity.port`, default 4939; resolved 2026-09-01, [#45](https://github.com/theagenticage/hercule/issues/45)) and the client matches the returned id against online fleet runners; placement correctness never depends on this detection ([14-web-app](./14-web-app.md)).

When the operating machine has a runner, **threads default to "local"**: sessions the user opens from the client with no Agent behind them (Threads, [02-domain-model](./02-domain-model.md)) are placed on that machine's runner unless the user picks another, so working from a laptop feels like working locally. *(Amended 2026-10-13, [#593](https://github.com/theagenticage/hercule/issues/593).)* A Thread a session starts does not get "local": that alias is resolved by a client, and a session's call has none. ~~The calling session's runner is not copied either, so a call that names no runner is placed by the controller like any other placement without a runner (section 5.5); a session that wants a particular runner names it with `runnerId`.~~ *(Amended 2026-10-14, [#688](https://github.com/theagenticage/hercule/issues/688).)* Every spawn by a session, a Thread or from an Agent, runs next to its caller unless the call says otherwise: on the calling session's runner when the call names none, and in the caller's workspace when the call names no workspace and no other runner. A session usually spawns another to work on its own files, such as a reviewer, so landing on another machine is never what it meant. A spawn the call sends to another runner gets no workspace unless it asks for one, because the caller's files are not there. Following the caller counts as explicit choice (section 5.5): a reserved runner takes the spawn, and a draining or retired one refuses it with a message that says to send `runnerId`. Workflow placements ignore this and use the default runner. Resolving the "local" alias counts as explicit choice for a reserved runner (section 5.5). (Resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43).)

### 5.5 Reserved runners

A runner may be flagged **reserved**: it hosts only work explicitly placed on it, and placement fallback never chooses it. Explicit means the request names the runner (a UI pick or a workflow's named runner), the client's "local" alias resolved it, or the placement follows a workspace already living there (pin-once-landed: the workspace's creation was itself an explicit act). *(Amended 2026-10-14, [#688](https://github.com/theagenticage/hercule/issues/688).)* A session's spawn that names no runner follows the calling session to its runner, and that counts as explicit too (section 5.4). The default-runner and local-runner fallback steps skip reserved runners, and the fleet default runner cannot be flagged reserved.

The flag exists for personal machines: a laptop joined as a runner should host "open this repo here", never a 3 a.m. cron routine that happened to fall through placement. Set it at join (`--reserved`; the "Add machine" spot offers a "Personal machine - only runs work you send to it" checkbox) or toggle it on the runner page at any time. The controller's auto-joined local runner is not reserved by default, so a single-machine install keeps hosting scheduled work.

### 6.2 Session supervision

The runner's session supervisor:

- Resolves `SessionSpec.workspaceId` to a directory and starts the session through the harness adapter with a `HarnessRunnerContext`.
- Injects the session's environment: `HERCULE_API_URL` and `HERCULE_TOKEN` (the session token minted by the controller at session start, dead when the session ends), `HERCULE_SESSION=1`, and the git credential configuration derived from the workspace's designated Connection (mechanics in [13-security](./13-security.md)). It makes the `hercule` binary reachable from the session (PATH prepend or absolute path: Open in [15-packaging-and-operations](./15-packaging-and-operations.md)) and materializes the shipped skill files ([11-public-api-and-agent-surface](./11-public-api-and-agent-surface.md)).
- Enforces two runner-owned timeouts, an inactivity timeout and an absolute timeout, since the harnesses have none built in. On expiry the runner stops the session and reports it as exited with the timeout as the reason (the reported outcome is this spec's consolidation; the tickets pin only the two timeouts).
- Enforces the session cap (section 5.3).
- Watches free disk space against a watermark; below it the runner reports itself as not accepting placements.
- Reconciles after a runner restart: it asks each adapter to list its live sessions and reports the outcome to the controller, so sessions the controller believes are running but the runner no longer has are marked exited.

There are no per-session CPU or memory caps.

Defaults (resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)): **inactivity 30 minutes, absolute 8 hours**. Inactivity means no normalized event from the harness while a turn is running - a stuck-harness detector, not an idle-between-turns rule (idle process unloading is ~~the assistant runtime's, [12-assistants](./12-assistants.md)~~ a third timeout, below *(amended 2026-09-25, [#92](https://github.com/theagenticage/hercule/issues/92))*). Both timeouts are about the work, so they are controller-wide defaults with a per-agent override carried on the session spec, never per runner. The disk watermark is about the machine: **10 GiB free** by default, overridable per runner, checked every 60 seconds and before each placement.

*(Amended 2026-09-10, [#67](https://github.com/theagenticage/hercule/issues/67).)* The timeouts ride the wire as `SessionSpec.timeouts { inactivityMs, absoluteMs }`, filled from controller settings `session.inactivityTimeoutMinutes` and `session.absoluteTimeoutMinutes` (whole minutes; 30 and 480 unset) - the runner holds no default of its own. Reconciliation on a `sessionsReport` is a status move, not a stream event: sessions on that runner in `starting | idle | busy` the report does not list go to `exited`, resumable by their native id. An announced shutdown stops every live session with reason `runner_restart` and waits, bounded, for their exits before the goodbye.

*(Amended 2026-09-25, [#92](https://github.com/theagenticage/hercule/issues/92).)* The spec may carry a third timeout, `timeouts.idleMs`: how long the session may sit with no turn before the runner stops its process with reason `idle_unload`, to be resumed in place by the next input. The runner counts it from the moment the session last became idle, ~~its start or the end of its last turn~~ the end of its last turn, or an input refused while no turn was open *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431))*, and a new turn cancels it. *(Amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431).)* The runner does not count it from the start: a start's input that was delivered opens a turn, so a session is never unloaded while it waits for its first turn. It is filled from the controller setting `session.idleUnloadMinutes` (whole minutes; 15 when unset) ~~and set only on assistant conversation sessions~~ on assistant conversation sessions ([12-assistants](./12-assistants.md) section 5.1). A Thread gets none yet, because unloading a Thread's process would also end any background process it started, such as a dev server. *(Amended 2026-10-05, [#83](https://github.com/theagenticage/hercule/issues/83).)* An agent step's session gets a fixed `idleMs` of 5 seconds, which reads no setting. Once its step's turn ends, the run may not prompt it again for days, or ever: the next iteration may wait for a signal. Meanwhile an idle session holds a slot of its runner's session cap, so on a runner with one slot the run's next agent step would wait forever for the slot the finished step holds. The next iteration's prompt resumes an unloaded step session in place, and the resume carries that prompt as its first input ([07-workflows](./07-workflows.md) section 4.2). So a resumed step session is never unloaded while its prompt is on the way. The cost is a resume per iteration, and any background process the agent left running ends at the unload, as it would for a Thread.

*(Amended 2026-10-05, [#355](https://github.com/theagenticage/hercule/issues/355); [#351](https://github.com/theagenticage/hercule/issues/351).)* **A session has a turn running while any of its agents does**, its own agent or one of its subagents ([./06-providers.md](./06-providers.md) section 13). A subagent can still run after the session's own agent's turn has ended, for example a background subagent. So:

- the idle timeout counts from the moment the last open turn of any agent ended, and a new turn of any agent cancels it, so a session is never unloaded while a subagent works;
- the inactivity timeout runs while any turn is open, and any normalized event, whichever agent it belongs to, restarts it.

The supervisor keeps the set of open turns by turn id, because one agent's `turn.completed` must not close another agent's turn.

*(Amended 2026-10-26, [#770](https://github.com/theagenticage/hercule/issues/770).)* **The supervisor ignores async questions.** They hold off neither the idle timeout nor the inactivity timeout, and the end of a turn does not concern them. Only the Requests an agent waits on (a blocking question or an approval) stop the inactivity timeout and hold off the idle timeout, as before. The reason: a thread has no idle timeout, and an agent step's session unloads 5 s after its turn, so an unanswered async question must not keep the runner slot that the run's next step needs. When the session unloads, its exit closes the question, and the question's text stays in the transcript ([./06-providers.md](./06-providers.md) section 6.5). The supervisor's handler for `SessionRespondToQuestion` cancels the idle wait before it hands the answer to the adapter, as the input handler does, so the session is not unloaded between an answer that starts a turn and that turn's `turn.started`. A refused answer starts no turn, so the idle wait comes back.

*(Amended 2026-09-22, [#200](https://github.com/theagenticage/hercule/issues/200).)* Reconciliation needs the runner to come back. A runner that never does - a machine wiped or lost, or one that was gone when the controller restarted - reports nothing, so the controller also ends sessions by itself: a session in `starting | idle | busy` whose runner is not `online`, and about which nothing was heard (its `lastActivityAt`) for longer than its own `SessionSpec.timeouts.absoluteMs`, goes to `exited`. A spec stored before the timeouts were on it is bounded by the default, 8 hours. The absolute timeout is the bound because a runner stops every session process at most that long after the process started, so past it the process is gone, or the runner is gone and can never say so. Before the bound, the session can still be running on a runner that is only out of reach (section 7), and the controller leaves it alone. The rule runs when the controller starts and then once a minute. It is a status move like reconciliation: queued inputs are cancelled with the reason, the session's token dies with it ([13-security](./13-security.md) section 5), the audit entry is `session.reconciled` with reason `runner_lost`, and the session stays resumable where its runner returns with the transcript. One case breaks the bound: a machine that was suspended does not count the suspended time, so its process can outlive the bound (a forward jump of the controller's clock has the same effect). The sessions report closes that gap in the other direction: a session the report lists that the controller holds as `exited` is sent `SessionStop`, because it runs on without a token and blocks a resume of the same session.

*(Amended 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), [ADR 0039](../adr/0039-workspaces-preserve-runner-local-git-state-and-human-work.md).)* Section 6.8 supersedes the managed-only main, standalone-primary, ephemeral-only setup, lease-only retention and deletion-before-confirmation rules in sections 6.3-6.7. Those sections retain the history of the earlier decisions; the accepted lifecycle is section 6.8.

### 6.3 Workspace kinds

A Workspace is a provisioned working area on one runner containing 0..N checkouts. A Checkout is one working copy of one resource; in v1 only git repos are checkout-able.

| Kind | Checkouts | Lifetime | Use |
|---|---|---|---|
| Primary | exactly 1 | long-lived; at most one per (resource, runner) | the resource's **main workspace**, shared by "just open X" sessions |
| Ephemeral, single | 1 | one job | the normal unit for workflow agent steps |
| Ephemeral, scratch | 0 | one job | sessions that need a working directory but no repo (e.g. mail sessions; mail truth lives on the server, reached through tools) |
| Ephemeral, multi-repo | several | one job | one root directory with one checkout subdirectory per resource |

A session may also run with no workspace at all (`workspaceId: null`; cwd rules in section 6.1).

*(Added 2026-10-19, [#768](https://github.com/theagenticage/hercule/issues/768).)* **Checkout subdirectory names.** In a workspace with two or more checkouts, each checkout sits in a folder named after its repo (`Subdirectory` in `@hercule/protocol`): one path segment of 1 to 64 characters, made of letters, digits, `.`, `_` and `-`. Two layers refuse names, each in any letter case:
- The wire type `Subdirectory` refuses `.`, `..` and `.git`. `.` and `..` are the workspace and its parent, and `.git` belongs to git. Only these three are in the schema, so a stored row or a frame that names `.claude` or `.agents` still decodes.
- The controller refuses `.claude` and `.agents` when it lays out a new workspace with several checkouts (a spawn, and a skills preview of the same repos). The harnesses read these two folders from the session's working directory, and in a workspace with two or more checkouts the working directory is the workspace root. A clone with one of these names would put a repository's settings, hooks and skills where Claude Code and Codex load them as the session's own, and no skill listing would show them. The refusal applies only when the controller lays out a new workspace. A workspace laid out before this change keeps its layout, and so does a provision that was still in progress when the controller was upgraded: it finishes with the layout it started with.

A repo called `.github` is fine: a leading dot alone is no reason to refuse a name. A spawn or a skills preview of repos with a refused name fails with a `validation` error that names the repo, before anything is sent to a runner.

Concurrent sessions in one primary workspace are allowed; the UI surfaces the overlap, there is no locking. A dirty primary is the next session's starting reality.

**Workspace status** (consolidated from the pinned lifecycle facts in 6.4, 6.5 and 6.7; [02-domain-model](./02-domain-model.md) mirrors it):

| Status | Meaning |
|---|---|
| `provisioning` | checkout(s) being created, setup command running |
| `ready` | usable; the normal state of a primary and of an ephemeral while its job runs |
| `failed` | setup command failed; the files may be on disk; never handed to a session |
| `lost` | its runner was retired, or the runner reported the directory gone |
| `deleted` | torn down by teardown or the TTL reaper; terminal, record kept |

*(Superseded 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), section 6.8.)* The transitions below are historical. Current removal passes through `disposing`, and current observations may mark a previously ready workspace unavailable.

Transitions: `provisioning -> ready | failed`; `ready | failed -> deleted` (teardown after clean completion, ~~dismissal of the failed run~~ `workspace.dispose` on the failed run's kept workspace *(amended 2026-09-25, [#260](https://github.com/theagenticage/hercule/issues/260))*, or reaping); any non-terminal status `-> lost` on runner retirement. Primaries are `ready` for their whole life unless they become `lost`. The status is the material state on the runner and nothing more: whether an ephemeral is kept for inspection is teardown policy read off ~~its run~~ its Workspace Leases (6.7; *amended 2026-09-27, [#263](https://github.com/theagenticage/hercule/issues/263)*), never a workspace state (resolved 2026-09-01, [Domain model residue](https://github.com/theagenticage/hercule/issues/46): `unusable` renamed `failed`, `kept-on-failure` dropped).

Non-repo resources get no workspaces in v1: folder resources need a versioning story for non-git materials (post-v1), and mailboxes never produce workspaces.

*(Superseded 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), section 6.8.)* Failed preparation may leave files. A fresh primary uses a distinct ID and directory; the old failed record is not marked deleted without a removal outcome. The following earlier rule no longer applies.

*(Amended 2026-09-16, [#72](https://github.com/theagenticage/hercule/issues/72).)* **A failed primary is superseded by the next provision.** "At most one per (resource, runner)" counts only `provisioning` and `ready`. A primary that could not be made holds nothing, so `workspace.provision` and a spawn asking for the main workspace both stand it down - marking it `deleted`, keeping the row and the machine's words as the record of the attempt - and open a fresh one in its place. This is the one way a primary reaches `deleted`; nothing tears one down on request. **Adopt-in-place is not built**: a primary is always a Hercule-managed clone under the runner's storage directory. **The user-facing word for a primary is "main workspace"**; `primary` stays the kind in code, on the wire and in the database.

### 6.6 Toolchains

Toolchains (node, python, go, docker, ...) are the machine owner's responsibility. The runner probes them and reports them as capabilities; placement filters on them. Hercule installs only harness CLIs (section 3.3). Hercule-managed toolchains and a revived Environment concept are post-v1.

The probed toolchain list is deliberately minimal in v1 (resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)): **`git` and `gh`** only, reported as `{ name, version, path }` (raw `--version` output, parsed to semver where it parses). Anything else the owner installs by hand and, if placement needs it, expresses as a user label (`node`, `gpu`); the fuller answer is the post-v1 Environment concept. Placement filters match toolchain names (optionally a semver range) and labels.

*(Amended 2026-09-27, [#263](https://github.com/theagenticage/hercule/issues/263), [ADR 0036](../adr/0036-a-workspace-is-kept-by-leases-its-holders-release.md).)* **A workspace is kept by the leases its holders release.** ~~The sweep reads one kind of fact, the workspace's Workspace Leases, and never the status of a session or a run.~~ *(Superseded 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), section 6.8.)* Active leases still protect use, but the sweep also checks the workspace retention policy; manual workspaces do not expire.

- **Acquire.** A session acquires a lease on the workspace it is placed in, and again when it is resumed; a run acquires one on its workspace when its first workspace step opens it. The lease is active until the holder releases it.
- **Release.** The holder releases its lease with a retention, and the time the workspace is kept until is fixed then: the release time plus the retention's window, read from the settings at that moment. A later settings change moves only later releases.

| Retention | Kept for | Released by |
|---|---|---|
| `none` | nothing: the next sweep may delete it | a run that completed, or was cancelled without `keepWorkspace` |
| `orphan` | `workspace.orphanTtlHours` (default **24 hours**) | a session that exited and cannot be resumed; a session whose conversation is deleted, again |
| `idle` | `workspace.idleTtlDays` (default **30 days**) | a session that exited and can be resumed |
| `inspection` | `workspace.inspectionTtlDays` (default **14 days**) | a run that failed, or was cancelled with `keepWorkspace` |

- **The rule.** The sweep deletes an ephemeral workspace on an online runner once it has no active lease and every lease's kept-until time has passed. ~~The latest lease wins: a thread that joined a failed run's workspace keeps it for its own window, even after the run's window has ended.~~ *(Superseded 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), section 6.8.)* The latest released lease window applies to automatic workspaces. A Thread joining makes the workspace manual before releasing its lease. Every workspace gets its first lease in the transaction that opens it; a workspace with no lease at all would be a fault, and the sweep leaves it alone rather than delete files it cannot account for.
- **Releasing again.** A release also applies to a lease that is already released, and recomputes its kept-until time from the lease's own release time. Deleting an assistant releases each exited session of its conversations again as `orphan`, because nothing can resume those sessions any more.
- **A released lease is kept only where it keeps something.** On a primary, which the sweep never deletes, a lease is deleted when it is released, and acquired afresh when its session is resumed. When a workspace is gone (`deleted` or `lost`), its released leases are deleted with it. Only an active lease matters there: the credential rule reads it, and `Workspace.sessionIds` lists it. So the table does not grow with every session and run that ever ended.
- **The audit `reason`** of `workspace.deleted` is the retention of the lease with the latest kept-until time, with its holder (`run:<id>` or `session:<id>`); `run-completed`, `run-cancelled`, `run-failed` and `run-kept` are retired.
- **`workspace.dispose`** refuses a workspace with an active lease with `invalid_state`, and the message names everything to stop: the run to cancel and the sessions to stop, both when both hold it.
- **Leases carry no actor.** The holder is the actor, and the `workspace.deleted` audit entry records the deletion.

### 6.8 Runner-local Git storage, preparation and ownership

*(Added 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459), [ADR 0039](../adr/0039-workspaces-preserve-runner-local-git-state-and-human-work.md).)* These rules apply equally on the controller's local runner, the desktop Mac's runner and remote supported runners. Locality is path-selection convenience, never a mode choice.

**Selected repository.** One Resource/Runner pair selects existing or managed Git storage. Existing mode registers the canonical working-copy root and discovers its common Git directory through Git, including linked worktrees. Managed mode uses runner-owned bare storage, and new main and ephemeral working copies are worktrees of it. A workflow-only runner need not create an unused main working copy. Repeating the same selection is idempotent; a different path, repository or mode conflicts. No automatic replacement flow is included.

**Adoption.** `workspace.attach` persists the user-supplied path and selected remote, scoped to the selected runner, before delivery. An offline runner receives the same durable instruction later. The controller does not resolve that path on its machine or send it to another runner. Only the user with `workspace.write` may attach external paths; session actors cannot supply them through adoption or ordinary spawn. The runner normalizes subdirectories to the canonical checkout root, exposes the normalized location, and validates the selected remote's canonical identity against the Resource. *(Amended 2026-10-13, [#636](https://github.com/theagenticage/hercule/issues/636).)* Remotes written with the same host are the same repository as written. When the written hosts differ, the runner reconciles an SSH remote by the host SSH connects to: it reads it from `ssh -G`, run in the checkout's directory with the remote's user and port, so it sees the settings Git's own `ssh` sees. An HTTPS or other non-SSH remote is never resolved through the SSH configuration. The evaluation has a deadline. When a host needed for the comparison cannot be resolved, the remotes do not match; an unresolved host is never compared as written. Registration changes no files, branch, remotes, hooks or persistent Git configuration, and performs no clone, fetch or setup. An unavailable or mismatched path fails visibly. A disappeared adopted checkout is unavailable, never recreated; adopting the same restored path again validates it again.

**Starting revisions.** Each new Checkout accepts `startingRevision`: `{ kind: "current" }`, `{ kind: "local", branch }` or `{ kind: "remote", branch? }`. Remote without a branch means the remote default. Without a revision, existing mode uses the selected checkout's current committed state; managed mode uses the fetched remote default. Local/current needs no fetch. Remote requires a successful fetch and refreshes the remote default; failure never falls back to local state. Resolve fully qualified refs in the selected repository and persist the actual `baseCommit` before replay can select an advancing branch. Deprecated `baseBranch` means an explicit remote branch; both fields together are invalid. Frozen historical run policies retain their stored values and are translated visibly rather than rewritten. New worktrees get new branches; dirty tracked files stay in the source. `.workspaceinclude` copies only from the selected main workspace on that runner, retaining visible missing-source warnings.

**Coordination.** Serialize first-use selection/bootstrap per Resource/Runner pair, then shared Git mutations by canonical common-directory identity. Linked-worktree aliases therefore share coordination. Coordinate checkout-index mutations where they touch the same index. Independent repositories proceed concurrently. Do not hold repository coordination through arbitrary setup or a session's lifetime. External Git processes remain outside these locks; respect Git errors and never delete their lock files or force branch occupancy.

**Preparation.** Freeze creation instructions and applicable setup when opening the workspace. The runner durably records creation in progress, preparation started, and terminal ready or failed/interrupted outcomes. Ready means every required checkout and setup completed successfully, recorded before reporting it. Duplicates and reconnects return the terminal result and warnings without rerunning setup. Directory existence never proves readiness. A process death during arbitrary setup reports interruption and never silently repeats the command; recovery creates a fresh workspace. A new failed attempt has a distinct managed directory and cannot recursively delete an earlier attempt. Unreadable registry state requires recovery and cannot be treated as an empty registry.

Setup runs once per newly created managed working copy, including a newly created managed main. Adoption, join, resume and completed replay run no setup. Preserve the scrubbed environment, deadline and credential restrictions of section 6.5 and spec 13 section 9. A later Resource edit cannot change a pending instruction.

**Observation.** `workspace.inspect` requests facts from its runner; `workspace.read` returns persisted state. Record observation time, current branch/HEAD, usable refs and availability for every workspace kind. Inspect at menu decisions, explicit refresh, start/resume and completed turn/exit, coalescing per workspace. Publish changes on the workspace live topic. Offline inspection is an actionable unavailable error; a client may show the last observation's age without claiming it is current. Starting work independently validates the actual repository and requested ref. No idle polling or per-token inspection is introduced.

**Retention and disposal.** Ownership (`managed | adopted`), repository mode (`managed | existing`), retention and active use are separate. Adoption registers an existing checkout through `workspace.attach`; it does not transfer ownership of the files to Hercule. Attached main directories are user-owned; generated worktree paths are managed even when the shared repository is user-owned. A Thread opening or joining a Workspace sets `retentionPolicy: manual` in the lease-acquisition transaction, and this policy survives exit. Backfill existing Thread workspaces. Scratch directories for workspace-less sessions remain transient. Workflow automatic workspaces retain section 6.7's lease windows until a Thread makes them manual. Manual retention never grants credentials or creates an eternally active lease.

Automatic cleanup removes only clean generated paths and never uses force. Tracked changes, untracked files, ignored files and files at a multi-repo root all block cleanup with an actionable retained reason. This includes ignored dependencies and private configuration; no implicit disposable-file list exists. Single-repo worktrees use non-forced Git removal; refusal cannot be followed by recursive deletion. Multi-repo cleanup preflights every checkout and root file, preserves remaining files on refusal, and truthfully records partial removal. The one root file that does not block cleanup is the empty `.git` file the runner writes at the root of a workspace with no single checkout, so Claude Code's search for project settings stops there ([06-providers](./06-providers.md) section 9.4, "The root boundary"). Cleanup removes it only when it is exactly that: a regular file with no bytes. A `.git` that is a directory or holds anything blocks cleanup like any other root file. Committed branches and source repositories survive removal.

Explicit `workspace.dispose { id, discardChanges? }` may force-remove only known managed workspace paths when the user explicitly chooses `discardChanges: true`; automated cleanup cannot set it. Active holders refuse disposal. `workspace.detach { id }` forgets an attached primary registration with no filesystem deletion, refuses active holders, and explains existing derived worktrees. Those worktrees retain their source binding and remain usable while that Git repository exists.

Reserve `disposing` in the database transaction that checks leases, retention and ownership. Admission, join and resume recheck readiness in their lease-acquisition transaction and refuse `disposing`. Filesystem I/O happens outside transactions. Mark `deleted` only after confirmed removal; refusal restores an available record with its reason, and interrupted transport leaves durable idempotently retriable intent. Detachment uses the same admission protection but never removes files.

**Compatibility.** Add migrations without editing old ones. Preserve IDs, file contents, branches, Git topology and harness transcript associations. Existing standalone main clones remain the selected repository for new local work; cache-derived ephemerals retain the old cache, and a cache-only selection stays bare. No branch copying, moving, resetting or clone conversion occurs. Bind each new Checkout to its actual repository. Capability/version negotiation rejects unsupported adoption, revision, inspection and safe disposal visibly; never send an older runner unsafe substitute semantics. Legacy reads remain available.

## 7. Runner lifecycle and connectivity

A runner carries two independent axes. **Connectivity** (`online | offline | unreachable`) is written only by Runner Connections, from the socket. **Lifecycle** (`active | draining | retired`) is written only by user operations. They vary independently - a `draining` runner can be `unreachable` at the same time, and the controller reports both rather than collapsing them into one state.

### Connectivity

| Connectivity | Meaning | Placements | Sessions |
|---|---|---|---|
| `online` | connected, hello complete | accepted (subject to cap, watermark and lifecycle) | running |
| `offline` | announced shutdown: outbox flushed, sessions cleanly interrupted and resumable | wait for return | interrupted, resumable |
| `unreachable` | silence: no announcement, connection lost | wait for return | unknown; UI shows "state unknown, last seen X" |

### Lifecycle

| Lifecycle | Meaning | Placements | Sessions |
|---|---|---|---|
| `active` | normal fleet member | accepted (subject to cap, watermark and connectivity) | running |
| `draining` | user-initiated: no new placements, running sessions finish | refused | run to completion |
| `retired` | terminal: credential revoked, workspaces marked lost, session records preserved but unresumable | refused | none |

Transitions (the tickets pin the two axes, drain -> retire, drain -> active (`runner.undrain`), and force-retiring an unreachable runner; the rest of this list is this spec's consolidation):

- `online -> offline` on an announced shutdown; `offline -> online` on reconnect (outbox replays).
- `online -> unreachable` when the socket drops without an announcement and stays down; `unreachable -> online` on reconnect (outbox replays). An `unreachable` runner's sessions may well still be running; the controller reports honestly that it does not know.
- `active -> draining` by user action; `draining -> active` by user action (`runner.undrain`), cancelling a drain in progress.
- `active | draining -> retired` by user action once sessions have finished, or immediately by force. Force-retiring a runner whose connectivity is `unreachable` is allowed with an explicit confirmation.
- `retired` is terminal. Re-enlisting the same machine creates a new runner: new identity, credential, name and labels, a new storage directory, no workspace adoption. The old records stay under the retired runner.

Silence threshold (resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)): WebSocket ping every **15 seconds**; `online -> unreachable` after **60 seconds** without a pong (four missed intervals). Reconnect backoff is section 2.3's (1 s doubling to 30 s, reset on wake or network change).

*(Corrected 2026-09-05, [#61](https://github.com/theagenticage/hercule/issues/61).)* The 15 seconds and the 60 are a **protocol `Ping`/`Pong` pair, not a WebSocket control frame.* A runtime answers a control-frame ping for its process, so a control frame proves the machine is up rather than that the runner is; and the server-owned socket the upgrade yields has no ping to send. The controller sends `Ping`, the runner answers `Pong`, and only a `Pong` advances what the silence window is measured from. The runner answers a `Ping` without waiting for any session's work, so a harness that is slow to start never makes its runner look silent *(amended 2026-10-05, [#431](https://github.com/theagenticage/hercule/issues/431); section 2.2)*.

## 8. Promotion and portability

Promotion moves the controller to another machine by migrating its state; it is never a live handoff, and there is never a moment with two authoritative controllers ([ADR 0005](../adr/0005-promotion-is-migration-behind-a-stable-controller-identity.md)).

### 8.1 Logical controller identity

The controller has a persistent identity: an id plus key material, created at install and carried in the bundle. Runners authenticate that identity at whatever address it appears. Address announcements and the forwarding pointer (8.3) are signed with it, so "controller moved" cannot be spoofed. Because the new machine resumes the same identity, runner seq/ack state and outboxes continue as if the controller had merely reconnected.

### 8.2 The pull ceremony

Old controller A, new machine B.

1. **Mint.** On A (CLI or web app) the user mints a short-lived, single-use promotion token. Minting freezes nothing. Authority originates on the controller, mirroring runner join: nobody on the network can pull state uninvited. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* The CLI form is `hercule controller promotion-token create`. It prints the `hercule promote` command for B. A does not know the address B reaches it at, so `--from` is the URL the CLI reached A at; when that is loopback, the command holds a placeholder and the CLI asks the user to fill it in. Creating a token invalidates any earlier one not yet spent.
2. **Run.** On B the user runs `hercule promote --from <A-addr> --token <t>`. The command binds B's port so it can answer probes, then contacts A. Install, moving day and promotion are one story: `promote` is auto-initialization with the Data Root arriving by pull ([15-packaging-and-operations](./15-packaging-and-operations.md)). *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* Optional flags: `--address <B-addr>` (required when B's `bind.host` is loopback or a wildcard), `--yes` (skip the confirm prompt), `--no-service` (skip the Service Unit and run the controller in the foreground). B does not bind its port before the switch, since nothing probes it (step 3); it checks the port is free instead. Every check that needs no answer from A runs before the transfer, because the transfer spends the token: the token's format, an empty Home and an empty Master Key store, the Service Unit can be installed, the port is free. *(Amended 2026-10-10, [#103](https://github.com/theagenticage/hercule/issues/103).)* B checks the Home is empty by reserving it: it takes the controller lock and claims the database's name with a placeholder database, and holds that lock until the switch is done. *(Amended 2026-10-18, [#109](https://github.com/theagenticage/hercule/issues/109).)* The reservation holds two locks until the switch is done. The first is the controller lock: the exclusive lock on `controller.lock` in the Data Root, the same lock a running controller holds ([04-state-store](./04-state-store.md), Engine and driver). `promote` takes it when it starts reserving and never deletes the file. So a controller started in the Home meanwhile cannot take the lock and refuses to start, and a second `promote` into the same Home finds it taken. A leftover `controller.lock` is harmless: the empty-Home check ignores it. The second is an exclusive SQLite lock on the database file, as before this change: the placeholder database holds it under the database's name, and the received database is locked the same way before it is renamed into place. A Hercule from before this change knows only the lock on the database file, so this lock keeps an older binary from starting in the Home while it is being received. A `promote` whose process is killed cannot clean up: it leaves its directory in `promotion-transfer/`, the placeholder under the database's name, `controller.lock`, and the Master Key if it had created one. The next `promote` refuses that Home as not empty, as it refuses any Home that holds a database, and the user clears it by hand. Whether a `promotion-transfer/` directory exists decides nothing, because A uses one too.
3. **Probe.** A, over its live runner connections, asks each runner to check that it can reach B's address. The confirm screen shows the fleet with a check per runner. The user states or confirms B's reachable address here (detected default, overridable; plain `IP:PORT` fully supported, nothing assumes Tailscale). *Specified but droppable for v1: shipping without the probe changes nothing structural.* *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* The probe is not shipped.
4. **Confirm.** The commit point, before anything freezes. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* Before it, B shows what a read of A answered: the controller id and each runner with its connectivity. `--yes` skips the confirm. Without a terminal and without `--yes`, `promote` refuses. Declining leaves A serving and the token unused.
5. **Transfer.** A goes read-only and streams the bundle: the SQLite database plus secrets packed at export (re-encrypted under a key derived from the promotion token; B re-wraps them under its own master key, which never leaves a machine: [13-security](./13-security.md)). Mutating operations fail with `promotion_in_progress` (409); GET still answers. *(Amended 2026-10-10, [#103](https://github.com/theagenticage/hercule/issues/103).)* So do `HEAD` and the operations that change nothing but take a body, which the operation table marks `readOnly` ([11-public-api-and-agent-surface](./11-public-api-and-agent-surface.md) section 1.5). ~~Event pollers, the scheduler and placement skip their ticks for the same window.~~ *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* Event pollers, the scheduler, placement and every other background pass wait for the same window, and run once A serves again. So do a runner's session reports, and A starts no queued session and sends no queued input, because B would start or send them again. In-flight sessions on runners keep running. The freeze expires with the promotion token, so a transfer that never switches lifts on its own. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* The token is spent on transfer, not on switch. The freeze waits for the requests and background passes already running to finish before the copy starts. Workflow runs wait between two of their writes, never inside one: a step that waits or calls a plugin keeps going, and its record ends once A serves again. A step's result a runner reports is held the same way, and the runner keeps it until A has recorded it. When A seals instead, B has those records still running: B asks the runner for a workspace step's result again, and fails a plugin step that was in flight with `interrupted`, as after any restart. ~~A read still records the use of the credential it carries: a login token's renewed expiry and an API key's last use are written on A after the copy, so B has older values, which changes nothing a user notices.~~ *(Amended 2026-10-10, [#103](https://github.com/theagenticage/hercule/issues/103).)* From the copy until the freeze ends, A's database refuses every write, so a writer the freeze did not stop fails loudly instead of writing a change B never receives. The seal is the one write after the copy; A's database refuses writes after it too, also after a restart, until `--force-unseal` (8.3). Reads keep working, inside a transaction too. A read made while frozen records no use of the credential it carries: a login token's expiry is not renewed and an API key's last use is not updated, so A and B hold the same values. A login token close to its expiry may need a new sign-in on B. An OAuth refresh waits for the freeze as well, before it calls the provider: many providers invalidate the old refresh token when they hand out a new one, so a refresh after the copy would leave B holding a token that no longer works. A runner that dials A while frozen gets no hello until A serves again, when it gets its hello, or seals, when it gets the forwarding pointer (8.3); a runner whose hello deadline passes first dials again. A connected runner's liveness answers and machine reports are not recorded while frozen, and its departure is recorded once A serves again. A probe of a provider instance stores its snapshot once A serves again, and drops it once A seals. The bundle carries the database and one file per attachment row; a file with no row (an upload that never finished) stays behind. *(Amended 2026-10-18, [#312](https://github.com/theagenticage/hercule/issues/312).)* ~~It also carries one ustar archive per Skill Revision row, driven by the `skill_revisions` rows, not by the folders under `<Data Root>/skills/`, so the archives keep each file's mode. A row whose folder is missing fails the promotion, as a missing attachment does. B computes each archive's hash and refuses the transfer when one does not equal its row's hash ([04-state-store](./04-state-store.md)). Today's transfer copies only `attachments/`; [#732](https://github.com/theagenticage/hercule/issues/732) builds this.~~ *(Amended 2026-10-18, [#732](https://github.com/theagenticage/hercule/issues/732).)* It also carries one archive per distinct hash in `skill_revisions`: the revision's stored `<Data Root>/skills/<revisionHash>.tar`, sent as it is, so each file's mode travels with it. The rows drive the transfer, not the files: a row whose file is missing fails the promotion, as a missing attachment does. B refuses the transfer when its header does not list exactly the hashes in the received `skill_revisions`, once each, and when an archive fails its checks, its hash among them ([04-state-store](./04-state-store.md)). *(Amended 2026-10-10, [#103](https://github.com/theagenticage/hercule/issues/103).)* A writes its copy of the database, and B saves the whole transfer before it unpacks it, in `promotion-transfer/` in its own Data Root ([15-packaging-and-operations](./15-packaging-and-operations.md) section 5), never in the system's temporary directory: that is held in memory on many Linux systems and can be too small for a whole database. Each machine removes what it wrote there when the transfer ends, however it ends. A session event a runner reports between A's copy and that runner's reconnect to B is not on B: until #145's outbox and #492's replay land, promote while no agent is working.
6. **Switch.** A announces the new address (signed) and seals itself. Runners reconnect to B and replay their outboxes. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* B posts the spent token to A's switch path with `{ newAddress }`; a repeated switch gets the same answer, so B retries it while A cannot be reached. A persists sealed state, sends `ForwardingPointer` to every connected runner, and answers later dials with the same frame instead of hello. One frame serves both: the announcement and the forwarding pointer carry the same signed address. Each runner verifies the Ed25519 signature against the public key pinned in `runner.json`, rewrites `controllerUrl`, and reconnects, A's local runner included. B then installs the Service Unit (`hercule serve`), or with `--no-service` runs `hercule serve` in the foreground.

Aborting at any point before step 5 restores A untouched. Cold move: no drain phase, no session interruption. *(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* After the transfer, B undoes a failure on both machines when it can:

- **The transfer or B's unpacking fails, or A refuses the switch.** B cancels the transfer (a `DELETE` on the transfer path with the spent token), which ends A's freeze, so A serves again. B empties its Home (database, attachments, Master Key). A retry starts from a new token. *(Amended 2026-10-10, [#103](https://github.com/theagenticage/hercule/issues/103).)* Unpacking also fails, before B writes any received data to its Home, when the transfer names another controller id than the preview of step 4 showed: the preview and the transfer are two requests, and something between the machines, such as a load balancer or a changed DNS record, can send them to different controllers.
- **A cannot be reached to switch.** B cannot tell whether A sealed. The cancel tells it once A answers: a sealed A refuses the cancel with the address it sealed to. If that is B's address, B finishes the promotion. If A cannot be reached at all, B keeps the received Home and says how to tell the two cases apart by hand. A that heard nothing more stays read-only until the token expires, and then serves again.

*(Added 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* A serves four promotion routes. Each takes the promotion token as `Authorization: Bearer`. None is an operation of the public API: the caller holds a token, not a user credential, so no grant applies and no CLI row exists, and A's audit entries name the system as the actor. They sit behind neither the pre-setup gate nor the promotion gate; each checks A's phase itself. Refusals use the error envelope ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md) section 1.5).

- **`GET /api/v1/controller/promotion-transfer`** previews the transfer for step 4. It answers `{ controllerId, runners: [{ name, connectivity }] }`, every runner that is not retired. It changes nothing and does not spend the token. It is `unauthenticated` for a token that is not live and unused, `promotion_in_progress` while another transfer holds the freeze, and `controller_sealed` once A is sealed.
- **`POST /api/v1/controller/promotion-transfer`** spends the token, freezes A, and streams the transfer (`application/octet-stream`). It is `unauthenticated` for a token that is not live and unused. ~~The token is spent before the freeze, so it is used up even when the freeze is then refused: `promotion_in_progress` while another transfer holds it, `controller_sealed` once A is sealed, and `invalid_state` when the running work has not finished within 60 seconds or an attachment's file is missing.~~ *(Amended 2026-10-10, [#103](https://github.com/theagenticage/hercule/issues/103).)* It is `promotion_in_progress` while another transfer holds the freeze and `controller_sealed` once A is sealed, and both leave the token unspent, because spending it is a write A refuses then. Otherwise the token is spent before the freeze, so it is used up even when the freeze then fails with `invalid_state`: the running work has not finished within 60 seconds, or an attachment's file is missing. A stream that breaks off ends the freeze.
- **`DELETE /api/v1/controller/promotion-transfer`** cancels: it ends the freeze of the spent token's transfer and answers `204`, also when that freeze has already ended. It is `unauthenticated` for a token that was never spent, and `controller_sealed`, with the address, once A is sealed.
- **`POST /api/v1/controller/promotion-switch`** takes `{ newAddress }`, an http or https origin with no user name or password (`validation` otherwise), seals A, and answers `200 { newAddress }`, the address A sealed to. It is `unauthenticated` for a token that was never spent, and `invalid_state` when A is not frozen for that token's transfer (cancelled, expired, or restarted). A switch repeated with the token that sealed A gets the same answer; with any other token it is `controller_sealed`.

### 8.3 Sealing and fencing

After promotion A is sealed: it refuses to serve and answers anything that dials the old address (runners that missed the announcement, stale browser bookmarks) ~~with a signed forwarding pointer naming B~~ with B's address *(amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103))*:

- A runner gets the signed `ForwardingPointer` frame in place of the hello (section 2.2), and verifies it against the controller identity it pinned.
- A browser, the CLI, or any other API client gets the HTTP error `controller_sealed` (503) carrying `details.newAddress`, for every operation except `setup.read`, whatever credential it sends ([./11-public-api-and-agent-surface.md](./11-public-api-and-agent-surface.md) section 1.5). That error is not signed, because these clients pin no key to check it with. The web app's files are still served, so a bookmark loads the page, and its API calls get that error.

Un-sealing requires an explicit force flag (disaster recovery only). When A is fully gone, the last-resort escape hatch is a local re-point command run on each runner.

*(Amended 2026-10-09, [#103](https://github.com/theagenticage/hercule/issues/103).)* The force flag is **`hercule serve --force-unseal`**: it clears sealed state at boot and this machine serves again. The other machine may still be serving under the same identity. A sealed controller that boots without the flag stays sealed.

The re-point command (resolved 2026-08-31, [#43](https://github.com/theagenticage/hercule/issues/43)) is **`hercule runner set-controller <url>`**: it keeps the runner's existing credential and verifies at hello that the identity at the new address is the one it enrolled with; on mismatch it refuses with "this is a different controller; use `hercule runner join`". A fresh join token is never needed for a re-point, because a controller that cannot resume the logical identity is by definition a different controller - and that path is re-enlistment, not re-pointing.

### 8.4 Bundle fallback

When A and B cannot see each other: export a bundle file on A, carry it, import on B. Pull is internally export plus import, so both paths produce the same result.

### 8.5 Portability rules

- **The bundle is relocatable.** Controller-owned paths are relative to the Data Root; the paths of adopted checkouts remain scoped to their runner as opaque facts that promotion never rewrites (amended 2026-10-07, [#459](https://github.com/theagenticage/hercule/issues/459)); the rules are stated once in [04-state-store](./04-state-store.md).
- **Secrets are packable**: the running controller can enumerate and extract them for export. Keychain storage is allowed; write-only machine-bound storage is not ([13-security](./13-security.md)).
- **Future artifact or blob storage lives inside the Data Root** and moves with the bundle; streaming or resumable transfer is the escape hatch if volume ever hurts.

### 8.6 Fleet continuity

- A's local runner is an ordinary fleet member and survives promotion as itself: same identity, name, workspaces; it re-points to B like every other runner. No retire, no re-enlist. "Laptop" stays named "laptop".
- B gets a fresh auto-joined local runner, standard controller behaviour.
- The fleet-level default runner is unchanged by promotion. Promotion changes who the brain is, not where work runs.
- "Local" (section 5.4) resolves on the client device and therefore follows the user, not the controller.

## Post-v1

- Fleet auto-discovery and push-install; v1 keeps the fully programmatic join exchange and the reserved "Add machine" spot.
- Plan-shipping to runners (self-orchestration while disconnected); v1 keeps hello capability negotiation so it lands without a protocol break.
- Native OS sandboxing (macOS Seatbelt, Linux Landlock), containers as a remoter option; both return as a probed runner capability behind hello negotiation.
- Hercule-managed toolchains and an Environment concept (named toolchain plus setup bundles); v1 keeps toolchains as probed facts and the setup command in controller state.
- Folder-resource workspaces; v1 workspaces are git-only.
- Runner-side plugin loading; v1 runner-side harness execution is built-in but plugin-shaped ([05-plugins](./05-plugins.md)).
- Load balancing, session migration and failover between runners; v1 pins work where it lands.
- Windows runners.
- Artifact storage on the controller; when it lands it lives inside the Data Root (8.5).
