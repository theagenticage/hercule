# Proposing is not doing

A decision Notification's bound actions are proposals: an agent session, a run's notify step, a plugin or the core attaches a frozen contract operation to an answer, and the operation runs only when the user chooses that answer, as the user, under the user's full parity. We decided that authoring is *not* checked against the proposer's permission profile - a `worker` session that may not call `workflow.run` may still propose "Start Bugfix" - because the click is the authorisation, not the proposal. The alternative, validating the bound operation against the producer's profile at creation, was rejected on two grounds: it does not close the hole it aims at (in the shipped triage topology the notification is created by an ungated `run:<id>` action step from the agent's structured output, so a session-side check fences a path with no gate in it), and it blocks the product's value center, agents preparing and proposing work they may not perform themselves, including asking the user a question whose answers reply into their own session. What makes the click safe instead: every contract operation renders its own `describe(input)` line, shown by the core on every answer on every surface and never authored or suppressed by the producer; a small set of operation families (credential, secret, infra, permission, connection.manage, bulk-destructive) is not bindable by non-core producers because no one line can make those clicks informed; and the audit entry names decider, proposer and channel. Accepted cost: an agent can put anything else in front of the user, so the quality of the describe line and of the decision UI carries the security weight a profile check would otherwise carry.
