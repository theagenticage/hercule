# Provider adapter is a thin interface behind a normalized event stream

A provider is specced as two named surfaces: a **ProviderDefinition** (controller-side static self-description: identity, config schema, declared capabilities), registered by the provider plugin, and a **ProviderAdapter** (runner-side execution surface: `probe` plus five session methods - `startSession`, `sendInput`, `interrupt`, `respondToRequest`, `stopSession` - plus `listSessions` for reconciliation) whose only output channel is one stream of normalized events. Normalization happens at the runner, closest to the vendor protocol, with a tagged `raw` passthrough per event; the runner-controller protocol stays vendor-agnostic. This copies the shape t3-code proved against five harnesses (thin imperative adapter + fat event union) rather than per-concern RPC surfaces or vendor-passthrough events.

**Amended 2026-10-01 ([#309](https://github.com/theagenticage/hercule/issues/309)):** `respondToRequest` is split in two. `respondToApprovalRequest` takes a decision on an approval, and `respondToQuestion` takes the answers to a question, so the adapter has six session methods. An approval and a question take different inputs, and one method taking either would leave each adapter to sort out which it was given ([spec 06](../spec/06-providers.md) section 6.5). The shape of the interface is unchanged: thin, imperative, and one normalized event stream out.

**Amended 2026-10-11 ([#282](https://github.com/theagenticage/hercule/issues/282)):** the adapter gains a one-shot method, `generateText`, beside `probe` and the session methods. It makes one model call with no tools, no workspace and nothing persisted, and returns the call's outcome directly rather than through the event stream, because a text generation has no session for events to belong to. This is a second kind of work for the adapter, not a change to the session surface: the session methods and the one normalized event stream are unchanged. The reasons are in [ADR 0041](./0041-text-generation-is-one-model-call-on-a-runner.md), and the method in [spec 06](../spec/06-providers.md) section 14.

**Amended 2026-10-28 ([#896](https://github.com/theagenticage/hercule/issues/896)):** adapter failures are tagged errors, not strings. `startSession` and `sendInput` fail with an `AdapterError`, a union of tagged errors defined in `@hercule/protocol` so they cross the wire: `HarnessNotInstalled`, `HarnessLoginMissing`, `SessionAlreadyRunning`, `ResumeTranscriptMissing`, `SessionNotRunning`, `InputNotDelivered`, `SteerRefused`, `ModelChangeRefused`, `HarnessProtocolError`, and the catch-all `AdapterFailed`, which carries a message for any failure that has no tag of its own. `respondToQuestion` fails with its own `AnswerNotDelivered`, which is not in the union. The tag travels on `SessionInputResult`, which is also the answer to a start's input. The interface is still thin: it gains an error type, not a method. The reasons and the per-tag table are in [spec 06](../spec/06-providers.md) section 4.

**Amended 2026-10-30 ([#406](https://github.com/theagenticage/hercule/issues/406)):** [ADR 0048](./0048-harnesses-and-provider-accounts-are-separate.md) renames the adapter to the Harness Adapter and its `ProviderDefinition` to the `HarnessDefinition`, and gives the name `ProviderDefinition` to a new contribution, a Provider's: the company that serves the models. The adapter's surface is unchanged. Every call that runs a harness for an account now names the Provider Account, the harness and the Harness Home the controller resolved, where it named a provider instance.

- **The runner owns the words and the thread's failure row.** The adapter says what failed and the supervisor adds how to fix it (the install or login command, which only the supervisor can name). The runner writes `runtime.error` with `class` set to the tag (not for `SteerRefused`, which is no failure, nor for a duplicate start, which is a no-op), and nothing reads `class` for behaviour. A failed start ends the session, but a mid-session `HarnessProtocolError` does not: the controller gives up on an input before a slow harness answers, so a crash exit could run a requeued input twice. The message is written for the user and shown as written.
- **The controller owns the input's fate, per tag.** The input goes back to waiting when the harness certainly did not take it and trying again can work. It fails when the harness may have taken it, or when the setup would fail the same way again. The controller never writes `runtime.error`.
- **Why a tag and not a string.** A string cannot tell a refused steer, which is no failure, from a missing harness, which is. The controller would have to read the words, and words change.
- **This follows t3-code's shape.** t3-code's adapters fail with a union of tagged errors, not with strings (`packages/provider-core/src/server/ProviderAdapter.ts`, checked 2026-10-28). The two differ in what a tag names. t3-code's tags name the operation that failed (`ProviderAdapterTurnStartError`, `ProviderAdapterSteerRunError`) and carry the driver and a cause, with the message built from fixed text. Hercule's tags name what went wrong, because the controller reacts to the cause and not to the operation, and the tag crosses a network boundary, so it carries the user's message and no cause object. t3-code's `OrchestrationV2ProviderFailure` (`packages/contracts/src/orchestrationV2.ts`) is a class, message, code and retry hint on a failed turn; Hercule's `runtime.error` is its counterpart.

Consequences worth recording:

- **Turn semantics are adapter-authored.** A turn is the user-visible episode (user input until the agent goes idle). Adapters mint turn ids where the vendor has none (Claude), pass native ids through where they exist (Codex), and open synthetic turns for unsolicited output. Steering (delivering input into a running turn) is implicit in `sendInput`: busy session steers, idle session opens a turn, and the result reports which happened (`delivery: "opened" | "steered"`). The adapter is the authority on what happened - never event-order inference.
- **The input queue is controller-owned domain state**, not a vendor feature. Queued input is editable and cancelable until the controller flushes it on `turn.completed`. Vendor-native queues (Codex follow-up `turn/start`, pi `followUp()`) go unused: they are process-local (less durable than the controller DB) and can't offer editing. The only cost is sub-second flush latency over the runner WebSocket.
- **Degradation is declared, never silent** (deviation from t3-code, ~~which offers every access mode on every provider and degrades in prose only~~ *amended 2026-10-28, [#896](https://github.com/theagenticage/hercule/issues/896): t3-code now reads `supportedRuntimeModes` from each provider instance's snapshot and falls back to a fixed `approval-required` when a thread's mode is not supported, `apps/server/src/orchestration-v2/RuntimePolicy.ts`; Hercule's fallback is the closest less permissive mode, not one fixed mode*). The definition declares per-mode and per-feature support as pure facts (`accessModes: native | unsupported`, `steering`, `fork`, `mcpPassthrough`); *which* mode an unsupported mode falls back to is controller policy (shipped default: `auto` falls back to `auto-accept-edits`, its closest behavioral neighbour), resolved before the session starts so adapters only ever receive modes they natively support. Amendment (2026-08-28, from [ADR 0015](0015-secrets-are-encrypted-per-value-under-a-keychain-held-master-key.md)'s ticket, the security model): the fallback chain is hardcoded in v1, not a configurable map, and only ever moves to a less permissive mode. The UI derives affordances from declaration plus policy, per the capability-not-provider-name rule inherited from old agentick. The security model settled the guardrail: the chain never escalates permissiveness.
- **`readThread`/`rollbackThread` are deliberately absent from v1.** The controller's normalized per-session stream is the observable record; provider-history rollback returns with the checkpoint/revert feature (t3-code's paired git-ref + `rollbackThread` design is the reference).
