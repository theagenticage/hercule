# Provider adapter is a thin interface behind a normalized event stream

A provider is specced as two named surfaces: a **ProviderDefinition** (controller-side static self-description: identity, config schema, declared capabilities), registered by the provider plugin, and a **ProviderAdapter** (runner-side execution surface: `probe` plus five session methods - `startSession`, `sendInput`, `interrupt`, `respondToRequest`, `stopSession` - plus `listSessions` for reconciliation) whose only output channel is one stream of normalized events. Normalization happens at the runner, closest to the vendor protocol, with a tagged `raw` passthrough per event; the runner-controller protocol stays vendor-agnostic. This copies the shape t3-code proved against five harnesses (thin imperative adapter + fat event union) rather than per-concern RPC surfaces or vendor-passthrough events.

**Amended 2026-10-01 ([#309](https://github.com/theagenticage/hercule/issues/309)):** `respondToRequest` is split in two. `respondToApprovalRequest` takes a decision on an approval, and `respondToQuestion` takes the answers to a question, so the adapter has six session methods. An approval and a question take different inputs, and one method taking either would leave each adapter to sort out which it was given ([spec 06](../spec/06-providers.md) section 6.5). The shape of the interface is unchanged: thin, imperative, and one normalized event stream out.

Consequences worth recording:

- **Turn semantics are adapter-authored.** A turn is the user-visible episode (user input until the agent goes idle). Adapters mint turn ids where the vendor has none (Claude), pass native ids through where they exist (Codex), and open synthetic turns for unsolicited output. Steering (delivering input into a running turn) is implicit in `sendInput`: busy session steers, idle session opens a turn, and the result reports which happened (`delivery: "opened" | "steered"`). The adapter is the authority on what happened - never event-order inference.
- **The input queue is controller-owned domain state**, not a vendor feature. Queued input is editable and cancelable until the controller flushes it on `turn.completed`. Vendor-native queues (Codex follow-up `turn/start`, pi `followUp()`) go unused: they are process-local (less durable than the controller DB) and can't offer editing. The only cost is sub-second flush latency over the runner WebSocket.
- **Degradation is declared, never silent** (deviation from t3-code, which offers every access mode on every provider and degrades in prose only). The definition declares per-mode and per-feature support as pure facts (`accessModes: native | unsupported`, `steering`, `fork`, `mcpPassthrough`); *which* mode an unsupported mode falls back to is controller policy (shipped default: `auto` falls back to `auto-accept-edits`, its closest behavioral neighbour), resolved before the session starts so adapters only ever receive modes they natively support. Amendment (2026-08-28, from [ADR 0015](0015-secrets-are-encrypted-per-value-under-a-keychain-held-master-key.md)'s ticket, the security model): the fallback chain is hardcoded in v1, not a configurable map, and only ever moves to a less permissive mode. The UI derives affordances from declaration plus policy, per the capability-not-provider-name rule inherited from old agentick. The security model settled the guardrail: the chain never escalates permissiveness.
- **`readThread`/`rollbackThread` are deliberately absent from v1.** The controller's normalized per-session stream is the observable record; provider-history rollback returns with the checkpoint/revert feature (t3-code's paired git-ref + `rollbackThread` design is the reference).
