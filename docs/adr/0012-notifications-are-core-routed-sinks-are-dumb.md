# Notifications are core-routed; sinks are dumb

Every notification - from core internals (breaker tripped, run failed, runner unreachable), from a workflow's built-in `notify` action step, or from a plugin via a requestable `notifications` plugin capability (e.g. Gmail warning its OAuth token is expiring) - is one persisted core-owned Notification record. Delivery is core-push, never plugin-claim: the web-app inbox always records it, and the core router alone decides fan-out to delivery sinks. A sink is a channel contribution that optionally implements notification delivery - it rides the existing channel extension point, keeping the fixed v1 set of four intact - and the user toggles delivery per channel connection. The v1 routing policy is deliver-to-all-enabled: duplicates are the user's explicit configuration, visible and self-fixable. Producer-side muting (silence a chatty plugin's notifications) is distinct from sink-side toggles (stop delivering to Discord). We considered a notifications host service plugins subscribe to and self-decide delivery from - rejected because it makes dedup impossible and forecloses centralized smarts; and priority-order first-success routing - rejected for v1 because a failed first hop silently swallows the notification. Because routing decisions live only in the core, presence-aware delivery ("desktop idle, send to phone") lands post-v1 as a router upgrade without touching any plugin; the standing commitment is that the sink contract grows additively (device class, presence, receipts), with sinks reporting nothing treated as always-available. Accepted cost: sinks cannot exercise channel-specific judgment about what deserves delivery, and a second delivery path bypassing the router is forbidden even where it would be convenient.
