# Assistants remember through distilled memory, not merged sessions

An assistant is long-lived but provider sessions are finite, so something must carry identity across time. We resolve it with per-container conversations and generational sessions: a conversation is one platform container (a Discord channel or DM, a Slack thread, a web chat), each with its own session lineage; when the live session hits a context-size ceiling or a timer, it is rotated - what matters is distilled into memory, a fresh session continues the conversation, and the old session's subscriptions migrate to the successor. Distillation is part of the rotation contract, not an optional pass. Memory is assistant-scoped, topic-indexed markdown held by the controller: maintained by the assistant itself, visible and editable by the user, hard-bounded in size, injected at session start; transcript recall is full-text search over the assistant's own conversations. No vector store anywhere in v1. Field research over OpenClaw, Hermes (NousResearch), nanobot, and Letta Code (`research/assistant-systems.md`) shows unanimous convergence on this shape, and two of its rejections are deliberate: OpenClaw's default of merging all DMs into one everlasting "main session" - the one-brain feel comes from shared memory plus recall, never from merged transcripts (reinforced by Letta's migration away from vector archival memory to markdown); and per-channel personas on a single assistant - a different context means a different assistant with its own memory, because two writers on one memory corrupt it (Hermes documents exactly this failure). Consequence: cross-assistant recall is post-v1 and will arrive as agent-to-agent communication, not shared storage.
