# Git credentials derive from Connections, delivered on demand

Runners never hold user-managed git credentials; clone/fetch/push auth derives from the GitHub Connection of the checkout being touched. The runner configures each session with a git credential helper (via `GIT_CONFIG_*` env) that asks the runner daemon, which resolves checkout -> resource -> Connection and fetches the token from the controller on demand - nothing lands on runner disk, and short-lived tokens become a drop-in upgrade. With `credential.useHttpPath=true` plus a username hint the helper resolves identity per checkout, so one workspace can mix GitHub accounts at the git level. The `gh` CLI is the binding constraint: it acts as one account per host per process, so each session gets `GH_TOKEN` injected from the workspace's designated Connection. Identity follows the repo, never the agent, in v1; per-agent git identity is a post-v1 policy addition (an agent -> Connection association) on this unchanged plumbing. The rejected alternative - runner-local, user-managed auth (`gh auth login` per machine) as the primary model - fails multi-identity exactness and requires N manual logins across a fleet; it survives only as the documented fallback for non-GitHub remotes.
