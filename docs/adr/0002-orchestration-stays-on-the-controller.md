# Orchestration stays on the controller; runners host sessions and workspaces

Runners could self-orchestrate (ship them a whole execution plan, gaining progress while disconnected), but v1 places only sessions and workspaces on runners: the controller alone interprets execution plans, schedules steps, and owns all domain state, while runners own material state (workspace files, provider-native session data, an event outbox). One brain keeps scheduling, subscriptions, and the event log in one place, and honest disconnect semantics (a disconnected runner keeps running its *sessions*, buffers events, and replays on reconnect - but plan progression waits) turned out to cover the laptop-sleep reality without splitting the brain. The controller-runner protocol negotiates a capability list at hello, so plan-shipping can be added later as an optimization without a protocol break. Placement is deliberately dumb: capability filter, then explicit choice, then default runner; work pins where it lands (workspaces and provider session state are that machine's disk) and queues when its runner is full - no load balancing, no migration, no failover in v1.
