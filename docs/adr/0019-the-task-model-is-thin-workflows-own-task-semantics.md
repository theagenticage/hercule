# The task model is thin; workflows own task semantics

**Amended 2026-09-04 ([#46](https://github.com/theagenticage/hercule/issues/46), [#59](https://github.com/theagenticage/hercule/issues/59)):** this ADR originally allowed a hard delete of a task. That sentence is superseded by the deletion rules of [spec 02](../spec/02-domain-model.md) and [spec 09](../spec/09-tasks.md): `task.delete` is soft, setting `deletedAt` and leaving the row and its provenance in place; a deleted task answers `not_found` on read and drops out of `task.query` and search, and `task.deleted` carries the final snapshot. Pruning deleted tasks outright is post-v1. Everything else here stands.

**Amended 2026-11-07 ([#1029](https://github.com/theagenticage/hercule/issues/1029), [ADR 0052](./0052-tasks-have-a-stage-and-threads-join-them.md)):** a Task gains a fixed `stage` of seven values, and `status` becomes a coarse reading of it, written only from the stage. The core still never moves a stage on its own, with one exception: it creates a Task for a Thread that has none to join, at the `exploring` stage. The sentence "the core never decides when a task is in progress or done" still holds for everything that happens after the Task exists. Everything else here stands.

**Amended 2026-11-07 ([#1032](https://github.com/theagenticage/hercule/issues/1032), [ADR 0054](./0054-external-entities-are-durable-records-kept-true-by-polls.md)):** a Task's outside things are no longer only provenance. Each provenance entry with a `ref` also writes a row in `task_entity_links` (`task_id`, `ref`, `linked_at`, `linked_by`, `following`), in the same transaction, and `externalEntity.takeOn` and `addToWork` write one too. Provenance stays the append-only history, and the link is the relation: it is what Work groups and filters by, and what finds a ref's active Task. A ref is still not unique across Tasks, so one ref may be linked by many Tasks over time. An External Entity is unique on its ref, which is a separate thing. The core still never decides when a Task is in progress or done, and a link moves no stage. Everything else here stands.

A Task is a plain row - `id`, `title`, markdown `description`, `status`, `priority`, `labels[]`, optional `projectId`, append-only `provenance[]`, `createdAt`, `updatedAt`, `statusChangedAt` - with one fixed status axis (`open`, `in-progress`, `done`, `cancelled`), any-to-any transitions, and no state machine, auto-transitions, or completion gating in the core: the core never decides when a task is in progress or done, and "done means the PR merged" is a shipped-workflow convention (the work run holds a signal trigger on the PR-merged event and its final step is `task.update status=done`), never a rule - the model stays work-type-agnostic. Priority is one optional four-value enum (`urgent`/`high`/`normal`/`low`, default `normal`) that user and agents write through the same op; the actor-stamped event log replaces any "suggested priority" shadow field. Provenance entries are `{ref?, eventId?, runId?, at, actor}`; external refs are fully-qualified canonical ids (`github:issue:owner/repo#42`) owned by the defining plugin, with the connection excluded from identity and no uniqueness constraint across tasks - the `task.query` guard treats "any open task with this ref" as the duplicate signal. Tasks link to at most one project; run and session links live on the run/session side and the task's list is derived. Labels are bare strings created implicitly; colors and groupings are presentation. No subtasks, task dependencies, comment threads, or assignee in v1 - enrichment edits the description or appends provenance. `task.created` carries a full snapshot; `task.updated` carries per-field diffs (`{old, new}` for scalars, `{added, removed}` for arrays, one event per update op) so CEL routes on `event.payload.changes.status.new == "done"` without fetch-and-compare. Agent search is structured filters plus SQLite FTS over title/description, no vectors. Delete is soft (`cancelled` = decided not to do; delete = should never have existed; the event log keeps the audit trail). We rejected a richer task engine (states, assignment, auto-transitions from run activity) because every semantic it would hard-code is already expressible as an editable workflow, and core auto-transitions would make the optional run-task link load-bearing against the all-links-optional work triangle. Accepted cost: nothing marks a task done when its run succeeds unless a workflow says so; shipped defaults must demonstrate the pattern.
