# External accounts are core-owned Connections

A Connection is a core-owned record naming one external account: a plugin-defined type plus label, credentials (stored via the secrets model), and status - e.g. `gmail`/"work", `github`/"personal". Plugins declare which connection types they service and drive the flow that establishes one; the core owns storage, listing, and the single connected-accounts UI. Event-source plugins run one ingest loop per connection and stamp every event with its connection id; triggers select their connections explicitly (a named connection or a deliberate "any", never a silent all), and outbound actions name the connection they act as, reachable from workflow inputs like any envelope field, so reply-as-the-triggering-account needs no new machinery. A Resource may reference the Connection used to reach it (the mailbox resource references the gmail connection; a repo resource, the GitHub connection that clones it). This replaces both per-account plugin registration (fragments configuration and UX, no central listing) and plugin-internal account arrays (the core could neither scope events by account nor render one connected-accounts view). Accepted cost: connection types are namespaced by their defining plugin, so two plugins wanting the same external service each define their own type and the user authenticates twice; deduping on OAuth identity is a later nicety.

**Amended 2026-09-13 ([#71](https://github.com/theagenticage/hercule/issues/71)):** "namespaced by their defining plugin" is made concrete by [ADR 0034](./0034-a-catalog-contribution-is-identified-by-its-qualified-id.md) - a connection type is identified by its qualified id `<pluginId>/<word>`, so the examples above are `gmail/gmail`/"work" and `github/github`/"personal", and two plugins may declare the same word.
