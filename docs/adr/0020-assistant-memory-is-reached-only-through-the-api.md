# Assistant memory is reached only through the API

An assistant reads and writes its memory exclusively through `hercule memory` operations on the public API - `list`, `read`, `search`, `write`, `append`, `delete` - never through files on a runner. Memory is two tiers of markdown held by the controller: one `core` document, always injected at session start (cap 4,000 chars: who the user is, standing preferences, what is live), and named topic documents (line 1 `# <name>`, line 2 `> <gist>`; cap 12,000 chars each, 24 topics) of which only a generated index (name, size, gist) is injected, bodies fetched on demand. Caps are enforced at the write operation: an over-cap write fails with the current size and the agent consolidates. Rotation keeps a flush turn on the dying session ("record what is durable that is not yet in memory") as a safety net, and provider-native compaction is disabled for assistant sessions so rotation is the only memory event. No journal tier and no background "dream" pass. We tested the alternatives with a real agent before deciding (prototype `prototype/memory-interface`, 216 chains on Claude Sonnet 5, Codex gpt-5.6-luna and pi glm-5.3): memory as native files, as read-only files plus API writes, and API-only all scored identically on recall and record across eight scenarios, every fact was recorded in the turn it was mentioned, and a journal tier produced only duplicate entries. With ergonomics a wash, the API-only shape wins on everything else: nothing on runner disk to materialize, lock, resync or leak; assistant sessions stay literally workspace-less; caps, audit stamping and taint gating sit on one write seam (the only cap overflow in the experiment, Codex at 12,009 chars, was caught there and would have passed silently as a file write); and the web app edits the same documents through the same operations. Accepted costs: no `grep` over memory (`search` is the API's substitute; the experiment shows agents use it), and the CLI must offer one unambiguous content channel because a weaker model mixed `--content` with a heredoc before retrying. Read-only materialization can be added later as a pure read convenience without touching the write path; that is the escape hatch if dogfooding shows read ergonomics suffering.
