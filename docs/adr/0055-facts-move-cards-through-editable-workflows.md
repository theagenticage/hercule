# 55. Facts move cards through editable workflows

Date: 2026-11-08

## Status

Accepted by [Work overview: the design and its tickets (#1026)](https://github.com/theagenticage/hercule/issues/1026), built by [#1035](https://github.com/theagenticage/hercule/issues/1035). Amends [ADR 0019](./0019-the-task-model-is-thin-workflows-own-task-semantics.md), which left what a stage means to shipped workflows and shipped none, and [ADR 0046](./0046-handing-a-signal-off-tracks-the-work-on-a-task.md), which rejected matching a pull request to its Task by the run's branch name. Keeps [ADR 0052](./0052-tasks-have-a-stage-and-threads-join-them.md) true: the core never moves a stage on its own. Builds on [ADR 0054](./0054-external-entities-are-durable-records-kept-true-by-polls.md). The rules are in [spec 09](../spec/09-tasks.md), [spec 10](../spec/10-triage-intake-and-notifications.md) and [spec 20](../spec/20-external-entities.md).

## Context

Work shows a Task as a card at a stage. Until now only a person, an agent or a workflow moved it. A pull request opened from a Thread, or merged by someone else, left the card where it was, so the board went stale and the user had to keep it true by hand.

Moving the card is a rule about what the work means: a merged pull request lands a card, an open one puts it in review. ADR 0019 and ADR 0052 keep such rules out of the core. So the core must only report what happened, and a workflow must decide what to do with it.

Four things make this harder than "run a workflow on `pr.merged`":

- **Events can be missed.** A merge that no event reported still happened. Entity state is kept true by polls (ADR 0054), and the same must hold for the move.
- **Order matters, and time cannot give it.** A queued run can arrive after a newer drag. A repeated fact must not undo a drag for ever. Two changes of one poll can share a millisecond, and a clock can step back.
- **One merged pull request does not mean the work is finished.** A card must land only when nothing linked to it is still open.
- **A Thread's pull request is not linked to its Task.** The Task has to find it.

## Decision

**The core records a Fact when a linked thing changes state, and emits `task.entityChanged` with it. Two small, ordinary, editable workflows turn Facts into stage moves. A Task's own `stageFactId` fence makes a person's drag win until a newer Fact arrives.**

- **What a Fact is.** A Fact is a row in `task_entity_facts`: one live Task, one External Ref, the entity's `lifecycle` (`open`, `completed` or `abandoned`), the `previous_lifecycle` (null when the entity was only just linked or first observed), and the time it was observed. One Fact and one Platform Event `task.entityChanged` are written, in the transaction of the change, for each live Task that links the ref, in five cases only: the lifecycle changed; a link was added; a linked ref was first observed; an unlink left nothing open and at least one completed link; and a change of access or a first full record changed the Task's open or completed count. Never for a change of title, status, owner or facts. Never for a first observation that no Task links, so 300 existing pull requests start no runs. A poll that changes nothing writes nothing.
- **A Fact comes from the entity, not from a raw event.** An entity's state is kept true by polls, so a merge that no event reported is still a Fact. A missed event loses nothing. The Fact is also written when a link and a poll arrive in either order: a link added to a pull request that already merged writes its Fact at once.
- **The order is a database id, not a time.** A Fact's `id` is an `INTEGER PRIMARY KEY AUTOINCREMENT`, and there is one writer, so ids follow commit order. `observed_at` is for display and is never compared. Two Facts of one poll in the same millisecond have different ids. A clock that steps back changes nothing.
- **The fence.** A Task has `stage_fact_fence`, the highest Fact id already accounted for. A `task.update` that names `stage` and `stageFactId` is checked inside its own transaction. The Fact must exist and belong to the Task. A Task at `done` or `dropped` is never moved by a Fact. A Fact at or below the fence, or voided by an unlink, does nothing. With `onlyWhenLinkedWorkFinished` the write counts the links again and does nothing unless nothing is open and something completed. Otherwise the fence moves to the Fact and the stage is written. A stage written by a person or an agent with no `stageFactId` sets the fence to the highest Fact id in the table, so every Fact recorded so far is overruled, even when the stage is the same: it is an explicit "keep it here". A reorder inside a column carries no `stage` and affirms nothing. "Nothing happens" returns the Task as it is, with no error: a run must not fail because the user dragged a card. A new Fact after a drag applies, which is what "until new facts arrive" means.
- **The cause is its own column.** The fence alone cannot say which Fact placed the current stage: a person's write sets the fence to the table's maximum, which may be the Fact of another Task. So `tasks.stage_cause_fact_id` holds the Fact that placed the stage. A Fact write that changes the stage sets it. A Fact write whose stage the Task already holds moves only the fence, and the cause stays. Any stage decision with no `stageFactId` clears it (a `task.update` with a stage even when it is the same, `task.move` with a stage, a merge, a legacy status write that changes the stage). Unlinking the cause's ref keeps the cause. The card's cause label ("Pull request #6221 merged") is built from that Fact's own `lifecycle` and the entity kind's stored noun and identifier, never from the entity's latest state, so a pull request that is reopened later does not rewrite why the card moved.
- **What counts as open.** A card lands only when nothing linked is still open. `countLinkedWork` counts every link of a Task as open, completed or neither, by one table (spec 09): a context link counts as neither, a link that cannot be read counts as open, `open` is open, `completed` is completed, and `abandoned` is neither. A Task is ready to land when nothing is open and something completed. The first merged pull request of two never lands a card. Classification as work comes from the stored record, so a record stays counted after its plugin leaves.
- **No shipped workflow sets Done.** Landed means the thing shipped. Done means the Task's acceptance criteria are met, and the user decides that ([spec 09](../spec/09-tasks.md#finishing-a-task)). A user's own workflow may set `done`, because `task.update` is the same operation for everyone.
- **Two shipped workflows do the moves.** `card-in-review` listens to `task.entityChanged` for an open `github/pull-request` and writes `in-review`. `card-landed` listens for `openLinks == 0 && completedLinks > 0` and writes `landed` with `onlyWhenLinkedWorkFinished`. Each passes the Fact's id as `stageFactId`. They run with no agent and no workspace, so a run costs a few rows and no model call. They are ordinary workflows: listed, editable, disabled or deleted like any other. Their complete sources are in [spec 09](../spec/09-tasks.md#the-shipped-workflows).
- **A person can link and unlink by hand, and an unlink sticks.** `task.linkEntity` and `task.unlinkEntity` are operations. An unlink removes the link, voids that pair's Facts so a Fact queued before the unlink dies with it even if the user links the pair again before its run gets there, and writes a suppression so the next scan does not add back what the user took away. A link by hand, or an explicit provenance `ref`, clears the suppression.
- **A Thread's pull request is linked by a join on the head.** Hercule already knows the branch a checkout really has: the runner reports it after each turn, and a rename is followed. An entity holds `repository.head` as `(remote, branch)`. A controller daemon step joins the two. This is not a branch-name match, which ADR 0046 rejected because an agent may rename its branch. That rejection was about the name the run was given, which an agent may change. This join reads the branch the checkout really has now. It also matches on the head's remote, not the target's: a fork's head remote differs from the Resource's, so a fork's pull request does not match, and two repositories that share a branch name never match each other. Two live Tasks on one branch link neither, and the step logs why. A wrong link is worse than a missing one.
- **A pull request opened and merged between two scans is still found.** The inventory is `is:open`, so such a pull request may never appear in it. The plugin is asked for the tracked branches (`listTrackedBranches`) and looks each up by its head, merged and closed included. Its Fact then has `previous_lifecycle` null and `lifecycle: completed`, and the card lands.
- **These are the first shipped workflows in code.** Spec 10 described shipped workflows, but nothing shipped one. This slice takes the minimum: a table `shipped_workflows (key, workflow_id, installed_at)` with one stable key per workflow, installed at boot once, never upgraded and never put back after the user deletes it. A row means "this key was installed once". Changing a shipped source later does not reach anyone who has the key, and no new key is minted to get round that. The first install is one transaction: both workflows with their triggers, both rows, and a reconciliation that writes one Fact for every live Task's link to an entity that exists, so cards with a pull request linked before this build are corrected. If a source fails to validate, nothing is installed, the boot goes on, and a Notification `core.shipped-workflow-failed` is raised for each key that failed, withdrawn on a later successful boot. **[#502](https://github.com/theagenticage/hercule/issues/502) stays open:** who owns a shipped workflow, how one is upgraded and how the user gets a changed default are not decided here.

## Considered options

- **Move the card in the core when a pull request merges.** Rejected, as in ADR 0019 and ADR 0052. The core would hard-code what "landed" means, and the user could not edit or switch it off.
- **Trigger on the raw `github.pull_request.merged` event.** Rejected. A poll can see the merge without an event, a Task is not named by the event, and a missed event would be a stale card for ever. A Fact comes from the entity.
- **Order by time.** Rejected. Two changes in one poll can share a millisecond and a clock can step back. A timestamp cannot tell a late run from a newer drag. A database id can, and the core checks it where it writes.
- **Last write wins.** Rejected. A queued run can land after a newer drag, and a repeated Fact would undo a drag for ever.
- **Work out the cause from the fence.** Rejected. A person's drag sets the fence to the table's maximum, which can be another Task's Fact. A separate column says which Fact placed the stage.
- **Let `card-landed` set Done.** Rejected. Done means acceptance criteria are met, and a merge does not show that. Landed is "the thing shipped".
- **Land a card on the first merged pull request.** Rejected. A second pull request or the ticket may still be open. Nothing may be open, and something must have completed.
- **Match a pull request to its Task by branch name.** Rejected by ADR 0046 and still rejected. The join here reads the branch the checkout has now and the head remote of the pull request.
- **Match on the pull request's target.** Rejected. A fork's pull request would match the wrong Resource. The user links a fork's pull request by hand.
- **Link a ticket from a pull request's text.** Not done. It needs reading text. A Take or a handoff links it, or the user does.
- **Ship the workflows as hard-coded behaviour that can be switched off.** Rejected. The user would have a setting and no way to read or change the rule. A workflow is the rule, in the place where the user already edits rules.
- **Put a shipped flag and a name on `workflows`.** Rejected for now. It would decide #502 by accident. A table of installed keys is the least that makes "install once, never put back" true.
- **Upgrade shipped workflows by minting a new key.** Rejected. It would leave the old workflow running beside the new one for everyone who has it. Upgrades are for #502.

## Consequences

- New tables `task_entity_facts`, `task_entity_link_suppressions`, `shipped_workflows` and `tracked_branch_attempts`, and two columns on `tasks`: `stage_fact_fence` and `stage_cause_fact_id`. Migration `0117-stage-facts` adds only, so it needs no upgrade fixture. The first boot of the new build does write rows, so `e2e/upgrade.test.ts` is extended.
- A new Platform Event and Core Kind, `task.entityChanged`. A bare trigger on it fires for every Fact, so a workflow that listens must filter, as both shipped workflows do.
- `task.update` gains `stageFactId` and `onlyWhenLinkedWorkFinished`. Two new operations: `task.linkEntity` and `task.unlinkEntity`. `WorkCard` gains `stageCause`.
- A new Notification kind, `core.shipped-workflow-failed`.
- The plugin host's `IngestContext.entities` gains `listTrackedBranches`. It grows additively, so `hostApi` stays 8.
- The tasks domain declares a port, `LinkedEntities`, answered in the controller daemon from the database alone. It must never require `PluginHost` or `ExternalEntityService`: ingest sits below the plugin host and calls `TaskService`.
- External entities call `TaskService` around every write that can change a linked entity's state: a snapshot before, and the Facts after, in the same transaction. All the rules live in tasks.
- At first install, a manual placement from before this build has no fence to respect, so a linked Task can move once. Later drags are fenced. The release note says so.
- A user who deletes a shipped workflow keeps it deleted, and one who edits it keeps the edit. Neither is reached by an upgrade. That is the cost of not deciding #502 here.
- An outside change that is not a lifecycle change still only shows on the timeline (ADR 0054). A second pull request, or someone else's assignment, moves nothing and stops nothing.
- Measuring is left to [#1047](https://github.com/theagenticage/hercule/issues/1047), as for the other slices of this map.
