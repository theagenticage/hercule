# Plugins request capability scopes in a manifest and register contributions in code

Every plugin carries a deliberately coarse static manifest - identity, a single host API version integer, requested plugin capabilities (scope-style: "the channels API, the workflow-actions API"), and a typed config schema - while its contributions (the concrete channel, event source, provider, or workflow actions it provides) are registered imperatively through the granted capability APIs, with full type support and no manifest bookkeeping. The obvious alternative, a VS Code-style declarative manifest listing every contribution, was rejected: contribution definitions get complex fast, forcing dynamic JSON construction and a manifest that drifts from the code, and it taxes every internal feature with bookkeeping to serve third-party review that v1 (all-internal plugins) doesn't need. Pure single-hook imperative registration was also rejected, because it makes a plugin's surface invisible until it runs: the fix is two hooks, a pure, cheap `register()` that only declares contributions and an `activate()` that starts real machinery (connect, poll). The controller runs `register()` for every installed plugin at boot regardless of enabled state, so the full contribution catalog always exists - workflow validation, pickers, and "what does this disabled plugin offer" read the catalog, never the live plugin - and runs `activate()` only for enabled plugins. Capability APIs evolve additively; a breaking change mints a new capability name (`channels.v2`) rather than a version field, so load-time compatibility stays one integer check plus name lookup. V1 plugins are in-process, controller-only npm workspace packages listed in one static registry file (runner-side provider execution stays built-in but plugin-shaped until real hooks are learned from three implementations), but the API is shaped for later isolation and third-party loading: dependencies are handed in, never imported; nothing crosses the host API that couldn't be serialized; external plugins will differ from internal ones only in trust, not in kind.
