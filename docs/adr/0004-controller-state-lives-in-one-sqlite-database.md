# Controller state is plain relational rows in one SQLite database

The controller persists everything durable in a single SQLite database file, accessed through per-entity repository interfaces whose internals commit to SQLite freely (json functions, upserts, WAL); swapping engines later means rewriting repository internals, not callers, and tests run against SQLite's own `:memory:` mode rather than mocks. Postgres was rejected as a standing ops dependency with no payoff for a single-user, single-writer-process controller (ADR 0002's one brain), and a dialect-agnostic SQL layer as a permanent lowest-common-denominator tax hedging a migration that may never happen. State is plain relational rows, not event-sourced: t3-code's event-sourced orchestration core was studied as prior art and turned out narrow (one thread-shaped aggregate; config lives in plain tables and JSON files), to mutate its "immutable" log in migrations rather than version events, and to still drop side effects on crash (in-memory PubSub, no durable reactor cursors) - so log-as-truth machinery (deciders, projectors, cursor bootstrap) would tax Hydra's wide entity catalog while buying nothing it needs. The genuinely log-shaped data - the domain event log (ingress events plus internal audit entries) and the per-session normalized event streams - are append-only tables written in the same transaction as the state they accompany, which in one embedded database gives event-sourcing's atomicity for free. Queue and scheduling state are ordinary rows in the same store, and every consumer of committed events reads from a durable position (delivery rows / per-reactor cursors with attempt counts): at-least-once side effects with idempotency keys where external systems allow, exactly-once state changes inside the transaction, and never an in-memory-only bridge between log and side effect. Streaming token deltas are coalesced in memory and flushed at message/turn boundaries, not persisted per token. Explicitly outside the store: workspace contents and provider-native session state (runner disk, ADR 0002/0003) and process logs (rotated files); there is no controller-side blob directory - if it is durable and domain-relevant it is a row, keeping backup and promotion a one-artifact story. Retention is keep-everything in v1; secrets handling is deferred to the security & secrets ticket.
