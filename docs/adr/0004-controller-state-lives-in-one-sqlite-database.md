# Controller state is plain relational rows in one SQLite database

The controller persists everything durable in a single SQLite database file, accessed through per-entity repository interfaces whose internals commit to SQLite freely (json functions, upserts, WAL); swapping engines later means rewriting repository internals, not callers, and tests run against SQLite's own `:memory:` mode rather than mocks. Postgres was rejected as a standing ops dependency with no payoff for a single-user, single-writer-process controller (ADR 0002's one brain), and a dialect-agnostic SQL layer as a permanent lowest-common-denominator tax hedging a migration that may never happen. State is plain relational rows, not event-sourced: t3-code's event-sourced orchestration core was studied as prior art and turned out narrow (one thread-shaped aggregate; config lives in plain tables and JSON files), to mutate its "immutable" log in migrations rather than version events, and to still drop side effects on crash (in-memory PubSub, no durable reactor cursors) - so log-as-truth machinery (deciders, projectors, cursor bootstrap) would tax Hercule's wide entity catalog while buying nothing it needs. The genuinely log-shaped data - the domain event log (ingress events plus internal audit entries) and the per-session normalized event streams - are append-only tables written in the same transaction as the state they accompany, which in one embedded database gives event-sourcing's atomicity for free. Queue and scheduling state are ordinary rows in the same store, and every consumer of committed events reads from a durable position (delivery rows / per-reactor cursors with attempt counts): at-least-once side effects with idempotency keys where external systems allow, exactly-once state changes inside the transaction, and never an in-memory-only bridge between log and side effect. Streaming token deltas are coalesced in memory and flushed at message/turn boundaries, not persisted per token. Explicitly outside the store: workspace contents and provider-native session state (runner disk, ADR 0002/0003) and process logs (rotated files); there is no controller-side blob directory - if it is durable and domain-relevant it is a row, keeping backup and promotion a one-artifact story. Secrets handling is deferred to the security & secrets ticket.

Amendment (2026-08-28, spec assembly): this ADR originally said "retention is keep-everything in v1". That sentence is superseded by [ADR 0009](0009-all-events-flow-through-one-persisted-pipeline.md) (events are persisted whether or not they match and pruned by TTL, default ~90 days; run records copy their triggering event so pruning never breaks audit) and by the security model (security events and actor-stamped mutations are kept at least 90 days). Domain rows are never pruned; only the event log and per-session streams carry a TTL. See [docs/spec/04-state-store.md](../spec/04-state-store.md).

Amendment (2026-10-08, [#465](https://github.com/theagenticage/hercule/issues/465)): images attached to prompts are files, not rows. This replaces "there is no controller-side blob directory" above.

- Each image's bytes are one immutable file at `<dataDir>/attachments/<id>`, inside the Data Root beside the database. Its metadata (name, media type, size, sha256, creation time, uploading actor) is a row. The database holds no absolute path: a file's path follows from its id, so the files move with the Data Root.
- The controller writes a temp file, renames it to its id, and only then inserts the row. A rename is atomic, so a half-written file never sits under a real id.
- Image bytes stay out of SQLite because they would bloat the database and every copy of it, for data that is written once and never queried.
- The cost: backup and promotion are no longer one artifact. A backup or a promotion must copy `attachments/` along with the database. The pre-migration `VACUUM INTO` copy holds the rows but not the files. That is safe, because migrations never touch the files.

Amendment (2026-10-18, [#109](https://github.com/theagenticage/hercule/issues/109)): test databases open exactly as production opens one (lock file, writer, read-only reader), and the ADR's mention of SQLite's `:memory:` mode is out of date. This replaces "tests run against SQLite's own `:memory:` mode rather than mocks" above.

- The controller now opens two connections to its one database file: a writer for every transaction and a read-only reader for everything else. A `:memory:` database cannot be shared by two connections and has no WAL, so it can no longer stand in for production.
- The point of the original sentence stands: real SQLite, no mocks. The same repository code runs in tests and in production.
- Test databases were already files in a temporary directory. What changes is that they now open exactly like production: lock file, writer, read-only reader. Running the whole controller test suite takes the same wall time as before.
- Transactions start with a plain deferred `BEGIN`. A read-only transaction must keep working while writes are stopped during a promotion, so they cannot all start with `BEGIN IMMEDIATE`. Inside one process this cannot conflict, because one writer connection serves every transaction. The cost: a process outside Hercule that writes to the database (a `sqlite3` shell, another program) makes a transaction that reads and then writes fail at once with `SQLITE_BUSY_SNAPSHOT`. Outside processes can now open the database at all, which the old exclusive lock forbade. They must not write to it.
- The one-controller guarantee is a lock file, `controller.lock` in the Data Root, not a lock on the database. The ADR above does not describe the guarantee, so nothing in it changes. The rules callers rely on are the concurrency contract in spec 04.
