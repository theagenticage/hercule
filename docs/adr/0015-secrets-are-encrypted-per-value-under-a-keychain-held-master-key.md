# Secrets are encrypted per-value under a keychain-held master key

All secret values - Connection credentials, plugin KV secrets, runner credentials - live as rows in one owner-scoped secrets table in the controller database, each value encrypted under a master key held in the OS keychain (plain key file as the Linux/headless fallback); the SQLite file itself stays plain. This puts disk theft and backup/bundle leaks in the threat model: any copy of the database, including a promotion bundle, is useless without the master key, which never leaves its machine - promotion export re-encrypts the packed secrets under a key derived from the single-use promotion token, and the new controller re-wraps them under its own master key, satisfying the enumerable-and-extractable constraint from ADR 0005. Plaintext-at-rest was rejected because every OAuth token would leak with any DB copy; passphrase-on-start was rejected because it breaks unattended restart of an always-on controller; whole-database encryption (SQLCipher) was rejected because it encumbers every read path to protect mostly non-secret rows. Secrets never appear in the event log or API responses - references only.
