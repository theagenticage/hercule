# All events flow through one persisted pipeline

Every event - ingested by an event-source plugin (GitHub, Gmail) or emitted by the core (cron ticks, manual/synthetic events, platform events like `run.failed`) - is normalized into one envelope (id, source, connection, kind, occurredAt/receivedAt, plugin-supplied dedupKey, per-kind payload with declared schema, raw passthrough) and appended to the event log in the controller database. Plugins only emit; the core alone persists, matches, and dispatches. Matching is a durable-cursor consumer: it reads events past its cursor, evaluates every enabled start trigger and live subscription, fan-outs to all matches, and inserts the resulting effect rows - a pending run, a signal delivery, a queued session input - advancing the cursor in the same transaction. There is no delivered-events table: UNIQUE constraints on the effect rows (trigger id + event id, subscription id + event id) make crash-redo harmless, and effects that must leave the database (chat posts, API calls) go through outbox rows with retry. All events are persisted whether or not they match, pruned by TTL (default ~90 days); run records copy their triggering event so pruning never breaks audit. New sources baseline at "now" and never emit history. We considered plugins dispatching directly (unauditable, and plugins would need to know the dispatch machinery), in-memory event routing (t3-code's bridge, already rejected by the store decision), and a separate delivery-tracking table (redundant given effect-row uniqueness). Accepted cost: every trigger fire pays a log write and a matcher wakeup, and even cron ticks travel the full pipeline.
