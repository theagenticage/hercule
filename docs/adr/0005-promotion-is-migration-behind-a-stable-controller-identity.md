# Promotion is migration behind a stable controller identity

Moving the controller to another machine (promotion) is a state migration, not a live handoff: the old controller freezes read-only, streams its bundle (the SQLite database plus packed secrets) to the new machine, and seals itself; there is never a moment with two authoritative controllers, and the alternatives - a two-controller handoff protocol or shared-storage HA - were rejected as split-brain machinery a single-user system doesn't need when a few minutes of read-only is acceptable. The move is safe and seamless because the controller's identity is logical, not an address: an ID plus key material created at install and carried in the bundle. Runners authenticate that identity wherever it appears, so the new-address announcement and the sealed old controller's "moved to X" forwarding pointer are signed and unspoofable, and because the new machine resumes the same identity, runner seq/ack state and disk outboxes replay across the move as if the controller had merely reconnected - in-flight sessions never stop, so promotion needs no drain phase. Authority mirrors runner join: a single-use promotion token minted on the old controller gates the pull, so no machine on the network can take the state uninvited, while the ergonomic flow stays one guided command on the new machine (with export/import of a bundle file as the offline fallback). Two portability rules keep the bundle relocatable: the controller database stores its own machine's paths only relative to a single data root (never absolute), and runner-side locations are opaque runner-owned facts keyed by ID that promotion never rewrites. The cost accepted: no high availability - the controller moves, it doesn't fail over.
