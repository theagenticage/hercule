# Workflow graphs route on declared outputs; cycles are bounded by capped edges

A workflow's control flow lives entirely in its graph. Steps emit outputs; edges and steps carry conditions (CEL, tentatively, pending research) over those outputs; neither actions nor agents redirect flow imperatively. An agent step's declared output schema is the whole contract between the agent and the graph: prompts persuade, schemas route. Iteration is expressed with ordinary edges, not a special back-edge type: any edge may carry `maxTraversals >= 1` (the number of times it may fire per run), and validation requires every cycle to contain at least one capped edge, so graphs are bounded by construction; exhausting a cap fails the run with reason `iteration-limit`. We considered actions that can steer (hides routing inside plugin code, making the graph unreadable), a distinct back-edge taxonomy (needless classification; boundedness per cycle is the real invariant), and a human-gate step (dropped from v1: failure notifications plus re-run cover the human moment until dogfooding shows what question a recipe can pose upfront). Accepted cost: an agent cannot invent a route missing from the graph at runtime; work that needs a novel route uses an ad-hoc generated execution plan instead.
