# Triage is a workflow pattern inside core-enforced bounds

Hercule has no triage engine. Deciding what matters is an ordinary workflow: a CEL trigger filter is the rules layer, a cheap agent step with a structured-output schema is the judgment layer, and graph edges route the verdict - the same blocks every other workflow uses, user-readable and user-editable. The recommended topology (convention, never enforced) puts triage at the only doorway between raw external events and expensive work: triage workflows trigger on external events and create or update Tasks; work workflows trigger on task platform events (`task.created`, `task.updated`). The core's contribution is mechanical: a per-trigger spawn bound (default ~30 runs/hour, per-trigger configurable) with breaker semantics - exceeding it auto-pauses the trigger, holds matched events visibly, and notifies the user, who resumes with one click (optionally discarding the backlog). Dropping excess would be silent loss; blind queueing just delays the stampede; a tripped breaker is itself the review moment where the user sees what almost spawned and fixes the filter. The exact-ref `task.query` built-in action (provenance refs, labels, status - identity matching, never content matching) enables the guard-before-agent pattern: ~~duplicate signals~~ later events about the same thing *(amended 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395))* route straight to `task.update` for pennies, which is what makes generous spawn limits affordable. We considered a dedicated core triage component (its config would duplicate what workflows already express, and "what matters" would end up buried in engine settings instead of an editable prompt), a marked triage workflow type for enforcement (core cannot tell triage from any other workflow without it becoming that engine), and other core bounds - a global concurrent-run cap (redundant: per-runner session caps already queue excess at placement), spend caps (unenforceable: subscription-auth providers report no reliable per-run cost; v1 displays cost, never gates on it), and quiet hours (pausing a workflow covers it). Accepted cost: nothing stops a user from wiring expensive work directly to raw events; the topology is protection by convention and shipped defaults, not by machinery.

**Note, 2026-08-31 (ticket [#42](https://github.com/theagenticage/hercule/issues/42)):** the decision stands - triage is an ordinary workflow, the core has no triage component, spawn bounds are the only core bound - but the shipped default changed shape. Instead of one run per event with a structured verdict routed by edges, v1 ships one scheduled **Triage** run a few times a day whose agent reads every event since the last run and acts through the public API (creates proposals, attaches ~~signals~~ events *(amended 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395))* to tasks, offers actions, enriches events), leaving no verdict field: what it decided is carried by the Tasks and Notifications it wrote. Reason: a run that sees one event cannot group ~~signals~~ events *(amended 2026-10-10, [#395](https://github.com/theagenticage/hercule/issues/395))* or connect them across sources, and those connections are Intake's value center. The per-event shape, the guard-before-agent pattern and `task.query` remain available for user-authored workflows; spawn bounds now matter for event-triggered work workflows rather than for triage itself. Owner: spec 10.

**Note, 2026-10-10 (ticket [#395](https://github.com/theagenticage/hercule/issues/395); decided in [#384](https://github.com/theagenticage/hercule/issues/384), [#392](https://github.com/theagenticage/hercule/issues/392), [#397](https://github.com/theagenticage/hercule/issues/397), [#398](https://github.com/theagenticage/hercule/issues/398) and [#399](https://github.com/theagenticage/hercule/issues/399)):** the decision stands, and Intake now has three places where something decides what reaches the user ([ADR 0040](./0040-intake-holds-signals-notifications-are-hercules-own-messages.md)). Each keeps judgment in an editable workflow:

- **A plugin's rule reports; it does not judge.** A signal kind's rule answers `yes`, `no` or `undecided` only from what the source itself says: you were asked for a review, a message is addressed to you. That is a statement by the source, like a permission request, not a guess about relevance.
- **Where the source says nothing certain, a workflow decides.** The core ships the **Screener**, an ordinary editable workflow that answers `yes` or `no` for one event and one kind ([spec 10 §9.8](../spec/10-triage-intake-and-notifications.md#98-screening-and-the-screener)). Text generation may fill a signal's body, but never decides whether an event becomes a signal.
- **Triage raises core Signals.** The shipped Triage workflow acts by raising `proposal`, `offer`, `unsure` and `fyi` Signals through `signal.raise`, not Notifications and not Tasks labelled `proposed`. The core still cannot tell it from any other workflow.
- **`availableToTriage` scopes reading, not judgment.** The per-kind switch decides which events triage is offered; what matters among them stays in the editable prompt ([spec 05 §8.2](../spec/05-plugins.md#82-intake-settings)).
- **A fixed threshold that only offers is not a judgment.** The core suggests an Ignore Rule after the user marked the last five signals of a group Done without answering ([spec 10 §9.9](../spec/10-triage-intake-and-notifications.md#99-ignore-rules)). The threshold is fixed and visible, it only raises an `offer`, and the user decides.

Owner: spec 10 §9.
