# Hercule ships as one self-contained binary, supervised by the OS, living in one home directory

Hercule distributes as a single Bun-compiled executable per platform (macOS arm64, Linux x64/arm64; GitHub Releases behind a `curl | sh` installer, brew tap later) - no Docker image and no npm-global install in v1. One artifact carries all three roles: `hercule serve` (controller), `hercule runner` (runner daemon), and the CLI verbs (ops and hercule-as-a-tool are the same binary, ADR 0013). Docker was rejected because it fights the settled substrate at every turn - keychain-held master key (ADR 0015), bare-process sessions (ADR 0003), the auto-joined local runner spawning provider CLIs, and promotion's run-one-command ceremony (ADR 0005); npm-global was rejected because it drags a Node version story onto every runner machine. The single-artifact choice is guarded by a mode-isolation constraint: the codebase splits into `controller`, `runner`, and shared `protocol`/`contract` packages with separate entrypoints behind a thin dispatcher, and the runner entrypoint must not import controller packages (no DB engine, no plugin host, no web bundle in its module graph) - enforced by a dependency-lint rule in CI, not convention. The Bun bet is validated (findings: `research/bun-compile.md` on `research/bun-compile`; verdict go-with-workarounds): the Agent SDK officially documents Bun compilation (embed the platform's native claude binary, extract via the SDK's `extractFromBunfs`), `bun:sqlite` and full-stack asset embedding are blessed under `--compile`, and cross-compilation covers all three targets. Pinned workarounds: spawn-not-fork in compiled mode, `BUN_BE_BUN=1` for pi's on-disk TypeScript children, the `security` CLI instead of the archived keytar, pin the Bun version, and prototype macOS notarization early (undocumented by Bun). Note t3-code is not prior art here - it runs the SDK under Node, not a compiled Bun binary; the SDK docs carry the bet.

Supervision is never our own daemon: `hercule service install` generates a user-level native unit (systemd user unit with linger on Linux, launchd LaunchAgent on macOS) and the OS owns restarts; foreground `hercule serve` stays the dev mode. User-level rather than system-level because Hercule is single-user and the master key lives in the login keychain, which a macOS system daemon cannot reach. The local runner (ADR 0002) is hosted as a supervised child process of the controller (`hercule runner --local`, self-spawned from the same binary) joining over loopback WebSocket - one service unit per machine, zero special-casing in the runner code path. Everything lives in one Hercule home, `~/.hercule` (overridable via `HERCULE_HOME`), with the moving part fenced: `data/` is the Data Root promotion moves (ADR 0005), beside runner-owned material state (`runner/`), `logs/`, `backups/`, and `config.toml`. XDG splitting was rejected because it scatters the promotion story across three trees. The config file holds only keys needed before the database opens (data root, bind, log level); everything else stays in the DB. There are no curated per-key flags: a codex-style generic override (`-c key=value`, plus `HERCULE_*` env mapping) reaches any config key, with precedence flag > env > file > default; only `--home` remains a real flag since it locates the config file itself.

**Amended 2026-08-31 ([#43](https://github.com/rogierpennink/hydra/issues/43), [ADR 0028](./0028-provider-harnesses-are-runner-installed-executables.md)):** the embedded-Claude-binary clause is withdrawn. Sessions drive the runner-installed `claude` (floor-pinned to the compiled-in SDK's version), the SDK's platform packages are excluded from the build, and the binary lands at roughly 60-70 MB instead of 250-270 MB. pi likewise ships as its own standalone binary driven over RPC, so `BUN_BE_BUN=1` is no longer needed for pi children. Everything else in this ADR stands.

First run is zero-ceremony and desktop-proof: `hercule serve` on an empty home auto-initializes (create home, migrate schema, mint master key into the keychain, start the local runner) and prints a one-time setup URL - and that terminal print is the CLI's entire onboarding role, because onboarding logic lives wholly in the web app and public API (setup state and one-time token are API surface, password setup is a web view; the CLI never prompts interactively). The future desktop app then *is* the installer - it manages the binary, runs serve, reads the token, and opens the same setup views - rebuilding nothing. Upgrades: forward-only migrations embedded in the binary run automatically at boot inside a transaction, preceded by a timestamped DB file backup; an older binary meeting a newer DB refuses to start. `hercule upgrade` self-updates (fetch, verify checksum/signature, atomic swap, supervisor restart); the controller checks the releases feed and surfaces updates as an ordinary Notification - no unattended auto-install in v1 (that convention arrives with the desktop app). Fleet skew is warn-don't-block (hard refusal only on protocol incompatibility, which hello negotiation already implies), and the controller can upgrade a runner remotely with one WS command reusing the same self-update path - upgrade controller first, then runners, as a UI-nudged convention. Disaster recovery beyond promotion: a daily SQLite online backup (`VACUUM INTO`) into `~/.hercule/backups/` with short retention; offsite backup is the user copying that directory, honest because secrets stay encrypted and inert without the keychain-held master key.
