# One operation vocabulary, coarse grants, explicit routes

Every public-API operation has one identifier, `<entity>.<verb>` with the entity singular (`task.create`, `session.spawn`, `workflow.submit`), and that identifier is used verbatim as the built-in workflow action id, as the `hercule` CLI command (`hercule session spawn`), and as the key in the contract package; `query` is the single list verb of every entity and returns that entity's items, so there is no `list`/`search`/`query` distinction anywhere (`memory` keeps its prototype-tested `list`/`search` because they return different types). Grants keep the coarse families ticket #18 pinned, renamed singular (`task`, `workflow`, `session`, `infra`, ...), with read/write-style verbs plus a few custom ones, and are deliberately *not* one-to-one with operation families: `infra.write` covers `runner.*`, `plugin.*`, `provider.*` and `controller.*`, and the operation-to-grant mapping is an explicit table in the contract that every 403 and every `--help` reads from. Grants are unscoped in v1 (a grant on a family covers every entity in it; `memory` is the sole exception, pinned to the token's assistant). HTTP routes are resource paths with methods (`GET /api/v1/tasks?label=bug`, `POST /api/v1/sessions/{id}/interrupt`) written explicitly per operation in the same table, with a derivation convention the table follows and a CI test that operations and routes are one-to-one. We rejected plural-everywhere ids (nicer mechanical mapping to grant names, uglier CLI, and the grant mapping is a table anyway), a fine-grained CRUD grant per entity (regular, but a second vocabulary agents must learn and profiles that grow with every entity; finer grants can land inside a family later without breaking profiles), and one RPC path per operation (it buys only the absence of a route table, which we want explicit regardless, and forfeits GET semantics and conventional resource URLs). Accepted costs: three spellings of one noun exist by rule (singular op id, plural path noun, coarse grant family) and are reconciled only by the table; an assistant with `session.read` can read every session's transcript, which is intended (assistants exist to help their human know what is happening) and is the reason scoped grants stay a post-v1 refinement rather than a v1 wall.

*Amended 2026-09-15 ([#126](https://github.com/rogierpennink/hydra/issues/126)).* The identifier is no longer used verbatim as the `hercule` CLI command. The CLI spells each operation for a terminal (`hercule task list`, `hercule runner join-token create`), in a table beside the grant table in the contract, one row per operation, one-to-one with the operations by test, and its `--help` names the operation id, route and grant. The id keeps naming the endpoint, the contract key, the workflow action and, through the grant, the 403; the CLI table is the fourth spelling of one noun and, like the other three, is reconciled by a table and nothing else. Spec 11 §6.3 holds the spelling rules.
