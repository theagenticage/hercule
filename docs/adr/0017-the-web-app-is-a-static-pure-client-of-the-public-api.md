# The web app is a static pure client of the public API, with a subscriptions-only live overlay

The web app ships as a static SPA (Vite, React 19, TanStack Router) served by the controller at its own origin - no SSR, no rendering runtime beside the controller, and no privileged path: every query and mutation goes through the same HTTP API that agents and the CLI use (ADR 0013). Live-ness is an overlay, not a parallel API. One WebSocket per client carries subscriptions only - live-topic subscribe/unsubscribe, payload-carrying deltas for append-only streams (session transcripts, the event feed; reconnect replays from the store's durable cursors), and invalidation nudges for mutable records, which the client refetches over HTTP (TanStack Query owns all HTTP read state). Nothing is reachable over the socket that HTTP cannot answer. The single multiplexed socket is forced, not chosen: the plain-HTTP LAN default (ADR 0015) means browsers speak HTTP/1.1 with its per-origin connection cap, so parallel SSE streams do not fit. Auth stays cookie-free so the UI remains an undistinguished API client: the browser holds the ordinary opaque bearer token, and the WebSocket authenticates with a short-lived single-purpose ticket fetched over HTTP (t3-code's pattern) - no cookie jar, no CSRF machinery. An actively watched session additionally gets ephemeral token-delta passthrough, a live tap beside the durable path: the store keeps coalescing at message/turn boundaries (ADR 0004 context), deltas stream only to subscribed watchers, and reconnect falls back to the coalesced records.

**Amended 2026-09-02 ([#53](https://github.com/theagenticage/hercule/issues/53), [ADR 0031](./0031-the-backend-is-written-on-effect.md)):** the WebSocket is an Effect RPC connection. The hand-rolled envelope pinned by #45 is superseded and its semantics kept as streaming RPC methods (one per topic family, taking a cursor; the ticket presented once at connect). The socket still carries live-topic subscriptions only, every query and mutation stays on HTTP, and the web app stays a TanStack Query client whose React code writes no Effect code (`effect` reaches it only transitively through the contract's schemas): `client-core` wraps the derived HttpApi client into promise functions and the RPC streams into plain subscribe callbacks. The everything-over-WebSocket rejection stands, with `@effect/atom-react` named as the revisit if it ever falls.

Desktop-readiness is achieved through structure, not a shell. Client logic lives in framework-agnostic packages: `client-core` (typed client over the contract package, WebSocket supervisor with reconnect/replay, live stores, auth) with a thin React bindings layer, and a shared `ui` package holding the component library (shadcn/ui) - so `apps/web` is routes and presentation only, with no domain logic in components. A future desktop app (planning assumption: Electron, since any realistic option renders web tech; the decision belongs to the post-v1 desktop effort) reuses core and components wholesale while staying free to build desktop-specific UI - explicitly not a wrapped webview. We rejected SSR meta-frameworks (a second server-side runtime and a privileged UI path), everything-over-WebSocket à la t3-code (would fork every operation into two invocation paths where t3-code has only one consumer), and cookie sessions (shell-hostile, adds a CSRF surface). Performance conventions are pinned as named, lint-enforced-where-possible rules: React Compiler on from day one, fine-grained external-store subscriptions and never React Context for changing data, every unbounded list virtualized, token deltas batched outside React and flushed at most once per animation frame, route-level code splitting with a CI bundle budget.
