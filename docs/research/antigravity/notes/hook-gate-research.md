# Can a home PreToolUse hook be the edit-watch gate? (agy 1.5.15, Linux, home neon)
Scripts: recorder/scenarios/t9-gate.ts (part 1), t10-escalate.ts + rec8/cfg/*.json (part 2). Recordings: rec8/*.jsonl (first line = setup note, then `note` lines for each request/answer/prompt). Hook logs: /var/tmp/hercule-1282-hookdir/{<name>,t10/<name>}/. Workspaces /var/tmp/hercule-1282-work/, private TMPDIR. `<home>/config/hooks.json` absent before, removed after every run (checked).

## Part 1: the gate
- ENV: a hook process sees the agy process's environment (HERCULE_T9_MARK set only on the agy process arrived in all 9 runs).
- ID: hook input `toolCall.id` is EQUAL to the ACP `toolCallId` of the `tool_call` update (and of the permission request's toolCall) for `run_command`, `edit_file` and `write_file`, in every run (default, accept-edits, full). `toolCall.name` is the same tool name (`run_command`, `edit_file`, `write_file`, also `read_file`). Args are in `toolCall.args` (`CommandLine`, `Path`, ...). Other fields: conversationId, cwd, workspacePaths, stepIdx, hookEventName.
- It runs for EVERY tool call (matcher "" ), so a matcher `run_command|edit_file|write_file` limits it (matcher is a regex on the name; read_file also fired in the edit runs).
- ORDER: runs before the tool, in default, accept-edits and full access (`--dangerously-skip-permissions`), once per call. For calls that ask: the hook ran 3-6 ms BEFORE the permission request (run-default: hook 1795694497700, request ...704; write-default hook ...127, request ...219 after model time; edit-default likewise). So the start mark is taken before the Request: it is early, which spec 19 allows. For a call that asks, the runner's own allow-answer mark (already in the adapter) is later and moves the start (spec: only first Request moves start).
- Home hook and workspace `.agents/hooks.json` hook BOTH run when both exist (ws-run: workspace at ...339, home at ...342; no short-circuit even when the first answers auto_approve, see part 2).

## Part 2: can a session escalate through workspace files, and can the home hook stop it?
(`$HOOK` = `bun /var/tmp/hercule-1282-hookdir/t10/hook.ts <tag> <decision> <regex on args>`: answers the decision only when the regex matches `toolCall.args`.)

1. Escalation in accept-edits (recordings rec8/e1*.jsonl):
 - e1a: edit tool writes `<ws>/.agents/hooks.json` (hook auto_approve for `MARKERWORD`): the write ran with NO request. Same turn, `echo MARKERWORD > ran.txt`: ASKED (1 request), hook did not run. So a hooks file written mid-turn is NOT picked up by the next call of that turn.
 - e1a2: same, but the command comes in the NEXT prompt (same process): hook ran, auto_approve, 0 requests. A fresh agy process in the same workspace: hook ran too, 0 requests. So the escalation works from the next turn on.
 - e1b3: file created by a shell command (`sh mk.sh`): that command ASKED once (allowed by me); next prompt `echo MARKERWORD`: hook auto_approved, 0 requests.
 - e1c control: pre-existing workspace hook: auto_approve, 0 requests.
2. Home hook (matcher `edit_file|write_file`, regex ".") against 9 writes in accept-edits (cwd = `<root>/sub`, root is a git repo; targets: sub/.agents/hooks.json, sub/.agents/mcp_config.json, sub/.agents/rules/x.md, sub/AGENTS.md, sub/.agents/skills/x/SKILL.md, root/.agents/hooks.json, root/AGENTS.md, sub/lnk.md (symlink to root/.agents/rules/z.md), `sub/../.agents/rules/y.md`), with a workspace hook auto_approve on the same calls:
 - `deny` (e2-deny): all 9 failed with "tool call denied by pre-tool hook: <reason>", nothing written (the existing hooks.json kept its content, the symlink target untouched). deny BEATS the workspace auto_approve. Both hooks ran for each call (workspace first, home second, ~65 ms apart because of bun).
 - `force_ask` (e2-force_ask, with and without the workspace hook): does NOT make edit_file/write_file ask in accept-edits: the 5 writes inside the cwd ran with 0 requests, even with only the home hook. Writes outside the cwd (root/...) asked by agy's own rule (1 request; I rejected it and the rest of that batch failed). So only `deny` is usable against writes; `auto_approve` from a workspace hook beats `force_ask`.
 - What the hook sees of the path: `toolCall.args.Path` AS GIVEN: absolute, with `..` unresolved (`.../sub/../.agents/rules/y.md`), a symlink not resolved (`.../sub/lnk.md`). A hook that denies by path must resolve the path itself (and a symlink or a linked folder, which only a shell command can create, hides the real target).
3. Which workspace files change approvals (default mode unless said):
 - `.agents/hooks.json` (yes, above). `.agents/plugins/<n>/{plugin.json,hooks.json}` (e3a): hook auto_approve, 0 requests. `.agents/plugins.json` `{"entries":[{"path":"myplugins"}]}` + `myplugins/<n>/...` (e3b): same, 0 requests.
 - `.agents/mcp_config.json` (e3c, accept-edits): a stdio server `{"command":"sh","args":["-c","touch $ROOT/SPAWNED; sleep 20"]}` was SPAWNED at the first prompt with no tool call and no request (code execution by file). Calls of its tools ask (mcp-research.md section 7).
 - Not measured to change approvals (instructions or skills only, no approval code in them): `AGENTS.md`, `GEMINI.md`, `.agents/rules/*.md`, `.agents/skills/*`, `skills.json`. Not tested; docs list no permission setting in them.
 - A hook-only defence must therefore cover: edit_file/write_file to `.agents/hooks.json`, `.agents/mcp_config.json`, `.agents/plugins/**`, `.agents/plugins.json` (plus the doc-only `.agents/agents.json`, `.agents/rules.json`) in the cwd, every parent up to the git root; and shell commands (they ask in accept-edits, but in full access nothing asks).
