02How far along, and where

No code map needed

Every command a session runs, and every file it reads, searches or edits, already reaches the controller as an event. Today the controller stores those events and reads none of them.

The proposal: read each event once, as it arrives, into a small record on the session, the digest. Every list and board then reads one line from it.

First, a finding

Agents keep no plan today

We counted what the sessions on this runner really did.

0todo or task calls in 496 Claude sessions
0plan updates in 188 Codex sessions
0plan tools in pi
86%of test commands piped, most into tail, head or grep

Claude's SDK turned its todo tools off by default for current models. Codex has a plan tool, and no session here used it. pi has none. And a test piped into tail reports the exit code of tail: only 2 of 240 test commands were marked failed.

So Hercule asks for a plan, with a tool of its own: hercule progress. Where there is no plan, a row shows only facts: what the agent does, where, and for how long. Never a bar.

What is it doing now?

Phase: the kind of work, right now

One word for the latest tool call of the turn. It says what the agent is doing in this turn, never a guess at the stage of the project.

PhaseWhenHow sure
ExploringReads and searches, before any edit in this turn.Good. Codex parses its own commands; for Claude and pi the runner parses the shell commands.
ChangingA file edit. Reads after an edit stay Changing.Reliable. Completed edits, and the edit watch.
VerifyingA test, typecheck, lint or build command ran.Reliable that it ran. Whether it passed, only when the output is recognised.
Shippinggit commit, git push, gh pr create or gh pr merge, or a pull request through the GitHub Connection.Reliable. The command text.

Two states win over the phase: Waiting, when a Request is open, and Resting, when the session is idle. The peek panel always says why a session sits where it does: "Verifying: ran pnpm test checkout 40s ago".

A command is classed by its first real program, after cd … && and env. The list is a setting with these defaults, so a project with its own just test can add it.

Where?

Focus: the folder it works in

No code map, only the paths of the files the turn touched.

  1. Take the turn's file paths, relative to the checkout. An edit weighs 3, a read 1, a search 0.5. Reads and searches count only while the turn has no edit yet. Root files every agent reads, such as AGENTS.md and package.json, do not count.
  2. Add up the weight under every folder.
  3. The focus is the deepest folder with at least 60% of the weight. The heaviest file is the hot file. When no folder reaches 60%, the focus is the two heaviest top folders.

How far along, without a plan

Milestones: what Hercule saw happen

Facts with a time, in the order a coding task usually meets them. They are evidence, not a plan: a research thread may reach none and still be done. Here is the 3-D Secure fix at 09:30.

  1. Changed09:24the first file edit
  2. Tested09:28the first test command
  3. Passing09:28when the output is recognised: "24 passed"
  4. Committed09:29git commit succeeded
  5. Pushednot yetgit push succeeded
  6. PR opennot yetgh pr create, or the GitHub Connection

Passing is the careful one. A failing summary clears it. An output Hercule does not recognise leaves it unknown, and the row then says "Tests ran", never "Tests pass".

How far along, with a plan

The progress tool

Sessions already use the hercule command line. One new verb takes the whole list each time, the way Claude's old todo tool did.

What the agent runs

  --step "Find the cause:done" \
  --step "Write a failing test:done" \
  --step "Fix handlePaymentResult:done" \
  --step "Run the checkout tests:done" \
  --step "Push the branch:doing" \

To get plans, Hercule's session instructions gain two sentences:

Keep a progress list with hercule progress when a task has more than three steps. Update it when a step is done.

Short questions get no plan, and that is fine. When a provider keeps a plan of its own (Claude's todo tools, if turned on, or Codex's plan updates), Hercule reads that too, and the latest plan wins. A plan that grows shows as it is: "3 of 9", up from "3 of 7". The row never claims a percentage the agent did not give.

Is it cheap?

What it costs

A few comparisons per eventDone once, as each event is stored, where Subagent.activity is built today.
No extra read, no model callThe digest is folded from events the controller already stores.
One small columnOn the session's row, written in the same transaction as the event that changed it.
Nothing per tokenSent with the session updates that already go out, batched over one second, like usage and tool counts.

Clients read nothing new: the digest comes with the session query every list already makes. Spec 18 turned down an activity line on the phone because it cost one transcript read per row. The digest removes that cost.

The work

What changes, where

Runner
Turns hercule progress into a plan event, and maps the providers' own plans. Copies the exit code, duration, folder and git details of each command out of the raw event into typed fields. A small shell parser classes reads, searches, checks and git. Read and search paths become checkout-relative, as edits already are.
Session instructions
Two sentences asking for hercule progress.
Protocol
The steps on plan events; the exit code on finished commands.
Controller
buildSessionDigest, beside buildSubagentActivity. A digest column (a migration), the turn's start time and the turn count.
Contract
Session.digest and Session.turnStartedAt.
Client-core
One function that turns a digest into the row's line, and one that groups sessions by phase for the Kanban, each with its own test.

One choice to make on purpose: once Claude's todo calls become plan events, they stop counting as tool calls.

Honestly

What it does not do

  • It does not make agents keep a plan. Some will skip it, and their rows say less.
  • It gives no percentage without a plan. Phase and milestones say what happened, not how much is left.
  • The phase is this turn's work, not where the whole task stands. A thread that ran its tests and then reads more files is Exploring again, and that is true.
  • Focus needs files. A question or a web search has no focus, and the row says less.
  • The main checkout has no edit watch, but its tool calls still carry paths, so focus still works there.

03The List

The List, three ways

Each draws the same 70 sessions from the same digest, and each keeps Waiting on you on top.

Rows

Today's sidebar row, full width, grouped by project. The second line becomes the digest line. A project folds to one line ("webshop · 14 working · 1 needs you"), and quiet threads fold into "9 resting".

Table

One 36px line per thread, in quiet aligned columns: status, thread, progress, where, machine, age. Sort by any column. Made for scanning many rows fast, as in Linear.

Outline

Zoom levels. First one line per project, then its threads, then one thread's digest and crew. → zooms into the line you are on, ← zooms out. At rest, the whole morning is five lines.

04Finding and zooming

Find it, then look closer

One field: "Find a thread". Type anywhere in the overview and the field fills.

Plain words match titles, branches, folders and models. Words with a colon narrow further:

  • project:webshop
  • in:src/checkout
  • model:codex
  • on:build-box-1
  • by:me
  • is:waiting

Beside the field sit four lenses, as quiet text: All · Following · Mine · Needs you. Following is the threads you follow, with F or from the peek panel. Mine is the threads you started yourself, not the partners your agents started. A filter never hides a thread that waits on you without saying so: "1 waiting thread hidden".

The peek panel

Select a thread and a panel slides in at the right, without leaving the list: the plan's steps, the milestones, the focus with its hot files, the last check, the crew, the ask with its buttons, and Open thread. It is the zoom on one thread.

↑ ↓ walk · space peek · ↩ open · F follow · esc clear

05The Kanban

The Kanban, two ways

Cards are small and calm: a face, the title, one muted line and the age. Within a column, cards group by project, and resting cards fold to a count.

By state the default

Needs you · Working · To review · Resting · Done today. To review holds the threads whose turn ended after you last looked. Every column comes from facts Hercule has, plus one small new field: when you last looked.

By phase

Exploring · Changing · Verifying · Shipping, with Needs you as a narrow lane on the left and Resting folded on the right. Cards move when the work does. Changing and Shipping are reliable; Exploring and Verifying are good but not certain, so every card can say why it sits where it does.
