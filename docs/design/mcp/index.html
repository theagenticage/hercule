MCP in Hercule

An exploration. What it takes to give sessions MCP tools that are set up once and work on every runner, whether a plugin can bring its service's MCP server along with its sign-in, and whether Hercule's own API should speak MCP beside the CLI.

17 November 2026, changed after Rogier's review the same day after his review of the screens prototype on 19 November, and after his decisions of 20 November (see section 10) · Nothing here is built. The facts behind it are in three research notes (protocol and harnesses, vendor sign-in, t3-code, how an OAuth sign-in comes back, how harnesses handle a tool list that changes) and one measurement (CLI against MCP, scripts in benchmark/).

1Short answers

Set up once, use on every runner?
Yes

The controller keeps the MCP servers and stands between every session and every server. A runner stores nothing.

No second sign-in for a service?
Yes, for Sentry, Linear, GitHub

Their MCP servers take the token the Connection already holds. This comes from their docs and source. It is not yet proven with a real call.

Can a plugin bring MCP, sign-in included?
Yes

About ten lines per plugin: the server's address, and how to present the Connection's token to it.

Servers that are not from a plugin?
Yes

A URL added in Settings or with the CLI. No sign-in, a pasted token, or OAuth run once by the controller.

Hercule's own API over MCP?
Possible; a small gain, at a cost

All 280 measured runs passed, by CLI and by MCP alike. A tool per operation saves about one request per task. The CLI costs the least context. Keep the CLI as the main surface.

2The idea in one picture

A session only ever holds its own Session Token, which it already has today for the hercule CLI. It points its harness at the controller. The controller checks the token, takes the service's credential from the Connection, and makes the call. The vendor's token never leaves the controller.

What a session actually gets

Every session gets one MCP server: the gateway, at one fixed address that is the same for every thread and every runner. The gateway knows the thread from the Session Token, and answers with the tools of that thread's servers. This is everything the harness is given:

// Claude Code: the SDK's mcpServers option
mcpServers: {
  tools: {
    type: "http",
    url: "http://controller:4937/mcp",
    headers: { Authorization: "Bearer <session token>" },
  },
}

// pi: Hercule keeps --no-extensions and switches on
// exactly what it needs, then adds the gateway from
// its own extension.
pi --no-extensions -e builtin:mcp -e builtin:tool-search \
   -e <Hercule's extension> ...
pi.registerMcpServer("tools", { url, headers, exposure: "deferred" })
# Codex: config on thread/start
mcp_servers.tools.url = "http://controller:4937/mcp"
mcp_servers.tools.bearer_token_env_var = "HERCULE_TOKEN"

# Codex reads a changed tool list only with this switch,
# which is under development (0.164 and later).
features.mcp_tool_list_changed = true

# What the agent sees, in a thread with Sentry and Linear:
mcp__tools__sentry__search_issues
mcp__tools__linear__create_issue

The harness names every MCP tool mcp__<server>__<tool>. The gateway is the one server, so its name is in front of every tool; it is ours to choose, and it is short and neutral. The gateway puts the MCP Server's name in front of each tool. A Session Token lives exactly as long as its harness process, so there is nothing to refresh on the runner.

Tool search is the harness's own. Claude Code, Codex and pi each show the model tool names or one line, and load a tool's details when the model searches. The gateway offers no search tool of its own. What it must do well: keep each full name short (pi cuts at 64 characters, Claude Code drops a tool above 128), and write a first line of instructions that says what is inside, because Codex shows the model that one line and no names.

A thread's list can change while it runs. The gateway then sends the standard "tool list changed" message. Taking a server away works at once on every harness, because the gateway refuses the call. An added server is usable at once on Claude Code, on Codex with the switch above, and on pi (tested on Claude Code and Codex on 20 November; pi from its source).

The gateway speaks MCP on both sides. Facing a session it accepts the older handshake that the clients in Codex and pi still send. Facing a server it speaks the revision that server has. So a harness on an old revision can use a server that only speaks the newest one (2026-07-28), which it could not reach directly. The first build forwards tools only: no resources, no prompts, and no questions from a server to the user.

4Seams

Five places where behaviour can change without editing the code around it. Two are new. Two exist and get one more thing through them. One is used exactly as it is.

SeamWhat a caller must knowWhat sits behind itAdapters, and why the seam is real
new
The gateway
POST /mcp		 One address and a Session Token. Nothing about which servers exist, their sign-ins or their protocol versions. Who is calling, the grant check, which servers this session gets, the credential, one retry after a refresh, the error a person can act on, the audit entry. Three callers that differ: Claude Code, Codex, pi. Three harness MCP clients on three protocol revisions. The gateway is the one place that absorbs that.
new
The MCP Server catalogue
mcpServer.*		 Six operations. A server has a name, a status and its tools. Where a server came from. A plugin's declaration and a URL the user typed end as the same record, so nothing above this seam knows the difference. Two sources: plugin and user. This is what makes "not from a plugin" free once "from a plugin" works.
reused
Connections
credentials(id)		 "Give me this Connection's credential, fresh." Encrypted storage, one refresh at a time, needs-reauth, the reconnect screen. All of it exists. Every plugin's poll loop and every workflow action already cross it. The gateway is one more caller. This is what removes the second sign-in.
widened
Plugin registration
registerMcpServer		 A pure function from a Connection to a URL and headers. Each vendor's quirk: Sentry wants Sentry-Bearer, GitHub picks tool sets by header, Linear is plain Bearer. Three plugins, three different answers. The gateway has no vendor name in it.
widened
Session delivery
SessionStart.mcpGateway		 One fact: this session has the gateway. How each harness is given an MCP server, and what it needs switched on to search tools and to notice a changed list. Three adapters, one mapping function each. A changed list needs no new frame: the harness hears it from the gateway.

The gateway is the deep module here: its interface is a URL, and everything hard is behind it. The test surface is the same URL: a fake MCP server on one side, a session token on the other, and every rule above can be checked without a harness.

5Interface changes

Sketches, to make the size concrete. Names follow the repository's rules; the spec work decides the final spelling.

plugin-host: a plugin declares its service's server

// packages/plugin-host/src/mcp-servers.ts
/** A remote MCP server a plugin offers to sessions,
 *  reached with a Connection of the plugin's own type. */
export interface McpServerContribution {
  /** The host makes the qualified id `sentry/sentry`. */
  readonly id: string;
  readonly displayName: string;
  /** One line for Settings: what an agent can do with it. */
  readonly description: string;
  /** The qualified type of the Connection it is reached with. */
  readonly connection: { readonly type: string };
  /** The server's address without path or query, known
   *  before any Connection exists. It is how a server the
   *  user added by hand is recognised as this one. */
  readonly origin: string;
  /** Returns where the server is and the headers that carry
   *  the credential, for one Connection. Pure: no I/O. */
  readonly buildUpstreamRequest: (connection: {
    readonly credentials: Record<string, string>;
    readonly config: unknown;
  }) => {
    readonly url: string;
    readonly headers: Readonly<Record<string, string>>;
  };
}
// plugins/sentry/src/mcp-server.ts - the whole change
export const mcpServer: McpServerContribution = {
  id: "sentry",
  displayName: "Sentry",
  description:
    "Search and read issues, events and traces; update an issue.",
  connection: { type: SENTRY_CONNECTION_TYPE },
  origin: "https://mcp.sentry.dev",
  buildUpstreamRequest: ({ credentials }) => ({
    // The Connection's scopes do not cover project
    // management, so those 18 tools are left out.
    url: "https://mcp.sentry.dev/mcp" +
      "?disable-skills=project-management",
    headers: {
      Authorization: `Sentry-Bearer ${credentials.accessToken}`,
    },
  }),
};

// plugins/sentry/src/index.ts, in register()
yield* registerMcpServer(host, mcpServer);

What does not change

  • Connections. No new method. The gateway calls the same credentials the poll loops call.
  • The secrets table. The token of a server added by URL is stored there too, owned by its MCP Server.
  • The normalized event stream. tool_call { kind: "mcp" } with detail.server exists (spec 06 section 6.3), so the transcript and the apps already draw these calls. One addition: a call the gateway refuses also gets a line of its own on the thread, as a runtime.warning. The prototype showed why: the failed call sits inside a closed work stretch, so the user never sees it.
  • Approvals. An MCP tool call reaches the same approval seam as any other tool on Claude Code and Codex. The Access Mode decides, as today.

6Flows

6.1 A plugin's server, with no second sign-in

The user already connected Sentry for the Inbox. Settings › MCP servers lists that Connection with a switch, because its plugin offers a server. Switching it on is the whole setup.

6.2 A server that is not from a plugin

The user adds a URL. The controller finds out what the server needs. OAuth runs once, on the controller, whichever machine the browser is on.

Step 8 is the sharp edge. MCP requires the redirect to be localhost or HTTPS, and a controller reached at a tailnet address over plain HTTP is neither. So the desktop app listens on the user's own machine for a moment, receives the redirect, and hands the whole query string (code, state, issuer or error) to the controller, which exchanges the code with the verifier it kept. Pasting the redirected address is the last resort: the web app without HTTPS on the controller, and a CLI run over SSH. MCP has no device code. No client we looked at splits the listener and the exchange over two machines, so slice 3 starts by proving it (note).

7State machines

7.1 An MCP Server

Five states. The status is stored, because Settings shows it and a start frame leaves out a server that is not ready, and says so on the thread.

A server that acts through a Connection follows it: when the Connection goes to needs-reauth, the server goes to needs sign-in, and reconnecting the Connection brings both back. Entering needs sign-in or unreachable tells the user once, as a Notification. A session that is already running keeps its list; a call to a server that is not ready fails with the reason.

7.2 One tool call inside the gateway

Every way out carries a message a person or an agent can act on. Nothing falls back silently.

The third refusal also moves the MCP Server to needs sign-in (7.1). The server's own sign-in challenge is never passed to the harness: a harness that sees one tries to open a browser on the runner. Each refusal also puts a line on the thread, with what the user can do about it.

8CLI against MCP, measured

t3-code reaches for MCP first. Its repository holds no measurement behind that choice: the one written reason compares MCP with building a plugin per harness, not with a CLI (note). So this measures it for Hercule.

Method. A real controller from this branch's binary, in a throwaway home. Ten tasks an agent meets in practice, each in a project of its own, each checked against the controller's state afterwards. Four ways to reach Hercule:

ArmWhat the agent has
cliToday: hercule on PATH, the orientation in the system prompt, the skill.
mcp-searchOne MCP tool per operation, 214 tools, derived from the same contract table as the CLI. The harness loads a tool's schema only when the agent searches for it. This is what Claude Code and Codex do by default.
mcp-metaTwo MCP tools: hercule_help and hercule_call. The CLI's idea, spoken over MCP.
mcp-eagerThe 214 tools, all loaded up front. What an older harness, or tool search switched off, would do.

What every session carries before it does anything

Tokens added to the first request, Claude Code with Sonnet. Lower is better.

What it shows

  • Success is the same. All 280 runs passed their check: every arm, on Sonnet, on Haiku and on Codex. Nothing here supports "more correct calling" for MCP.
  • A tool per operation saves about one request on Claude Code. Sonnet: 5 requests a task against 6, and 10.7 s against 13.2 s. Haiku: 4 against 6. The agent finds its tools in one search; with the CLI it reads help twice first. On Codex the two are level: 22.4 s against 22.3 s.
  • The CLI carries the least into every session: about 600 tokens, against about 3,400 for the names of 214 tools. Every session pays this, also the many that never call Hercule. With all tools loaded it is about 92,000, in every request.
  • Each has a task it is better at. Moving data into a file, the CLI pipes it: 88K tokens against 121K. Six writes in a row, tools run side by side in one request: 120K against 178K.
  • Typed tools fail less on the first try. Runs with a refused call that the agent then corrected, on Sonnet: 6 of 30 by CLI, 0 of 30 with a tool per operation, 4 of 30 with two tools. Four of the six CLI refusals were one papercut: --project refused an id tail that most flags accept. That is fixed on this branch.
  • The two-tool shape is the weakest. Most lookups, most refused calls, and the slowest on Codex (27.2 s). A free-form input gives away what typed tools are good at.

Tokens read per task

Median input tokens over every request of a run, Claude Code with Sonnet, three runs per bar.

Every run

Medians per run. "Lookups" are calls that only read documentation: --help, hercule_help, a tool search, opening the skill. Codex reports usage per turn, so it has no per-request figures. Run with Claude Code 2.1.325 and Codex 0.169.0, the versions installed on 17 November.

What it does not show

  • Whether the CLI and MCP tools get in each other's way when a session has both. Every run had one or the other.
  • The agent ran with the user's API key, not a Session Token with a Permission Profile, so no run met a 403.
  • Ten tasks over tasks, projects, initiatives, the wiki and profiles. No session spawning, no long transcripts, no workflow YAML.
  • Three runs per task and arm, 30 per arm. A difference of 10% in tokens is inside the noise. The context cost, the pass rates and the request counts are not.

Recommendation

  • Keep the CLI as the one surface every session has. It costs the least context, it is the only one that works on pi today, a shell can pipe it, and nothing measured here beats it on success.
  • Do not add a tool per operation to every session. The gain is one request per Hercule task on Claude Code, and none on Codex. The price is a second way to do everything, about 2,800 more tokens in every session on a harness that defers tools, and about 91,000 more on one that does not.
  • Where it could pay: an Agent that does little but call Hercule, such as a triage agent. There the saved request is most of the work. That makes it a choice per Agent, not a default.
  • If Hercule's own tools are wanted later, for an assistant session without a shell (spec 12, post-v1), the gateway serves them at /mcp/hercule from the same contract table. The prototype in benchmark/mcp-server.ts is that derivation, in about 300 lines. It needs the command tree moved from @hercule/cli into @hercule/contract.

9Shapes not chosen

ShapeHow it would workWhy not
One gateway address per server The first shape on this page: /mcp/sentry, /mcp/linear, and the harness is given the thread's servers one by one. It keeps each service's usual tool names, and Codex shows the model a line per server. But a thread's list could not change while it runs: Codex does not let a loaded thread's servers change, and every other harness needs its own call for it. With one address a changed list is one standard message. Rogier decided for one address on 20 November.
Hand the vendor's token to the runner The start frame carries each server's real URL. The harness asks a helper command for the header (headersHelper on Claude Code, http_headers_helper on Codex), and the helper asks the runner, which asks the controller, as gh does today. It works on paper and keeps the controller out of the data path. But the refresh depends on each harness re-running its helper after a 401, which the Claude SDK's types do not even list. Sentry and GitHub kill the old token the moment it is refreshed, GitHub about every 8 hours, so every long session would rely on that. A server that challenges for sign-in makes the harness try OAuth on the runner. pi gets nothing. And every vendor token then lives in runner memory.
A bridge process per session on the runner hercule mcp-bridge sentry as a stdio server the harness starts. It forwards to the vendor with a token from the runner. Uniform across harnesses, but one extra process of the 99 MB binary per server per session, and the controller sees no call: no grant check per call and no audit.
Each harness signs in itself Link the user's own harness MCP config, as User Material does for instructions. The opposite of the brief: one sign-in per server per harness per machine, stored in three different places. ADR 0032 already left this out for that reason.
Plugin-written tools instead of the vendor's server A plugin's workflow actions (sentry/issue.resolve) offered to sessions as tools, run inside the controller. Not wrong, and nearly free later: an action already has a name, a description, an input schema and the Connection it acts through. But Sentry's own server has 59 usable tools against the plugin's three actions, kept current by Sentry. Start with the vendor's server; add a plugin's own tools where no vendor server exists.

10Decisions, and where this differs from the spec

DecisionRecommendationWhat it touches
1. Gateway in the controller, or tokens handed to runners
decided, 20 Nov		Gateway. It is the more robust of the two and the only one where a sign-in problem always reaches the user through Hercule.New ADR. Every tool call passes the controller: one more hop on the tailnet, and a controller that is down takes MCP tools with it, as it does the CLI.
2. Where a sign-in lives
decided, 20 Nov		Separate. A server from a plugin is reached with the plugin's Connection, so nothing new is signed in to. A server added by URL keeps its own sign-in, on the server's own page, as the prototype draws it. It is not a Connection and does not show in the Connections list.The mcp-servers domain stores those sign-ins itself, in the same secrets table, and shares the code that refreshes a token with connections. No built-in mcp plugin and no new Connection type. The gateway has two places a credential comes from.
3. One fixed address
decided, 20 Nov		Every session gets one MCP server, the gateway, at one address that is the same for every thread. The gateway knows the thread from the Session Token and answers with the tools of that thread's servers, each with its server's name in front. The harness's own tool search does the searching; the gateway offers none.The start frame only says that the session has the gateway. The list of servers is not in it, which differs from spec 06 section 4 and #222: they put a raw mcpServers config on the Agent and the stored SessionSpec. A list that differs per thread at one address is safe on all three harnesses (note). Nothing is kept per thread between starts, so a thread resumed after days gets its current list.
3a. Harness versions
decided, 20 Nov		The design assumes the latest version of each harness, which is what runs. It does not design around the versions the spec names as pinned.Spec 06 names pinned versions and says pi has no MCP. On 20 November the machine ran Claude Code 2.1.329, Codex 0.171.0 and pi 1.5.2.
4. Who gets which server
decided in review		A thread has its own list of servers. It starts as the list its Project names; a thread with no project starts from a default list kept in Settings. The user changes a thread's list under the composer's plus button, on the Draft Thread and on a started thread. An MCP Server is a building block and knows nothing of projects or threads. Two Connections to one service, such as a work and a hobby Sentry, are two servers; each project names the right one. Workflow steps and assistant sessions get none until an Agent can name servers too.The glossary says a Project has "no behaviour, and one default only". It gains a second thing it names. The domain graph gets edges from projects and sessions to mcp-servers, never the reverse. The session record carries the list, so a client can read it, with the servers left out at the last start. One list cannot hold two servers with the same name. A change to a started thread's list reaches the agent through the gateway's "tool list changed" message. Taking a server away works at once everywhere. An added server is usable at once on Claude Code, on Codex with its mcp_tool_list_changed switch on, and on pi.
4a. Where servers are managed
decided in review		Settings › MCP servers is the one place: one list with switches. First every Connection whose plugin offers a server, on or off, then the servers added by URL. A Connection's own page only says that it offers agent tools and links to that list. Off is enabled: false, never a delete: the name and the projects that name the server stay. For now a project is given a server on the server's own page, a box per project.No grid of projects against servers, and not the sidebar's project menu. The prototype is in apps/desktop/src/renderer/specimens/prototype-mcp/.
4b. GitHubA session's GitHub server uses the Connection that already backs its workspace, so the tools act as the same account that pushes.ADR 0016: identity follows the repo.
5. Taint
decided, 20 Nov		No. A result from an MCP server does not mark the session tainted. Much of what a server returns is trusted, or holds no text an outsider wrote.Spec 13 section 10 stays as it is. What still guards the Skill Library: no shipped Permission Profile can apply a skill.
6. OAuth for user-added servers
partly decided in review		How the sign-in comes back: the desktop app catches the redirect on the user's machine and hands it to the controller. That is acceptable for now. Pasting the address is the last resort only. Still open: a relay page on hercule.sh for the web app, and which client registration to use. Client ID Metadata Documents need one public HTTPS document for all Hercule installs. Dynamic registration needs none but is deprecated, with removal no earlier than July 2027.Spec 13 section 3.1 ("ships no OAuth client secret and hosts no OAuth relay"). A relay page would change that line. A static metadata document is not a relay, but it is the first thing Hercule would host.
7. Hercule's own MCP server
decided, 20 Nov		Not in v1, and no door is closed. The server name hercule is kept for it, so no server the user adds can take it, and the command tree it would be derived from stays in one place.ADR 0013 and spec 11 stand for v1. #199 stays open for after v1.
8. Which tools are callable
decided in review		Not in v1. The gateway can do it: it answers tools/list and forwards tools/call itself, so a tool can be switched off for every harness in one place. One ticket to look into it later, including whether a project may override a server's tool settings.v1 stores and shows each server's tool list, and changes nothing in it.
9. Duplicates
decided in review		One server per address and external account; a second is refused as a conflict. Nothing is created by itself: a plugin's server exists once the user switches it on. When a plugin offers an address the user added by hand, switching it on offers "Replace": the record keeps its name and the projects that name it, and moves to the plugin's Connection. Adding by hand an address a plugin already offers is refused, with a pointer to that Connection's row in the list.The same rule as a repo Resource and its remote. The plugin's declaration carries the server's address as plain data (section 5).
10. pi
decided, 20 Nov		Hercule keeps starting pi with --no-extensions, so that only what Hercule chose runs. It switches pi's built-in MCP on explicitly, with -e builtin:mcp, and its tool search with -e builtin:tool-search, and adds the gateway from its own extension with the tools set to deferred.The pi harness then declares mcpPassthrough: "native". From pi's source at 1.5.2; not run yet.
