# Work overview: what we decided

The design that came out of a long grilling session with Rogier, 2-6 November 2026. Rogier confirmed it as the shared understanding. Every example here is invented: this repository is public, and no real work data may ever land in it.

The lo-fi prototype that informed all this is beside this file. It runs from `index.html` over `file://`, on invented data. It is input for design, not a design.

## The problem

Hercule can notice work (events, signals) and do work (threads, runs). Nothing holds work the user has taken on, or the external things that concern them. So their picture of their work is pieced together from things that each disappear on their own schedule:

- Intake is a flat feed. It has no hierarchy, so you cannot tell that two signals talk about the same pull request.
- A signal leaves the moment you act on it. Hand a review to a workflow and the pull request is gone from view until it returns. Unless Tracking catches it, it is gone again.
- Real work lives in threads. Those are linked to nothing, and they end up lying around unseen. When a model read 14 unfinished threads, nearly all had the user as the next move, and several had waited weeks.
- Threads mostly stall because the next move costs real thinking, or because a bigger question is unanswered, not because they were forgotten.

The goal is 100x productivity. Past a few active sessions, human attention is the limit. It goes to four things: **deciding, recognizing, checking and expressing**. A design is judged by which of these it makes cheaper.

## The model

```
Events ─▶ Intake (signals, triage)          noisy, you rarely look
             │  rises when it matters
             ▼
          Inbox (External Entities)    ◀──  direct: PRs, review requests,
             │                              assigned tickets
             │  hand to an agent, or take it on yourself
             ▼
          Tasks  ─▶ Overview: Work, List, One surface, Tracks
             ▲
          threads join Tasks automatically
```

| Concept | What it is |
|---|---|
| **External Entity** | A durable record of an outside thing that concerns you: a pull request, a ticket, a triage cluster. Holds its External Ref, title, state, link, and how it concerns you (assigned, opened by you, review requested, mentioned, following). Kept true by plugin polls, so a missed event loses nothing. Never a copy of the ticket. The phrase is for code and docs; the UI says "Pull request" or "Issue" |
| **Signal** | Attached to its entity through its thread ref, and shown inside it, in Inbox and in Intake. A signal can end; the entity stays. A second review request or a mention adds a line to the same card. Signals with no entity, such as an agent's question, stay on their own |
| **Entity kind** | Declared by a plugin, never drawn by it. One generic card draws every kind from fixed slots: mark and identifier, title, status (a shape from a small fixed set, plus a tone), person, a few facts, pace (fast or slow), what to group by, which workflows fit. Customization hooks can grow later. A triage cluster is Hercule's own kind and belongs to no plugin, because triage can combine sources |
| **Task** | What you are actively involved in. Creating a Task is what turns "keeping an eye on it" into "actively involved". It is the existing Task: "a unit of human intent", extended, not replaced |
| **Stage** | One word from a fixed list: Exploring, Planned, Building, In review, Landed, plus the ends Done and Dropped |
| **blockedBy / blocks** | Strong links between Tasks. Together they form a DAG, and they are real structure on One surface, not lines |
| **Follow-up** | A weak relationship: provenance saying this Task came from that one. Never part of a hierarchy |
| **Initiative** | A lasting intent, with an optional target (then it is a goal). Most Tasks have none, and that is normal: the design must never collapse into a giant "no initiative" group. Initiatives are created by hand |
| **Zone, Topic** | Later. Zone: where it acts, mostly a fact from the folders it touches. Topic: what it is about, generated by a cheap model. A test gave 91% agreement between independent runs |

## The rules

- A new thread joins the Task of the session that started it, then the Task of its workspace, and otherwise gets a new Task. Same workspace usually means same work, such as an implementer and its reviewer. Merging Tasks by hand covers the rest. Starting a thread from a Task's card joins that Task. No ceremony: starting a thread is enough.
- Stage comes from facts first (PR opened, PR merged, ticket closed), through shipped, editable workflows, so the core still never moves a card itself. Then agent reports. The user can always drag, and a drag wins until new facts arrive.
- Every Task always shows what it is about and where it stands, even while active. The user should never have to reread a thread. A cheap model call keeps that summary current after a turn ends, using the state of linked objects too. It only describes: it never moves a card or decides anything.
- Done means the acceptance criteria are met. Criteria are domain-agnostic, and the more testable they are, the more can be signed off on evidence. Any step may need permission; the existing Permission Requests cover that.
- A workflow declares which entity kinds it takes, and the card offers it by name. This replaces Hand to an agent in Intake. The handoff creates or continues the Task carrying the same ref. Tracking goes away, because the Task on the board is now where you follow the work.
- Proposals come only from evidence, never from asking agents to think of things.
- No automation in the first build. No policies, no auto-pickup. Build the views, use them, and see if they help. The manual path must always stay fast.

## The Overview

This becomes the Overview, the "all threads" view from the "Five radical sidebar thread designs" thread. The views are different ways of seeing what is going on:

```
Overview:   Office  ·  Work  ·  (later) List  ·  One surface  ·  Tracks
Inbox:      its own place, feeding Work
```

The Office stays exactly as it is and shows sessions, not Tasks. The sidebar stays about "right now".

## What Rogier chose, and why

Fifteen lo-fi views were built on his real work; he kept these. His words are in quotes.

- **Work (Home in the prototype):** "a good default". Kanban with plans on top. Stages are columns, projects are lanes. "I do think kanban is inescapable as a view... I still want to be able to see proper cards, not tiny cells." "Too much like excel" was the verdict on a table of small cells. Each initiative is a thin horizontal line across the stages with a mark per piece, opening in place into a band of cards: "I'd also like to play with seeing initiatives as a more horizontal concept." Streams such as many similar items fold into piles that fan open.
- **Inbox:** "yes this is great". Card based. "It's a lot of text" was the verdict on text rows. "Recognizable as 'github prs', with a clear github icon, pr name, author." "Especially the provenance: logo should help tell inbox items apart from each other, a linear item through logo alone looks like a linear item which is different than a github item." Different kinds behave differently: review requests and PRs are fast and time-sensitive, tickets are slow and need context such as team or project. Triage items rise to the top. Grouping by project, where one exists, would be nice.
- **One surface (later):** a mind map that zooms to cards. "The location-based memory potential here is really great." Chains of blockers are real structure.
- **Tracks (later):** one calendar timeline, "for the purpose of visualizing how long tasks take from conception to delivery".
- **List (later):** "a simple list view". A row is a title, one muted line and one mark.

What he rejected, so nobody repeats it:

- "Too much complexity on the page." "The original crew thread list is still better than all of these simply because it's quieter." The goal is "to declutter the user's mind, not add to it".
- Heavy metaphors. Metro lines "didn't do it for me". The garden, the invented map and the five radical directions did not survive.
- Tiny cells, walls of text, dashboards of numbers, anything that feels like a spreadsheet.

Spatial memory is why he cares about layout. Research (Data Mountain; Cockburn and McKenzie) says what makes it work is that things stay where they are, and that 2D works as well as 3D. Things must never reshuffle because of activity. Recency sorting is banned from the main views.

**The standard for design is that the UI is effective and beautiful.** Rogier: "I don't care about the ADR or spec. The only standard is whether the UI is effective, and whether it's beautiful. If we need to make changes, that's fine." Specs, ADRs and the design book change to follow good design, not the other way round.

## The first build

A complete Inbox and one complete work view in 8 vertical slices, each with testable UI, after the hi-fi design:

1. Backbone: Tasks get stages, threads link to Tasks and join by the rule above, migration. The only backend-only slice.
2. Work board, first light: the Overview switcher with Office and Work, Tasks as cards by stage in project lanes, drag to change stage.
3. Cards say what they are about: the summary writer, a details pane with threads and links, Done, Drop, merging Tasks.
4. Inbox, first light: durable External Entities for your PRs and review requests, on the generic card, with "Take it on myself" creating a Task.
5. Signals inside entities, plus Linear: signals show on their card, Linear is the second kind, Intake groups by entity too.
6. Hand to an agent from the Inbox: workflows offer themselves per entity kind, handing off creates the Task and run, Tracking and the old action go.
7. Cards keep themselves true: PR opened, PR merged and ticket closed move cards, and a Task links its entities.
8. Plans and blockers: initiatives as ribbons on Work, `blockedBy` shown on cards.

Later: triage clusters, List, One surface with Topics, Tracks, policies, the agent report tool, Zones, the retrospective, seeds, initiative schedules.

The test after slice 8: after two weeks of daily use, does the user open Work every morning, and has work stopped going missing?
