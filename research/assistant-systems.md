# Research: how personal AI assistant systems solve channel binding, conversation boundaries, and memory

Feeds [#17](https://github.com/rogierpennink/hydra/issues/17) (assistant design: memory, identity, channel binding). Studies four open systems against their docs and source: OpenClaw, Hermes (NousResearch/hermes-agent), nanobot (HKUDS), and Letta Code.

**Verdict up front: the field has converged, and it converged on Hydra's shape.** All four systems independently landed on: (1) platform container = conversation boundary, with a session key derived deterministically from route facts (channel, chat id, thread id); (2) one assistant identity spanning all surfaces by default, with per-slice binding overrides routed by most-specific-match; (3) mention-gated participation in groups, always-on in DMs; (4) memory as agent-maintained markdown files scoped to the assistant (not the conversation), distilled by a background reflection pass; (5) cross-surface recall through distilled memory plus transcript search, not shared transcripts. Letta even migrated away from vector-DB archival memory to git-backed markdown. Hydra's model (generational sessions per conversation, assistants = agent + prompt + bindings + memory, assistant-scoped memory on the controller) is validated; the deltas worth stealing are in section 6.

## 2. Conversation boundary: what is one session

All four derive a deterministic session key from route facts, and all four treat the platform container as the boundary for shared/group traffic. They differ on DMs.

| System | Session key shape | DM default | Group/thread default |
|---|---|---|---|
| OpenClaw | `agent:<id>:<channel>:<kind>:<peerId>[:thread:<tid>]` (`src/routing/session-key.ts`) | **All DMs on all channels collapse into one "main session"** (`dmScope: "main"`) - "there is one brain, and this is where it thinks" (`docs/concepts/main-session.md`). Opt-out scopes: per-peer, per-channel-peer, per-account-channel-peer | One session per group/room; threads get a `:thread:<id>` suffix on the parent key. Cron runs get a fresh session per run |
| Hermes | `agent:main:{platform}:{chat_type}[:{chat_id}][:{thread_id}][:{participant_id}]` (`docs/session-lifecycle.md`) | One session per DM chat | **Per-user private lanes inside a group** by default (`group_sessions_per_user: true`); threads shared by all participants, messages prefixed `[sender]` to keep prompt caching |
| nanobot | `{channel}:{chat_id}`; Discord threads `discord:<parent>:thread:<tid>` (`nanobot/session/keys.py`) | One session per chat. Opt-in `unifiedSession: true` collapses everything to one key (documented as single-user multi-device mode) | One shared session per group; DingTalk offers per-sender isolation as a flag |
| Letta Code | Route `(channel, accountId, chatId, threadId)` -> `(agentId, conversationId)` persisted in `~/.letta/channels/<ch>/routing.yaml` (`src/channels/routing.ts`) | One conversation per DM | Each Slack thread auto-creates a fresh conversation on the bound agent (`registry-routes.ts`). Agent and conversation are explicitly distinct concepts: "one agent can have many conversations, every conversation uses the same identity and long-term memory" |

**Fresh vs resume.** Resume-forever is the default everywhere; context pressure is handled by compaction, not by session rotation. Resets are layered on top:

- OpenClaw: no auto-reset by default; opt-in daily reset (`session.reset: {mode: "daily", atHour: 4}`) and idle reset (`idleMinutes`, measured from last real user interaction - heartbeats don't keep it alive); first to expire wins; overridable per chat type and per channel. Manual `/new`, `/reset`. On reset the tail of the old conversation is flushed to daily memory notes and recent notes are re-primed into the new session - i.e. **reset = rotate + distill**, exactly Hydra's generational model.
- Hermes: reset policy per platform/chat-type: `none`, `idle` (default 1440 min), `daily` (4 AM), or `both`. A session_key maps to a current session_id incarnation; `/resume <title>` can switch back to an old incarnation. Crash recovery: sessions active in the last 120 s get `resume_pending` and the gateway synthesizes a message so the agent auto-continues.
- nanobot: `/new` archives the discarded transcript into memory (`consolidator.archive_session`) before clearing - again rotate + distill. Idle sessions are auto-summarized after 15 min TTL.
- Letta: `/new` per routed chat rotates the route to a fresh conversation; `/fork` branches.

## 3. Channel binding and identity

Unanimous default: **one identity, one memory, everywhere**. Multiple personas are supported everywhere, but always as fully isolated assistant instances, never as one assistant with per-channel memory:

- OpenClaw: multiple **agents** in one gateway, each with its own workspace (persona files `SOUL.md`, `IDENTITY.md`, `USER.md`, `MEMORY.md`), own state dir, own SQLite session store (`docs/concepts/multi-agent.md`). Top-level `bindings: []` maps traffic slices to agents: `match` on channel (required) + optional accountId, peer kind/id, guildId, teamId, Discord roles; precedence by specificity then config order. Bindings pick the agent only - access control (pairing, allowlists, groupPolicy) is a separate layer. `identityLinks` maps one human's ids across channels to a canonical peer id.
- Hermes: identity = a **profile** (home dir with config, SOUL.md, memories, sessions, state DB). `profile_routes` route by platform + guild + chat + thread, conjunctive match, most-specific wins (thread=8 > chat=4 > guild=2). Docs explicitly warn never to point two agents at one profile (memory writes compound).
- nanobot: one identity per instance; per-channel personas = run multiple instances with separate workspaces. "Use a separate configured agent workspace when identity or memory must be isolated" (`docs/memory.md`).
- Letta Code: every route names its own agentId, so different chats can bind to different agents (each agent = own MemFS); one Slack workspace account carries one agent binding.

All four also converge on the same access-control mechanism, kept separate from binding: pairing codes for unknown DM senders + allowlists per channel/group (OpenClaw pairing/`allowFrom`; Hermes per-platform allowlists; nanobot pairing-code flow with `/pairing approve`; Letta `dmPolicy: pairing|allowlist|open`).

## 4. Addressing / wake rules

Unanimous pattern: DMs always-on (gated by access control, not attention); groups mention-gated by default, with an escape hatch to always-on. The refinements differ:

- OpenClaw (`docs/channels/groups.md`): three-stage pipeline - groupPolicy (open/disabled/allowlist), allowlists, then `requireMention` (default true). **Unmentioned messages are stored as context only**; on the next mention the agent sees up to 50 skipped messages. Implicit mentions (reply-to-bot, quote-of-bot, bot-in-thread) bypass gating. Regex `mentionPatterns` derived from the agent's identity name. Owner can flip a group always-on (`/activation always`); always-on chatter can arrive as quiet "room events" with reply visibility mediated by a message tool - the agent decides when to speak.
- Hermes: same defaults; `DISCORD_HISTORY_BACKFILL` prepends scrollback since the bot's last reply when mentioned; once the bot participates in a thread, no further mention needed; ignores messages that mention only other users; bot-to-bot ignored by default (documented ack-loop warning). Telegram `observe_unmentioned_group_messages` appends unmentioned messages as observed context with a safety note that observed lines are context, not instructions.
- nanobot: per-channel `groupPolicy` (mention/open/allowlist), plus per-group overrides; QQ supports probabilistic reply (mentions always, others with probability p).
- Letta: Slack first turn needs a mention, then the bot's threads are tracked and reply without mention; routes can be `detached` (silent until mentioned again); `/pause`/`/resume` per chat. Distinctive: inbound messages arrive as notifications in the agent's queue and **replying is a tool call**, not an automatic response.

## 5. Memory model

The strongest convergence in the study, from four independent teams:

| Aspect | OpenClaw | Hermes | nanobot | Letta Code |
|---|---|---|---|---|
| Representation | Markdown files in agent workspace: `USER.md`, `MEMORY.md`, daily `memory/YYYY-MM-DD.md`, `DREAMS.md`; "the model only remembers what gets saved to disk" | Two markdown files, **hard-bounded**: `MEMORY.md` (~800 tokens), `USER.md` (~500 tokens), frozen snapshot at session start (prompt-cache preservation) | Markdown: `SOUL.md`, `USER.md`, `MEMORY.md` always in context + append-only `memory/history.jsonl` archive | **MemFS**: git-backed markdown filesystem per agent, `system/` (always in prompt), `reference/` (on demand), `skills/`; file tree always in prompt as signposts |
| Scope | Per agent workspace, global across that agent's conversations | Per profile, global | Per workspace, global | Per agent, shared across all its conversations |
| Writer | Agent (tool + self-directed) + automatic flush before compaction and on session reset | Agent via `memory` tool (add/replace/remove); optional human approval queue; entries scanned for prompt-injection patterns | Automatic Consolidator (context pressure, `/new`) feeds the archive; Dream edits the durable files | Agent file edits; every edit is a git commit |
| Distillation | **"Dreaming"**: cron background consolidation scores recall signals, promotes items into `MEMORY.md` with dedup/supersede, taint gating for untrusted content, human-reviewable diary (`docs/concepts/dreaming.md`) | None by design: overflow errors force the agent to consolidate in-turn ("bounded, curated"); background self-improvement review after turns can save memories | **Dream**: cron agent (2h) reads new archive entries since a cursor, makes "the smallest honest change" to the durable files; every edit git-committed, `/dream-restore <sha>` reverts | **Sleeptime/reflection**: background subagents review recent conversations and update MemFS; reflection commits identifiable in git log; `/doctor` audits placement/duplication/token usage |
| Retrieval beyond prompt | `memory_search` (hybrid vector+keyword over memory files) + `sessions_search` (FTS over transcripts) | `session_search` (SQLite FTS5 over all transcripts) - no vectors, no LLM summarization | Durable files always in context; raw history filtered to same session key | `reference/` files read on demand; list-messages APIs |
| Vector DB | Optional (embeddings for memory search; plugins) | No (external providers optional) | No | **Migrated away from it** (V1 archival memory retired) |

Context pressure within a session is a separate mechanism everywhere: OpenClaw auto-compaction (summarize old turns, keep recent, preserve tool pairing) + session pruning of old tool results; Hermes micro-compaction (`trajectory_compressor.py`); nanobot AutoCompact; Letta per-conversation auto-compaction.

## 6. Cross-surface recall

Nobody shares raw transcripts across surfaces as the primary mechanism. The stack, everywhere, is:

1. **Assistant-scoped memory files** - a fact learned on Telegram is in the system prompt of the next Discord session, automatically. This is the primary mechanism in all four.
2. **Transcript search as a tool** - OpenClaw `sessions_search`/`sessions_history` (with a visibility policy: main session sees all, groups see less); Hermes `session_search` with prompt guidance to search before asking the user to repeat themselves. Letta bridges via reflection + `/init` subagents reviewing prior sessions.
3. **Special cases**: OpenClaw's shared main session makes DM cross-surface recall trivial (it is literally one conversation) and adds "Active Memory" (automatic retrieval over other private transcripts before private replies - default ON only when DMs are unified, OFF once isolation is configured; groups excluded both directions). Hermes has explicit `/handoff <platform>` (move a live conversation, same session_id, to another surface) and a channel directory so the agent can proactively message any known chat. nanobot records `last_channel` per session and delivers background-work results to the most recently active chat.

Privacy boundary worth noting: OpenClaw and nanobot both treat group sessions as excluded from cross-conversation recall by default; OpenClaw's group sessions can run sandboxed with restricted tools while DMs run on the host ("one brain, two postures").

## 7. Lessons for Hydra

Hydra's model going in: generational sessions per conversation (rotate + distill), several assistants each = agent + prompt + bindings + memory, memory assistant-scoped on the controller.

1. **The core model is validated - and rotation should distill on the way out.** Assistant-scoped memory + per-conversation sessions is exactly the endgame all four reached. The specific detail to copy: OpenClaw and nanobot both make session rotation a memory event (flush the tail of the dying conversation to notes / archive the transcript into memory before clearing). Hydra's generational rotation should include a distill step as part of the rotation contract, not as a separate background nicety. Letta's agent-vs-conversation split (`agentId` + `conversationId` in every route) is the cleanest formalization of Hydra's assistant-vs-session split.
2. **Bind by route facts, most-specific wins, and keep access control out of binding.** All four converge on the same binding record: match on (channel, account, guild/team, chat, thread) with specificity precedence, resolving to an assistant. And all four keep who-may-talk (pairing, allowlists, group policy) as a separate layer from which-assistant-answers. Hydra should adopt both the shape and the separation. Also steal OpenClaw's `identityLinks` (map one human's platform ids to a canonical person) - Hermes's E.164 canonicalization shows what happens without it (session fragmentation).
3. **Never share memory between assistants; share by search or explicit bridge.** Every system that supports multiple personas isolates them completely (workspace/profile/MemFS per assistant), and Hermes documents why: two writers on one memory compound corruption. If Hydra ever wants cross-assistant sharing, do it Letta-style (explicit shared blocks) or via search tools, not by pointing two assistants at one store.
4. **Group ergonomics need three specific features, not just mention-to-wake**: (a) store-unmentioned-as-context so the assistant has the room's recent history when woken (OpenClaw's context-only storage, Hermes's history backfill); (b) implicit mentions (reply-to-assistant, assistant-in-thread) bypass gating; (c) mark observed group content as untrusted context, not instructions (Hermes's safety prompt, OpenClaw's taint gating in Dreaming). The last one matters doubly for Hydra since distillation will chew on group content.
5. **Make memory bounded, auditable, and versioned.** Two independent teams (nanobot, Letta) landed on git-committed markdown memory with revert; OpenClaw keeps a human-reviewable dream diary; Hermes hard-caps memory size and offers a write-approval queue. Since Hydra stores memory on the controller, version it there (git or equivalent) and keep distillation output reviewable. Hermes's hard token budget is worth considering as a forcing function for curation quality.
6. **Avoid: vector-first memory, and the unified-DM default for multi-user deployments.** Letta retired its vector archival store in favor of files + search; Hermes deliberately ships FTS only. Plain markdown + full-text transcript search is the proven baseline; add embeddings later if retrieval quality demands it. OpenClaw's all-DMs-are-one-session is elegant for a strictly single-operator tool but both OpenClaw (Active Memory auto-off under isolation) and nanobot (unifiedSession warnings) document its sharp edges - Hydra's per-conversation sessions with assistant-scoped memory is the safer general default; if "one brain" feel is wanted, get it from memory + transcript search, not from a merged session.
