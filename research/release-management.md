# Research: release management for Hydra

Prepared for [rogierpennink/hydra#191](https://github.com/rogierpennink/hydra/issues/191) (2026-09-14). Method: five parallel sub-agents (glm-5.3-flash) — three primary-source studies of comparable agent tooling (t3-code, OpenClaw, Hermes), a tooling-landscape survey against official docs, and fit experiments run against this repo's real history in scratch clones (nothing was written to origin; no tags or releases exist yet, before or after).

## Verdict (synthesis)

Hydra can have largely auto-generated release notes **today, from what it already writes**: 79% of the last 300 commits on `main` are Conventional Commits, the strays are exactly the noise a changelog should drop, and both git-cliff (scope-grouped, best output of everything tested) and GitHub's `--generate-release-notes` (flat but correct, because our PR titles are already conventional) produce usable notes from the repo as-is. The real decision is not the notes tool but **who gates a release**: a human merging a release PR (release-please), a human running one command (GitHub-native, git-cliff), or nobody (semantic-release). Changesets is a poor fit — its per-PR change-file ceremony buys independent multi-package versioning, and Hydra ships one binary with one version. The reference repos converge on the same shape at very different scales: a **human-gated, train-like release act** (merge a PR / run one command), **notes generated mechanically then optionally edited** (OpenClaw's agent editorial pass; Hermes' hand-curated milestones), a **prerelease channel that absorbs validation before stable** (t3-code's promote-the-verified-nightly invariant is the best idea found), and **immutable releases** because an auto-updater consumes the feed — which Hydra's spec already commits to: `hydra upgrade` verifies a minisign-signed `SHA256SUMS` and checks the releases feed every 24 h ([spec 15](../docs/spec/15-packaging-and-operations.md)). The failure modes to design against are equally consistent: vestigial notes tooling whose output no longer matches the published notes (Hermes), baroque machinery only an agent can navigate (OpenClaw), and junk tags in the public namespace (Hermes).

## Spec anchors found while synthesizing

From `docs/spec/15-packaging-and-operations.md` (already normative; any release process must satisfy these):

- L8: "Published on GitHub Releases behind a `curl | sh` installer. A brew tap comes later (see Post-v1)."
- L159: "An older binary that opens a newer database MUST refuse to start" — versions must be well-ordered.
- L168: `hydra upgrade` "fetches the release for this platform, verifies its checksum and signature, swaps the binary atomically".
- L172: the controller "checks the releases feed and surfaces an available version as an ordinary Notification" — a prerelease channel must not pollute this feed for default consumers.
- L184: release signing resolved in #44 — **minisign-format ed25519**; CI signs the release's `SHA256SUMS`; public key embedded in the binary and published as a repo file.
- L186: update-check cadence — controller boot + every 24 h, jittered; hardcoded.
- L228: cross-compilation matrix and macOS codesign constraints (already implemented in `.github/workflows/build.yml`).

Also load-bearing after #189/#190: workflow artifacts are 1-day CI plumbing; published binaries are **release assets** (quota-free, uncapped).

## Reference study 1: t3-code ([pingdotgg/t3code](https://github.com/pingdotgg/t3code))

### Verdict

T3 Code runs a fully custom, GitHub-Actions-native release pipeline with no third-party changelog tooling: one ~1000-line `release.yml` drives stable, nightly, and preview channels, and release notes are GitHub's auto-generated "What's Changed" (PR titles + authors + links), pinned to the previous tag within the same channel. There is no CHANGELOG.md and no release-please/changesets/semantic-release anywhere. Versioning is a single workspace-wide semver counter (0.0.x) that moves in lockstep across all packages; the meaningful identity is date + run-number in nightly tags. The standout idea is the canary promotion model: a scheduled job cuts nightlies automatically from `main` every 30 minutes when there are changes, and a stable release never builds `main` HEAD — it re-releases the exact commit the latest nightly shipped, so stable only ever ships what nightly users already ran. Distribution is broad (desktop installers with signing/notarization, self-contained CLI archives, npm with OIDC trusted publishing, curl installers, AUR, hosted web, Discord announcements), all from the same workflow with strict publish-ordering invariants.

### Facts

**1. Versioning.** Single workspace-wide semver: `apps/server/package.json`, `apps/desktop/package.json`, `apps/web/package.json`, and `packages/contracts/package.json` all read `"version": "0.0.40"` (checked in clone). Nightlies use the next patch as base: `0.0.40` in package.json → `v0.0.41-nightly.YYYYMMDD.<run_number>` (`scripts/resolve-nightly-release.ts:88-124`: `` `${baseVersion}-${channel}.${date}.${runNumber}` ``). Stable cadence: only 5 stable releases ever (`gh api repos/pingdotgg/t3code/releases?per_page=100`): v0.0.36 Aug 29 → v0.0.40 Sep 8 — roughly weekly. Nightlies: multiple per day (30 most recent tags are all nightly/preview).

**2. Tooling.** 100% custom. Grep for release-please/changesets/semantic-release/git-cliff across `.github/` and `package.json`: zero hits. `.github/workflows/release.yml` triggers on: (a) cron `"8,38 * * * *"` (every 30 min, change-gated), (b) tag push `v*.*.*` excluding `*-nightly.*`/`*-preview.*`, (c) `workflow_dispatch` with a `channel` choice (stable/nightly/preview) and optional `version`. Publishes via `softprops/action-gh-release@v3`. Supporting scripts: `scripts/check-nightly-release.cjs` (`.github/scripts/`), `resolve-nightly-release.ts`, `resolve-previous-release-tag.ts`, `update-release-package-versions.ts`, `build-npm-platform-packages.ts`, `notify-discord-release.ts`.

**3. Release notes.** Fully auto: the release job sets `generate_release_notes: ${{ ... != 'preview' }}` with `previous_tag: ${{ needs.preflight.outputs.previous_tag }}` — GitHub-generated notes pinned to the previous tag *in the same channel* (stable↔stable, nightly↔nightly). Real example, [v0.0.40](https://github.com/pingdotgg/t3code/releases/tag/v0.0.40): `## What's Changed` / `* fix(mobile): keep pending messages in the chat timeline by @juliusmarminge in #10449` — a flat PR-title list, scannable only because contributors conventionally prefix PR titles (`fix(scope):`, `feat(scope):`); nothing enforces this. Preview releases get a static `> [!WARNING] Do not install` body instead, with the rationale in a workflow comment: "Generated notes would list every commit since the previous preview, which is unmerged branch history no one should read as a changelog."

**4. Prerelease channels.** Three: stable, nightly, preview. Nightlies require new commits + ≥6h since the last nightly (release.md "Nightly builds"). Preview is a maintainer-only pipeline-exercise train: published under npm dist-tag `preview` ("which nothing resolves by default"), carries no electron-updater manifests, and the workflow actively *refuses to publish* if updater metadata appears on it. Reachable only via `npx t3@preview`, `T3CODE_CHANNEL=preview`, or `t3 update --channel preview`.

**5. Distribution.** Desktop: electron-builder DMG (mac arm64/x64), AppImage (linux x64/arm64), NSIS (win x64/arm64) attached to GitHub Releases with `latest*.yml`/`nightly*.yml` + blockmaps (electron-updater over GitHub Releases). CLI: Node single-executable archives per platform (`t3-<version>-<platform>-<arch>.tar.gz`) + `SHA256SUMS` written "from the signed bytes that get uploaded"; npm publishes `t3` launcher + five `@t3code/t3-<platform>-<arch>` optionalDeps via OIDC trusted publishing with `--provenance`, dry-run first. Also: curl installers (`scripts/install.sh`/`install.ps1` at t3.codes), AUR (`publish-aur.yml`), hosted web on Vercel with latest/nightly domain aliases, Discord webhook announcements. Signing: macOS Developer ID + notarization (ad-hoc fallback), Windows Azure Trusted Signing; every archive executed in a smoke test before upload (`scripts/smoke-cli-archive.ts`).

**6. Day-to-day flow.** Merge PRs to `main` → scheduled job auto-cuts a nightly (tag, prerelease, npm `nightly` dist-tag) → maintainer verifies the nightly, then dispatches Release with `channel=stable`; it builds the *latest nightly's commit* ("Nightly is the release candidate: verify the nightly, then promote it" — `docs/operations/release.md`), the tag is created at publish time, and a `finalize` job commits version bumps back to `main` as a GitHub App bot (`chore(release): prepare vX.Y.Z`). Pushing a `vX.Y.Z` tag by hand also works for explicit commits.

**7. Monorepo.** Everything moves together: one version, aligned at release time across the four packages + lockfile, bumped back to `main` only on stable. Nightlies never commit version bumps.

**8. Notable.** *Good:* stable-promotes-a-verified-nightly invariant; `concurrency` group with `queue: max` serializes nightlies without dropping queued stable runs; publish-ordering invariant (npm first, GH Release second, web deploy third) because servers self-update to the client's exact npm version; per-channel note ranges. *Bad:* the doc admits footguns — "There is no dry-run tag path. Pushing any accepted non-nightly tag... classifies the run as the stable channel" and "no non-publishing workflow_dispatch mode"; the ~1000-line hand-rolled workflow is heavy machinery; and 0.0.x-forever versioning means the version number communicates almost nothing (the run number is the real counter).

## Reference study 2: OpenClaw ([openclaw/openclaw](https://github.com/openclaw/openclaw))

### Verdict

OpenClaw runs a CalVer release train (`YYYY.M.PATCH`, patch = sequential monthly train number, not the day) at a cadence of roughly every 1–3 days, always beta-first with stable promoted after validation. Everything is driven by custom in-repo tooling — no release-please/changesets/semantic-release — consisting of ~100 GitHub Actions workflows, ~60 release scripts, and, remarkably, **agent skills** (`.agents/skills/release-openclaw-maintainer`, `.agents/skills/openclaw-changelog-update`) through which an AI agent performs the release under explicit operator approval. Release notes are the famous part: a mechanical history manifest is generated from merged PRs, then an agent writes grouped, user-facing editorial notes ("sorted by user interest", preserving every PR ref and `Thanks @…` credit), which are published in two formats — polished docs pages "formatted for people" and raw Markdown "for AI agents and tools". Distribution is npm-first (four dist-tag channels) with signed native apps (macOS/Windows/Linux/iOS/Android), Docker, and a plugin registry (ClawHub) riding the same train. The machinery is impressively rigorous but has grown baroque: a 1,446-line release policy doc and a publish workflow whose own documentation paragraph is over 900 words.

### Facts

**1. Versioning.** CalVer, documented in `docs/reference/RELEASING.md` ("Version naming", lines ~20–32): regular releases `YYYY.M.PATCH` (tag `v2026.9.4`), correction releases `YYYY.M.PATCH-N` (e.g. `v2026.7.1-2`), beta `YYYY.M.PATCH-beta.N`, alpha `-alpha.N`; "Never zero-pad"; "PATCH is a sequential monthly release-train number, not a calendar day" (hence `2026.6.35`). npm versions are immutable — "never delete, republish, or reuse." Four channels: `stable` (npm `latest`), `extended-stable` (trailing month's `.33+` maintenance line), `beta`, `dev` (main head). Cadence from `gh api repos/openclaw/openclaw/releases`: stables on Aug 31, Sep 1, Sep 3, Sep 5, Sep 8, Sep 10, Sep 11 — releases every 1–3 days. No semver/1.0 concept anywhere.

**2. Tooling.** Entirely custom. Key workflows: `openclaw-release-prepare.yml`, `openclaw-release-promote.yml` (named "OpenClaw Release Button"), `openclaw-release-publish.yml`, `openclaw-npm-release.yml`, `full-release-validation.yml`, `docker-release.yml`, `macos-release.yml`, `windows-node-release.yml`, `linux-app-release.yml`, plus reusable validation/CI workflows. `package.json` has ~20 `release:*` scripts (`release:prep`, `release:candidate`, `release:check`, `ci:full-release`, …) pointing into `scripts/` (`release-candidate-checklist.mts`, `release-changelog.mjs`, `render-github-release-notes.mts`, `check-changelog-attributions.mjs`, …).

**3. Release notes.** Three-stage pipeline: (a) mechanical — "Initial changelogs are generated at release time from merged PRs and commits" (`CONTRIBUTING.md:83`); a complete "contribution record" (every PR/SHA) is kept separately in `CHANGELOG/records/`. (b) Agent editorial pass — the `openclaw-changelog-update` SKILL.md instructs: "Produce grouped user-facing release notes sorted by user interest while preserving every relevant issue/PR ref and every human `Thanks @...` attribution"; the `release-openclaw-maintainer` skill orchestrates the whole release with agent-facing phase references and explicit approval rules. (c) Rendering — `render-github-release-notes.mts` compacts the section to GitHub's 125,000-char body limit and appends a "### Release verification" evidence tail. Notes live as one file per release (`CHANGELOG/2026.9.3.md`, ~114KB: `### Highlights` / `### Changes` / `### Fixes`, with bold one-liners like "**Share selected conversations:** explicitly publish a revocable read-only view… (#139489)"). Post-release, approved docs pages (`docs/releases/`, e.g. 2026.8.1 split into 20+ topic files) become the editorial source and are mirrored back via `pnpm changelog:from-docs` (RELEASING.md "Post-release documentation publication"). Real release body (v2026.9.4, published by `github-actions[bot]`): "20 direct commits · 1,558 pull requests · 294 contributors", dual links — docs "formatted for people", raw changelog "plain Markdown for AI agents and tools" — plus a giant `### Thanks` list and provenance marker `<!-- openclaw-release-publication:docs-v1 -->`.

**4. Prerelease channels.** Yes: `beta.N` prereleases are the default train ("Releases move beta-first; stable follows only after the latest beta is validated"); alpha builds are an internal track. Betas get their own tags, changelogs, and GitHub prereleases. Promote-to-`latest` is an explicit later step.

**5. Distribution.** npm `openclaw` (dist-tags alpha/beta/latest/extended-stable) via `install.sh`/`install-cli.sh`; Docker images; signed+notarized macOS app with Sparkle `appcast.xml`; signed Windows installer; Linux AppImage + `.deb` with a signed monotonic `latest.json` updater; iOS TestFlight and Android APK via separate release workflows; ClawHub for plugins. No Homebrew formula for OpenClaw itself was found (brew is used only to provision Node). Release assets include uploaded validation/dependency evidence zips.

**6. Maintainer flow** (RELEASING.md operator checklist, steps 1–9): manual — cut `release/YYYY.M.PATCH` branch from green main, `pnpm release:prep`, agent writes/freezes notes, review SDK diff, push signed tag, run the printed publish command. Automated — Full Release Validation (cross-OS lanes, npm preflight, Docker builds), plugin+core npm publish, ClawHub staging, draft GitHub release with rendered body, registry readback verification, then finalization. Failures are classified (product vs harness vs infra) before retry.

**7. Monorepo.** One unified version: root `package.json` = `2026.9.4`; publishable `packages/*` (ai, gateway-client, gateway-protocol) share it; private ones are `0.0.0-private`; `scripts/sync-plugin-versions.ts` keeps plugins locked to core.

**8. Good / bad.** **Good:** agent-authored notes with enforced attribution; dual human/agent-facing formats; immutable-version discipline and beta-first promotion; contribution records separating mechanical provenance from curated prose; evidence-verified publish gates. **Bad:** extreme complexity (100 workflows, 1,446-line policy doc, multi-thousand-word checklist entries) that only the agent-operator can navigate; notes routinely exceed 65–125KB — overwhelming rather than readable; and the complexity leaks (one release literally titled "…beta.4 (mistakenly published as 2026.9.1-beta.1)").

*Not determined from primary sources: which LLM writes the editorial notes (skills are tool-agnostic); whether any checksum/signing summary page exists beyond per-channel evidence files.*

## Reference study 3: Hermes ([NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent))

"hermes" searches surfaced ~20 candidates; the clear winner is NousResearch/hermes-agent (245k★ agent platform, top hit for `hermes agent` and `hermes in:name`, with an ecosystem: hermes-webui 18k★, hermes-desktop 14k★, awesome-hermes-agent). `facebook/hermes` (11k★) is a JS engine, not agent tooling; `matcornic/hermes` is an email package. No substitution needed.

### Verdict

Releases are cut by a hand-run, custom ~2,700-line script (`scripts/release.py`) that invents a dual versioning scheme: a CalVer tag (`v2026.9.14`) paired with a semver product version (`v0.21.3`). Notes are auto-generated from conventionally-prefixed commits with heavy contributor attribution, but milestone releases are hand-curated prose that outgrew the generator. Distribution is Docker + curl-installer + desktop apps, deliberately *not* PyPI/npm; there is no prerelease channel, no signing, no attached artifacts — the release is a tag and a notes page, and CI builds Docker from the `release: published` event. One maintainer (teknium1) does it all from a laptop. Mature in attribution and Docker hygiene; immature in channel discipline and note/tooling divergence.

### Facts

1. **Versioning + cadence.** CalVer tags `vYYYY.M.D`, same-day re-releases suffixed (`.2`) by `next_available_tag()` (release.py:2146). Parallel semver in `hermes_cli/__init__.py` (`__version__`, `__release_date__`); title format: *"Hermes Agent v0.21.3 (v2026.9.14)"*. 33 real tags 2026-03→2026-09: ~2–8/month, roughly weekly, sometimes 3/week. Pre-1.0 (v0.21.x) with enormous windows — v0.21.0 notes claim "~5,800 commits · ~2,475 merged PRs · 760+ contributors". The public tag list also contains junk: `premerge-oh-god`, `merge-commit-backup`, `backup/*`. [api tags, clone]

2. **Release tooling.** No release-please/changesets/semantic-release/git-cliff, no release workflow. One custom script: `python scripts/release.py --bump minor [--publish]`. Dry-run default; `--publish` does: rewrite version files (regex over `__init__.py`, `pyproject.toml`) → `git commit -m "chore: bump version to…"` → annotated tag → `git push origin HEAD --tags` → `gh release create --title … --notes-file .release_notes.md`. It explicitly does **not** use `--generate-release-notes`.

3. **Notes generation.** `generate_changelog()` (release.py:2437) groups commits by conventional-prefix regex into ⚠️ Breaking / ✨ Features / 🔧 Improvements / 🐛 Fixes / 📚 Docs / 🧪 Tests / 🏗️ Infrastructure, links `([#PR])` or commit SHA, appends `— @author`, then a 👥 Contributors section ranked by commit count. Attribution is a cottage industry: a frozen `LEGACY_AUTHOR_MAP` dict plus one-file-per-email mappings in `contributors/emails/` ("file additions never conflict", contributors/README.md). In practice the published notes have **diverged from the generator**: v0.21.0 is hand-curated narrative ("**The Pantheon Release.** … a society of named agents with their own faces and group chats"), and v0.21.3 openly says *"Also in the window, undocumented here on purpose…"* — producer: the maintainer, with the script's baseline as fallback.

4. **Prerelease/nightly.** None — 0 prereleases across all releases. The rolling channel is Docker `:main`/`:latest`, pushed on every main merge (docker.yml merge job: "On main pushes: tags both :main and :latest"), plus git-installs via `hermes update`. Cloud/desktop agents "auto-update to the newest release tag" (v0.21.3 notes).

5. **Distribution.** Docker Hub `nousresearch/hermes-agent`, multi-arch (native amd64/arm64 runners, push-by-digest, `imagetools create` manifest merge, retry-hardened, environment-scoped secrets) — triggered on `release: published` to tag `:<calver>`. Bootstrap installers `scripts/install.sh`/`install.ps1` (git-clone-based). Electron desktop apps (macOS "ad-hoc signature" fallback, stable TCC signing identity — install.sh:3364). `setup.py` **actively blocks** wheel/sdist outside Nix: *"pip/PyPI and Homebrew are no longer supported distribution methods"*. No release assets, no checksums, no cosign/GPG.

6. **Maintainer's day-to-day.** Merge → locally run `release.py --bump X --publish` → script commits bump + tags + pushes → `gh release create` → the published release event triggers docker.yml build/publish. Entirely manual; all 10 recent releases authored by `teknium1`. On `gh` missing, the script fails soft: keeps `.release_notes.md` and prints the manual command.

7. **Monorepo versioning.** Not applicable as such — one repo, one version, though desktop/gateway/web ship inside it. `update_version_files()` rewrites several files so the semver and CalVer date stay in lockstep.

8. **Notably good / bad.**
   - **Copy:** per-email contributor-map files (conflict-free attribution at scale); CalVer tags that downstream auto-updaters (Cloud, Docker) can pin; "patch tag exists so fixes reach Cloud agents" rationale stated in the notes; dry-run-first release script; deliberately narrow supply-chain scanner ("trained reviewers to ignore… keep checks ruthlessly narrow", supply-chain-audit.yml); honest notes about what's deliberately undocumented.
   - **Avoid:** notes generator whose output no longer matches published notes (vestigial tooling); single-machine manual tagging; junk backup tags in the public namespace; no prerelease/staging channel despite auto-updating consumers; version scattered across files regex-rewritten at release time.

## Tooling landscape (surveyed against official docs)

### Verdict

Every mainstream option keys off artifacts Hydra already produces — Conventional Commits and PRs — so the real decision is who gates the release: a human merging a release PR (release-please), a human running one command (GitHub-native, git-cliff), or nobody (semantic-release). Binary distribution (per-platform assets, SHA256SUMS, attestations, installers, a rolling `nightly` tag) is orthogonal to the notes tool and is standard GitHub Actions work; release assets carry no size or bandwidth cap, so they sidestep Actions storage concerns entirely. Monorepo versioning machinery (release-please manifest mode, changesets' dependent-bumping) solves independent per-package versions, which Hydra does not have — it ships one versioned binary. Bun-compiled prior art is thin: no large project ships a dominant release template, though GoReleaser now officially supports Bun as a build builder and documents the canonical hygiene checklist. Changesets' intent-file model adds per-PR ceremony whose payoff — independent multi-package versioning — Hydra doesn't collect, making it a poor fit despite its maturity.

### Facts

**1. GitHub-native notes (`.github/release.yml` + `gh release create`)**
1. Auto-generated notes list merged PRs, contributors, and a full-changelog link; `.github/release.yml` maps labels to categories and excludes labels/authors ([docs](https://docs.github.com/en/repositories/releasing-projects-on-github/automatically-generated-release-notes)).
2. `gh release create --generate-notes` does the same from the CLI and auto-titles the release; assets are uploaded via separate API calls after draft creation; `--fail-on-no-commits` guards empty releases ([gh manual](https://cli.github.com/manual/gh_release_create)).
3. **What you don't get:** version selection is entirely human — you pick the tag; no CHANGELOG.md file is maintained; notes are driven by PR titles/labels, not commit types.

**2. Release Drafter**
1. On each merge to the default branch it appends a categorized entry to a persistent **draft** release; categories match labels; `$RESOLVED_VERSION` is computed from category `semver-increment`s (label-driven version *suggestion*); `autolabeler` labels PRs automatically; publishing the draft stays human, or `publish: true` auto-publishes; a prerelease-draft workflow (`update_prerelease_draft`) exists ([README](https://github.com/release-drafter/release-drafter)).
2. Notes key off PR **labels**, not commits — label discipline becomes load-bearing; version is advisory until you publish.

**3. release-please (Google)**
1. Parses Conventional Commits (`feat:` → minor, `fix:` → patch, `!:` → major) and maintains a **Release PR** kept up to date; merging it updates `CHANGELOG.md` and version files, tags, and creates the GitHub Release; squash-merges recommended; lifecycle labels `autorelease: pending/tagged/published` ([README](https://github.com/googleapis/release-please)).
2. It explicitly "does not handle publication to package managers" — build/attach binaries belongs to a tag-triggered workflow you write (same README).
3. Monorepo: manifest config with a `packages` map, combined or `separate-pull-requests`, `node-workspace` plugin, `bootstrap-sha`; `release-type: node` reads `package.json`; prereleases via `prerelease`/`prerelease-type: beta` ([manifest docs](https://github.com/googleapis/release-please/blob/main/docs/manifest-releaser.md)). For a single-version repo the manifest is just one entry.
4. `extra-files` updates arbitrary files via generic/jsonpath/yaml substitutions — e.g. patching a generated version file ([customizing](https://github.com/googleapis/release-please/blob/main/docs/customizing.md)).

**4. Changesets**
1. Intent model: the contributor commits a **change file** (semver bump type + blurb) with the PR; `changeset version` consumes them into CHANGELOG + version bumps; `changeset publish` npm-publishes ([intro](https://github.com/changesets/changesets/blob/main/docs/intro-to-using-changesets.md), current docs at [changesets.dev](https://changesets.dev/guide/getting-started)).
2. Deliberately monorepo-first: dependents are auto-bumped; bumps flatten to the highest type; info lives in files precisely so squash-merges stay safe ([decisions](https://github.com/changesets/changesets/blob/main/docs/decisions.md)).
3. Automation: [changesets/action](https://github.com/changesets/changesets/blob/main/docs/automating-changesets.md) maintains a version PR; changeset-bot prompts non-blockingly; `changeset status --since=main` blocks CI. Contrast with commit-driven tools is explicit (decisions doc, "What distinguishes this from Semantic Release").
4. Solo-dev cost: one extra file per PR plus a version-PR merge per release; npm-centric — for a binary you'd tag off the version PR and build elsewhere.

**5. semantic-release**
1. Fully automated: every push to a release branch runs it in CI; it derives the version from commits, publishes, and creates the GitHub release/notes with no human step ([README](https://github.com/semantic-release/semantic-release)).
2. Official docs document **no monorepo workflow** — the FAQ covers CI providers, Git hosts, and non-JS publishing, but not monorepos/workspaces ([FAQ](https://semantic-release.gitbook.io/semantic-release/support/faq)).
3. Risk profile for a solo maintainer: releases land without a review gate, CI holds a write token, and commit-message hygiene becomes the only guardrail; a bad merge publishes immediately.

**6. git-cliff**
1. Generates changelogs from Conventional Commits with fully templated output; GitHub integration adds contributor/PR links; ships a first-class GitHub Action ([GitHub integration](https://git-cliff.org/docs/integration/github), [git-cliff-action](https://git-cliff.org/docs/github-actions/git-cliff-action)).
2. It produces notes only — versioning, tagging, and asset upload stay with you, making it a natural pair for manual `gh release create` with `git cliff --latest` as the body ([docs](https://git-cliff.org/docs/)).
3. No monorepo versioning feature appears anywhere in the docs ([sitemap](https://git-cliff.org/docs/)).

**7. Binary distribution hygiene**
1. GitHub Releases: assets per release with "no limit on the total size of a release, nor bandwidth usage" ([About releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)) — outside Actions artifact quotas.
2. GoReleaser documents the reference checklist even for non-Go projects: a `checksum` SHA256/512 file ([checksum](https://goreleaser.com/customization/package/checksum/)), Homebrew tap formula in your own tap repo ([homebrew](https://goreleaser.com/customization/publish/homebrew_formulas/)), Scoop bucket manifest ([scoop](https://goreleaser.com/customization/publish/scoop/)), Nix ([nix](https://goreleaser.com/customization/publish/nix/)), and artifact attestations ([attestations](https://goreleaser.com/customization/publish/attestations/)).
3. `actions/attest` produces SLSA build provenance via GitHub OIDC (needs `id-token`); available to public repos on all plans; `subject-checksums` attests an entire SHA256SUMS file in one shot ([README](https://github.com/actions/attest)).
4. curl|sh prior art: Bun's own installer is `curl -fsSL https://bun.com/install | bash`, with pinned installs (`| bash -s "bun-v1.3.3"`) and Homebrew/npm/Docker alternates ([bun install docs](https://bun.com/docs/installation)).
5. Nightly channel: GoReleaser's `--nightly` publishes to a rolling tag (e.g. `nightly`/`devel`) with `keep_single_release: true` replacing the previous one, skipping taps and other publishers ([nightlies](https://goreleaser.com/customization/publish/nightlies/)) — the standard pattern for a force-moved prerelease channel without dated-tag sprawl.

**8. Bun-specific prior art**
1. `bun build --compile` cross-compiles exactly Hydra's matrix: `bun-darwin-arm64`, `bun-linux-x64`, `bun-linux-arm64`, plus musl/baseline variants and Windows ([bun docs](https://bun.com/docs/bundler/executables)).
2. GitHub topic search finds only small projects shipping compiled Bun binaries — no dominant release-automation template exists ([search](https://api.github.com/search/repositories?q=topic:bun+compiled+binary&sort=stars)).
3. Closest mature prior art: GoReleaser (Go-first, officially multi-language since v2.5) has a first-class **Bun builder** wrapping `bun build --compile` ([builder docs](https://goreleaser.com/customization/builds/builders/bun/), [v2.5 announcement](https://goreleaser.com/blog/goreleaser-v2.5/)) — usable directly, or as a blueprint for a hand-rolled Actions workflow.

### Shortlist

**A. GitHub-native + manual tag + Actions asset workflow.** Add `.github/release.yml` with categories mapped to `feat:`/`fix:`-style labels, a release workflow that builds the three targets on tag push, uploads assets plus SHA256SUMS and an `actions/attest` provenance attestation, and cut releases with `gh release create --generate-notes`. Ritual: one command per release. Trade-off: versioning and CHANGELOG.md stay fully manual, and notes reflect PR labels rather than commit types — you must keep the two vocabularies aligned.

**B. release-please + tag-triggered binary workflow.** release-please owns version and CHANGELOG.md from the Conventional Commits Hydra already writes; a release-type with `extra-files` can bump the generated version source; merging the Release PR tags and creates the GitHub Release, whose tag triggers the build/checksum/attest workflow; a scheduled `--nightly`-style run can drive a rolling prerelease tag. Ritual: merge PRs; merge the bot's release PR when you want to ship. Trade-off: bot-PR churn and dependency on release-please's conventions (package.json/CHANGELOG layout), and its monorepo machinery — including the two-version subtlety with build-time baked versions — is weight Hydra doesn't need.

**C. git-cliff + manual `gh release`.** git-cliff generates both the release body (`git cliff --latest --github`) and a maintained CHANGELOG.md from the existing commit history, while the human tags, runs `gh release create`, and the workflow attaches binaries/checksums/attestations; nightly is a cron workflow publishing to a rolling `nightly` tag. Trade-off: zero bot infrastructure and total control over notes text, but nothing converges on its own — version discipline and changelog freshness depend entirely on the maintainer running the ritual every time.

## Fit experiments against this repo

### Verdict

**Commit-driven changelog tooling works on this history today.** 79% of the last 300 subjects conform to Conventional Commits, and the strays are exactly the noise you want dropped: 26 merge commits and ~25 human-titled squash PRs ("Record X decisions (ticket #N)"). git-cliff is the standout: out of the box it produced clean, scope-grouped sections and silently discarded all 63 non-conforming commits. GitHub auto-notes also work but are flat PR-title lists; label-driven categorization is dead weight right now — **0 of 30 merged PRs carry any release-ish label** (`enhancement`: 0), so a `release.yml` would sort everything into a catch-all until PR labeling becomes a habit; the Hydra triage labels (needs-triage, ready-for-agent, …) are workflow labels and should not become note categories. **Biggest surprise:** release-please's dry run proposed `chore(main): release 1.0.0` — with no tags it ignored the `0.1.0` in package.json and jumped straight to 1.0.0. Also note its node strategy wants to touch package-lock/samples files that don't exist, and it knows nothing about the build-time `version.ts` — that file is the real desync risk. Nothing was written to origin: 0 tags, 0 releases before and after; the dry run printed the PR it *would* have opened. Repo permissions are wide open (push: true, Actions allowed: all), so tag creation from CI is unblocked.

### Experiments

**1. Commit-convention audit** — `git clone --bare` → `/tmp/hydra-fit.git`; last 300 subjects on `main` matched against the CC regex. **237/300 (79%)** conform. Types: feat 87, fix 49, docs 34, refactor 30, test 21, chore 8, ci 5, style 2, build 1. Top scopes: web 29, controller 27, runners 20, sessions 15, spec 14, cli 9, client-core 7. One wart: `runners` vs `runner` both used (20 vs 13). The 63 misses: 26 merge commits ("Merge pull request #165…"), plus well-written but untyped squash titles like "Thread surface and composer (#69)" and "Assemble the v1 spec (ticket #21)". **Verdict: clean enough — a changelog tool with a filter produces professional notes today.**

**2. GitHub auto-notes preview** — `gh api -X POST repos/rogierpennink/hydra/releases/generate-notes -f tag_name=v0.1.0 -F previous_tag_name= -f target_commitish=main` succeeded, preview-only. Output: `## What's Changed` with 30 PR-title bullets ("* feat: access modes and approvals (#70) by @rogierpennink in …", plus a "New Contributors" section — solo maintainer makes that section forever awkward). Flat, uncategorized, PR-based (uses merge/PR titles, not commit subjects). A candidate `.github/release.yml` was drafted (categories: Features←enhancement, Bug Fixes←bug, Documentation←documentation, Other←catch-all `*`; wontfix excluded). The default labels (`bug`, `enhancement`, `documentation`) exist and would work as categories, but nothing labels PRs with them today; the triage labels describe issue workflow, not change type, and mapping them to note sections would be semantically wrong. **Verdict: works mechanically, but categorization needs a new habit (label PRs feat/fix) before it adds anything.**

**3. git-cliff dry run** — git-cliff 2.14.1 via brew, run in a scratch clone with the default config. Since there are no tags, all 238 entries land under `[unreleased]`, grouped per type with scopes prefixed:

```
## [unreleased]
### 🚀 Features
- Scaffold the nine workspace packages (#55)
- *(controller)* Hydra Home, bootstrap config, database client and embedded migrations (ticket #56)
- *(runners)* The join exchange and `hydra runner join` (ticket #61)
- *(web)* Router, entry guard, setup and login screens, onboarding timezone step (ticket #58)
### 🐛 Bug Fixes
- *(cli)* Password fields are stdin-only (ticket #57)
### 📚 Documentation … ### 🚜 Refactor … ### 💼 Other
- Pnpm workspace, pinned toolchain, lint and test setup (#55)
```

Exactly 238 bullets for 237 CC commits + 1; all 63 non-conforming commits silently dropped (default `filter_unconventional`). **Verdict: best output of everything tested; grouping and noise handling are near-perfect as shipped.**

**4. release-please dry run** — first attempts failed informatively: `GH_TOKEN` env is *not* read (404 unauthenticated, rate-limit 60); the token must be a `--token=` flag. Then, per docs: `npx release-please@latest release-pr --token=$TOKEN --dry-run --release-type=node --repo-url=rogierpennink/hydra`. It fetched history via the API (709 commits incl. merges, ~70 flagged "could not be parsed" — merges and untyped titles, tolerated with warnings) and printed the PR it would open without creating anything: title `chore(main): release 1.0.0`, branch `release-please--branches--main--components--hydra`, body containing a fully formatted `## 1.0.0` changelog with Features/Bug Fixes sections and commit links, and file updates `package.json "updating from 0.1.0 to 1.0.0"` + a new CHANGELOG.md (plus attempted package-lock/samples/changelog.json/.release-please-manifest.json — all absent, harmlessly skipped in dry run). **Verdict: dry run is real and side-effect-free, but it would (a) mint 1.0.0 not 0.1.0, and (b) only version the root package.json — plumbing it into the binary needs extra work.**

**5. Version plumbing** — `scripts/gen-version.ts` reads `version` from the **root `package.json`** (`0.1.0`), appends `git rev-parse --short HEAD`, and writes `packages/home/src/version.ts` (`export const VERSION = "0.1.0+c775a10"`, not checked in) at build time; `packages/hydra` and `packages/home` package.jsons mirror `0.1.0`. So a release tool must write **root package.json only**; the binary's version follows at the next build. Desync surfaces: (a) tag vs root package.json vs CHANGELOG (release-please owns all three consistently); (b) `+sha` suffix means a re-built old tag reports its build SHA, benign; (c) if you ever tag without merging the release PR, binary and tag disagree until next merge. `--extra-files` can't easily cover `version.ts` (generated, custom format), but it doesn't need to. Permissions: `{"admin":true,"maintain":true,"pull":true,"push":true,"triage":true}`, Actions `allowed_actions: "all"` — **nothing restricts CI tag creation; default GITHUB_TOKEN with `permissions: contents: write` suffices.**
